# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Workspace-level guidance lives in `../CLAUDE.md` (Pipelex multi-repo workspace). This file covers only what is specific to `pipelex-mcp`.

## What this repo is

`pipelex-mcp` exposes registered-method discovery, MTHDS validation, inputs projection and preparation, and durable method runs to MCP hosts. It ships as **two servers from one capability core** (see the Architecture section): a hosted **Skybridge console** for remote-connector hosts (ChatGPT, claude.ai, Cowork) and a local **workshop** stdio server distributed on npm as `@pipelex/mcp` for coding-agent hosts (Claude Code, Codex, Cursor). Both register the same MCP tools — `mthds_list_methods`, `mthds_validate`, `mthds_inputs_template`, `mthds_prepare_inputs`, and the `mthds_run` / `mthds_run_status` / `mthds_run_results` durable-run family — plus one per-shell tool on each side: the console-only `mthds_upload_attachments`, which turns a file the user attached in the chat into a run-ready `pipelex-storage://` reference (ChatGPT's Apps runtime is the only host that substitutes the attachment), and the workshop-only `mthds_download_artifacts`, which saves a completed run's produced files under the server's working directory (see the Architecture section for both). `mthds_list_methods` is the source-free name/intent → canonical-id bridge into the existing current-content validate → inputs-template → run flow. An assistant that already holds `.mthds` file contents (or, on the workshop, their on-disk paths) calls `mthds_validate` for a stable, structured verdict it can use to explain and repair diagnostics, `mthds_inputs_template` for a fill-in template of a pipe's declared inputs, `mthds_prepare_inputs` to turn filled file-bearing inputs run-ready (uploading assets to Pipelex storage on the workshop; pass-through only on the console), and the run family to execute a method durably. On a positive validation verdict the `mthds_validate` tool ships a Skybridge view, `run-graph`, that renders the method graph interactively with `@pipelex/mthds-ui`'s `GraphViewer` (hosted console only — the workshop is tools-first, no views); `mthds_list_methods`, `mthds_inputs_template`, `mthds_prepare_inputs`, and the status/results tools are plain tools with no view.

It is a thin MCP front-end over the existing Pipelex validation stack — it does no validation itself. It forwards file contents to a **Pipelex API** (`POST /v1/validate`, `POST /v1/build/inputs`) through the `PipelexApiClient` from the `@pipelex/sdk` npm package (published from `../pipelex-sdk-js`), then projects the API's reports into MCP output. `@pipelex/sdk` is the Pipelex hosted-platform SDK — the same one `pipelex-app` uses, and the only one carrying the durable run lifecycle the later run-backed tools need; it re-exports the open `mthds/protocol` surface, so the MCP imports one SDK.

`SPEC.md` is the source of truth for product requirements and design decisions — read and update it when changing behavior. `AGENTS.md` mandates using the **`skybridge` skill** when planning or updating this codebase; do so.

## Commands

Use the `Makefile` (wraps the npm scripts):

- `make check` (= `npm run check`) — lint + format:check + build (Skybridge) + build:local (tsup) + typecheck. The pre-flight gate; run before declaring work done. **`build` runs before the standalone `typecheck`** on purpose: Skybridge regenerates the view-name registry (`.skybridge/views.d.ts`, gitignored) as `build`'s first step, and `tsc` needs it to resolve `mthds_validate`'s `view.component`. A cold `typecheck` with no prior `build`/`dev` won't know the view name. `build:local` bundles the workshop bin and sits between the two.
- `make test` / `make t` — Vitest run.
- **`make agent-test` — the target an agent runs after touching code.** Same hermetic suite as `make test`, but it captures stdout and replays it **only on failure**, printing a heartbeat line every `HEARTBEAT_INTERVAL` seconds (default 15) so a slow run is distinguishable from a hung one. A green vitest run is a few hundred lines of context spent to learn one bit; this reduces it to two. Use it in place of `make test` whenever you are an agent — the failure output is not abridged, so nothing is lost.
- `make all` — clean + check + test.
- `make dev` — Skybridge dev server. MCP endpoint at `http://localhost:3000/mcp`, DevTools UI at `http://localhost:3000`.
- `make dev-local` — local workshop stdio server from TypeScript. `make inspect-local` opens MCP Inspector against that entrypoint.
- `make build-local` — bundle the npm-distributed `pipelex-mcp` executable to `dist/local/main.js` with tsup. `npm pack` runs this automatically through `prepack`.
- `make deploy` — deploy via Alpic (`alpic deploy`).

The live targets — `smoke`, `test-e2e`, `test-e2e-run`, `seed-e2e-fixture`, `test-all` — are **the only ones that touch the network**, and all of them are deliberately outside `make all` / `make check` so the local gate and CI stay hermetic. They share one gate (`live-preflight`): it resolves `PIPELEX_BASE_URL` / `PIPELEX_API_KEY` once (shell or command line wins over `.env`, which wins over the hosted default), probes `/v1/version`, and refuses to start without a key. Calling the underlying npm script directly skips those guards, which is what a keyless local OSS runner needs. See "Detecting API drift" below for why they exist.

- `make smoke` (= `npm run smoke`) — spawns the workshop stdio server the way a host does, completes the MCP handshake, and calls the read-only tools against a live Pipelex API, asserting on their `structuredContent`. Read-only; spends no inference credit.
- `make test-e2e` / `make te` (= `npm run test:e2e`) — the live capability suite (`src/**/*.e2e.ts` under `vitest.e2e.config.ts`). Free of inference credit: the run family skips itself unless `PIPELEX_E2E_RUN=1`. **Not free of side effects**: `prepare.e2e.ts`'s workshop arm uploads one 1x1 PNG to Pipelex storage on every run, ungated and unremovable (the SDK exposes no delete), because it is the only live proof the upload path still rewrites a local path to a `pipelex-storage://` reference.
- `make test-e2e-run` — the same suite **including** the run family, which executes the fixture method for real and therefore **spends inference credit**. Its own target so nothing reaches it by accident.
- `make seed-e2e-fixture` (= `npm run seed:e2e-fixture`) — **writes**: creates or refreshes the one durable fixture method the by-id legs need, in whichever organization the API key selects. Idempotent; run it once per organization.
- `make test-all` — **every test in the repo**, in cost order: the hermetic suite, then `smoke`, then the live suite *including* the run family, so it **spends inference credit**. That is why it is `test-all` and not folded into `make all`, which stays the hermetic gate. It runs `live-preflight` first, so a missing key fails in a second rather than after the unit suite, and it deliberately does **not** seed — a catalog write stays hand-invoked, and an unseeded organization already fails the by-id legs with the seed command in the message.

Run a single test with Vitest directly: `npx vitest run src/capabilities/validate.test.ts` or filter by name with `npx vitest run -t "projects pending signatures"`. The same works for the live suite with `--config vitest.e2e.config.ts`, as long as the environment already carries the API target and key that `make test-e2e` would have resolved.

### Running against the validation API

The tool needs a reachable Pipelex API serving `POST /v1/validate`. During early development this is the **local OSS `pipelex-api`** runner (temporary — production target is the hosted Pipelex API only):

```bash
cd ../pipelex-api && make run      # serves http://localhost:8081
PIPELEX_BASE_URL=http://localhost:8081 npm run dev
```

- `PIPELEX_BASE_URL` defaults to the hosted Pipelex API (`https://api.pipelex.com`) when unset; set it to `http://localhost:8081` to develop against the local OSS runner.
- `PIPELEX_API_KEY` is optional — set it only when the configured API requires auth. Workshop dev (`make dev-local`) normally runs without it. Note it has **no effect on the console**: `contextsForRequest` always overrides `apiKey` with the caller's verified OAuth token.
- **`make dev` (the console) now requires `WORKOS_AUTHKIT_DOMAIN` and `PIPELEX_MCP_RESOURCE_INDICATOR`** and throws at startup without them — per-user OAuth is its only auth posture, so there is no keyless dev mode. Put both in `.env` (the dev tunnel URL is what must be registered as that env's Resource Indicator — origin with a trailing slash, not `/mcp`). To iterate on capability code without a WorkOS setup, use `make dev-local` / `make inspect-local`: the workshop shell shares the same capability core and authenticates with a plain `PIPELEX_API_KEY`.
- Both variables can live in a gitignored `.env` at the repo root instead of prefixing the command: `nodemon.json` overrides Skybridge's default dev exec with `tsx --env-file-if-exists=.env src/server.ts` (keep its `watch`/`ext` in sync with Skybridge's defaults — a `nodemon.json` replaces them entirely, not additively). `.env` is dev-only and not watched — restart the dev server after editing it.

### Detecting API drift

The unit suite cannot see the failure mode that actually breaks this server. Every capability reaches `@pipelex/sdk` through a hand-written narrow interface (`CatalogClient`, `MethodFetchClient`, `RunClient`, …) and every test injects a fake satisfying that interface, so `tsc` catches a **type** change on the SDK side and nothing at all catches a **wire-shape** change. That is not hypothetical: `mthds_list_methods` failed every real call with `wire.map is not a function` — the platform had reshaped `GET /v1/methods` into a page object while the pinned SDK still called `.map()` on it — and the whole suite stayed green. There is no OpenAPI schema to diff against (`/v1/openapi.json` is 403), so a live call is the only available detector.

There are two live detectors, at two different altitudes, and they are complementary rather than redundant.

**`make smoke`** drives the real shell over stdio, so it covers the whole path a host exercises: handshake, `tools/list`, then `mthds_list_methods` (row shape plus the projection invariant — method source, stored inputs/outputs and org fields must appear nowhere in the result), `mthds_validate`, and `mthds_inputs_template`. Its assertions live in `scripts/smoke.ts`. It carries two inline fixtures because one is not enough: the canonical `quick_start` bundle validates, but declares no inputs, so its template is `{}` and would pass just as happily if the projection dropped every field — the second fixture declares one input so the template check proves something.

**`make test-e2e`** goes wider and one layer down: one `*.e2e.ts` per capability, calling the capability functions with a context that has **no `client` seam**, so the real `PipelexApiClient` runs against the real API. That is the layer the drift lives at. It covers the catalog (`catalog.e2e.ts` — paging, server-side search, the projection invariant, and the fixture row's server-derived `description`), validation (`validate.e2e.ts` — including that an invalid bundle is a *produced* verdict, never an error), the inputs template (`inputs.e2e.ts` — both formats, the `explicit` shape switch, an unknown `pipe_ref`), the by-id fetch-and-forward leg (`shared.e2e.ts` — `getMethodClosure`, which had the same blind spot `listMethods` had and no live coverage at all), input preparation (`prepare.e2e.ts` — the workshop arm really uploads a 1x1 PNG, the console arm really refuses a local path), and the run lifecycle (`run.e2e.ts`).

**`run.e2e.ts` is split on cost, and the split is what keeps the suite schedulable.** Its free half always runs and spends nothing: reading the status and results of a run id that does not exist proves the two lifecycle routes are reachable and still classify as `input_domain`@`run_id`, and one start on an unknown `method_id` — refused before anything executes — proves `/v1/start` still accepts the run source the way this client sends it. That last check exists because `method_id` is a named SDK option the client reserves on `extra` with a **runtime** throw, so sending it the wrong way compiles and passes the mocked suite; the free tier could not reach the start path at all until it was added, which is how the 0.14.0 bump's break stayed invisible. Its paid half executes the fixture for real and runs only under `PIPELEX_E2E_RUN=1` (`make test-e2e-run`), so `make test-e2e` and any future scheduled canary cannot reach it by accident.

**The by-id legs need a durable fixture method, seeded once per organization.** The SDK had no method delete when this was designed; since 0.14.0 `deleteMethod` exists but is an **asynchronous acceptance** (a resolved promise means "deletion accepted", never "gone"), so a create-per-run suite would still be racing its own cleanup. Instead `make seed-e2e-fixture` stores one method named `pipelex_mcp_e2e_fixture` (its bundle and every other fixture live in `src/capabilities/e2e-support.ts`), and the suites resolve its catalog id **by name at run time** rather than hardcoding a `mt_…` — an id belongs to one organization, this repo is public, and a scheduled canary would run under a different key from a developer's. A missing fixture fails loudly with the seed command in the message, so "not seeded" and "wrong organization" read the same and both point at the fix.

**`make test-e2e` cannot pass vacuously**, and that guarantee is the fixture's: it keeps the catalog non-empty, so `catalog.e2e.ts`'s row assertions always execute rather than looping zero times, and a missing key **fails** the suite instead of skipping it. `make smoke` deliberately does not share it — being fixture-free and seed-free is what keeps it read-only and runnable in an organization nobody has seeded. On an empty catalog it still proves the page envelope survived the wire, which is the reshape that motivated it; it withholds its row-shape PASS and says out loud that row projection was not exercised. Non-vacuous row coverage is `make test-e2e`'s job, not smoke's.

A failure in either detector means the *shipped* client disagrees with the *live* API; the fix belongs in `../pipelex-sdk-js`, then a bump here through the `bump-sdks` skill — never a patch that papers over it in this repo. Anything a live run reveals that contradicts a unit-test fake gets folded back into the fake in the same change, so the two layers cannot disagree silently.

`scripts/` is dev tooling, not shipped code: it is linted and Prettier-checked with `src/`, but it typechecks under its own `tsconfig.scripts.json` because the base config pins `rootDir` to `src/` (`npm run typecheck` runs both projects, so `make check` still covers it). The `*.e2e.ts` files and `e2e-support.ts` do sit under `src/`, so they are linted, formatted and typechecked with everything else — they are excluded from the *default* suite by suffix and from the bundles by reachability (nothing the two entrypoints import reaches them).

### CI

GitHub Actions under `.github/workflows/` (ported from the sibling TS repos, minus the CLA piece that doesn't apply here):

- `quality-checks.yml` — on every PR, runs `npm ci` then `make all` (the same gate as local). Meant to be a required status check on `main`.
- `guard-branches.yml` — enforces the `work-branch → dev → release/vX.Y.Z → main` flow: **only a `release/vX.Y.Z` branch may target `main`** (`dev` no longer can — it's promoted *into* the release branch instead), and work branches must be prefixed (`fix/`, `feature/`, `refactor/`, `chore/`, `docs/`, `ci-cd/`, `changelog/`, `codex/`).
- `version-check.yml` — on PRs into `main` or a `release/vX.Y.Z` branch: asserts `package.json`'s `version` equals the `X.Y.Z` in the release branch name and (for `main`) is strictly greater than `main`'s current version.
- `changelog-check.yml` — on a release PR into `main`: asserts `CHANGELOG.md` has a `## [X.Y.Z]` entry (no `v` prefix in the heading — the `v` lives on the branch name and the git tag only).
- `release.yml` — **manually triggered** (`workflow_dispatch`, never on push): publishes `@pipelex/mcp` to npm, deploys the hosted console to Alpic, and tags `vX.Y.Z`. Merging to `main` ships nothing on its own — a human runs this from the Actions tab. It always checks out `main`, and the `version` input must match `main`'s `package.json` (the guard against running before the release PR merged). The `target` input (`both` | `npm` | `alpic`) exists to retry one leg after a partial failure without re-shipping the other; a publish of an already-published version is skipped, so re-running at the same version is safe. Needs `ALPIC_API_KEY` as a repo secret; npm auth is OIDC trusted publishing (registered against this repo + the `release.yml` filename), so no npm token exists anywhere — **renaming this workflow breaks publishing** until the trusted publisher is re-registered.

The `release/vX.Y.Z` branch, the version bump, the changelog finalization, and the PR are produced by the **`/release` skill** (`.claude/skills/release/`) — run it to cut a release rather than hand-assembling these. After the release PR merges, shipping is the `release.yml` dispatch above (`make publish` / `make deploy` remain as local escape hatches). Both surfaces go out from the same `main` commit at the same `package.json` version. Retry transient finishing-step failures at that version; if a permanent defect makes the commit unshippable after npm publication, deprecate it and fix forward with one new version for both surfaces.

## Architecture

The repo ships two thin shells over one capability core: the Skybridge HTTP console for hosted connectors and the plain MCP-SDK stdio workshop for coding agents. Both map over `src/tools.ts`, so tool names, schemas, descriptions, annotations, and handler wiring stay identical; only the hosted shell adds views and host-specific metadata. The workshop injects the cwd-bound file resolver and declares views unavailable.

**Two exceptions to "both shells register the same table", one per shell:** `src/tools.ts` exports two more ordered tables beside `toolDefinitions` — `consoleOnlyToolDefinitions` (holding `mthds_upload_attachments` alone) and `workshopOnlyToolDefinitions` (holding `mthds_download_artifacts` alone). The hosted shell registers the shared table plus the console-only one (it registers tool-by-tool, for views and `_meta`); `local/server.ts` loops over the shared table plus the workshop-only one. Each exception exists for the same reason inverted: the attachment tool's sole argument is a host-substituted reference the host gates on the declared JSON Schema, which no stdio host performs; the download tool writes under a working directory the console does not have. On the wrong shell either would be *structurally unreachable* rather than merely unused, and registering it would spend every user's tokens on every `tools/list` advertising a capability that cannot fire. Keep them tables, not duplicated definitions: one definition per tool, one registration site per shell. The invariant that still holds, and that matters for routing: **no tool name means different things on the two shells.** (Cost of the split: `tools.ts` importing both per-shell capabilities links some unreachable code into each bundle, since esbuild cannot tree-shake module-scope Zod construction. Accepted deliberately — removing it would fork the context plumbing; revisit only if either per-shell surface grows past one tool.)

The whole server is a handful of small files under `src/`:

- `server.ts` — thin Skybridge entrypoint; `hosted/server.ts` owns the console shell and its views/host metadata. `tools.ts` is the ordered shared tool-definition table both shells register.
- `hosted/contexts.ts` — the console's per-request capability contexts, and the whole of its auth posture on this side of Skybridge. **Auth is per-user OAuth and nothing else** (bring-your-own-key has been removed — there is no second posture, no keyless mode, and no shared-key fallback). Skybridge's `workosProvider` verifies the caller's AuthKit token and the MCP SDK transport surfaces it as `extra.authInfo`; `contextsForRequest` lifts that token into `apiKey` on **every** capability context, which `@pipelex/sdk` then sends upstream as `Authorization: Bearer`. The override is unconditional — a server-held `PIPELEX_API_KEY` must never fund a signed-in caller's work, since the credential picks the active org and therefore the whole visible catalog. The tokenless branch is unreachable in production (no console tool allows anonymous, so Skybridge mounts `requireBearerAuth` server-wide) and exists only to **fail closed** — note it sets `apiKey` to the **empty string, not `undefined`**: `PipelexApiClient`'s constructor reads `options.apiKey ?? process.env.PIPELEX_API_KEY`, so an absent key silently borrows the deployment's env key, which is the precise opposite of the intent. `contexts.test.ts` pins this on the wire (no `Authorization` header goes out) rather than by asserting the field, because the field alone does not prove it. The token rides the transport only — never a tool argument, so it never enters the model's context. The workshop doesn't import this: its per-user credential is a `plx_sk_` key in the host-supplied `PIPELEX_API_KEY` env. `../server.ts` refuses to boot unless both `WORKOS_AUTHKIT_DOMAIN` and `PIPELEX_MCP_RESOURCE_INDICATOR` are set, and `createHostedServer` takes the resolved `OAuthConfig` as its **required first argument** — a console that cannot authenticate a caller is unrepresentable.
- `local/server.ts` — constructs the plain MCP SDK server, registers the shared tool table with local contexts, and injects one cwd-bound file resolver. `local/main.ts` owns stdio transport and graceful shutdown; `local/log.ts` keeps diagnostics on stderr so stdout remains protocol-only.
- `capabilities/catalog.ts` — the `mthds_list_methods` capability and its narrow `CatalogClient.listMethods()` test seam. It calls only the SDK's `listMethods`, validates the rows of the one page it gets back, and bounds names/descriptions by Unicode code point. **Search, ordering and paging belong to the server** (`q` / `limit` / `cursor`): filtering a returned page locally would be searching fifty rows of ten thousand and calling it a search, and re-sorting would reorder a page against the cursor that produced it. A blank query omits `q` rather than sending `""`, which the API rejects as bad input. **Non-negotiable projection invariant:** `mthds`, `python`, `input_data`, `pipe_output`, `org_id`, and `created_by_user_id` must never reach `structuredContent`, `content`, `_meta`, or logs — the index projection stopped returning them, but keep validating what *arrives* rather than trusting the declared type, so a looser server cannot leak through. There is deliberately no total count (counting means reading the whole catalog) and no `has_source`: recomputing it would cost a `getMethod` per row, so a source-less method now surfaces at the point of use, as an `input_domain` no-verdict at `method_id`. **The summary carries a render directive on purpose**: a listing is read near-verbatim by the user, so `catalogSummary` tells the model to report each method with name **and** description, and puts the description before the demoted `method_id`. Keep that directive in the summary, not (only) in the tool description — ChatGPT caches a connector's tool list at add-time, so the summary is the sole channel where a presentation fix reaches existing installs. No view, no `_meta`.
- `capabilities/shared.ts` — the plumbing the capabilities share: the submitted-files input schema (a per-item union, `{ content, uri? } | { path }` — see "The files union and the resolution seam" below), the `ToolError` model, file resolution (`resolveSubmittedFiles` + the `FileResolver` seam), request-shape validation (`validateMethodSelectorRequest`, shared by every method-taking tool — it enforces the two selector rules: strict one-of on the tooling tools, files-win-plus-linkage on `mthds_run`), the by-id fetch-and-forward leg (`fetchMethodFiles` + `MethodFetchClient`, narrowed since the selector unification to `mthds_inputs_template` and `mthds_prepare_inputs` — `mthds_validate` forwards its selector to the server instead), env-derived API config (`buildApiConfig` — `PIPELEX_BASE_URL`/`PIPELEX_API_KEY`), and `classifyError`. `classifyError` takes per-route `ClassifyErrorOptions` (the 400/422 class/locator/hint and the route named in the 404 hint) so each capability points the agent at its own knobs; the class override lets catalog listing classify a missing active-org 400 as `config` without changing other routes, and catalog listing picks its 400 arm by request shape so a rejected `cursor` stays `input_domain`@`cursor` instead of telling the caller their key is wrong. It also maps the `@pipelex/sdk` `InputPreparationError` family (the upload/preparation errors `mthds_prepare_inputs` can raise) ahead of the generic `PipelineRequestError` arm.
- `capabilities/validate.ts` — the validation logic. Zod input/output schemas, the API call (`validateFiles`), and projection of the API report into MCP `structuredContent` + the view-only `_meta` graph payload (`toolResult`). Also accepts `method_ref` (a published method address) and `method_id` as **server pass-throughs**: the selector rides the `/v1/validate` body (`ValidateMethodSelector`) and the hosted API resolves it — no fetch-and-forward, no method source in the conversation. The three source forms are mutually exclusive (`validateMethodSelectorRequest`, rule `one_selector`).
- `capabilities/inputs.ts` — the inputs-template logic. Zod input/output schemas (`files?` beside `method_id?`, `pipe_ref?`, `explicit?` default true, `format?` default json), the API call (`buildInputs`, adapting the MCP `uri` provenance label to the build envelope's `source`), and projection of the report into `structuredContent` plus a composed Markdown summary that includes the template in a fenced code block (the build routes return a plain `message`, not `rendered_markdown`). The three source forms are mutually exclusive (rule `one_selector`). A `method_ref` request is a **server pass-through** — the address rides the build envelope itself (`BuildInputsRequest.method_ref`) and the runner resolves it. A `method_id` request **fetches-and-forwards** via the shared `fetchMethodFiles` (in `capabilities/shared.ts`, also used by `mthds_prepare_inputs`): the SDK's `getMethodClosure` → files, each labeled with the method id as provenance, adapted to the build envelope's `source` here — the SDK's own canonical expansion, since the build routes have no server-side `method_id`; a source-less stored method (the SDK's `EmptyMethodSourceError`) is an `input_domain` no-verdict at `method_id` raised without calling the build route, and fetch-leg failures classify against `/v1/methods/{id}`. No view, no `_meta`.
- `capabilities/prepare.ts` — the input-preparation logic (`mthds_prepare_inputs`). Zod input/output schemas (`files?`/`method_id?`, `pipe_ref?`, required filled `inputs`), and preparation of file-bearing input values via `@pipelex/sdk`'s `prepareInputs`: uploads local paths / `data:` URLs / bytes to Pipelex storage and rewrites them to `pipelex-storage://`, projecting the result into `structuredContent` (`inputs`, `uploads: string[]`) plus a composed Markdown summary with the prepared inputs in a fenced block. Takes exactly one of `files` / `method_id` — **no `method_ref`**: preparation is the SDK's client-side walk (`prepareInputs`), so an address the server never sees here has nothing to resolve it, and a console-only variant would fork the tool contract across shells. The by-id path fetches-and-forwards via the shared `fetchMethodFiles`, exactly as `mthds_inputs_template`. **The per-deployment asset boundary is a `PrepareContext.allowUpload` seam** (analogous to `resolver`): the workshop (`allowUpload: true`) delegates the upload walk to the SDK's `prepareInputs`; the hosted console (`false`, the default) runs its own **pass-through-only** walk — it resolves the signature via `buildInputs` (explicit) and rewrites `http(s)` / `pipelex-storage://` values but refuses any upload-needing value up front (`input_domain`@`inputs`), so it never hands raw inputs to `prepareInputs` and never triggers a server-side `readLocalPath` (the LFI/DoS/existence-oracle hazard). **No produced-invalid arm** — an unresolvable closure is a no-verdict `status:"error"` (the SDK throws `InputPreparationError` without structured `validation_errors[]`). No view, no `_meta`.
- `capabilities/attachments.ts` — the chat-attachment ingest capability (`mthds_upload_attachments`, **console-only**) plus the mandated four-field host-attachment Zod schema (`download_url`/`file_id` required, `mime_type`/`file_name` optional — declared here rather than imported from `skybridge/server`'s `FileRef`, because the capability core stays Skybridge-free; a local mirror emits a byte-identical JSON Schema). Per attachment, sequentially: fetch within the boundary → `uploadFile` → `pipelex-storage://`. The host's `file_name` is user-supplied, so it is reduced to a bare printable basename before it names a stored asset. Per-item errors ride `attachments[i].error` and **partial success is a produced verdict** (`status:"ok"`, `is_valid:false`) — successful uploads are never discarded because a sibling failed. Never touches the filesystem. No view, no `_meta`.
- `capabilities/attachment-fetch.ts` — the **attachment fetch boundary**: the console's analogue of the workshop's path trust boundary, deny-by-default, reporting failures as values rather than throwing. See the Conventions entry below before changing anything here.
- `capabilities/upload-ceiling.ts` — `MAX_UPLOAD_BYTES` (**derived** from AWS API Gateway's 10 MiB request quota and base64's 4/3 inflation, not hardcoded) plus `SizeGuardedPipelexApiClient`, which refuses an oversize upload locally with the same `RejectedAssetError` the SDK maps a real `413` onto — so every downstream classifier keeps working and only the message improves, because it can name the true limit. It overrides `upload` (the wire call), which is the one seam both upload paths share: the SDK's own `prepareInputs` walk calls it through `this`. It does **not** skip reading/base64-encoding a local asset first — the SDK owns that inside `uploadFile`, so a real pre-flight needs a change in `@pipelex/sdk`. **The app-level 50 MiB `MAX_UPLOAD_MIB` is unreachable through the public gateway; never quote it as the limit.**
- `capabilities/artifacts.ts` — the run-artifact download capability (`mthds_download_artifacts`, **workshop-only**): reads the run through the results route, finds every `pipelex-storage://` reference in the FULL main output (`collectStorageUris` in `shared.ts` — a scheme walk, not a field-name heuristic), resolves each to a fresh presigned link via the SDK's `resolveStorageUrl`, and saves it under the working directory. Owns the write-side path trust boundary (`resolveSaveDir` — lexical `..` refusal, then a real-path check on the deepest *existing* ancestor BEFORE `mkdir`, then again after; a symlink pointing out of the workspace can never have directories created at its target) and the filename rule (`artifactFilename` — last key segment, `[A-Za-z0-9._-]`, no leading dot, length-capped with the extension kept, extension from content type when the key has none). The per-deployment seam is `ArtifactsContext.saveRoot`: the workshop sets it to its working directory; absent, the tool refuses fail-closed. Verdict discipline is the run family's (`state`-discriminated; `running`/`failed` are produced) plus `all_saved` for the walk; partial success is produced. No view, no `_meta`.
- `capabilities/artifact-download.ts` — the **download boundary** and the `ArtifactDownloader` seam: http(s) only (`http:` accepted on purpose — the local stack's object store mints plain-http presigned links), no credentials, redirects refused, bounded timeout, a 1 GiB accident-guard cap enforced from `content-length` before a byte is written and again mid-stream, streaming to a file opened **exclusively** (`openUniqueFile`, `wx`, numeric suffix on collision — "never overwrite" is a property of the open flag, not of an exists-check), no partial file left behind. Reports failures as values, like the other boundaries.
- `capabilities/run.ts` — the durable-run family (`mthds_run` / `mthds_run_status` / `mthds_run_results`) over the SDK's run lifecycle (`start` / `getRunStatus` / `getRunResult`). On a shell whose `RunContext.artifactDownloadAvailable` is set (the workshop), a completed results summary whose full output references stored files counts them and names `mthds_download_artifacts` — prose only, the structured contract is untouched. Starts from `files?`, `method_ref?`, or `method_id?` (rule `run_source`: files + `method_id` is the one legal pair — the files run, the id is run-history linkage; `method_ref` is a complete run source of its own and pairs with nothing). The platform resolves `method_id` natively on `/v1/start` (id-only runs the stored method's current content; beside files it rides the SDK's named `method_id` option — `PipelexStartOptions`, never `extra`, which the SDK refuses at runtime for reserved keys). `method_ref` rides the SDK's named Pipelex-API run-source extension, is resolved by the runner (git fetch at the tag), and the resolved commit comes back as `method_provenance` on the start ack — narrowed defensively (`narrowMethodProvenance`), projected into `structuredContent`, and echoed in the summary so the run stays explainable when a tag moves. Also owns `main_stuff` bounding (the prune ladder under `MAIN_STUFF_CAP`), the run-usage projection (`summarizeUsage` — run-level null-aware cost + `input`/`output` token totals only, branching on `usage_assembly_error` not the null list; per-pipe stays off the model-facing surface — `computeUsageByPipe` rides view-only `_meta.usage_by_pipe` alongside the full per-call `tokens_usages` for a future detailed-cost surface, and usage is never rendered into the prose), and the per-route classify options, including the by-id variants picked by request shape.
- `local/files.ts` — the local workshop's filesystem-backed `FileResolver` (`localFileResolver`): resolves `{ path }` items relative to the server's working directory, rejects any non-`.mthds` path *before touching the filesystem* (the `{ path }` arm is contracted to `.mthds` files — this keeps a prompt-injected `.env`/`.git/config`/key path from ever being opened), enforces the realpath containment boundary, and maps non-`.mthds` paths / escapes / missing files / non-regular files / read failures to `FileResolution` failures (never throws). Consumed by the local stdio shell; the hosted server never imports it.
- `helpers.ts` — `generateHelpers<AppType>()` exposes `useToolInfo`/`useCallTool` for the views.
- `views/run-graph.tsx` — the **run-graph** Skybridge view, registered on `mthds_validate`. It is the generic renderer for a method's run graph, deliberately **not** named after the validation trigger: today it shows the **dry-run graph** (`mthds_validate` feeds it the method structure from the validation dry run); a future `mthds_run` can register the same component for a **live-run graph** (with execution status). It reads the verdict from `useToolInfo` (`output`) and the graph from `responseMetadata.graph_spec` (the view-only `_meta` channel), then renders it with `@pipelex/mthds-ui`'s `GraphViewer` (inline preview + a `useDisplayMode` fullscreen toggle, sized from `useLayout`). On a runnable verdict it also renders the **input form** below the graph: `@pipelex/mthds-ui/form/react`'s `RunPanel` over the wire input-form descriptor (`responseMetadata.input_form` — since kernel 0.5.0 the descriptor IS the field derivation and `RunPanel` requires it) with the IO contract co-walked beside it (`responseMetadata.pipe_io_contracts`), each looked up for the pipe in play with `@pipelex/mthds-form`'s twin selectors `getPipeInputForm` / `getPipeIOContract` (the main pipe from `responseMetadata.main_pipe_ref`, or the pipe node the user last clicked via `GraphViewer`'s `onNodeSelect`). Run calls `mthds_run` through `useCallTool` with the validation's own `files` / `method_id`, follows the run with the shared `useRunPolling` hook, and fires `terminalFollowUpPrompt` once on the terminal status — the same handoff `run-follow` does, minus the results fetch (the model fetches results as its own turn). Two things to know: `running` is set synchronously inside `onRun` because that is the panel's only duplicate-run guard across the round trip, and no `uploadFile` is passed, so file-bearing inputs render a dropzone with nowhere to store (the console has no tool that takes browser bytes — a deliberate open item, not an oversight). It falls back to a compact empty state for invalid results and for no-graph / `include_graph: false` results that carry no form pair. Being a registered view, it also satisfies Skybridge's "≥1 view entry" production-build requirement (the old `build-placeholder.tsx` is gone). The renderer name (`run-graph`) is the durable family; the `available_view_specs` kinds (`dry_run_graph`, later `live_run_graph`) name the content variant it's fed.

### The files union and the resolution seam

Every files-taking tool (`mthds_validate`, `mthds_inputs_template`, `mthds_prepare_inputs`, `mthds_run`) shares one per-item input union: inline contents (`{ content, uri? }`) or a file path (`{ path }`). The arms are non-strict with first-match semantics — a pathological item carrying both keys parses as the content arm and `path` is ignored (strict arms were rejected in Phase 0: an unknown-key failure would surface as a noisy zod union error from the SDK layer instead of our instructive `ToolError`).

On all four files-taking tools (`mthds_validate`, `mthds_run`, `mthds_inputs_template`, `mthds_prepare_inputs`), `files` is **optional** beside separate top-level selectors — `method_ref?` (a published method address, `github.com/<owner>/<repo>[/<selector>][@<tag>]`; not on `mthds_prepare_inputs`) and `method_id?` (a registered method's catalog id). Neither is a third union arm: an address or an id is not a file, and a mixed array would falsely suggest merging. `validateMethodSelectorRequest` enforces the two selector rules (SPEC.md → "Method Selectors"): the tooling tools take **exactly one** source form; `mthds_run` lets files + `method_id` pair (files run, id is linkage) while `method_ref` pairs with nothing. Resolution: `mthds_validate` forwards either selector to the server; `mthds_inputs_template` forwards `method_ref` on the build envelope and expands `method_id` via **fetch-and-forward** (`fetchMethodFiles`), as does `mthds_prepare_inputs`; on `mthds_run` both selectors resolve natively server-side on `POST /v1/start` — see Run Scope.

What a `{ path }` item *does* is decided by the **resolution seam**, not the schema: each capability's context carries an optional `resolver?: FileResolver`, and `resolveSubmittedFiles(files, resolver)` runs **ahead of** the request-shape checks (`validateMethodSelectorRequest` sees only resolved `{ content, uri? }` items). With a resolver (the local workshop), `{ path }` items are read from disk and the resolved item carries `uri` = the submitted path — that's the provenance win: diagnostics locate to files the agent can open. Without one (the hosted console), each `{ path }` item is rejected with an instructive `input_domain` error at `files[i].path` naming the local workshop (`npx @pipelex/mcp`). Resolvers report failures as `FileResolution` values, never throw; every resolution failure is `input_domain` at `files[i].path`, `retryable: false` — the resolver supplies only message and hint.

### The output streams (contract vs presentation vs view)

This mirrors the workspace's "format follows consumer" rule — read `../CLAUDE.md` → "Surface output conventions". A tool result carries up to three independent streams (`mthds_validate` uses all three; `mthds_inputs_template` has no view, so it uses the first two):

- **`structuredContent`** — the machine contract the model reads. A machine consumer branches on these fields, never on transport.
- **`content` text** — the human/LLM-readable Markdown summary. For `mthds_validate` it is the API's `rendered_markdown` (with a short `## Views` note appended when a renderable view is available — see below) and is deliberately **not duplicated** into `structuredContent`. For `mthds_inputs_template` the capability composes it (the build routes return a plain `message`) and deliberately **does** repeat the template in a fenced code block — the template is the small payload the model must read, not a large view artifact.
- **`_meta`** — large, view-only data that **never reaches the model's context**. The graph (`_meta.graph_spec`) rides here so the agent acts on the verdict + Markdown summary, never the raw spec; the `run-graph` view reads it back via `responseMetadata.graph_spec`. `_meta` still travels on the raw MCP result, so a non-LLM programmatic consumer can read it off the wire — it is withheld from the model, not from the transport. The form's per-pipe artifact pair rides the same channel (`_meta.pipe_io_contracts` and `_meta.input_form` — the wire input-form descriptor the capability requests via `views: ["input_form"]` — plus `_meta.main_pipe_ref`) on a runnable verdict that carries both, for the input form. Because the model never sees `_meta`, `structuredContent.available_view_specs` is its structured signal a view exists to surface: it lists the renderable view kinds — `"dry_run_graph"` (the method graph from the validation dry run, riding `_meta.graph_spec`) and `"input_form"` (the main pipe's fill-in form, derived from `_meta.input_form` with `_meta.pipe_io_contracts` beside it; only on a runnable verdict with both artifacts, since a form whose Run can only fail — or whose fields cannot be derived — is not worth advertising). (The view-kind identifier and the `_meta` key are intentionally distinct: the key mirrors the API's `graph_spec` field and the view's `responseMetadata.graph_spec` reader, while the identifier names what kind of view it drives.)

### Verdict vs no-verdict (the `status` discriminator)

A successful `mthds_list_methods` call is `status:"ok"` with counts and a `methods` page; it is a read result, not a method verdict, so it has no `is_valid` field. The failure arm still uses the shared `status:"error"` + `errors[]` shape.

A *produced* verdict is always `status: "ok"`, regardless of whether the bundle passed — discriminate on `is_valid` (and, for validation, `is_runnable`). This discipline is shared by both tools: an unresolvable closure on `mthds_inputs_template` is a produced `is_valid: false` verdict with `validation_errors[]`, exactly like an invalid bundle on `mthds_validate`. `status: "error"` is reserved for **"no verdict could be produced"**: bad request shape, unreachable/misconfigured API, or a runtime fault. Those carry an `errors[]` array, each tagged with an `ErrorClass`:

- `input_domain` — the submitted request is wrong (empty `files`, blank `uri`, blank `pipe_ref`, API 400/422 — which on `/v1/build/inputs` includes an unknown `pipe_ref` and an unresolvable `main_pipe` default).
- `config` — environment/auth is wrong (`PIPELEX_BASE_URL`/`PIPELEX_API_KEY`, API unreachable, 401/403/404).
- `runtime` — unexpected server-side fault (API 5xx, unknown errors, a reachable-but-malformed report).

`classifyError` (in `capabilities/shared.ts`) maps `@pipelex/sdk` error types (`ApiUnreachableError`, `ClientAuthenticationError`, `ApiResponseError`, `PipelineRequestError`) and HTTP statuses onto these classes; each capability passes `ClassifyErrorOptions` for its route-specific 400/422 locator/hint and 404 route name, plus the deployment's auth-failure texture (`options.auth`, threaded from the context's `authError` field — the hosted console's "reconnect the connector and sign in again" wording at `authorization` vs the default `PIPELEX_API_KEY` env-var wording). Every `ToolError` also carries `retryable` — set here, where the concrete SDK error/HTTP status is still known, because the class+locator pair alone can't tell an unreachable API (transient) from a missing run lifecycle (permanent, same `config`@`PIPELEX_BASE_URL`) or a 5xx from a malformed report (both `runtime`); the `run-follow` view's poll loops branch on it via `isTransientPollError`. When you add a new failure mode, classify it here — including its `retryable` verdict — rather than letting it fall through to a generic `runtime` message.

A `ToolError` also carries an optional `kind`, which **refines a class that the headline cannot use**. Its only member is `paywall`, set in the 402 arm: a plan limit is deliberately `config`, so every class-derived headline announced "the Pipelex API is unreachable or misconfigured" for a billing refusal — and on a host that shows the agent only the top content line, that was the entire message. Each capability now declares its headlines as an `ErrorSummaries` record (three classes **plus** `paywall`) and looks one up through `summaryForToolError`, which consults `kind` before `class`. The mandatory `paywall` entry is the point of the type: a new capability that forgot one would silently inherit the connectivity headline, and this makes that a type error instead of a review catch. The `class` contract is untouched — a machine consumer still branches on `class`; `kind` is what lets it tell a billing refusal from an unreachable API without sniffing the message, exactly as `retryable` separates a transient `config` from a permanent one. A future cause of the same shape gets a new `kind` member and a headline in every table; it does not get re-classified.

### State projection rules (in `validationResult`)

- Valid + runnable → `is_valid=true`, `is_runnable=true`; the graph is returned on `ValidationResult.graphSpec` (projected onto the tool result's `_meta.graph_spec` by `toolResult`), never in `structuredContent`.
- Valid + pending signatures → `is_valid=true`, `is_runnable=false`, `pending_signatures` populated.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated.
- `include_graph` defaults to **true**; pass `false` to omit the graph from a valid report (`graphSpec` stays undefined).
- `available_view_specs` is populated from what was produced: `"dry_run_graph"` exactly when `graphSpec != null` (valid verdict + `include_graph`), `"input_form"` exactly when `inputForm != null` (valid + runnable + non-empty `pipe_io_contracts` AND a non-empty `input_form` descriptor — both are set together, since the kernel derives the fields from the descriptor and a report without one, e.g. from a runner that ignored the `views` token, must advertise nothing rather than an empty form; independent of `include_graph`), and `[]` otherwise (invalid, pending signatures without a graph, error). When the list is non-empty a `## Views` note worded for the present kinds (`viewsNote`) is appended to the Markdown summary. Add a new view kind to the `viewSpecSchema` enum and set it here when its spec is produced.
- The capability always calls the API with `allowSignatures: true`, `render: ["markdown"]`, and `views: ["input_form"]` (the descriptor opt-in — lenient on the server, so a runner that predates it simply returns no `input_form`). A report missing `rendered_markdown` is a hard error.

### State projection rules (in `inputsResult`)

- Valid → `is_valid=true`, resolved `pipe_ref`, echoed `format`/`explicit`, and the template on exactly one of `inputs` (json) / `inputs_toml` (toml) — the unused field is absent.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated; no `pipe_ref`, no template fields.
- The request always sends its defaults explicitly: `format: "json"`, `explicit: true` unless overridden. A valid report missing its format-selected template field is a hard error (surfaced as a `runtime` no-verdict).
- The summary is composed by the capability (title, API `message`, resolved pipe, fenced template block matching `format`).

## Testing conventions

Tests are colocated (`*.test.ts`, Node environment). Each capability is tested by **injecting a fake client** via its context's `client` field (`CatalogContext.client`, `ValidationContext.client`, `InputsContext.client`) — the capability uses `context.client` when present and only constructs a real `PipelexApiClient` otherwise. Use this seam to test API behavior without a live `pipelex-api`. The **resolver seam works the same way**: inject a fake `FileResolver` via the context's `resolver` field to test `{ path }` handling without touching the filesystem (leave it absent to test the hosted rejection); the real `localFileResolver` is tested against actual temp directories in `local/files.test.ts`. The attachment capability adds a third seam of the same shape: inject a fake `AttachmentFetcher` via `AttachmentsContext.fetcher` to exercise ingest without network, while the real boundary is tested directly in `attachment-fetch.test.ts` (allowlist incl. the suffix-only attack, oversize refused before the body is read, a lying `content-length`, refused redirects, timeout, expired-URL `403`). The artifact download capability mirrors it: inject a fake `ArtifactDownloader` via `ArtifactsContext.downloader` (the fakes in `artifacts.test.ts` still write through the real `openUniqueFile`, and every walk runs against a real temp working directory, so containment, collision suffixing and relative-path reporting are exercised on disk), while the real boundary is tested in `artifact-download.test.ts` against a loopback `node:http` server (streams to file, never overwrites, declared oversize refused before any file is opened, a lying `content-length` leaves no partial file, refused redirects, `404` vs `5xx` classes, non-http(s) links refused without a request). `local/server.test.ts` pins cross-shell tool parity plus the shell-level properties that are un-hotfixable once users add a connector: the **emitted four-field JSON Schema**, the `openai/fileParams` key that *is* the substitution mechanism, and the workshop's **absence** of the console-only tool. Pure projection/classification functions (`projectCatalog`, `validationResult`, `inputsResult`, `classifyError`, `validateMethodSelectorRequest`, `validateInputsRequest`, `resolveSubmittedFiles`, `fetchMethodFiles`) are exported specifically so they can be tested in isolation; the shared ones are covered in `shared.test.ts`.

**Two suites, two jobs — and the second exists because the first mocks the boundary that actually breaks.** The default suite (`*.test.ts`, `vitest.config.ts`) fakes every client, so it proves the projections and never touches the wire; that is what keeps `make all` and CI hermetic. The live suite (`*.e2e.ts`, `vitest.e2e.config.ts`, run by `make test-e2e`) does the opposite: it builds each capability's context from `liveApiConfig()` and supplies **no** `client` seam, so the real `PipelexApiClient` reaches the real API. Selection is by suffix — the default `include` is `*.test.ts`, so an e2e file can never be picked up by the hermetic run. When a live run reveals behavior that contradicts a unit fake, fix the fake in the same change: a fake that has drifted from the wire is how the mocked suite goes green over a broken client. Shared fixtures, the fixture-method lookup and the API config guard live in `src/capabilities/e2e-support.ts`.

## Conventions & gotchas

- **No backward-compatibility burden** (workspace rule) — change shapes directly; record breaking changes in `CHANGELOG.md` (and reflect the new shape in `SPEC.md`).
- **The attachment fetch boundary is a security boundary — treat it like `local/files.ts`, not like plumbing.** It is the one place this server fetches a URL it did not configure, which makes a public endpoint an SSRF surface. It denies by default: `https:` only; the hostname must be `oaiusercontent.com` (apex or **any** subdomain) or match `oaisdmntpr<azure-region>.blob.core.windows.net`; no credentials in the URL; no non-default port; redirects refused outright; the 7 MiB cap enforced from `content-length` **before the body is read** *and* again mid-stream; a bounded total budget; no headers sent; non-2xx refused. **The two host rules are asymmetric on purpose — don't "harmonize" them.** The `oaisdmntpr` prefix is required, never optional, *only* because `blob.core.windows.net` is multi-tenant (any Azure customer can register under it, and a literal list is dead — one user produced three different Azure regions in one afternoon). `oaiusercontent.com` is OpenAI's own locked domain, so there is no "any customer" hazard for a prefix to filter, and narrowing it just queues up the next outage: the boundary originally allowed only `files.oaiusercontent.com` and refused every attachment the day serving moved to `sdmntpr<region>.oaiusercontent.com`. Two rules to keep when editing: **fetch the already-parsed `URL` object, never re-parse the raw string** (re-parsing at the fetch is how an allowlist gets walked past), and remember that these hosts are undocumented vendor infrastructure that changes without notice — **the host check is a filter, not the defence**, so the cap, the timeout, and the no-redirect rule must each hold on their own.
- **The artifact download path is a write-side security boundary — treat `capabilities/artifacts.ts`'s `resolveSaveDir` / `artifactFilename` and `capabilities/artifact-download.ts` like `local/files.ts`.** It is the one place this server writes a file it did not create for itself, into the user's workspace. Three rules to keep when editing: the filename is derived from the storage key and never from a caller argument; the directory is real-path-checked on its deepest existing ancestor *before* `mkdir` (a check only after `mkdir` lets a symlinked ancestor create directories outside the workspace); and the file is opened with `wx` so "never overwrite" cannot race. The download link comes from our own API, so the fetch is not the SSRF surface the attachment boundary guards, but the cap, the timeout and the no-redirect rule hold on their own regardless of who named the URL.
- **The `mthds_upload_attachments` description is mechanism, not documentation, and cannot be hot-fixed.** ChatGPT gates the attachment substitution on the description as well as the schema (a defensive wording measurably yields empty calls that look like a host failure), *and* it caches a connector's tool list at add-time and never refreshes it — so a description defect leaves every existing installation broken until each user re-adds the connector. Review changes to that text with the same rigour as a schema change, and say "re-add the connector" in the release notes.
- **Never log request `_meta`.** ChatGPT attaches `openai/userLocation` (city, region, country, timezone, latitude/longitude) plus stable `openai/subject` / `openai/session` / `openai/organization` identifiers to **every** `tools/call`. That is PII arriving on a surface we did not ask for, on every route.
- **Branding:** keep MTHDS-standard concepts neutrally named inside the Pipelex-branded envelope (`bundle_blueprint`, `graph_spec`, `pipe_io_contracts`, `input_form`) — see `../CLAUDE.md` "Brand boundaries".
- `no-console` is an **error** in ESLint — don't leave `console.*` calls.
- **The input form's kernel, `@pipelex/mthds-form`, is a direct dependency on purpose.** `@pipelex/mthds-ui` declares it as an *optional peer* (its `FieldStringsProvider` / `FieldPresentationProvider` are React contexts, so a nested copy would silently read defaults), which means it is never installed transitively — the view would fail to build without our own entry. Its controls are Tailwind classes over shadcn semantic tokens, and under this repo's Tailwind 4 build they resolve to `@alpic-ai/ui/theme`'s `--color-*` tokens; `src/index.css` therefore carries a `@source` glob for the kernel's `dist/` and deliberately does **not** import the kernel's prebuilt `theme.css` / `styles.css` (the latter ships Tailwind preflight and would double-load the reset). Forgetting the glob yields a form that is *mostly* styled — focus ring, placeholder colour, dropzone state gone — so diff the built stylesheet rather than eyeballing it.
- The SDK dependency is the **published `@pipelex/sdk` npm package** (public on npm), not a `file:../pipelex-sdk-js` link. CI just runs `npm ci` — there is no sibling repo to check out. To develop against local `../pipelex-sdk-js` (or `../mthds-ui`) changes, use the Makefile switches — `make use-local-sdk` / `make use-local-ui` (or `make use-local` for both) point the dep at the sibling repo via a `file:` link, and `make use-npm-sdk` / `make use-npm-ui` (or `make use-npm`) switch back to npm; `make check` refuses to run while a `@pipelex` dep is a local link (the `check-no-local-deps` guard), so don't commit the link. Bump the `^x.y.z` range once the change is published. `mthds` is no longer a direct dependency — it rides along transitively through `@pipelex/sdk`.
- Keep `SPEC.md`'s declared input/output shapes, the Zod schemas in `capabilities/`, and `README.md` in sync when a tool contract changes.

## Versioning & changelog

`pipelex-mcp` follows [Semantic Versioning](https://semver.org). `version` in `package.json` is the source of truth and is git-tagged (`vX.Y.Z`) on release. All notable changes are recorded in [`CHANGELOG.md`](CHANGELOG.md) using the [Keep a Changelog](https://keepachangelog.com) format.

- Work in progress accumulates under `## [Unreleased]` — don't mint a new `## [x.y.z]` heading per commit. Mint it (and the `vX.Y.Z` tag) only when you actually release that version; the newest versioned heading must then match `package.json`'s `version`. To cut a release, use the **`/release` skill** (`.claude/skills/release/`): it promotes `## [Unreleased]` to `## [x.y.z]`, bumps `package.json`, regenerates `package-lock.json`, and opens the `release/vX.Y.Z → main` PR that the CI gates expect. Note the version-string split: the `v` prefix is on the branch name, git tag, and PR title only — never in `package.json` or the `## [x.y.z]` changelog heading.
- `0.1.0` is the first tagged release. It **retires the `v0.x` prototype-increment track** (`../docs/mcp/archive/2026-06-design/02-delivery/v0.x-prototype-plan.md`): the milestones once called v0.1 / v0.2 / v0.3 were build increments, not package versions, and all shipped together as `0.1.0`. Use the changelog + semver from here on, not the v0.x numbering. `../docs/mcp/cold-start.md` remains the cold-start brief for resuming work; `CHANGELOG.md` is the source of truth for what has shipped.
