# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Workspace-level guidance lives in `../CLAUDE.md` (Pipelex multi-repo workspace). This file covers only what is specific to `pipelex-mcp`.

## What this repo is

`pipelex-mcp` exposes MTHDS validation, inputs projection and preparation, and durable method runs to MCP hosts. It ships as **two servers from one capability core** (see the Architecture section): a hosted **Skybridge console** for remote-connector hosts (ChatGPT, claude.ai, Cowork) and a local **workshop** stdio server distributed on npm as `@pipelex/mcp` for coding-agent hosts (Claude Code, Codex, Cursor). Both register the same MCP tools — `mthds_validate`, `mthds_inputs_template`, `mthds_prepare_inputs`, and the `mthds_run` / `mthds_run_status` / `mthds_run_results` durable-run family — plus one console-only tool, `mthds_upload_attachments`, which turns a file the user attached in the chat into a run-ready `pipelex-storage://` reference (ChatGPT's Apps runtime is the only host that substitutes the attachment; see the Architecture section). An assistant that already holds `.mthds` file contents (or, on the workshop, their on-disk paths) calls `mthds_validate` for a stable, structured verdict it can use to explain and repair diagnostics, `mthds_inputs_template` for a fill-in template of a pipe's declared inputs, `mthds_prepare_inputs` to turn filled file-bearing inputs run-ready (uploading assets to Pipelex storage on the workshop; pass-through only on the console), and the run family to execute a method durably. On a positive validation verdict the `mthds_validate` tool ships a Skybridge view, `run-graph`, that renders the method graph interactively with `@pipelex/mthds-ui`'s `GraphViewer` (hosted console only — the workshop is tools-first, no views); `mthds_inputs_template`, `mthds_prepare_inputs`, and the status/results tools are plain tools with no view.

It is a thin MCP front-end over the existing Pipelex validation stack — it does no validation itself. It forwards file contents to a **Pipelex API** (`POST /v1/validate`, `POST /v1/build/inputs`) through the `PipelexApiClient` from the `@pipelex/sdk` npm package (published from `../pipelex-sdk-js`), then projects the API's reports into MCP output. `@pipelex/sdk` is the Pipelex hosted-platform SDK — the same one `pipelex-app` uses, and the only one carrying the durable run lifecycle the later run-backed tools need; it re-exports the open `mthds/protocol` surface, so the MCP imports one SDK.

`SPEC.md` is the source of truth for product requirements and design decisions — read and update it when changing behavior. `AGENTS.md` mandates using the **`skybridge` skill** when planning or updating this codebase; do so.

## Commands

Use the `Makefile` (wraps the npm scripts):

- `make check` (= `npm run check`) — lint + format:check + build (Skybridge) + build:local (tsup) + typecheck. The pre-flight gate; run before declaring work done. **`build` runs before the standalone `typecheck`** on purpose: Skybridge regenerates the view-name registry (`.skybridge/views.d.ts`, gitignored) as `build`'s first step, and `tsc` needs it to resolve `mthds_validate`'s `view.component`. A cold `typecheck` with no prior `build`/`dev` won't know the view name. `build:local` bundles the workshop bin and sits between the two.
- `make test` / `make t` — Vitest run.
- `make all` — clean + check + test.
- `make dev` — Skybridge dev server. MCP endpoint at `http://localhost:3000/mcp`, DevTools UI at `http://localhost:3000`.
- `make dev-local` — local workshop stdio server from TypeScript. `make inspect-local` opens MCP Inspector against that entrypoint.
- `make build-local` — bundle the npm-distributed `pipelex-mcp` executable to `dist/local/main.js` with tsup. `npm pack` runs this automatically through `prepack`.
- `make deploy` — deploy via Alpic (`alpic deploy`).

Run a single test with Vitest directly: `npx vitest run src/capabilities/validate.test.ts` or filter by name with `npx vitest run -t "projects pending signatures"`.

### Running against the validation API

The tool needs a reachable Pipelex API serving `POST /v1/validate`. During early development this is the **local OSS `pipelex-api`** runner (temporary — production target is the hosted Pipelex API only):

```bash
cd ../pipelex-api && make run      # serves http://localhost:8081
PIPELEX_BASE_URL=http://localhost:8081 npm run dev
```

- `PIPELEX_BASE_URL` defaults to the hosted Pipelex API (`https://api.pipelex.com`) when unset; set it to `http://localhost:8081` to develop against the local OSS runner.
- `PIPELEX_API_KEY` is optional — set it only when the configured API requires auth. Local dev normally runs without it.
- Both variables can live in a gitignored `.env` at the repo root instead of prefixing the command: `nodemon.json` overrides Skybridge's default dev exec with `tsx --env-file-if-exists=.env src/server.ts` (keep its `watch`/`ext` in sync with Skybridge's defaults — a `nodemon.json` replaces them entirely, not additively). `.env` is dev-only and not watched — restart the dev server after editing it.

## Architecture

The repo ships two thin shells over one capability core: the Skybridge HTTP console for hosted connectors and the plain MCP-SDK stdio workshop for coding agents. Both map over `src/tools.ts`, so tool names, schemas, descriptions, annotations, and handler wiring stay identical; only the hosted shell adds views and host-specific metadata. The workshop injects the cwd-bound file resolver and declares views unavailable.

**One exception to "both shells register the same table":** `src/tools.ts` exports a **second** ordered table, `consoleOnlyToolDefinitions`, holding `mthds_upload_attachments` alone. The hosted shell registers both tables (it already registers tool-by-tool, for views and `_meta`); `local/server.ts` loops over `toolDefinitions` only and is untouched. The tool's sole argument is a host-substituted attachment reference and the host gates that substitution on the declared JSON Schema, so on the workshop it would be *structurally unreachable* rather than merely unused — registering it there would spend every workshop user's tokens on every `tools/list` advertising a capability that cannot fire. Keep it a table, not a duplicated definition: one definition per tool, one registration site per shell. The invariant that still holds, and that matters for routing: **no tool name means different things on the two shells.** (Cost of the split: `tools.ts` importing the attachment capability links ~18 KB of unreachable code into the workshop bundle, since esbuild cannot tree-shake module-scope Zod construction. Accepted deliberately — removing it would fork the context plumbing; revisit only if the console-only surface grows past one tool.)

The whole server is a handful of small files under `src/`:

- `server.ts` — thin Skybridge entrypoint; `hosted/server.ts` owns the console shell and its views/host metadata. `tools.ts` is the ordered shared tool-definition table both shells register.
- `hosted/byok.ts` — the console's **bring-your-own-key** interim auth (until console OAuth; deliberately disposable — delete, don't migrate). An Express middleware on `/mcp` extracts the caller's `plx_sk_` key (`Authorization: Bearer` header first, `?api_key=` query fallback) into `req.auth`, which the MCP SDK transport surfaces to tool handlers as `extra.authInfo`; `contextsForRequest` then derives per-request capability contexts — a supplied key overrides `apiKey` everywhere and sets the "your key was rejected" auth texture, a fully keyless request gets the "bring your own key" texture, and a server-held env key keeps the default env-var wording. Keyless requests are never rejected at the transport (the handshake must work); they fail instructively at the capability layer. The key rides the transport only — never a tool argument, so it never enters the model's context. The workshop doesn't import this: its per-user key is the host-supplied `PIPELEX_API_KEY` env.
- `local/server.ts` — constructs the plain MCP SDK server, registers the shared tool table with local contexts, and injects one cwd-bound file resolver. `local/main.ts` owns stdio transport and graceful shutdown; `local/log.ts` keeps diagnostics on stderr so stdout remains protocol-only.
- `capabilities/shared.ts` — the plumbing the capabilities share: the submitted-files input schema (a per-item union, `{ content, uri? } | { path }` — see "The files union and the resolution seam" below), the `ToolError` model, file resolution (`resolveSubmittedFiles` + the `FileResolver` seam), request-shape validation (`validateFilesOrMethodIdRequest`, shared by all three files-or-`method_id` tools), the by-id fetch-and-forward leg (`fetchMethodFiles` + `MethodFetchClient`, shared by `mthds_validate`, `mthds_inputs_template`, and `mthds_prepare_inputs`), env-derived API config (`buildApiConfig` — `PIPELEX_BASE_URL`/`PIPELEX_API_KEY`), and `classifyError`. `classifyError` takes per-route `ClassifyErrorOptions` (the 400/422 locator/hint and the route named in the 404 hint) so each capability points the agent at its own knobs; it also maps the `@pipelex/sdk` `InputPreparationError` family (the upload/preparation errors `mthds_prepare_inputs` can raise) ahead of the generic `PipelineRequestError` arm.
- `capabilities/validate.ts` — the validation logic. Zod input/output schemas, the API call (`validateFiles`), and projection of the API report into MCP `structuredContent` + the view-only `_meta` graph payload (`toolResult`). Also accepts `method_id` via the shared `fetchMethodFiles` fetch-and-forward leg — `/v1/validate` has no by-id support either, so a by-id call fetches the stored method and forwards its source as files, same as `mthds_inputs_template`.
- `capabilities/inputs.ts` — the inputs-template logic. Zod input/output schemas (`files?` beside `method_id?`, `pipe_ref?`, `explicit?` default true, `format?` default json), the API call (`buildInputs`, adapting the MCP `uri` provenance label to the build envelope's `source`), and projection of the report into `structuredContent` plus a composed Markdown summary that includes the template in a fenced code block (the build routes return a plain `message`, not `rendered_markdown`). A `method_id`-only request **fetches-and-forwards** via the shared `fetchMethodFiles` (in `capabilities/shared.ts`, also used by `mthds_validate`): the SDK's `getMethodClosure` → files, each labeled with the method id as provenance, adapted to the build envelope's `source` here; a source-less stored method (the SDK's `EmptyMethodSourceError`) is an `input_domain` no-verdict at `method_id` raised without calling the build route, and fetch-leg failures classify against `/v1/methods/{id}`. Files win when both are supplied (no linkage concept on the build routes). No view, no `_meta`.
- `capabilities/prepare.ts` — the input-preparation logic (`mthds_prepare_inputs`). Zod input/output schemas (`files?`/`method_id?`, `pipe_ref?`, required filled `inputs`), and preparation of file-bearing input values via `@pipelex/sdk`'s `prepareInputs`: uploads local paths / `data:` URLs / bytes to Pipelex storage and rewrites them to `pipelex-storage://`, projecting the result into `structuredContent` (`inputs`, `uploads: string[]`) plus a composed Markdown summary with the prepared inputs in a fenced block. The by-id path fetches-and-forwards via the shared `fetchMethodFiles` (files win), exactly as `mthds_validate` / `mthds_inputs_template`. **The per-deployment asset boundary is a `PrepareContext.allowUpload` seam** (analogous to `resolver`): the workshop (`allowUpload: true`) delegates the upload walk to the SDK's `prepareInputs`; the hosted console (`false`, the default) runs its own **pass-through-only** walk — it resolves the signature via `buildInputs` (explicit) and rewrites `http(s)` / `pipelex-storage://` values but refuses any upload-needing value up front (`input_domain`@`inputs`), so it never hands raw inputs to `prepareInputs` and never triggers a server-side `readLocalPath` (the LFI/DoS/existence-oracle hazard). **No produced-invalid arm** — an unresolvable closure is a no-verdict `status:"error"` (the SDK throws `InputPreparationError` without structured `validation_errors[]`). No view, no `_meta`.
- `capabilities/attachments.ts` — the chat-attachment ingest capability (`mthds_upload_attachments`, **console-only**) plus the mandated four-field host-attachment Zod schema (`download_url`/`file_id` required, `mime_type`/`file_name` optional — declared here rather than imported from `skybridge/server`'s `FileRef`, because the capability core stays Skybridge-free; a local mirror emits a byte-identical JSON Schema). Per attachment, sequentially: fetch within the boundary → `uploadFile` → `pipelex-storage://`. The host's `file_name` is user-supplied, so it is reduced to a bare printable basename before it names a stored asset. Per-item errors ride `attachments[i].error` and **partial success is a produced verdict** (`status:"ok"`, `is_valid:false`) — successful uploads are never discarded because a sibling failed. Never touches the filesystem. No view, no `_meta`.
- `capabilities/attachment-fetch.ts` — the **attachment fetch boundary**: the console's analogue of the workshop's path trust boundary, deny-by-default, reporting failures as values rather than throwing. See the Conventions entry below before changing anything here.
- `capabilities/upload-ceiling.ts` — `MAX_UPLOAD_BYTES` (**derived** from AWS API Gateway's 10 MiB request quota and base64's 4/3 inflation, not hardcoded) plus `SizeGuardedPipelexApiClient`, which refuses an oversize upload locally with the same `RejectedAssetError` the SDK maps a real `413` onto — so every downstream classifier keeps working and only the message improves, because it can name the true limit. It overrides `upload` (the wire call), which is the one seam both upload paths share: the SDK's own `prepareInputs` walk calls it through `this`. It does **not** skip reading/base64-encoding a local asset first — the SDK owns that inside `uploadFile`, so a real pre-flight needs a change in `@pipelex/sdk`. **The app-level 50 MiB `MAX_UPLOAD_MIB` is unreachable through the public gateway; never quote it as the limit.**
- `capabilities/run.ts` — the durable-run family (`mthds_run` / `mthds_run_status` / `mthds_run_results`) over the SDK's run lifecycle (`start` / `getRunStatus` / `getRunResult`). Starts from `files?` and/or `method_id?`: the platform resolves `method_id` natively on `/v1/start` (id-only runs the stored method's current content; beside files it rides `extra.method_id` as run-history linkage while the files run). Also owns `main_stuff` bounding (the prune ladder under `MAIN_STUFF_CAP`), the run-usage projection (`summarizeUsage` — run-level null-aware cost + `input`/`output` token totals only, branching on `usage_assembly_error` not the null list; per-pipe stays off the model-facing surface — `computeUsageByPipe` rides view-only `_meta.usage_by_pipe` alongside the full per-call `tokens_usages` for a future detailed-cost surface, and usage is never rendered into the prose), and the per-route classify options, including the by-id variants picked by request shape.
- `local/files.ts` — the local workshop's filesystem-backed `FileResolver` (`localFileResolver`): resolves `{ path }` items relative to the server's working directory, rejects any non-`.mthds` path *before touching the filesystem* (the `{ path }` arm is contracted to `.mthds` files — this keeps a prompt-injected `.env`/`.git/config`/key path from ever being opened), enforces the realpath containment boundary, and maps non-`.mthds` paths / escapes / missing files / non-regular files / read failures to `FileResolution` failures (never throws). Consumed by the local stdio shell; the hosted server never imports it.
- `helpers.ts` — `generateHelpers<AppType>()` exposes `useToolInfo`/`useCallTool` for the views.
- `views/run-graph.tsx` — the **run-graph** Skybridge view, registered on `mthds_validate`. It is the generic renderer for a method's run graph, deliberately **not** named after the validation trigger: today it shows the **dry-run graph** (`mthds_validate` feeds it the method structure from the validation dry run); a future `mthds_run` can register the same component for a **live-run graph** (with execution status). It reads the verdict from `useToolInfo` (`output`) and the graph from `responseMetadata.graph_spec` (the view-only `_meta` channel), then renders it with `@pipelex/mthds-ui`'s `GraphViewer` (inline preview + a `useDisplayMode` fullscreen toggle, sized from `useLayout`). It falls back to a compact empty state for invalid / no-graph / `include_graph: false` results. Being a registered view, it also satisfies Skybridge's "≥1 view entry" production-build requirement (the old `build-placeholder.tsx` is gone). The renderer name (`run-graph`) is the durable family; the `available_view_specs` kinds (`dry_run_graph`, later `live_run_graph`) name the content variant it's fed.

### The files union and the resolution seam

Every files-taking tool (`mthds_validate`, `mthds_inputs_template`, `mthds_prepare_inputs`, `mthds_run`) shares one per-item input union: inline contents (`{ content, uri? }`) or a file path (`{ path }`). The arms are non-strict with first-match semantics — a pathological item carrying both keys parses as the content arm and `path` is ignored (strict arms were rejected in Phase 0: an unknown-key failure would surface as a noisy zod union error from the SDK layer instead of our instructive `ToolError`).

On all four files-taking tools (`mthds_validate`, `mthds_run`, `mthds_inputs_template`, `mthds_prepare_inputs`), `files` is **optional** beside a separate top-level `method_id?` (a registered method's catalog id — deliberately not a third union arm: a method id is not a file, and a mixed array would falsely suggest merging). At least one of the two is required (`validateFilesOrMethodIdRequest`); inline files always win. On `mthds_validate`, `mthds_inputs_template`, and `mthds_prepare_inputs` (routes with no by-id support) a `method_id`-only request resolves via **fetch-and-forward** (`fetchMethodFiles`); on `mthds_run`, `method_id` resolves natively server-side on `POST /v1/start` — see Run Scope.

What a `{ path }` item *does* is decided by the **resolution seam**, not the schema: each capability's context carries an optional `resolver?: FileResolver`, and `resolveSubmittedFiles(files, resolver)` runs **ahead of** the request-shape checks (`validateFilesOrMethodIdRequest` sees only resolved `{ content, uri? }` items). With a resolver (the local workshop), `{ path }` items are read from disk and the resolved item carries `uri` = the submitted path — that's the provenance win: diagnostics locate to files the agent can open. Without one (the hosted console), each `{ path }` item is rejected with an instructive `input_domain` error at `files[i].path` naming the local workshop (`npx @pipelex/mcp`). Resolvers report failures as `FileResolution` values, never throw; every resolution failure is `input_domain` at `files[i].path`, `retryable: false` — the resolver supplies only message and hint.

### The output streams (contract vs presentation vs view)

This mirrors the workspace's "format follows consumer" rule — read `../CLAUDE.md` → "Surface output conventions". A tool result carries up to three independent streams (`mthds_validate` uses all three; `mthds_inputs_template` has no view, so it uses the first two):

- **`structuredContent`** — the machine contract the model reads. A machine consumer branches on these fields, never on transport.
- **`content` text** — the human/LLM-readable Markdown summary. For `mthds_validate` it is the API's `rendered_markdown` (with a short `## Views` note appended when a renderable view is available — see below) and is deliberately **not duplicated** into `structuredContent`. For `mthds_inputs_template` the capability composes it (the build routes return a plain `message`) and deliberately **does** repeat the template in a fenced code block — the template is the small payload the model must read, not a large view artifact.
- **`_meta`** — large, view-only data that **never reaches the model's context**. The graph (`_meta.graph_spec`) rides here so the agent acts on the verdict + Markdown summary, never the raw spec; the `run-graph` view reads it back via `responseMetadata.graph_spec`. `_meta` still travels on the raw MCP result, so a non-LLM programmatic consumer can read it off the wire — it is withheld from the model, not from the transport. Because the model never sees `_meta`, `structuredContent.available_view_specs` is its structured signal a view exists to surface: it lists the renderable view kinds. The only kind for now is `"dry_run_graph"` — the method graph from the validation dry run, whose spec is the one riding `_meta.graph_spec`. (The view-kind identifier and the `_meta` key are intentionally distinct: the key mirrors the API's `graph_spec` field and the view's `responseMetadata.graph_spec` reader, while the identifier names what kind of view it drives.)

### Verdict vs no-verdict (the `status` discriminator)

A *produced* verdict is always `status: "ok"`, regardless of whether the bundle passed — discriminate on `is_valid` (and, for validation, `is_runnable`). This discipline is shared by both tools: an unresolvable closure on `mthds_inputs_template` is a produced `is_valid: false` verdict with `validation_errors[]`, exactly like an invalid bundle on `mthds_validate`. `status: "error"` is reserved for **"no verdict could be produced"**: bad request shape, unreachable/misconfigured API, or a runtime fault. Those carry an `errors[]` array, each tagged with an `ErrorClass`:

- `input_domain` — the submitted request is wrong (empty `files`, blank `uri`, blank `pipe_ref`, API 400/422 — which on `/v1/build/inputs` includes an unknown `pipe_ref` and an unresolvable `main_pipe` default).
- `config` — environment/auth is wrong (`PIPELEX_BASE_URL`/`PIPELEX_API_KEY`, API unreachable, 401/403/404).
- `runtime` — unexpected server-side fault (API 5xx, unknown errors, a reachable-but-malformed report).

`classifyError` (in `capabilities/shared.ts`) maps `@pipelex/sdk` error types (`ApiUnreachableError`, `ClientAuthenticationError`, `ApiResponseError`, `PipelineRequestError`) and HTTP statuses onto these classes; each capability passes `ClassifyErrorOptions` for its route-specific 400/422 locator/hint and 404 route name, plus the deployment's auth-failure texture (`options.auth`, threaded from the context's `authError` field — the hosted console's BYOK wording vs the default `PIPELEX_API_KEY` env-var wording). Every `ToolError` also carries `retryable` — set here, where the concrete SDK error/HTTP status is still known, because the class+locator pair alone can't tell an unreachable API (transient) from a missing run lifecycle (permanent, same `config`@`PIPELEX_BASE_URL`) or a 5xx from a malformed report (both `runtime`); the `run-follow` view's poll loops branch on it via `isTransientPollError`. When you add a new failure mode, classify it here — including its `retryable` verdict — rather than letting it fall through to a generic `runtime` message.

### State projection rules (in `validationResult`)

- Valid + runnable → `is_valid=true`, `is_runnable=true`; the graph is returned on `ValidationResult.graphSpec` (projected onto the tool result's `_meta.graph_spec` by `toolResult`), never in `structuredContent`.
- Valid + pending signatures → `is_valid=true`, `is_runnable=false`, `pending_signatures` populated.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated.
- `include_graph` defaults to **true**; pass `false` to omit the graph from a valid report (`graphSpec` stays undefined).
- `available_view_specs` is populated from the produced graph: it holds `["dry_run_graph"]` exactly when `graphSpec != null` (valid verdict + `include_graph`), and `[]` otherwise (invalid, no graph, `include_graph: false`, error). On that same condition a `## Views` note is appended to the Markdown summary. Add a new view kind to the `viewSpecSchema` enum and set it here when its spec is produced.
- The capability always calls the API with `allowSignatures: true` and `render: ["markdown"]`. A report missing `rendered_markdown` is a hard error.

### State projection rules (in `inputsResult`)

- Valid → `is_valid=true`, resolved `pipe_ref`, echoed `format`/`explicit`, and the template on exactly one of `inputs` (json) / `inputs_toml` (toml) — the unused field is absent.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated; no `pipe_ref`, no template fields.
- The request always sends its defaults explicitly: `format: "json"`, `explicit: true` unless overridden. A valid report missing its format-selected template field is a hard error (surfaced as a `runtime` no-verdict).
- The summary is composed by the capability (title, API `message`, resolved pipe, fenced template block matching `format`).

## Testing conventions

Tests are colocated (`*.test.ts`, Node environment). Each capability is tested by **injecting a fake client** via its context's `client` field (`ValidationContext.client`, `InputsContext.client`) — the capability uses `context.client` when present and only constructs a real `PipelexApiClient` otherwise. Use this seam to test API behavior without a live `pipelex-api`. The **resolver seam works the same way**: inject a fake `FileResolver` via the context's `resolver` field to test `{ path }` handling without touching the filesystem (leave it absent to test the hosted rejection); the real `localFileResolver` is tested against actual temp directories in `local/files.test.ts`. The attachment capability adds a third seam of the same shape: inject a fake `AttachmentFetcher` via `AttachmentsContext.fetcher` to exercise ingest without network, while the real boundary is tested directly in `attachment-fetch.test.ts` (allowlist incl. the suffix-only attack, oversize refused before the body is read, a lying `content-length`, refused redirects, timeout, expired-URL `403`). `local/server.test.ts` pins the shell-level properties that are un-hotfixable once users add a connector: the **emitted four-field JSON Schema**, the `openai/fileParams` key that *is* the substitution mechanism, and the workshop's **absence** of the console-only tool. Pure projection/classification functions (`validationResult`, `inputsResult`, `classifyError`, `validateFilesOrMethodIdRequest`, `validateInputsRequest`, `resolveSubmittedFiles`, `fetchMethodFiles`) are exported specifically so they can be tested in isolation; the shared ones are covered in `shared.test.ts`.

## Conventions & gotchas

- **No backward-compatibility burden** (workspace rule) — change shapes directly; record breaking changes in `CHANGELOG.md` (and reflect the new shape in `SPEC.md`).
- **The attachment fetch boundary is a security boundary — treat it like `local/files.ts`, not like plumbing.** It is the one place this server fetches a URL it did not configure, which makes a public endpoint an SSRF surface. It denies by default: `https:` only; the hostname must match `oaisdmntpr<azure-region>.blob.core.windows.net` or `files.oaiusercontent.com`, with the **`oaisdmntpr` prefix required, never optional** (a literal host list is dead — one user produced three different Azure regions in one afternoon — and a suffix-only rule would admit any Azure customer's storage account); no credentials in the URL; no non-default port; redirects refused outright; the 7 MiB cap enforced from `content-length` **before the body is read** *and* again mid-stream; a bounded total budget; no headers sent; non-2xx refused. Two rules to keep when editing: **fetch the already-parsed `URL` object, never re-parse the raw string** (re-parsing at the fetch is how an allowlist gets walked past), and remember that the OpenAI host prefix is undocumented vendor infrastructure that can change without notice — **the host check is a filter, not the defence**, so the cap, the timeout, and the no-redirect rule must each hold on their own.
- **The `mthds_upload_attachments` description is mechanism, not documentation, and cannot be hot-fixed.** ChatGPT gates the attachment substitution on the description as well as the schema (a defensive wording measurably yields empty calls that look like a host failure), *and* it caches a connector's tool list at add-time and never refreshes it — so a description defect leaves every existing installation broken until each user re-adds the connector. Review changes to that text with the same rigour as a schema change, and say "re-add the connector" in the release notes.
- **Never log request `_meta`.** ChatGPT attaches `openai/userLocation` (city, region, country, timezone, latitude/longitude) plus stable `openai/subject` / `openai/session` / `openai/organization` identifiers to **every** `tools/call`. That is PII arriving on a surface we did not ask for, on every route.
- **Branding:** keep MTHDS-standard concepts neutrally named inside the Pipelex-branded envelope (`bundle_blueprint`, `graph_spec`, `pipe_io_contracts`) — see `../CLAUDE.md` "Brand boundaries".
- `no-console` is an **error** in ESLint — don't leave `console.*` calls.
- The SDK dependency is the **published `@pipelex/sdk` npm package** (public on npm), not a `file:../pipelex-sdk-js` link. CI just runs `npm ci` — there is no sibling repo to check out. To develop against local `../pipelex-sdk-js` (or `../mthds-ui`) changes, use the Makefile switches — `make use-local-sdk` / `make use-local-ui` (or `make use-local` for both) point the dep at the sibling repo via a `file:` link, and `make use-npm-sdk` / `make use-npm-ui` (or `make use-npm`) switch back to npm; `make check` refuses to run while a `@pipelex` dep is a local link (the `check-no-local-deps` guard), so don't commit the link. Bump the `^x.y.z` range once the change is published. `mthds` is no longer a direct dependency — it rides along transitively through `@pipelex/sdk`.
- Keep `SPEC.md`'s declared input/output shapes, the Zod schemas in `capabilities/`, and `README.md` in sync when a tool contract changes.

## Versioning & changelog

`pipelex-mcp` follows [Semantic Versioning](https://semver.org). `version` in `package.json` is the source of truth and is git-tagged (`vX.Y.Z`) on release. All notable changes are recorded in [`CHANGELOG.md`](CHANGELOG.md) using the [Keep a Changelog](https://keepachangelog.com) format.

- Work in progress accumulates under `## [Unreleased]` — don't mint a new `## [x.y.z]` heading per commit. Mint it (and the `vX.Y.Z` tag) only when you actually release that version; the newest versioned heading must then match `package.json`'s `version`. To cut a release, use the **`/release` skill** (`.claude/skills/release/`): it promotes `## [Unreleased]` to `## [x.y.z]`, bumps `package.json`, regenerates `package-lock.json`, and opens the `release/vX.Y.Z → main` PR that the CI gates expect. Note the version-string split: the `v` prefix is on the branch name, git tag, and PR title only — never in `package.json` or the `## [x.y.z]` changelog heading.
- `0.1.0` is the first tagged release. It **retires the `v0.x` prototype-increment track** (`../docs/mcp/02-delivery/v0.x-prototype-plan.md`): the milestones once called v0.1 / v0.2 / v0.3 were build increments, not package versions, and all shipped together as `0.1.0`. Use the changelog + semver from here on, not the v0.x numbering. `../docs/mcp/cold-start.md` remains the cold-start brief for resuming work; `CHANGELOG.md` is the source of truth for what has shipped.
