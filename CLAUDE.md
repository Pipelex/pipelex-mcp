# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Workspace-level guidance lives in `../CLAUDE.md` (Pipelex multi-repo workspace). This file covers only what is specific to `pipelex-mcp`.

## What this repo is

`pipelex-mcp` connects MCP hosts to Pipelex methods. It ships as **two servers with two tool sets over one capability core** (see the Architecture section), and no tool name is registered by both. The hosted **Skybridge console** is the Pipelex connector (server name `pipelex`) for chat hosts (ChatGPT, claude.ai, Cowork): it names a method by reference only, a catalog id or a published address, takes no `files` anywhere, and registers, in this order, `pipelex_list_methods`, `pipelex_show_method` (the method's signature and a fill-in inputs template for the model, and the `run-graph` view's graph and input form for the user), `pipelex_upload_attachments` (a ChatGPT chat attachment → a run-ready `pipelex-storage://` reference; ChatGPT's Apps runtime is the only host that substitutes one), `pipelex_run` (by reference, preparing its own inputs pass-through only), `pipelex_run_status`, `pipelex_run_results`, `pipelex_show_images` and the app-only `pipelex_request_upload` the run form calls. The local **workshop** stdio server, distributed on npm as `@pipelex/mcp`, is the Pipelex plugin's server (server name `pipelex-plugin`) for coding-agent hosts (Claude Code, Codex, Cursor); its method-taking tools take files, an address or an id: `mthds_list_methods`, `mthds_validate` (a stable verdict plus the main pipe's typed signature, and the method's flowchart written beside `{ path }` files as `method-graph.html`, a standalone page a browser draws), `mthds_inputs_template`, `mthds_codegen` (typed code for `ts-zod`, `python-pydantic` or `python-structures`, handed back verbatim with its `codegen.lock` or written under `output_dir`), `mthds_prepare_inputs` (uploading local assets), the `mthds_run` / `mthds_run_status` / `mthds_run_results` family, `mthds_show_images`, `mthds_download_artifacts` (a run saved under the working directory, its output as `main_stuff.json`) and the catalog pair `mthds_save_method` / `mthds_get_method`. Each server's `list_methods` is the source-free name/intent → canonical-id bridge into its run flow. The image tools are tools of their own precisely because an image in a model's context is permanent, so the results tools list the candidates for free and never inline one. The workshop is tools-first and registers no views; the console's are `run-graph` (on `pipelex_show_method`) and `run-follow` (on `pipelex_run`).

**The repository is an npm workspace of three packages, and the two servers ship separately.** `packages/core` (`@pipelex/mcp-core`, private and never published) holds the capability core, the shape both tool tables are written in and the shell-test helpers; `packages/workshop` is `@pipelex/mcp`, published to npm; `packages/console` (`@pipelex/mcp-console`, private) is the hosted console, deployed to Alpic. Each server has its own version, its own `CHANGELOG.md` and its own tag prefix, `vX.Y.Z` for the workshop and `console-vX.Y.Z` for the console, so a release of one never publishes or deploys the other (see CI and "Versioning & changelog"). The core exports its TypeScript source rather than a build, and each server's build inlines it: tsup into the workshop's `dist/main.js`, Skybridge's esbuild bundle into the console's `dist/server.bundle.js`. Neither server imports a workspace package at runtime, which is why each declares the core as a devDependency. The root holds what spans the three: the Makefile, the lint, format and test configuration, `scripts/` (the smoke test, the fixture seeder, the tool-text gate) and `tests/` (the tests that belong to no single package).

It is a thin MCP front-end over the existing Pipelex validation stack — it does no validation itself. It forwards file contents to a **Pipelex API** (`POST /v1/validate`, `POST /v1/build/inputs`, `POST /v1/codegen`) through the `PipelexApiClient` from the `@pipelex/sdk` npm package (published from `../pipelex-sdk-js`), then projects the API's reports into MCP output. `@pipelex/sdk` is the Pipelex hosted-platform SDK — the same one `pipelex-app` uses, and the only one carrying the durable run lifecycle the later run-backed tools need; it re-exports the open `mthds/protocol` surface, so the MCP imports one SDK.

`SPEC.md` is the source of truth for product requirements and design decisions — read and update it when changing behavior. `AGENTS.md` mandates using the **`skybridge` skill** when planning or updating this codebase; do so.

## Commands

Use the `Makefile` (wraps the npm scripts):

- `make check` (= `npm run check`) — lint + format:check + **check:tool-texts** + build (the console: Skybridge, then the server bundle) + **check:bundle** + **check:cascade** + build:local (the workshop: tsup) + typecheck (`tsc` over each package, then the root project). The pre-flight gate; run before declaring work done. **`check:tool-texts` is the length gate on what a host shows the model**: it builds both shells in process, reads the `instructions` from `initialize` and every tool `description` from `tools/list` — the emitted strings, not the source constants, since some descriptions are assembled from parts — and fails when any is over 1,800 Unicode code points. Claude Code cuts each of those texts at 2,048, and the workshop's instructions once reached the model cut mid-word because nothing measured them; the ceiling leaves headroom for one more sentence and for hosts whose cap nobody has measured. Its report also lists schema sizes and the `tools/list` payload, for information only. When it fails, move the detail to the layer that owns it (see the budget entry under Conventions) rather than raising the ceiling. It needs no build, so it runs before `build`. **`build` runs before the standalone `typecheck`** on purpose: Skybridge regenerates the view-name registry (`packages/console/.skybridge/views.d.ts`, gitignored) as `build`'s first step, and `tsc` needs it to resolve `pipelex_show_method`'s `view.component`. A cold `typecheck` with no prior `build`/`dev` won't know the view name. `build:local` bundles the workshop bin and sits between the two. **`check:cascade` sits right after `build` for the same reason inverted**: it reads the emitted stylesheet, so it is meaningless before one exists — see the cascade entry under Conventions for what it protects and why nothing else can. **`check:bundle` sits after `build` for the same reason**: it copies `packages/console/dist/server.bundle.js` alone into an empty temporary directory, boots it there with `NODE_ENV=production` against a local stand-in for the AuthKit discovery document and its JWKS (so it signs its own access token and never touches the network), and asserts that the console answers its protected-resource metadata, refuses an anonymous `POST /mcp` with 401, and serves the `tools/list` and view resources `packages/console/src/hosted/console.contract.json` pins, the production build's `?v=<hash>` on each view URI aside. It is the only gate that would notice the bundle failing to inline a package, or moving: the console starts from that bundle, and on Alpic the core's workspace link does not resolve (see the `dependencies` entry under Conventions).
- `make test` / `make t` — Vitest run.
- **`make agent-test` — the target an agent runs after touching code.** Same hermetic suite as `make test`, but it captures stdout and replays it **only on failure**, printing a heartbeat line every `HEARTBEAT_INTERVAL` seconds (default 15) so a slow run is distinguishable from a hung one. A green vitest run is a few hundred lines of context spent to learn one bit; this reduces it to two. Use it in place of `make test` whenever you are an agent — the failure output is not abridged, so nothing is lost.
- `make all` — clean + check + test.
- `make dev` — Skybridge dev server on a **pinned port, `6843`** (`CONSOLE_PORT` in the Makefile): MCP endpoint at `http://localhost:6843/mcp`, DevTools UI at `http://localhost:6843`. It sources `.env` ahead of the shell, prints the API target it resolved, and refuses to start when the port is held, when a localhost Resource Indicator names another port, or when it has the right port but is not the bare origin with a trailing slash — see "Running against the validation API" below for the precedence and the port rule.
- `make dev-local` — local workshop stdio server from TypeScript. `make inspect-local` opens MCP Inspector against that entrypoint.
- `make build-local` — bundle the npm-distributed `pipelex-mcp` executable to `packages/workshop/dist/main.js` with tsup. `npm pack --workspace @pipelex/mcp` runs this automatically through the member's `prepack`, which also copies the root `README.md` and `LICENSE` into the package for the tarball and removes the copies afterwards.
- `make deploy` — deploy the hosted console to Alpic **Production** (`alpic deploy`, release-guarded: a clean `main` at `origin/main`'s tip, whose HEAD is the commit that raised the console's version, and `make publish` the same for the workshop). `make deploy-dev` and `make deploy-staging` ship the **working tree** — not the branch the environment is named after, since this project has no Alpic git integration — to the other two consoles, without the release guards. They name their environment id explicitly because the tracked `.alpic/project.json` pins Production and is the only thing telling `release.yml` where a release goes; the CLI relinks that file to whatever it deployed, so the recipe restores it from a `trap` (an interrupt during the multi-minute build is the likely ending, and a restore that runs only on a clean exit is the one that misses). `make deploy-envs` lists the environments and their URLs.

The live targets — `smoke`, `test-e2e`, `test-e2e-run`, `seed-e2e-fixture`, `test-all` — are **the only ones that touch the network**, and all of them are deliberately outside `make all` / `make check` so the local gate and CI stay hermetic. They share one gate (`live-preflight`): it resolves the live targets' own pair, `PIPELEX_E2E_BASE_URL` / `PIPELEX_E2E_API_KEY`, once (make command line, then `.env`, then the shell, then the default — `make dev`'s order), prints where each value came from, probes `/v1/version`, and refuses to start without a key. **They never read `PIPELEX_BASE_URL` / `PIPELEX_API_KEY`**, and refuse either name on the make command line: those belong to every other tool and to the console's dev loop, and sharing them is how a shell profile exporting the production pair for other tools sent `make test-e2e` to production, where no fixture is seeded, and failed every by-id leg with a miss that read like drift. With the shell clear, the old resolution followed `.env` instead, which names whatever `make dev` points at. So `.env` carries the dev key twice on purpose, once for the console as `PIPELEX_API_KEY` and once for the live targets as `PIPELEX_E2E_API_KEY`; `PIPELEX_E2E_BASE_URL` is also the name `pipelex-sdk-js`'s live suite uses. **Their default is `https://api-dev.pipelex.com`, not production** — dev is the hosted plane the addressing campaign ships to, and it is the deployment that advertises the selectors, so defaulting to production meant the suite's by-selector coverage skipped on every default invocation. This is the live targets' default only; the server's own `PIPELEX_BASE_URL` default in `buildApiConfig` is still the production API. Calling the underlying npm script directly skips those guards, which is what a keyless local OSS runner needs. See "Detecting API drift" below for why they exist.

- `make smoke` (= `npm run smoke`) — spawns the workshop stdio server the way a host does, completes the MCP handshake, and calls the read-only tools against a live Pipelex API, asserting on their `structuredContent`. Read-only; spends no inference credit.
- `make test-e2e` / `make te` (= `npm run test:e2e`) — the live capability suite (`packages/*/src/**/*.e2e.ts` under `vitest.e2e.config.ts`). Free of inference credit: the run family skips itself unless `PIPELEX_E2E_RUN=1`. **Not free of side effects**, and the writes are of two kinds. Storage: `prepare.e2e.ts` uploads a 1x1 PNG on every run, ungated and unremovable (the SDK exposes no delete), because it is the only live proof the upload path still rewrites a local path to a `pipelex-storage://` reference, and `prepare-by-address.e2e.ts` uploads another for the by-address leg — gated only on the deployment advertising the selectors, which the live targets' default `api-dev` target does, so in practice it is not skipped either. Catalog: `catalog-write.e2e.ts` performs real **updates** against the seeded write fixture, in its setup and again in the tests that save, ungated because its whole subject is a write. What no `make test-e2e` run does is CREATE a catalog row — that stays behind `make seed-e2e-fixture`, for the reason recorded under "Detecting API drift".
- `make test-e2e-run` — the same suite **including** the run family, which executes the fixture method for real and therefore **spends inference credit**. Its own target so nothing reaches it by accident.
- `make seed-e2e-fixture` (= `npm run seed:e2e-fixture`) — **writes**: creates or refreshes the durable fixture methods the by-id legs and the catalog-write suite need, in whichever organization the API key selects. Idempotent; run it once per organization.
- `make test-all` — **every test in the repo**, in cost order: the hermetic suite, then `smoke`, then the live suite *including* the run family, so it **spends inference credit**. That is why it is `test-all` and not folded into `make all`, which stays the hermetic gate. It runs `live-preflight` first, so a missing key fails in a second rather than after the unit suite, and it deliberately does **not** seed — a catalog write stays hand-invoked, and an unseeded organization already fails the by-id legs with the seed command in the message.

Run a single test with Vitest directly: `npx vitest run packages/core/src/capabilities/validate.test.ts` or filter by name with `npx vitest run -t "projects pending signatures"`. The same works for the live suite with `--config vitest.e2e.config.ts`, as long as the environment already carries the `PIPELEX_E2E_BASE_URL` / `PIPELEX_E2E_API_KEY` pair that `make test-e2e` would have resolved (`vitest.e2e.config.ts` loads `.env` for it, without overriding the shell).

### Running against the validation API

The tool needs a reachable Pipelex API serving `POST /v1/validate`. During early development this is the **local OSS `pipelex-api`** runner (temporary — production target is the hosted Pipelex API only):

```bash
cd ../pipelex-api && make run      # serves http://localhost:8081
make dev PIPELEX_BASE_URL=http://localhost:8081   # or put it in .env and run `make dev`
```

- `PIPELEX_BASE_URL` defaults to the hosted Pipelex API (`https://api.pipelex.com`) when unset; set it to `http://localhost:8081` to develop against the local OSS runner.
- `PIPELEX_API_KEY` is optional — set it only when the configured API requires auth. Workshop dev (`make dev-local`) normally runs without it. Note it has **no effect on the console**: `contextsForRequest` always overrides `apiKey` with the caller's verified OAuth token.
- **`make dev` (the console) now requires `WORKOS_AUTHKIT_DOMAIN` and `PIPELEX_MCP_RESOURCE_INDICATOR`** and throws at startup without them — per-user OAuth is its only auth posture, so there is no keyless dev mode. Put both in `.env` (the dev tunnel URL is what must be registered as that env's Resource Indicator — origin with a trailing slash, not `/mcp`). To iterate on capability code without a WorkOS setup, use `make dev-local` / `make inspect-local`: the workshop shell shares the same capability core and authenticates with a plain `PIPELEX_API_KEY`.
- Both variables can live in a gitignored `.env` at the repo root instead of prefixing the command: `packages/console/nodemon.json` overrides Skybridge's default dev exec with `tsx --env-file-if-exists=../../.env src/server.ts`, run from the console's directory, and watches the core's source beside the console's (keep its `watch`/`ext` in sync with Skybridge's defaults — a `nodemon.json` replaces them entirely, not additively). `.env` is dev-only and not watched — restart the dev server after editing it.
- **`make dev` / `make dev-tunnel` source `.env` ahead of `npm run dev`, so `.env` wins over the shell.** Node's `--env-file` never overrides an inherited variable, so a `PIPELEX_BASE_URL` exported in a shell profile for other tools was silently sending the console to a different deployment than the one `.env` named. A variable on the make command line (`make dev PIPELEX_BASE_URL=http://localhost:8080`) still wins over both; the env-prefix form (`PIPELEX_BASE_URL=… make dev`) is just the shell and loses to `.env`. Precedence is therefore make command line > `.env` > shell > the server's default, the same order the live targets use for their own `PIPELEX_E2E_*` pair. The recipe prints `-> console API target: …` at startup so a wrong one is visible before the first tool call. `npm run dev` on its own keeps the plain `--env-file` behavior, and `make dev-local` / `make inspect-local` are unchanged (their scripts never read `.env`). `.env` is read by `sh` there, before Node's `--env-file` sees it, so keep it to plain `KEY=value` lines (no `$`, `#`, spaces or backticks inside a value; none of the console's keys carry any), and `set -a` exports the whole file to every process under `npm run dev`, the `alpic tunnel` CLI included — accepted, for a dev-only gitignored file. Command-line overrides are put back by name after `.env`, so any value survives, spaces and quotes included.
- **The console runs on a pinned port, `6843`, never on Skybridge's default 3000.** Skybridge's dev command walks up from 3000 to the next free port when it is busy — and it is busy whenever a Next.js app in the workspace is running — but the WorkOS Resource Indicator names the port (`http://localhost:<port>/` is the token's `aud`), so a console that drifted to 3001 booted cleanly and failed every tool call at audience verification. `make dev` / `make dev-tunnel` pass `--port`, read from the shell as `$CONSOLE_PORT` so the port follows the same precedence as every other console variable (command line, then `.env`, then the shell, then the Makefile default), which turns the fallback off, and the `CONSOLE_PORT_GUARD` refuses to start — naming the fix — when the port is not a number, when it is held by another process (`lsof` first, so a listener bound to loopback only is seen, with a wildcard-bind node probe behind it for a machine without `lsof`; a pinned port would otherwise die on `EADDRINUSE` under Skybridge's UI), when a localhost `PIPELEX_MCP_RESOURCE_INDICATOR` names a different port (no port means 80; `[::1]` counts as localhost), or when the port is right but the indicator is not the bare origin with a trailing slash, which gets its own message because the server's more exact refusal would be buried under Skybridge's UI; a non-localhost indicator (a tunnel URL) is left alone. The same port is what the WorkOS dashboard must know: the Resource Indicator and the DevTools origin on the CORS list. `make dev CONSOLE_PORT=<n>` overrides it for one run and a `CONSOLE_PORT=<n>` line in `.env` sets it for the checkout, for a port registered elsewhere; a bare `npm run dev` still gets Skybridge's default and its fallback. The vendored `skybridge` skill (hash-locked in `skills-lock.json`, so not editable here) still quotes Skybridge's default in its references — `alpic tunnel --port 3000` and the like; in this repo the port is `CONSOLE_PORT` and `make dev-tunnel` already passes it, so ignore the skill's port numbers.
- **A DevTools session lives as long as its WorkOS access token, and only a page reload renews it.** DevTools refreshes the token on connect only; after it expires a tool call gets the console's 401 (`"exp" claim timestamp check failed`), the MCP client throws rather than refresh, and DevTools shows nothing — which reads as "the tool ran and delivered nothing". Reload the tab (F5); never restart `make dev` for this, which fixes nothing and strands the connected tab on "Connecting to server…". The lifetime is the WorkOS application's "Access token duration" (Sessions tab): the default is five minutes, the dev tenant is set to one hour. Skybridge logs nothing for a tool call in dev, so an empty Logs pane proves nothing. When a call has to be traced, the running console can be instrumented without a restart: `kill -USR1 <pid>` opens the Node inspector, and a `diagnostics_channel` subscriber on `http.server.request.start` and `undici:request:*` evaluated through it shows every request in and every upstream call out.

### Detecting API drift

The unit suite cannot see the failure mode that actually breaks this server. Every capability reaches `@pipelex/sdk` through a hand-written narrow interface (`CatalogClient`, `MethodFetchClient`, `RunClient`, …) and every test injects a fake satisfying that interface, so `tsc` catches a **type** change on the SDK side and nothing at all catches a **wire-shape** change. That is not hypothetical: `mthds_list_methods` failed every real call with `wire.map is not a function` — the platform had reshaped `GET /v1/methods` into a page object while the pinned SDK still called `.map()` on it — and the whole suite stayed green. There is no OpenAPI schema to diff against (`/v1/openapi.json` is 403), so a live call is the only available detector.

There are two live detectors, at two different altitudes, and they are complementary rather than redundant.

**`make smoke`** drives the real shell over stdio, so it covers the whole path a host exercises: handshake, `tools/list`, then `mthds_list_methods` (row shape plus the projection invariant — method source, stored inputs/outputs and org fields must appear nowhere in the result), `mthds_validate`, `mthds_inputs_template`, and `mthds_codegen` (the canonical bundle as `ts-zod`: both artifact paths, the lock filename, every artifact carrying its content, nothing on `_meta`). Its assertions live in `scripts/smoke.ts`. It carries two inline fixtures because one is not enough: the canonical `quick_start` bundle validates, but declares no inputs, so its template is `{}` and would pass just as happily if the projection dropped every field — the second fixture declares one input so the template check proves something.

**`make test-e2e`** goes wider and one layer down: one `*.e2e.ts` per capability, calling the capability functions with a context that has **no `client` seam**, so the real `PipelexApiClient` runs against the real API. That is the layer the drift lives at. It covers the catalog (`catalog.e2e.ts` — paging, server-side search, the projection invariant, and the fixture row's server-derived `description`), validation (`validate.e2e.ts` — including that an invalid bundle is a *produced* verdict, never an error), the inputs template (`inputs.e2e.ts` — both formats, the `explicit` shape switch, an unknown `pipe_ref`), code generation (`codegen.e2e.ts` — the target loop over every SDK target, each artifact set fed to the SDK's offline `runCodegenCheck` to prove the trust chain survived the wire, an invalid bundle as a produced verdict, the **write arm** against a real temp working directory (write, regenerate over it, then a second target into the same directory to produce the orphan case D7 describes — the hermetic writer suite runs on a recorded response, so this is what proves a CURRENT engine still writes a checkable tree), and the two selector legs, which run wherever the API advertises them), the by-id fetch-and-forward leg (`shared.e2e.ts` — `getMethodClosure`, which had the same blind spot `listMethods` had and no live coverage at all), input preparation (`prepare.e2e.ts` — the workshop really uploads a 1x1 PNG), the console's show and run walk (`show.e2e.ts`, `console-inputs.e2e.ts` — free: a real report carries every artifact the view and template need, and the walk refuses a local path before any read), the run form's upload grant (`upload-grant.e2e.ts` — write-free: it mints grants and never sends a file, proving the route's projection, the `413` on an oversized declaration, and that the grant's host is one the `run-graph` view's CSP allows), the run lifecycle (`run.e2e.ts`), the run-saving tool (`artifacts.e2e.ts` — an unknown run id refused before anything is written, free; in the paid tier, a completed by-address run saved into a temp working directory, its `main_stuff.json` compared with the unbounded output the platform holds, and no stored file in it, so the bulk resolve route stays unexercised live), and the method graph page's CDN files (`graph-page.e2e.ts` — each pinned file fetched from jsDelivr and its SRI hash recomputed, since a wrong hash leaves every page blank while the hermetic suite, which cannot fetch, stays green; it calls no Pipelex API).

**The by-selector legs are gated on the live API, not on a date.** Every leg that needs the platform to resolve a `method_id` or a `method_ref` server-side asks `/v1/version` first — `apiAdvertisesExtension` in `e2e-support.ts` — and skips itself where the deployment does not advertise `method_ref`, the marker for the platform build that brought the whole three-selector surface (an API on the previous build advertises `[runs, method_id]`). That replaced a row of hardcoded `it.skip("… (gated)")` calls naming a checkpoint in a plan document, which is a gate nobody re-reads: the dev API served the surface while the tests stayed dark and said nothing.

**A skip is only allowed to mean one thing, so the probe asserts its own inputs.** `extensions` is an untyped extension field riding `VersionInfo`'s index signature — nothing types it in any repo, so a rename breaks no build — and every unexpected shape collapses to "advertises nothing", which is exactly what a deployment that legitimately serves no selectors looks like. Left alone that makes the suite skip its way to green through the wire drift it exists to catch. So the deployment decides which rules apply: on a hosted `implementation` (`pipelex-hosted`, which always declares `extensions` and always carries `runs`) an absent, non-array or `runs`-less value **throws**; on a bare runner, which declares no `extensions` at all, absence is the protocol's documented "protocol only" answer and yields an empty set, while a malformed value still throws. What survives that is a skip that really is a statement about the deployment. Note it is a statement you have to go looking for: vitest's default reporter prints per-file counts, not a line per skipped test.

One leg had no extension to probe and so stayed a hardcoded skip: `validate.e2e.ts`'s `default_pipe_ref` assertion, where the assertion IS the probe. It is live as of the `@pipelex/sdk` 0.19.0 bump — measured against the live suite's default target, which serves the field carrying the fixture's own ref — so the gate is now the assertion itself, and a deployment that stops serving the field fails the suite rather than skipping past it. Production could not be measured in the same pass: it answers this key with a 403. And `validate.e2e.ts`'s by-address leg keeps its own Python-free address instead of the shared `PUBLISHED_METHOD_REF`: `/v1/validate` resolves an address through the execution-locus gate, so a fetched package shipping any `.py` is a 403 there off a deployment that is **not** sandbox-hosted.

**`run.e2e.ts` is split on cost, and the split is what keeps the suite schedulable.** Its free half always runs and spends nothing: reading the status and results of a run id that does not exist proves the two lifecycle routes are reachable and still classify as `input_domain`@`run_id`, and one start on an unknown `method_id` — refused before anything executes — proves `/v1/start` still accepts the run source the way this client sends it. That last check exists because `method_id` is a named SDK option the client reserves on `extra` with a **runtime** throw, so sending it the wrong way compiles and passes the mocked suite; the free tier could not reach the start path at all until it was added, which is how the 0.14.0 bump's break stayed invisible. Its paid half executes the fixture for real and runs only under `PIPELEX_E2E_RUN=1` (`make test-e2e-run`), so `make test-e2e` and any future scheduled canary cannot reach it by accident. That half also runs a published package **by address** — `github.com/Pipelex/methods/text_stats` pinned at a tag, a PipeFunc method that buys no model call — and asserts the reported provenance down to the commit the tag resolved to. It sits in the paid tier despite spending no inference credit because the tier is about executing, not about the bill: `make test-e2e` must remain a suite that starts nothing.

**The by-id legs need a durable fixture method, seeded once per organization.** The SDK had no method delete when this was designed; since 0.14.0 `deleteMethod` exists but is an **asynchronous acceptance** (a resolved promise means "deletion accepted", never "gone"), so a create-per-run suite would still be racing its own cleanup. Instead `make seed-e2e-fixture` stores one method named `pipelex_mcp_e2e_fixture` (its bundle and every other fixture live in `packages/core/src/capabilities/e2e-support.ts`), and the suites resolve its catalog id **by name at run time** rather than hardcoding a `mt_…` — an id belongs to one organization, this repo is public, and a scheduled canary would run under a different key from a developer's. A missing fixture fails loudly with the seed command in the message, so "not seeded" and "wrong organization" read the same and both point at the fix. **That lookup follows the cursor, and a one-page read is a bug rather than a shortcut.** The platform applies `q` as a post-read filter over a bounded slice of the index per request, so a sparse match legitimately answers `{items: [], nextCursor: "…"}`; the index is keyed on the immutable `created_at`, so a fixture sinks monotonically as its organization accumulates methods and no update lifts it back. A lookup that stopped at the first page would therefore start reporting a seeded fixture as missing, permanently — and because that message sends the operator to `make seed-e2e-fixture`, whose own lookup is the same helper, the miss would route them into creating a second row the platform makes admin-only to delete. `catalogRowNamed` in `e2e-support.ts` is the one helper all three sites use, over the SDK's `iterateMethods`.

**The catalog-write suite takes a second seeded row, and never creates it.** `catalog-write.e2e.ts` exercises `mthds_save_method` against the real catalog, so it is the one suite whose subject is a write. It only ever **updates** `pipelex_mcp_e2e_catalog_write`, because a create is check-then-act across two round trips with no compare-and-swap: two concurrent first runs in one organization would each read no row and each create one, and the duplicate is permanent — the platform makes delete admin-only — after which every later run updates whichever row the server lists first. Seeding it by hand, once, is what takes that race out of the suite, and it keeps `make test-e2e` free of catalog *creates*, which is the reason the seed target exists as a separate gesture at all. The consequence to know is that `POST /v1/methods` — the tool's create arm — has no live coverage from the suite; what exercises it live is the seed script, through the SDK rather than through the tool.

**`make test-e2e` cannot pass vacuously**, and that guarantee is the fixture's: it keeps the catalog non-empty, so `catalog.e2e.ts`'s row assertions always execute rather than looping zero times, and a missing key **fails** the suite instead of skipping it. `make smoke` deliberately does not share it — being fixture-free and seed-free is what keeps it read-only and runnable in an organization nobody has seeded. On an empty catalog it still proves the page envelope survived the wire, which is the reshape that motivated it; it withholds its row-shape PASS and says out loud that row projection was not exercised. Non-vacuous row coverage is `make test-e2e`'s job, not smoke's.

A failure in either detector means the *shipped* client disagrees with the *live* API; the fix belongs in `../pipelex-sdk-js`, then a bump here through the `bump-sdks` skill — never a patch that papers over it in this repo. Anything a live run reveals that contradicts a unit-test fake gets folded back into the fake in the same change, so the two layers cannot disagree silently.

`scripts/` and `tests/` are dev tooling, not shipped code: they are linted and Prettier-checked with the packages, and they typecheck under the root `tsconfig.json`, which extends the shared `tsconfig.base.json` as the core's and the workshop's do (the console's extends Skybridge's own). `npm run typecheck` runs `tsc` over each package and then the root project, so `make check` covers them all. `tests/` holds what belongs to no single package: the tool-name rule across both shells, the Makefile recipe tests, the API-boundary lint test and the workspace manifest test. The `*.e2e.ts` files and `e2e-support.ts` sit under the packages' `src/`, so they are linted, formatted and typechecked with everything else — they are excluded from the *default* suite by suffix and from the bundles by reachability (nothing the two entrypoints import reaches them).

### CI

GitHub Actions under `.github/workflows/` (ported from the sibling TS repos, minus the CLA piece that doesn't apply here):

- `quality-checks.yml` — on every PR, runs `npm ci` then `make all` (the same gate as local). Meant to be a required status check on `main`.
- `guard-branches.yml` — enforces the `work-branch → dev → release branch → main` flow: **only a release branch may target `main`**, `release/vX.Y.Z` for the workshop or `release/console-vX.Y.Z` for the console (`dev` no longer can — it's promoted *into* the release branch instead), and work branches must be prefixed (`fix/`, `feature/`, `refactor/`, `chore/`, `docs/`, `ci-cd/`, `changelog/`, `codex/`).
- `version-check.yml` — on PRs into `main` or a release branch: asserts the released server's version (its member's `package.json`, read through `.github/scripts/track-version.sh`) equals the `X.Y.Z` in the release branch name and, for `main`, is strictly greater than `main`'s version of that server, while the other server's version is unchanged: a release carries one server.
- `changelog-check.yml` — on a release PR into `main`: asserts the released server's changelog (`packages/workshop/CHANGELOG.md` or `packages/console/CHANGELOG.md`) has a `## [X.Y.Z]` entry (no prefix in the heading — `v` and `console-v` live on the branch name and the git tag only).
- `release.yml` — **on the push to `main`**, which in this repo means the merge of a release PR, it ships each server whose version the pushed commit raised: the workshop is published to npm as `@pipelex/mcp` and tagged `vX.Y.Z`, the console is deployed to Alpic and tagged `console-vX.Y.Z`, all from the merge commit itself, so the run to verify is the one keyed to the merge SHA. A release of one server never publishes or deploys the other. What makes an unconditional trigger safe is that whether a push is a release is read from the pushed commit and from nothing else: the `detect` job compares each server's version at the commit with its version at the first parent, through `.github/scripts/track-version.sh` (which reads the root `package.json` at a commit from before the workspace split, when one version covered both servers), and a server ships exactly when the push *raises* its version — a strict increase, so a revert that lowers it cannot read as a release. A commit carrying a version `main` has already moved past, for the server being shipped, is refused outright, which is what stops a re-run of an older release's run from shipping that older tree: the tag legs would leave the existing tag alone, but the console deploy ships whatever tree it is handed and `npm publish` carries no `--tag`, so it would write the `latest` dist-tag back to the older release, and the run would end green having shipped a downgrade. That refusal (`.github/scripts/assert-not-behind-main.sh <track> <version>`) runs inside each shipping leg and not only in `detect`, because GitHub's "Re-run failed jobs" never re-executes a job that succeeded: `detect`'s verdict reaches a partial re-run as an output it wrote before the newer release existed, so each leg asks `main` for itself. A push that raises neither version ends green in seconds with every later job skipped, and the property survives a release run that died before publishing, which a registry-state test does not. `guard` then decides whether the commit is *shippable* — the released server's changelog must carry a `## [X.Y.Z]` heading, `make all` is re-run on the merge commit rather than trusted from the PR, and, for a workshop release, `npm view` is asked whether the version is already there, an answer the registry could not give failing the run instead of reading as unpublished. That lookup is the double-publish guard on the npm leg alone: the workshop's tag does not read it, so a release whose version reached npm by another route still gets tagged instead of ending green having shipped nothing, and a console release never asks the registry at all. The workflow keeps `workflow_dispatch` for one purpose: retrying one server's release after a partial failure, at the same version (`-f track=workshop` or `-f track=console`, with `-f version=X.Y.Z`). A dispatch is held to one check more, that the typed `version` equals what the commit carries for that server; it reads `main` whatever ref it was fired from, so it cannot ship a branch, and it refuses to run once `main`'s tip does not raise that server's version, since that tip is no longer its release commit. Every job checks out one SHA that `detect` resolved once. Needs `ALPIC_API_KEY` as a repo secret; npm auth is OIDC trusted publishing (registered against this repo + the `release.yml` filename), so no npm token exists anywhere — **renaming this workflow breaks publishing** until the trusted publisher is re-registered.

A release branch, its version bump, the changelog finalization, and the PR are produced by the **`/release` skill** (`.claude/skills/release/`), which asks which server ships — run it to cut a release rather than hand-assembling these. Merging that PR is what ships it, through the `release.yml` run above (`make publish` for the workshop and `make deploy` for the console remain as local escape hatches for a CI outage). Retry transient finishing-step failures at the same version; if a permanent defect makes a published workshop unshippable, deprecate that version on npm and fix forward with a new one.

## Architecture

The repo ships two thin shells over one capability core: the Skybridge HTTP console (the Pipelex connector) for chat hosts and the plain MCP-SDK stdio workshop (the Pipelex plugin's server) for coding agents. **Each shell owns its tool table** — `packages/workshop/src/tools.ts` for the workshop, `packages/console/src/hosted/tools.ts` for the console — built from the capability functions in `packages/core/src/capabilities/`, and each shell's emitted contract is pinned byte for byte (see Testing conventions). The console's table also carries each tool's view and host metadata. Each table module builds its own capability contexts too, and states its shell's settings there rather than receiving them as options: the workshop's `buildLocalToolContexts` sets the cwd-bound `{ path }` resolvers, the working directory as every writer's `saveRoot`, `artifactDownloadAvailable: true` and `viewsAvailable: false`; the console's `buildHostedToolContexts` sets views on, no resolver and no write root, and states `CONSOLE_TOOL_NAMES` on every context whose texts name a tool. **Every tool name the core writes into a summary, a hint or a schema description comes from `capabilities/tool-names.ts`**: `WORKSHOP_TOOL_NAMES` and `CONSOLE_TOOL_NAMES` each carry only their shell's tools, discriminated by `shell`, every context defaults to the workshop's, and a text naming a tool only one shell has is written per shell, the compiler saying where. `hosted/server.test.ts` fails on a workshop tool name in any console text or schema.

**The tables share no tool name, and differ by more than the names.** A chatbot runs methods rather than authoring them, so the console has no validate, inputs template, codegen or prepare tool and no `files` argument (`validateMethodReferenceRequest` in `shared.ts` is its selector rule): `pipelex_show_method` and `pipelex_run` cover what a chat user needed from those. Beyond that each shell holds what only it can serve: the console's `pipelex_upload_attachments` takes a host-substituted reference the host gates on the declared JSON Schema, which no stdio host performs, and its `pipelex_request_upload` has a view as its one caller; the workshop's `mthds_download_artifacts`, `mthds_save_method` and `mthds_get_method` turn on a working directory the console does not have. On the wrong shell each would be *structurally unreachable*, and registering it would spend every user's tokens on every `tools/list`. **One tool name means one contract** (`wip/mcp-server-split/design.md` in the workspace, D1): a name both shells registered would have to carry the same input schema, output schema and annotations on both; no name is shared since the console became `pipelex_*`, and `tests/tool-names.test.ts` guards the next one. The description is deliberately outside that test, because it is how each shell tells its own audience when to call the tool. **The workshop's table is registered in a loop; the console's is not.** `workshop/src/server.ts` iterates `localToolDefinitions`, while `hosted/server.ts` chains one `.registerTool` per tool, because the chain is what types `AppType`, which the views' `useToolInfo` / `useCallTool` read. So a tool added to the console is a definition in `hosted/tools.ts` and a link in that chain, and `hosted/server.test.ts` fails when a definition the module exports has no link, since nothing else would notice: the snapshot does not move and no linter flags an unused export.

The code is a handful of small files in three packages, and the list names each by its path inside its package's `src/`: `capabilities/…`, `tool-definition.ts` and `shell-test-support.ts` are the core's, `server.ts`, `helpers.ts`, `hosted/…` and `views/…` are the console's, and the workshop's files, which sat under `src/local/` before the split, sit at the top of its `src/` and are written `workshop/src/…` here, from `packages/`, since their bare names would collide with the console's.

- `server.ts` — thin Skybridge entrypoint; `hosted/server.ts` owns the console shell and registers the console's table through Skybridge's typed chain. It also chains two `.mcpMiddleware` handlers: `initialize` picks the instructions per handshake (`hostRendersViews`: the MCP Apps extension or a ChatGPT `User-Agent` gets the form variant, every other client the no-views one the snapshot pins), and `tools/call` answers the `RETIRED_TOOL_NAMES` — the console's pre-rename `mthds_*` names, which a cached ChatGPT tool list still calls — with an `isError` telling the user to remove the Pipelex connector and add it again. `hosted/tools.ts` is the table: the console's capability contexts (`HostedToolContexts`, `buildHostedToolContexts`) and every console tool's definition with its `view` and `_meta`. `tool-definition.ts` is the shape both tables are written in (`ToolDefinition`, `defineTool`), not a table, and it stays Skybridge-free because the workshop's bundle reaches it.
- `hosted/contexts.ts` — the console's per-request capability contexts, and the whole of its auth posture on this side of Skybridge. **Auth is per-user OAuth and nothing else** (bring-your-own-key has been removed — there is no second posture, no keyless mode, and no shared-key fallback). Skybridge's `workosProvider` verifies the caller's AuthKit token and the MCP SDK transport surfaces it as `extra.authInfo`; `contextsForRequest` lifts that token into `apiKey` on **every** capability context, which `@pipelex/sdk` then sends upstream as `Authorization: Bearer`. The override is unconditional — a server-held `PIPELEX_API_KEY` must never fund a signed-in caller's work, since the credential picks the active org and therefore the whole visible catalog. The tokenless branch is unreachable in production (no console tool allows anonymous, so Skybridge mounts `requireBearerAuth` server-wide) and exists only to **fail closed** — note it sets `apiKey` to the **empty string, not `undefined`**: `PipelexApiClient`'s constructor reads `options.apiKey ?? process.env.PIPELEX_API_KEY`, so an absent key silently borrows the deployment's env key, which is the precise opposite of the intent. `contexts.test.ts` pins this on the wire (no `Authorization` header goes out) rather than by asserting the field, because the field alone does not prove it. The token rides the transport only — never a tool argument, so it never enters the model's context. The workshop doesn't import this: its per-user credential is a `plx_sk_` key in the host-supplied `PIPELEX_API_KEY` env. `../server.ts` refuses to boot unless both `WORKOS_AUTHKIT_DOMAIN` and `PIPELEX_MCP_RESOURCE_INDICATOR` are set, and `createHostedServer` takes the resolved `OAuthConfig` as its **required first argument** — a console that cannot authenticate a caller is unrepresentable.
- `workshop/src/server.ts` — constructs the plain MCP SDK server and registers the workshop's table. `workshop/src/tools.ts` is that table: the workshop's capability contexts (`LocalToolContexts`, `buildLocalToolContexts`, which binds the cwd-bound file resolvers and the working directory) and `localToolDefinitions`, in the order a host lists them. It must import nothing from Skybridge: tsup bundles it into the npm package, and the workshop's `package.json` does not declare Skybridge at all, which `tests/workspace-manifests.test.ts` holds. `workshop/src/main.ts` owns stdio transport and graceful shutdown; `workshop/src/log.ts` keeps diagnostics on stderr so stdout remains protocol-only.
- `capabilities/catalog.ts` — the list capability (`pipelex_list_methods`, `mthds_list_methods`) and its narrow `CatalogClient.listMethods()` test seam. It calls only the SDK's `listMethods`, validates the rows of the one page it gets back, and bounds names/descriptions by Unicode code point. **Search, ordering and paging belong to the server** (`q` / `limit` / `cursor`): filtering a returned page locally would be searching fifty rows of ten thousand and calling it a search, and re-sorting would reorder a page against the cursor that produced it. A blank query omits `q` rather than sending `""`, which the API rejects as bad input. **Non-negotiable projection invariant:** `mthds`, `python`, `input_data`, `pipe_output`, `org_id`, and `created_by_user_id` must never reach `structuredContent`, `content`, `_meta`, or logs — the index projection stopped returning them, but keep validating what *arrives* rather than trusting the declared type, so a looser server cannot leak through. There is deliberately no total count (counting means reading the whole catalog) and no `has_source`: recomputing it would cost a `getMethod` per row, so a source-less method now surfaces at the point of use, as an `input_domain` no-verdict at `method_id`. **The summary carries a render directive on purpose**: a listing is read near-verbatim by the user, so `catalogSummary` tells the model to report each method with name **and** description, and puts the description before the demoted `method_id`. Keep that directive in the summary, not (only) in the tool description — ChatGPT caches a connector's tool list at add-time, so the summary is the sole channel where a presentation fix reaches existing installs. No view, no `_meta`.
- `capabilities/shared.ts` — the plumbing the capabilities share, including **the artifact fetch boundary's shared half**: `ALLOW_HTTP_ENV` / `parseAllowHttpOverride` / `allowsPlainHttp` / `buildArtifactFetchConfig` (the plain-http rule, derived from `PIPELEX_BASE_URL`'s scheme unless overridden), `BULK_RESOLVE_ERROR_OPTIONS` (the resolve route's whole-request refusals), and `ITEM_ERROR_TEXTURES` / `itemToolError`, which map the SDK's closed per-reference `code` vocabulary — shared by the download verdict's `ArtifactItemError.code` and the thrown `ArtifactFetchError.code`. All of it lives here rather than in `artifacts.ts` because the image tools need the same mapping on both shells and must not import the workshop-only download tool to get it; `itemToolError`'s `location` is therefore a parameter (`artifacts[i].uri` there, `images[i].uri` here). The image-inlining constants and the key prefilter (`imageCandidatesOf`, `looksLikeImageKey`, `storageKeyOf`) sit beside them, used by `run.ts` and `images.ts` alike. Also: the submitted-files input schema (a per-item union, `{ content, uri? } | { path }` — see "The files union and the resolution seam" below), the `ToolError` model, file resolution (`resolveSubmittedFiles` + the `FileResolver` seam), request-shape validation (`validateMethodSelectorRequest`, shared by every workshop method-taking tool — it enforces the two selector rules: strict one-of on the tooling tools, files-win-plus-linkage on `mthds_run`; the console's two reference-only tools use `validateMethodReferenceRequest`), the by-id fetch-and-forward leg (`fetchMethodFiles` + `MethodFetchClient`, narrowed to `mthds_inputs_template` alone — every other method-taking tool forwards its selector to the server, `mthds_prepare_inputs` since the SDK's `prepareInputs` grew all three), `blueprintMainPipeRefOf` (the blueprint's declared main pipe, qualified by its domain only when authored bare — shared by `validate.ts`'s `defaultPipeRefOf` and `console-inputs.ts`'s pipe selection), env-derived API config (`buildApiConfig` — `PIPELEX_BASE_URL`/`PIPELEX_API_KEY`), and `classifyError`. `classifyError` takes per-route `ClassifyErrorOptions` (the 400/422 class/locator/hint, the separate `preparation` locator for the SDK's client-side `InputPreparationError` base — which a route with a selector-shaped `badRequest` must set, or a client-side pipe failure reports the selector as the fault — and the route named in the 404 hint) so each capability points the agent at its own knobs; the class override lets catalog listing classify a missing active-org 400 as `config` without changing other routes, and catalog listing picks its 400 arm by request shape so a rejected `cursor` stays `input_domain`@`cursor` instead of telling the caller their key is wrong. It also maps the `@pipelex/sdk` `InputPreparationError` family (the upload/preparation errors `mthds_prepare_inputs` can raise) ahead of the generic `PipelineRequestError` arm.
- `capabilities/validate.ts` — the validation logic. Zod input/output schemas, the API call (`validateFiles`), and projection of the API report into MCP `structuredContent` + the view-only `_meta` graph payload (`toolResult`). Also accepts `method_ref` (a published method address) and `method_id` as **server pass-throughs**: the selector rides the `/v1/validate` body (`ValidateMethodSelector`) and the hosted API resolves it — no fetch-and-forward, no method source in the conversation. The three source forms are mutually exclusive (`validateMethodSelectorRequest`, rule `one_selector`). It also projects the **main pipe's signature** (`mainPipeSignatureOf` → `structuredContent.main_pipe`, plus one rendered line in the summary): the ref, the ordered inputs with their concept refs and multiplicities, and the produced concept — read from `pipe_io_contracts[main_pipe_ref]` (a required field on every valid report, not gated by the `views` token), with the input-form descriptor consulted for input **order** alone. The ref itself is `defaultPipeRefOf`: the report's `default_pipe_ref` — the API's own statement of what a selector-less run would execute, and the only signal that knows a `method_ref` package's manifest — with `mainPipeRefOf(bundle_blueprint)` behind it **only when the field is absent** (an older runner), never behind a stated `null`, which means the server determined no entry pipe at all. It is deliberately **not** on the views branch — the workshop is the shell an integrating agent uses — and every member is narrowed against what arrived, with any malformed one omitting the whole signature rather than emitting a partial one. The signature's `output` also carries **`images`**, the produces-images signal: the capability requests the standard's output-form descriptor beside the input form (`views: ["input_form", "output_form"]`) and `imageFieldPaths` walks the entry pipe's single output node for `kind: "image"`, recursing into an `object`'s `fields` and a `list`'s `item`, yielding paths in `$` notation (`["$"]` for a top-level `Image`, `["$[]"]` for an `Image[]`, `["$.picture"]` for a field of a structure). Three things are load-bearing: **`[]` and an absent member are different answers** (described-and-none versus nobody-said), a `document` node is deliberately not a picture, and `kind: "unknown"` is opaque rather than empty. **The third only holds because the walk reports its own completeness**: `imageFieldPaths` returns `{ paths, complete }`, and `complete` is false for an opaque node, an unknown kind, a non-record, a nameless field and the depth ceiling — all of which used to yield a bare `[]`, i.e. a confident "produces no pictures" off a node nobody had read. The member is published only when the walk was complete **or** it found at least one image; an incomplete walk that found nothing withholds it, and a `document` stays `complete` because "not a picture" is an answer, not a failure to look. The walk is a **total `Record<FieldKind, …>`** over the SDK's re-exported `FIELD_KINDS`, so a kind the standard adds fails the build here instead of reading as "no images"; the kernel `@pipelex/mthds-form` owns the same lookup but is reachable only through `@pipelex/mthds-ui`, which is build-side, and `validate.ts` ships in the workshop bundle, so the ten-line walk lives here rather than pulling a view package into `dependencies` for every `npx @pipelex/mcp` user. `signatureLine` appends ` (produces images)`, the one channel that reaches a ChatGPT install whose cached tool list predates the member.
- `capabilities/inputs.ts` — the inputs-template logic. Zod input/output schemas (`files?` beside `method_id?`, `pipe_ref?`, `explicit?` default true, `format?` default json), the API call (`buildInputs`, adapting the MCP `uri` provenance label to the build envelope's `source`), and projection of the report into `structuredContent` plus a composed Markdown summary that includes the template in a fenced code block (the build routes return a plain `message`, not `rendered_markdown`). The three source forms are mutually exclusive (rule `one_selector`). A `method_ref` request is a **server pass-through** — the address rides the build envelope itself (`BuildInputsRequest.method_ref`) and the runner resolves it. A `method_id` request **fetches-and-forwards** via the shared `fetchMethodFiles` (in `capabilities/shared.ts`): the SDK's `getMethodClosure` → files, each labeled with the method id as provenance, adapted to the build envelope's `source` here — the SDK's own canonical expansion, since the build routes have no server-side `method_id`; a source-less stored method (the SDK's `EmptyMethodSourceError`) is an `input_domain` no-verdict at `method_id` raised without calling the build route, and fetch-leg failures classify against `/v1/methods/{id}`. No view, no `_meta`.
- `capabilities/codegen.ts` — the code-generation logic (`mthds_codegen`). Zod input/output schemas (`files?` / `method_ref?` / `method_id?` under `one_selector`, a required `target` with no default, an optional `output_dir` for the workshop's write arm), the API call (`CodegenClient.codegen()` — always `kind: "types"`, never a `pipe_ref`, which the route rejects on `types`), and the projection of the report into `structuredContent` plus a composed Markdown summary (the route returns a plain `message`). **Every selector is a server pass-through** — no `fetchMethodFiles` leg; the runner resolves `method_ref`, the hosted platform resolves `method_id`. The `target` enum is closed in both directions against the SDK's `CodegenTarget`: `CODEGEN_TARGETS` is `as const satisfies readonly CodegenTarget[]` (a dropped target fails), and `CODEGEN_TARGET_PROFILES` is a `Record<CodegenTarget, …>` (a gained target fails until its profile — the audience clause of the decision rule, what the target emits, and its file names — is written; the tool description derives from the audience alone, and the `target` field description adds the rest, which is parameter detail the length budget keeps out of the description). **Every valid response is preflighted through the SDK's own `runCodegenCheck` in memory, on BOTH arms**, before it is written or relayed: one call establishes lock structure, canonical and unique paths on both sides, and stamp/hash agreement, so the hand-written checks keep only what the SDK cannot know — presence and typing, `isStampableArtifactPath` per artifact, that the report's `target`/`kind` **echo the request** (a report for another language is internally current, so the offline check cannot see it), and that `lock_filename` is exactly **`codegen.lock`** (it is joined under the write directory, so `../../…` would otherwise reach `writeFile` uncontained; pinning the exact name also keeps the lock where `pipelex codegen check` looks for it and makes it unable to alias an artifact path, the one hole the preflight cannot see because `runCodegenCheck` never learns the lock's filename). **The write arm is `CodegenContext.saveRoot`** — the same name and meaning as `ArtifactsContext.saveRoot`; `generateMthdsCode` owns it (hoisted report check → preflight → `writeCodegenTree` → projection), so `codegenResult` stays pure, synchronous and filesystem-free. On the written arm content is withheld from every stream (`written_to` per file, `output_dir`, `is_current`, `orphans`, `orphans_truncated`, `drifts`, `truncated: false`, no fenced blocks); `output_dir`'s presence is the arm discriminator. A refused or failed write is a `status: "error"` no-verdict — never a fallback to riding the content. **Bounding is by whole file, with the lock's bytes reserved off the top**: `boundArtifacts` gives the lock its bytes first and lets the artifacts fill the remainder under `CODEGEN_CONTENT_CAP` (64 KiB UTF-8 across the set), stopping at the first that does not fit — the rest carry `path` and `bytes` with `content` absent, `truncated: true`. A half file neither compiles nor passes the check, and dropping the lock to fit the code it anchors is the wrong casualty. Classify options are picked by request shape (files → 422 at `target`; by-ref → `method_ref`; by-id → `method_id`), and the 403 arm composes the deployment's auth wording with the hosted feature-flag gate through `classifyError`'s `forbidden` option. No view, no `_meta`, no `available_view_specs` (decided out on 2026-08-29).
- `capabilities/codegen-writer.ts` — the generated-tree writer behind `output_dir`, and the **write-side policy** the download tool must never share. `writeCodegenTree` returns a value and never throws. In order: contain the directory through `resolveSaveDir` (the one call that creates anything); contain every destination *and the lock* with `isInsideRoot` alone, creating nothing, so a refusal leaves the tree byte-identical, directories included; inspect every existing destination with **`lstat`** — a regular file carrying a codegen stamp (or, for the lock, the `# codegen.lock` prefix) is overwritten *hand-edited or not*, and a symlink, a directory or an unstamped file refuses the WHOLE write as `input_domain`@`output_dir`; write verbatim with the default overwriting flag, the deliberate inverse of the SDK download's exclusive `wx` create; then walk the directory (symlinks skipped, vendor/VCS directories pruned, under a file-count cap and a decoded-bytes budget that apply to orphan candidates only) and run `runCodegenCheck` with the lock **re-read from disk under a strict UTF-8 decoder**. `hasCodegenStamp` is a one-function mirror of the SDK's internal `hasStamp` (source of truth `pipelex/pipelex/codegen/stamp.py`), kept to one function so the swap is one line once the SDK exports it.
- `capabilities/graph-page.ts` — the method graph page `mthds_validate` writes beside the `{ path }` files it validated (`writeGraphPage`, triggered by `ValidationContext.saveRoot`, which only the workshop's `mthds_validate` context sets, so the save's validation leg writes none). The page embeds the `.mthds` files in the `mthds-sources` element and loads `@pipelex/mthds-ui`'s standalone viewer and elkjs from jsDelivr, pinned by exact version and SRI (`GRAPH_PAGE_ASSETS`, checked live by `graph-page.e2e.ts`); the viewer builds the static graph in the browser, so the page needs no API call and is written whatever the verdict. `serializeMthdsSourcesEmbed` is a **one-function mirror** of mthds-ui's export of the same name, not an import: declaring mthds-ui in the workshop's manifest would force the console onto the same range (the one-range manifest rule), and the release carrying the export changes the console's stylesheet contract, so the swap to an import waits for the console's mthds-ui bump. The write policy is codegen's, not the download tool's: `lstat` the destination, create a missing page with `wx`, replace only a file carrying `GRAPH_PAGE_MARK` (a `generator` meta element), and leave a foreign file, a symlink or a directory untouched. A failure is a returned `GraphPageOutcome`, never a throw and never a change to the verdict; `toolResult` renders its `## Method graph` section after the error details.
- `capabilities/workspace-boundary.ts` — the containment routine every filesystem-touching capability shares: `isInsideRoot` (containment without creation) and `resolveSaveDir` (containment plus the one `mkdir`, real-path-checked on the deepest *existing* ancestor before it and again after), with the `ToolError` location a parameter (`dir` / `output_dir`). `workshop/src/files.ts`, `artifacts.ts`, `codegen-writer.ts` and `graph-page.ts` import it. It also owns `checkDeepestExistingAncestor`, the probe both directory-creating sites run **before** `mkdir` — a real-path check that runs only afterwards reports an escape through a symlinked component instead of preventing it. **Containment only — never policy.**
- `capabilities/prepare.ts` — the input-preparation logic (`mthds_prepare_inputs`, **workshop-only**). Zod input/output schemas (`files?` / `method_ref?` / `method_id?` under `one_selector`, `pipe_ref?`, required filled `inputs`), and the whole request handed to `@pipelex/sdk`'s `prepareInputs`, which uploads local paths / `data:` URLs / bytes to Pipelex storage and rewrites them to `pipelex-storage://`; the result projects into `structuredContent` (`inputs`, `uploads: string[]`) plus a composed Markdown summary with the prepared inputs in a fenced block. **Every selector is a server pass-through** — since `@pipelex/sdk` 0.17.0 `prepareInputs` takes all three and reads the signature from one `POST /v1/validate` with `views: ["input_form"]`. Classify options are picked by request shape (files → 400/422 at `files`, the same texture `mthds_validate` gets for the same body; by-ref → `method_ref`; by-id → `method_id`) — **never at `pipe_ref`, which stopped riding the wire when pipe selection became client-side**. The SDK raises every client-side refusal of its own as a plain `InputPreparationError`, so all of them land at `pipe_ref` through `ClassifyErrorOptions.preparation`: right for *which pipe*, wrong for a broken closure, a missing descriptor or a bad file value, which only the console's walk tells apart (below) until the SDK raises them as distinct errors. **No produced-invalid arm** — an unresolvable closure is a no-verdict `status:"error"`. No view, no `_meta`.
- `capabilities/console-inputs.ts` — `pipelex_run`'s input walk (`prepareConsoleInputs`), **pass-through only**, which replaced the console arm `prepare.ts` had behind an `allowUpload` seam. It calls `validate` itself for the pipe's `input_form` descriptor, picks the pipe in the SDK's order, walks the same kinds, and rewrites `http(s)` / `pipelex-storage://` values to `{ url }` while refusing any upload-needing value up front (`UploadNotAllowedError` → `input_domain`@`inputs`, the hint naming `pipelex_upload_attachments`), so it never hands raw inputs to `prepareInputs` and never triggers a server-side `readLocalPath` (the LFI/DoS/existence-oracle hazard). **That mirror is forced, not lazy**: the filesystem read happens *inside* the SDK's walk, before the upload a client seam could refuse, and no value-shape pre-screen finds it without the descriptor — a bare string is a local path at a file position and ordinary text everywhere else. Keep the mirror in step with the SDK's `prepare-inputs.ts`: the invariant is that the console never prepares a different pipe from the one the SDK, and the run route, would. `default_pipe_ref` is read on **presence**: a stated `null` (or a stated ref the descriptor does not describe) is a refusal at `pipe_ref`, and only an **absent** field leaves the blueprint and single-pipe fallbacks standing. Its three client-side refusals take three locators, because they are three questions: `preparation` at `pipe_ref` for *which pipe*; `UnresolvableClosureError` through `closure` at the selector for *which method*; `MissingInputFormError` through `missingDescriptor`, `config` at `PIPELEX_BASE_URL`, for *which deployment*. A report with no `input_form` is refused, never degraded to a walk where no refusal can fire — and the test is for a usable **record**, not for `undefined`, since the report is extension-open transport nothing validates at runtime and a `null` in that slot used to die on `Object.keys` two frames down. The descriptor guards are this repo's and not the SDK's, and they run at every depth: the top-level field list, an `object`'s `fields` elements and a `list`'s `item` (a stated `item: null` passes an `!== undefined` test and then has `.kind` read off it). A malformed node falls to the pass-through arm, which is safe because it declares no file position, so nothing upload-bearing escapes unrefused; a malformed top-level field list is refused outright, because there would be nothing left to walk. `pipelex_run` skips the walk, and its `/v1/validate`, when `inputs` is absent or empty; its `files` selector arm serves the live leg alone.
- `capabilities/show.ts` — `pipelex_show_method` (**console-only**): exactly one of `method_id` / `method_ref` (`validateMethodReferenceRequest`), an optional `pipe_ref` checked against the declared pipes, one `POST /v1/validate` with `VALIDATE_VIEW_TOKENS` (the SDK always adds the Markdown render, which the tool discards), projected through `validate.ts`'s `projectValidationReport` with views on for the pipe named, plus the template from `inputs-template.ts`'s `inputsTemplateFor`, projected client-side from the pipe's `input_form` descriptor by `mthds/protocol`'s `projectInputsTemplate` (a descriptor it cannot walk yields no template; `mthds_inputs_template` still reads `/v1/build/inputs`). It composes its own summary (the signature, the template, and the "who goes first" rule the instructions complete per host); the graph and the form's artifacts ride `_meta` for `run-graph`. The graph is the dry run of the bundle's own `main_pipe`, so a package declaring none has no graph while its form and template still come.
- `capabilities/attachments.ts` — the chat-attachment ingest capability (`pipelex_upload_attachments`, **console-only**) plus the mandated four-field host-attachment Zod schema (`download_url`/`file_id` required, `mime_type`/`file_name` optional — declared here rather than imported from `skybridge/server`'s `FileRef`, because the capability core stays Skybridge-free; a local mirror emits a byte-identical JSON Schema). Per attachment, sequentially: fetch within the boundary → `uploadFile` → `pipelex-storage://`. The host's `file_name` is user-supplied, so it is reduced to a bare printable basename before it names a stored asset. Per-item errors ride `attachments[i].error` and **partial success is a produced verdict** (`status:"ok"`, `is_valid:false`) — successful uploads are never discarded because a sibling failed. Never touches the filesystem. No view, no `_meta`.
- `capabilities/upload-grant.ts` — the run form's upload grant (`pipelex_request_upload`, **console-only and app-only**: `_meta.ui.visibility: ["app"]`). The view sends the file's name, type and size, never its bytes; the capability asks `POST /v1/upload/grant` for a presigned, create-only `PUT` with the caller's token and relays it. **The grant is a bearer capability, so it rides `_meta.upload_grant` and nowhere else** — `structuredContent` carries only the reference, the expiry and the cap, and nothing logs it. Its refusals are picked by status in `uploadGrantErrorOptions`: the route's `400` is the platform's `require_active_org` (`config` at the credential, since no file changes it), its `422` is the body (`input_domain`), and its `413` is the declared size over the cap, classified through `classifyError`'s `tooLarge` option (`input_domain` at `size`). The grant's shape check lives in `capabilities/upload-grant-shape.ts`, which imports one type and nothing else, because the view bundles it for the browser. The bucket sources the views may reach are `hosted/app-buckets.ts`: **every source there is one bucket's own host, a plain origin.** The platform signs on the GLOBAL virtual-hosted host (`<bucket>.s3.amazonaws.com`), both its upload grants and the fresh links its bulk resolve route mints, and the lists carry the REGIONAL virtual-hosted form beside it, which is where the runtime signs a run's baked `public_url` from `pipelex` 0.66.0 (measured against api-dev on 2026-09-26) and what a pinned platform endpoint would produce. **The shared regional endpoint is deliberately not allowed**: the runtime signed PATH-style there before 0.66.0 (`s3.us-west-2.amazonaws.com/<bucket>/…`), where a bucket can be scoped only by path, and the Dev console's acceptance on 2026-09-25 showed a host did not keep the path; the endpoint's origin alone would admit every bucket in the region. A path-style source must never come back. The views still paint from the fresh links on `_meta.resolved_urls` (see `capabilities/run.ts`), because the baked link expires an hour after the run. `upload-grant.e2e.ts` checks a live grant's host against the upload list, write-free, since a grant stores nothing until the file is sent.
- `capabilities/attachment-fetch.ts` — the **attachment fetch boundary**: the console's analogue of the workshop's path trust boundary, deny-by-default, reporting failures as values rather than throwing. See the Conventions entry below before changing anything here.
- `capabilities/upload-ceiling.ts` — `MAX_UPLOAD_BYTES` (**derived** from AWS API Gateway's 10 MiB request quota and base64's 4/3 inflation, not hardcoded) plus `SizeGuardedPipelexApiClient`, which refuses an oversize upload locally with the same `RejectedAssetError` the SDK maps a real `413` onto, `code: "too_large"` included, and a message that names the true limit. **It does not reach a caller the way a real `413` does**: the SDK's `uploadFile` maps a real `413` before its catch-all, but wraps anything else `upload()` throws in an `UploadTransportError`, so the local refusal arrives as that wrapper's `cause`. `classifyError` unwraps it ahead of the transport arm. Without that, an oversize file classified as a retryable `runtime` fault telling the agent to retry, and the ceiling's tests could not see it, because they called `upload()` directly rather than going through `uploadFile` as every real caller does. It overrides `upload` (the wire call), which is the one seam both upload paths share: the SDK's own `prepareInputs` walk calls it through `this`. It does **not** skip reading/base64-encoding a local asset first — the SDK owns that inside `uploadFile`, so a real pre-flight needs a change in `@pipelex/sdk`. **The app-level 50 MiB `MAX_UPLOAD_MIB` is unreachable through the public gateway; never quote it as the limit of a path that crosses it.** The run form's upload grant is the one path that does not cross it (the browser sends the file straight to the bucket), and there the 50 MiB is the limit.
- `capabilities/artifacts.ts` — the run-saving capability (`mthds_download_artifacts`, **workshop-only**), **thin over the SDK's artifact stack** for the files: it reads the run through the results route itself (so a running or failed run never creates a directory), resolves the target — `dir`, or `runs/<run id>` from the run id the API answered (`defaultRunDir`) — and contains it through `workspace-boundary.ts`'s `resolveSaveDir`, writes the full `main_stuff` verbatim to `main_stuff.json` **first** (`writeOutputFile`: `wx`, a numeric suffix on a taken name, the partial file removed on failure; a failed write stops the save as `input_domain`@`dir` before anything is fetched), checks for references with the SDK's `collectArtifacts`, then hands the results in hand to the SDK's `downloadArtifacts` (`results` form, `scope: "main_stuff"` named explicitly), which resolves the whole set through the bulk route (`resolveArtifacts` → `POST /v1/resolve-storage-url/bulk`) and owns the filename rule, the never-overwrite create, the bounds and the per-item verdict. What stays here is the workshop's own: the tool envelope (run-state verdicts, `scope` and `output` on the completed verdict, `saved_paths` with the output first, paths made relative to the working directory, each item's `found_at` as the SDK answered it, bounded at `MAX_FOUND_AT_PATHS` with the rest counted in `found_at_omitted`, since the SDK answers one path per occurrence and the verdict is model-facing), the output file, the deployment gate, the **plain-http rule** (`allowsPlainHttp` — the SDK's `allowHttp` opt-in follows `PIPELEX_BASE_URL`'s scheme, `http:` being the local compose stack; `PIPELEX_MCP_ARTIFACTS_ALLOW_HTTP` overrides it both ways, and an unrecognized value refuses), the classification into `ToolError`s (`itemToolError` maps the SDK's per-item codes; `BULK_RESOLVE_ERROR_OPTIONS` textures the route's whole-request refusals; the SDK's thrown artifact errors are arms of `classifyError` in `shared.ts`, ahead of the generic `PipelineRequestError` arm), and the prose summary. The per-deployment seam is `ArtifactsContext.saveRoot`: the workshop sets it to its working directory; absent, the tool refuses fail-closed. Verdict discipline is the run family's (`state`-discriminated; `running`/`failed` are produced) plus `all_saved` for the walk; partial success is produced. No view, no `_meta`. It carries no walker, filename rule or downloader of its own — a change to any of those is an SDK change; the output file is the one thing it writes itself, because writing one JSON value is not the network work the SDK's stack exists for.
- `capabilities/images.ts` — the image-display capability, on **both** shells (`pipelex_show_images`, `mthds_show_images`). It reads the run through the results route (so a `running`, `failed` or candidate-free run is a produced verdict that fetches nothing), prefilters the stored references by storage key with `shared.ts`'s `imageCandidatesOf`, intersects the caller's `images` / `indices` selection with what the run produced (an unknown reference or an out-of-range index is an `input_domain` no-verdict, refused before any call), then fetches each survivor through the SDK's bounded `client.fetchArtifact` under four named caps in `shared.ts` — `MAX_INLINE_IMAGE_BYTES`, `INLINE_IMAGES_BUDGET`, `MAX_INLINE_IMAGES` (which bounds *attempts*), `MAX_IMAGE_CANDIDATE_ENTRIES` (which bounds how many are *enumerated*, the rest counted in `omitted`) — plus its own `INLINE_IMAGE_TIMEOUT_MS` and `INLINE_IMAGES_DEADLINE_MS`. **The deadline is the one that is easy to leave out, and then to under-apply**: the per-image timeout is per image and the walk is sequential, so without a shared wall-clock budget six stalled objects accumulate into a three-minute call and a host with a shorter deadline loses the whole result, successful pictures included. Each fetch gets `min(INLINE_IMAGE_TIMEOUT_MS, remaining)` **and** `AbortSignal.timeout(remaining)`, and the signal is not belt-and-braces: `fetchArtifact` resolves the reference before arming `timeoutMs`, under a fixed 30s budget only `options.signal` reaches, so the timeout alone left a 60s walk able to run to 90s (120s of call with the run lookup). Since the SDK re-throws a caller's abort untouched, the deadline arrives as a raw `DOMException` and both catch sites test `deadline.aborted` first — otherwise this tool's own budget reads as a whole-request failure, and as a no-verdict when nothing had yet inlined. A candidate reached with none left is `withheld: "deadline"` unattempted. The content-type gate reads the **response's** header, not the resolve route's `content_type`, which the SDK documents as a guess from the reference's extension. A picture that does not fit is a `withheld` reason (`size` / `budget` / `count` / `type` / `deadline` / `empty`), never an error and never resized; `empty` is the zero-byte object, which clears every other gate and would be emitted as `data: ""` — permanent, unrenderable context; a per-reference failure rides `error` through `shared.ts`'s `itemToolError`. A repeated selection is deduplicated in `selectCandidates`, preserving the caller's order — the entries are in the order *considered*, which is the caller's for a narrowed call and discovery order only otherwise. Verdict discipline is the run family's, plus `all_inlined` — which answers for the **run**, so the walk is handed `candidates.length` beside the selection and a narrowed call reports `false` while the run holds a picture it did not ask for; `omitted` counts against it too, but `omitted` is this listing's truncation (what the call *considered* lost to the cap) and is reached with `indices`, never `images`. Partial success is produced — **but a whole-request refusal that stopped the walk before any picture arrived is a `status: "error"` no-verdict** carrying the classified cause, since nothing was produced and the generic summary would otherwise bury a paywall or a rejected credential. **Every emitted block is `{ type: "image", data, mimeType, _meta: { uri } }` and carries no `annotations`** — see the convention below; the `_meta` half is measured on Codex by the probe's `meta` variant, not assumed from the standard. No view, no result `_meta`, no filesystem.
- `capabilities/run.ts` — the durable-run family (`mthds_run` / `mthds_run_status` / `mthds_run_results`) over the SDK's run lifecycle (`start` / `getRunStatus` / `getRunResult`). A completed result walks the **full** `main_stuff` twice in memory, on both shells and for free: `collectArtifacts` for the stored-file count and `imageCandidatesOf` for `structuredContent.image_candidates` (absent, not empty, when the output references no stored file) — bare references, deduplicated, capped at `MAX_IMAGE_CANDIDATE_ENTRIES` with the remainder in `image_candidates_omitted`, because the walk deliberately reads the FULL output and an unbounded projection of it is model-facing content outside the `MAIN_STUFF_CAP` discipline `main_stuff` obeys beside it. A completed result also carries the graph's three I/O artifacts on `_meta`, on the same terms as the graph itself (`viewsAvailable`, never `structuredContent`): `pipe_io_contracts` and `output_form` as a **pair**, because that is the renderer's own rule — `GraphViewer` shows a data node's VALUE only when it holds both, and the concept's structure table otherwise, so half the pair renders exactly like neither and is withheld instead of costing the wire — plus `input_form`, which answers only for the method's own inputs and is optional *given* the pair rather than independent of it — the renderer consults it only inside the gate the pair opens, so it rides only when the pair does. Each must be a non-empty map to ride (`hasArtifactEntries`, shared with `validate.ts` from `shared.ts`): the hosted results relay the keys as `null` for a run whose runner predates them, and an empty map drives nothing. One merged summary sentence then names the shell's image tool where there are candidates and, on a shell whose `RunContext.artifactDownloadAvailable` is set (the workshop), `mthds_download_artifacts` as the way to keep the run — the output as `main_stuff.json`, and the files with the `public_url` expiry — on **every** completed result, files or not, because a model that does not know the tool retypes the output into a file; the same flag makes the truncation sentence name the tool as the way to read the rest. Prose only, the structured contract is untouched. **The results tool never inlines an image and takes no flag that would let it**; that is the campaign's settled decision, not an omission. `pipelex_run` (the console's, by `PipelexRunContext` / `PipelexRunClient`) takes `method_id?` or `method_ref?` only, maps `pipe_ref` onto `pipe_code` when the caller named one, and runs `console-inputs.ts`'s walk first; its hints name `pipelex_show_method`, and an unknown run id reads as not visible to the caller's organization. `mthds_run` starts from `files?`, `method_ref?`, or `method_id?` (rule `run_source`: files + `method_id` is the one legal pair — the files run, the id is run-history linkage; `method_ref` is a complete run source of its own and pairs with nothing). The platform resolves `method_id` natively on `/v1/start` (id-only runs the stored method's current content; beside files it rides the SDK's named `method_id` option — `PipelexStartOptions`, never `extra`, which the SDK refuses at runtime for reserved keys). `method_ref` rides the SDK's named Pipelex-API run-source extension, is resolved by the runner (git fetch at the tag), and the resolved commit comes back as `method_provenance` on the start ack — narrowed defensively (`narrowMethodProvenance`), projected into `structuredContent`, and echoed in the summary so the run stays explainable when a tag moves. Also owns `main_stuff` bounding (the prune ladder under `MAIN_STUFF_CAP`), the run-usage projection over the SDK's `summarizeUsage` — the arithmetic is the SDK's and is never re-derived here: `projectRunUsage` reshapes the summary into the model-facing `structuredContent.usage` (its `state`, `cost_usd` for the SDK's `total_cost_usd`, one `tokens` figure adding the SDK's `input` and `output` totals, `calls`, `assembly_error`), present on every completed result; per-pipe stays off the model-facing surface — `projectUsageByPipe` puts the SDK's `by_pipe` rows, in its order, on view-only `_meta.usage_by_pipe` alongside the full per-call `tokens_usages` for a future detailed-cost surface, and usage is never rendered into the prose; **the views' fresh links** (`freshStorageLinks`: on a shell with views, a completed result resolves every stored reference of its output, then of its executed graph, deduplicated, `BULK_RESOLVE_MAX_URIS` per request, one request after another through `RunClient.resolveStorageUrls` under one `VIEW_LINKS_TIMEOUT_MS` deadline, and rides the minted `https:` links on `_meta.resolved_urls` — best effort and never part of the verdict, so a failed or slow request stops the walk, keeps what the earlier ones minted and sets `_meta.resolved_urls_partial`, which the views read the results again for; every reference is asked for because the payload's baked `public_url` expires an hour after the run, so a reference left without a fresh link paints nothing in a conversation reopened later); and the per-route classify options, including the by-id variants picked by request shape. A failed start goes through `classifyStartError`, which refuses a retry whenever the run may exist anyway (a timeout, a connection lost after sending, a 500, 502, 504 or 408; the 500 is the runner's failed start, which the platform relays as such and which can follow a start Temporal already recorded); its hint and its "Run may have started" headline live in `capabilities/start-outcome.ts`, which imports nothing so the views can bundle it, and the hint is the marker `startMayHaveRunError` reads, in the tool's headline and in both run views, since a start spends inference credit and the SDK cannot yet send the `Idempotency-Key` the hosted `/v1/start` honours.
- `capabilities/run-failure.ts` — why a failed run failed, on both shells: `runFailureOf` narrows the runner's stored error report into the `failure` object every failed arm of the run family carries (the status tool on a terminal status other than COMPLETED, and the `failed` state of the results, image and download tools), and the module words it twice, `failureSummaryLines` for the model's summary and `failureDisplayOf` for the console's views. **The two wordings differ on purpose**: the platform serves the runner's VERBOSE report, so `message` can quote a provider's raw text, which the model reads and the person never does; the views say why from `title`, what to do from `user_action`, and show a support line (run id, error type, time the run ended) that `views/components/failure-details.tsx` renders with a Copy button. A `wait_and_retry` user action always takes this module's own sentence, in `structuredContent` as in the summary: the runner words its detail for a pipe still inside its retries ("the system will retry automatically"), which is false of the stored report of a run that has ended. Its tests run over real failed runs recorded from the dev plane (`capabilities/failed-run-fixtures.ts` over `__fixtures__/failed-runs/`).

- `views/run-graph.tsx` — the **run-graph** Skybridge view, registered on `pipelex_show_method`. The graph is not always of that pipe: the validate graph arm dry-runs the bundle blueprint's `main_pipe` and stamps it on `graph_spec.pipeline_ref`, while the entry pipe is manifest-aware, so a `method_ref` package can open the form on a pipe the graph does not show. The view keeps the graph and captions it when the refs differ — `graphPipeRefOf` reads the graph's pipe, `graphCaptionFor` words the caption, both in `run-graph-selection.ts` and only saying the form runs the entry pipe while it does — and renders nothing extra when they agree or the graph names no pipe. Run calls `pipelex_run` through `useCallTool` with the show's own `method_id` / `method_ref` and the form's pipe as `pipe_ref`, follows the run with the shared `useRunPolling` hook, fetches `pipelex_run_results` itself with the shared `useRunResults` hook once the run is terminal (a view's own call mounts no other view, so `run-follow` never appears for it), and shows the results in place: the results panel takes the form's place, the dry-run graph gives way to the executed graph fed the results' own artifact pair, and the form folds behind "Edit inputs and run again", which brings the dry-run graph back with it, since only that graph's nodes switch the form's pipe — `views/run-graph-stage.ts`'s `formViewStage` is that transition table, `formRunInFlight` holds Run disabled until the run's results are read or their fetch has given up (a second run in that window would drop the only handle on the first one's output; `useRunResults` gives up after `RESULTS_FETCH_MAX_ATTEMPTS` reads, from `views/run-results.ts`, so no failure can hold it for good), and `runStatusLineFor` is the line under the form, all pure and tested in Node. The run it started, and its pipe, ride host-persisted view state (`run_id`, `run_pipe_ref`), which a remount follows again once, restoring that pipe as the form's too, since no conversation message carries the id; each press of Run clears the state before starting, so a failed start leaves nothing an older run could be restored from. **It sends no completion message** (design R2 of `wip/mcp-result-delivery/`): the user reads the output here, and the prompt was a draft in claude.ai's composer and nothing at all on ChatGPT; `run-follow`, where the model started the run, keeps its handoff. Two things to know: `running` is set synchronously inside `onRun` because that is the panel's only duplicate-run guard across the round trip, and a file-bearing input stores a picked file through the `uploadFile` callback `views/run-graph-upload.ts` builds: it calls `pipelex_request_upload` for a grant, sends the file with `@pipelex/sdk/upload`'s `uploadWithGrant` under the SDK's own time limit (the view passes no timer of its own, since the SDK bounds the `PUT` itself from `@pipelex/sdk` 0.24.0), and returns the reference only once storage has answered. A failed send is worded by `storageFailureMessage` from the error's `code` (`UploadTransportError`, `RejectedAssetError`) and never relays the SDK's message, which is advice for a caller holding the grant — a retry with the same grant before it expires, a longer `timeoutMs`, a look at the page's CSP — that the person at the form cannot follow; its tests drive the SDK's real `uploadWithGrant` over a stubbed `fetch`, so a change in how the SDK classifies storage's answer fails them. **The panel swallows a rejected upload silently** (its rejection handler is empty), so the view writes the failure into a line under the form itself, one per field, keyed by the field id the panel passes and dropped when that field's value changes (a pasted link, a clear, a later upload) or its list gains or loses a row, since a failed row holds nothing and a removed one reads the same by value — `clearChangedFields` in `views/run-graph-upload.ts`, since the panel commits nothing when an upload fails; without that, a failed upload looks exactly like the bug this path fixed, a dialog that opens and a field that stays empty. That module imports only `@pipelex/sdk/upload` and `capabilities/upload-grant-shape.ts`, never the SDK's main entry, which reaches `node:fs` and cannot be bundled for a browser. It renders the form alone when a result carries the form pair but no graph, and a compact empty state for invalid results and for results carrying neither. Being a registered view, it also satisfies Skybridge's "≥1 view entry" production-build requirement (the old `build-placeholder.tsx` is gone). The renderer name (`run-graph`) is the durable family; the `available_view_specs` kinds (`dry_run_graph`, later `live_run_graph`) name the content variant it's fed.
- `views/components/run-results-panel.tsx` — the **results panel** both run views show a settled run through, with `views/use-run-results.ts` (the results fetch loop moved out of `run-follow`: retry on `state: "running"` and on a transient error along the status ladder, paused while the tab is hidden, one fetch in flight, the snapshot stamped with its run id so a new run never shows the last one's results) and `views/run-results.ts` (the pure half, tested in Node). The output is the form kernel's `StuffViewer` in the `app` presentation, fed the full `_meta.main_stuff` (unless it is past `FULL_OUTPUT_RENDER_BUDGET`, when `outputToRender` hands it the bounded copy and the panel says so, since the kernel renders every row and every JSON token at once), over the field `outputFieldFor` derives with `buildResultField` from the executed pipe's `_meta.output_form` node and its contract's `output.json_schema`; the kernel's `JsonView` stands in, with a line saying why, when either is missing. The kernel's Download control is hidden (`hideDownload`): the host's sandboxed frame blocks the object URL, the `<a download>` and the popup it saves through. **Files paint from `_meta.resolved_urls`**: `runResultsViewOf` builds the kernel's synchronous `resolveUrl` over the links the results carried (`withLinks`, a lookup, rebuilt only when a later read adds links), the panel provides it through `ResultEnvProvider`, and every executed `GraphViewer` takes it as a prop; a reference with no link falls back to the baked `public_url`, which the CSP refuses. **Which pipe ran is `executedPipeRefOf`**: the executed graph's `pipeline_ref` first, since the runtime stamps it with the entry pipe it resolved (a view that ran the entry pipe without naming it cannot know which), the requested `pipe_ref` second, and no guess beyond. The header is `completedHeadline` / `failedHeadline`: the duration from the run record's `created_at` → `finished_at` (carried on `useRunPolling`'s snapshot from the status read; that snapshot is stamped with its run id too, so the render that first sees a new run reads it as just started rather than as the last run's terminal status), the cost at the graph panel's four decimals, `≥` when partial, absent when nothing was priced, and never a token count. Inline the output is height-bounded with a fade (a CSS mask, so no background colour has to match the host), never an inner scroll; fullscreen shows it whole and adds the executed graph, except where the view draws it at the top itself (`showGraph`). Both views' CSP lists `RUN_OUTPUT_SOURCES` as `resourceDomains` and `frameDomains`, for the output's images and its document previews. **Every renderer sits under a `RenderBoundary`** (`views/components/render-boundary.tsx`): each `GraphViewer`, the output's `StuffViewer` (which falls back to `JsonView`), `RunPanel`, and each view's root. A throw otherwise unmounts the whole view, and **ChatGPT drops the `null` values of a tool result it relays to a view**, which is exactly what made the graph validator throw there; mount a new package renderer under one too. **A partial set of links is read again**: when `_meta.resolved_urls_partial` is set, `useRunResults` settles the results at once and then reads them again on `LINK_REREAD_DELAYS_MS`, and `withLinksFrom` adds only the links each later read minted to the view on screen, keeping every artifact's identity and every link already painting, so a file the first read could not link paints once the route recovers, without a remount; the panel says some files may not show while the flag holds, in words that stay true once the last read has been made. `freshStorageLinks` sets the flag only for a failure `classifyError` calls retryable, so a refused credential or a deployment without the route costs no re-read.

### The files union and the resolution seam

Every files-taking tool — the workshop's alone, since no console tool takes `files` — (`mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`, `mthds_run`) shares one per-item input union: inline contents (`{ content, uri? }`) or a file path (`{ path }`). The arms are non-strict with first-match semantics — a pathological item carrying both keys parses as the content arm and `path` is ignored (strict arms were rejected in Phase 0: an unknown-key failure would surface as a noisy zod union error from the SDK layer instead of our instructive `ToolError`).

On every files-taking tool (`mthds_validate`, `mthds_run`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`), `files` is **optional** beside separate top-level selectors — `method_ref?` (a published method address, `github.com/<owner>/<repo>[/<selector>][@<tag>]`) and `method_id?` (a registered method's catalog id). Neither is a third union arm: an address or an id is not a file, and a mixed array would falsely suggest merging. `validateMethodSelectorRequest` enforces the two selector rules (SPEC.md → "Method Selectors"): the tooling tools take **exactly one** source form; `mthds_run` lets files + `method_id` pair (files run, id is linkage) while `method_ref` pairs with nothing. Resolution: `mthds_validate`, `mthds_codegen` and `mthds_prepare_inputs` forward either selector to the server (prepare's ride `POST /v1/validate`, the route its signature comes from); `mthds_inputs_template` forwards `method_ref` on the build envelope and expands `method_id` via **fetch-and-forward** (`fetchMethodFiles`), the one remaining user of that leg; on `mthds_run` both selectors resolve natively server-side on `POST /v1/start` — see Run Scope.

What a `{ path }` item *does* is decided by the **resolution seam**, not the schema: each capability's context carries an optional `resolver?: FileResolver`, and `resolveSubmittedFiles(files, resolver)` runs **ahead of** the request-shape checks (`validateMethodSelectorRequest` sees only resolved `{ content, uri? }` items). With a resolver (the workshop), `{ path }` items are read from disk and the resolved item carries `uri` = the submitted path — that's the provenance win: diagnostics locate to files the agent can open. Without one, each `{ path }` item is rejected with an instructive `input_domain` error at `files[i].path`; no shell builds such a context now, but the refusal stays as the fail-closed default. Resolvers report failures as `FileResolution` values, never throw; every resolution failure is `input_domain` at `files[i].path`, `retryable: false` — the resolver supplies only message and hint.

### The output streams (contract vs presentation vs view)

This mirrors the workspace's "format follows consumer" rule — read `../CLAUDE.md` → "Surface output conventions". A tool result carries up to three independent streams (`pipelex_show_method` uses all three; the workshop has no views, so its tools use the first two):

- **`structuredContent`** — the machine contract the model reads. A machine consumer branches on these fields, never on transport.
- **`content` text** — the human/LLM-readable Markdown summary. For `mthds_validate` it is the API's `rendered_markdown` and is deliberately **not duplicated** into `structuredContent`; `pipelex_show_method` composes its own, carrying the signature and the template. For `mthds_inputs_template` the capability composes it (the build routes return a plain `message`) and deliberately **does** repeat the template in a fenced code block — the template is the small payload the model must read, not a large view artifact.
- **`_meta`** — large, view-only data that **never reaches the model's context**. The graph (`_meta.graph_spec`) rides here so the agent acts on the verdict + Markdown summary, never the raw spec; the `run-graph` view reads it back via `responseMetadata.graph_spec`. `_meta` still travels on the raw MCP result, so a non-LLM programmatic consumer can read it off the wire — it is withheld from the model, not from the transport. The form's per-pipe artifact pair rides the same channel (`_meta.pipe_io_contracts` and `_meta.input_form` — the wire input-form descriptor the capability requests via the `views` token list — plus `_meta.output_form`, its twin requested by the same list and read by nothing yet, and `_meta.main_pipe_ref`) on a runnable verdict whose two artifacts each carry at least one entry, for the input form; the entry-pipe gate applies to the *advert*, not to the pair. Because the model never sees `_meta`, `structuredContent.available_view_specs` is its structured signal a view exists to surface: it lists the renderable view kinds — `"dry_run_graph"` (the method graph from the validation dry run, riding `_meta.graph_spec`) and `"input_form"` (the entry pipe's fill-in form, derived from `_meta.input_form` with `_meta.pipe_io_contracts` beside it; only on a runnable verdict with a settled entry pipe and both artifacts carrying that pipe, since a form whose Run can only fail — or whose fields cannot be derived, or that has no pipe to be for — is not worth advertising, even though the artifacts themselves still ride so a clicked pipe can get one). (The view-kind identifier and the `_meta` key are intentionally distinct: the key mirrors the API's `graph_spec` field and the view's `responseMetadata.graph_spec` reader, while the identifier names what kind of view it drives.)

`pipelex_run_results` uses the same channel for the same reason, and carries the same artifact names: `_meta.pipe_io_contracts` and `_meta.output_form` as a pair with `_meta.input_form` beside them, which is what makes the executed graph in either view show a completed run's actual values instead of its concepts' structure tables, and what the results panel derives the output's field from. **This was a shipped regression between `@pipelex/mthds-ui` 0.20.0 and the SDK carrying the fields**: 0.20.0 deleted `StuffViewer`, which had been rendering the value, and replaced it with a gate on the pair — so every hosted run graph silently dropped to the structure table until the producer chain (the Temporal build, the platform relay, `RunResults`) was finished and this read it. `run-graph`'s dry-run graph is deliberately NOT fed the show's pair: the renderer suppresses the data view on a dry run before it consults the props, so wiring them there would change nothing. Its executed graph, after a run from the form, is fed the results' pair like `run-follow`'s.

### Verdict vs no-verdict (the `status` discriminator)

A successful `mthds_list_methods` call is `status:"ok"` with counts and a `methods` page; it is a read result, not a method verdict, so it has no `is_valid` field. The failure arm still uses the shared `status:"error"` + `errors[]` shape.

A *produced* verdict is always `status: "ok"`, regardless of whether the bundle passed — discriminate on `is_valid` (and, for validation, `is_runnable`). This discipline is shared by both tools: an unresolvable closure on `mthds_inputs_template` is a produced `is_valid: false` verdict with `validation_errors[]`, exactly like an invalid bundle on `mthds_validate`. `status: "error"` is reserved for **"no verdict could be produced"**: bad request shape, unreachable/misconfigured API, or a runtime fault. Those carry an `errors[]` array, each tagged with an `ErrorClass`:

- `input_domain` — the submitted request is wrong (empty `files`, blank `uri`, blank `pipe_ref`, API 400/422 — which on `/v1/build/inputs` includes an unknown `pipe_ref` and an unresolvable `main_pipe` default).
- `config` — environment/auth is wrong (`PIPELEX_BASE_URL`/`PIPELEX_API_KEY`, API unreachable, 401/403/404).
- `runtime` — unexpected server-side fault (API 5xx, unknown errors, a reachable-but-malformed report).

`classifyError` (in `capabilities/shared.ts`) maps `@pipelex/sdk` error types (`ApiUnreachableError`, `ClientAuthenticationError`, `ApiResponseError`, `PipelineRequestError`) and HTTP statuses onto these classes; each capability passes `ClassifyErrorOptions` for its route-specific 400/422 locator/hint and 404 route name, plus the deployment's auth-failure texture (`options.auth`, threaded from the context's `authError` field — the hosted console's "reconnect the connector and sign in again" wording at `authorization` vs the default `PIPELEX_API_KEY` env-var wording). A route a deployment gates beyond authentication passes `options.forbidden` too: it replaces the hint on a **403 only** (never a 401), keeping the auth locator — `mthds_codegen` uses it because the hosted `/v1/codegen` sits behind a feature flag as well as a plan, so a valid credential can still be refused and "check your key" would mislead. Every `ToolError` also carries `retryable` — set here, where the concrete SDK error/HTTP status is still known, because the class+locator pair alone can't tell an unreachable API (transient) from a missing run lifecycle (permanent, same `config`@`PIPELEX_BASE_URL`) or a 5xx from a malformed report (both `runtime`); the `run-follow` view's poll loops branch on it via `isTransientPollError`. When you add a new failure mode, classify it here — including its `retryable` verdict — rather than letting it fall through to a generic `runtime` message. **The execution-locus gate's two 403s are the standing example, and both are branched on the runner's declared `error_type` ahead of the generic 401/403 arm** (`MethodStructuresRefusedError`, a fetched package declaring in-process Python structure classes; `CustomCodeRequiresSandbox`, any method shipping `.py` on a deployment that is not sandbox-hosted): they are `input_domain` at whatever named the method — `ClassifyErrorOptions.methodLocation`, set per request shape because `/v1/start` gates a submitted bundle and a stored method's injected source too — and the whole point is that the generic arm sends a caller whose credential is fine to go and mint a key.

A `ToolError` also carries an optional `kind`, which **refines a class that the headline cannot use**. Its only member is `paywall`, set in the 402 arm: a plan limit is deliberately `config`, so every class-derived headline announced "the Pipelex API is unreachable or misconfigured" for a billing refusal — and on a host that shows the agent only the top content line, that was the entire message. Each capability now declares its headlines as an `ErrorSummaries` record (three classes **plus** `paywall`) and looks one up through `summaryForToolError`, which consults `kind` before `class`. The mandatory `paywall` entry is the point of the type: a new capability that forgot one would silently inherit the connectivity headline, and this makes that a type error instead of a review catch. The `class` contract is untouched — a machine consumer still branches on `class`; `kind` is what lets it tell a billing refusal from an unreachable API without sniffing the message, exactly as `retryable` separates a transient `config` from a permanent one. A future cause of the same shape gets a new `kind` member and a headline in every table; it does not get re-classified.

### State projection rules (in `validationResult`)

- `projectValidationReport` is shared by `mthds_validate` (views off, so no graph, form artifact or advert ever appears on the workshop) and `pipelex_show_method` (views on, for the pipe the caller named); the rules below are the views-on reading.
- Valid + runnable → `is_valid=true`, `is_runnable=true`; the graph is returned on `ValidationResult.graphSpec` (projected onto the tool result's `_meta.graph_spec` by `toolResult`), never in `structuredContent`.
- Valid + pending signatures → `is_valid=true`, `is_runnable=false`, `pending_signatures` populated.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated.
- `available_view_specs` is populated from what was produced: `"dry_run_graph"` exactly when `graphSpec != null` (a valid verdict with a graph, on a shell that renders views), `"input_form"` exactly when a settled entry pipe (`mainPipeRef`) has an entry in `pipe_io_contracts` AND in the `input_form` descriptor, on a valid + runnable verdict whose two artifacts both rode. **The advert is narrower than the artifacts' own gate**: the pair rides whenever the verdict is runnable and both maps carry something (a runner that ignored the `views` token returns no descriptor, and then nothing rides and nothing is advertised, rather than an empty form), because `_meta` never reaches the model and the maps are what the view looks a pipe up in — gating them on the entry pipe made a click on a graph node dead for every pipe. A verdict with no entry pipe (a stated `default_pipe_ref: null`, or a blueprint ref that keys neither map) therefore advertises nothing and opens nothing, while a pipe the user clicks still gets its form. Note the advert can outlive `main_pipe`: the form derives from the descriptor, so a plain-object contract that fails to narrow advertises a working form and no signature. `[]` otherwise (invalid, pending signatures without a graph, error). When the list is non-empty a `## Views` note worded for the present kinds (`viewsNote`) is appended to the Markdown summary. Add a new view kind to the `viewSpecSchema` enum and set it here when its spec is produced.
- `main_pipe.output.images` is present exactly when the output-form descriptor arrived AND its entry for the effective entry pipe narrowed to a node; absent otherwise, which is "unknown" and not "none". Independent of `viewsAvailable`, like the rest of the signature.
- `main_pipe` is present on **every valid verdict** with an effective entry pipe (`defaultPipeRefOf`) whose contract entry narrows cleanly — pending signatures included, independent of `viewsAvailable` (the ref derivation is hoisted out of the views branch to feed it, so `_meta.main_pipe_ref` also rides a valid non-runnable verdict; the view ignores it). `item_count` is present exactly on the fixed arm, `required` is `presence !== "optional"`, and per-slot JSON Schemas stay out. When it was produced, `signatureLine` appends a `## Main pipe` section to the Markdown summary **before** the `## Views` note.
- The capability always calls the API with `allowSignatures: true`, `render: ["markdown"]`, and `views: ["input_form", "output_form"]` (the descriptor opt-in — lenient on the server, so a runner that predates a token simply returns no descriptor for it, and the members reading it stay absent). A report missing `rendered_markdown` is a hard error.

### State projection rules (in `inputsResult`)

- Valid → `is_valid=true`, resolved `pipe_ref`, echoed `format`/`explicit`, and the template on exactly one of `inputs` (json) / `inputs_toml` (toml) — the unused field is absent.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated; no `pipe_ref`, no template fields.
- The request always sends its defaults explicitly: `format: "json"`, `explicit: true` unless overridden. A valid report missing its format-selected template field is a hard error (surfaced as a `runtime` no-verdict).
- The summary is composed by the capability (title, API `message`, resolved pipe, fenced template block matching `format`, then the next step: `mthds_prepare_inputs`, or straight to `mthds_run` when every file value is already a URL or a storage reference).

### State projection rules (in `codegenResult`)

- Valid → `is_valid=true`, `target` / `kind` echoed, `crate_fingerprint` and `engine_version`, `artifacts[]` and `lock` from `boundArtifacts`, and `truncated` always present (`false` when everything rode whole).
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated; no artifact fields.
- A valid arm without a well-formed artifact list, a lock string, or a lock filename throws, which `generateMthdsCode` surfaces as a `runtime` no-verdict — what arrives is written into a user's tree, so it is checked rather than trusted.
- The summary is composed by the capability: title, API `message`, the axes line, the verbatim-write instruction, one `## \`path\` (N bytes)` section per file with a fenced block (`fenced` grows the fence past any backtick run in the content), the lock last, and a `## Withheld for size` section listing the withheld files when `truncated`.

## Testing conventions

Tests are colocated with the code they test, inside its package (`*.test.ts`, Node environment); the tests that span packages live in the root `tests/`, among them `tests/workspace-manifests.test.ts`, which holds the dependency rules below: only the workshop is public, it depends on no workspace package, it declares every runtime dependency of the core it inlines, `skybridge` is the console's alone, and a package named in several manifests carries one range everywhere. Each capability is tested by **injecting a fake client** via its context's `client` field (`CatalogContext.client`, `ValidationContext.client`, `InputsContext.client`, `CodegenContext.client`, `PrepareContext.client`, `ShowContext.client`, and on the console's run `PipelexRunContext.client`, a `RunClient` plus the walk's `validate`) — the capability uses `context.client` when present and only constructs a real `PipelexApiClient` otherwise. Use this seam to test API behavior without a live `pipelex-api`. The **resolver seam works the same way**: inject a fake `FileResolver` via the context's `resolver` field to test `{ path }` handling without touching the filesystem (leave it absent to test the fail-closed rejection); the real `localFileResolver` is tested against actual temp directories in `workshop/src/files.test.ts`. The attachment capability adds a third seam of the same shape: inject a fake `AttachmentFetcher` via `AttachmentsContext.fetcher` to exercise ingest without network, while the real boundary is tested directly in `attachment-fetch.test.ts` (allowlist incl. the suffix-only attack, oversize refused before the body is read, a lying `content-length`, refused redirects, timeout, expired-URL `403`). The artifact download capability runs over a **mocked SDK**: inject a fake `ArtifactClient` (`getRunResult` plus `downloadArtifacts`) via `ArtifactsContext.client`; the fakes in `artifacts.test.ts` write into the directory they are handed and answer the SDK's verdict shape, and every walk runs against a real temp working directory, so containment, directory creation, relative-path reporting and the classification of every SDK outcome (per-item codes, thrown errors) are exercised on disk. The download boundary, the filename rule and the never-overwrite rule are the SDK's and are tested there. **The two writers deliberately have no injected write seam**: `ArtifactsContext.saveRoot` and `CodegenContext.saveRoot` are directories, and a real `mkdtemp` directory is the better test double — `codegen-writer.test.ts` runs entirely against real temp trees with the recorded engine response, so containment, the overwrite rule, the orphan walk and the strict decoder are all exercised on disk. The image tools run over the same client seam: inject a fake `ImagesClient` (`getRunResult` plus `fetchArtifact`) via `ImagesContext.client`, answering real `Response` objects with chosen headers and bodies — a real `Response` rather than a stub, because the capability reads `content-type`, reads `content-length`, cancels a body it will not use, and errors a stream mid-read to exercise the cap. Its picture is a real 1x1 PNG's bytes for the same reason `e2e-support.ts`'s is: the tests assert the base64 that reaches the block. **Each shell has one contract test, and a file snapshot is at the heart of each**: `workshop/src/server.test.ts` and `hosted/server.test.ts` pin, byte for byte, everything the shell shows a host before a tool call — the `initialize` result, `tools/list`, and on the console `resources/list`, where the views' CSP lives — in `workshop/src/workshop.contract.json` and `hosted/console.contract.json` (`shell-test-support.ts` reads them, with the package version and Skybridge's dev origin replaced by placeholders). A diff to either file is a contract change: on the console it is one that strands every ChatGPT install until the connector is re-added, so update a snapshot with `npx vitest run -u` only for a change you meant, and say so in the release notes. Beside the snapshot, each test asserts the properties worth naming: on the console the **emitted four-field JSON Schema** and the `openai/fileParams` key that *is* the substitution mechanism, which are un-hotfixable once users add a connector; on the console also the retired-names answer, both instruction variants and the absence of every workshop tool name; on the workshop the dispatch through the real stdio entrypoint and the **absence** of the console-only tools. `tool-names.test.ts` is the one cross-shell test left, and it holds the D1 rule above. Pure projection/classification functions (`projectCatalog`, `validationResult`, `inputsResult`, `classifyError`, `validateMethodSelectorRequest`, `validateInputsRequest`, `resolveSubmittedFiles`, `fetchMethodFiles`) are exported specifically so they can be tested in isolation; the shared ones are covered in `shared.test.ts`.

**Two suites, two jobs — and the second exists because the first mocks the boundary that actually breaks.** The default suite (`*.test.ts`, `vitest.config.ts`) fakes every client, so it proves the projections and never touches the wire; that is what keeps `make all` and CI hermetic. The live suite (`*.e2e.ts`, `vitest.e2e.config.ts`, run by `make test-e2e`) does the opposite: it builds each capability's context from `liveApiConfig()` and supplies **no** `client` seam, so the real `PipelexApiClient` reaches the real API. Selection is by suffix — the default `include` is `*.test.ts`, so an e2e file can never be picked up by the hermetic run. When a live run reveals behavior that contradicts a unit fake, fix the fake in the same change: a fake that has drifted from the wire is how the mocked suite goes green over a broken client. Shared fixtures, the fixture-method lookup and the API config guard live in `packages/core/src/capabilities/e2e-support.ts`.

**The live targets' resolution is pinned the same way, by `tests/make-live-recipe.test.ts`**: it runs `make -f` from a temp directory holding its own `.env`, reads the preflight's target line under `make -n`, and checks that the ambient `PIPELEX_BASE_URL` / `PIPELEX_API_KEY` change nothing, the precedence of the `PIPELEX_E2E_*` pair, that the key is never printed, and the refusal of the old names on the command line.

**The console dev recipe has a hermetic test of its own, `tests/make-dev-recipe.test.ts`.** Makefile logic that reads configuration is untested by construction, so the test runs `make -n dev` / `make -n dev-tunnel` (which prints a recipe without executing it) and asserts the precedence order and the `--port` pin, then executes the recipe's prelude under `sh` in a temp directory with a free port to check every guard verdict: each Resource Indicator shape, a held port (loopback-bound too, where `lsof` exists), a port that is not a number, and `.env` versus shell versus command-line precedence for the API target and for the port. It spawns `make` with a minimal environment so a parent `make test` cannot leak `MAKEFLAGS` or its own overrides into it.

## Conventions & gotchas

- **No backward-compatibility burden** (workspace rule) — change shapes directly; record breaking changes in the changelog of the server they affect, `packages/workshop/CHANGELOG.md` or `packages/console/CHANGELOG.md` (and reflect the new shape in `SPEC.md`).
- **The attachment fetch boundary is a security boundary — treat it like `workshop/src/files.ts`, not like plumbing.** It is the one place this server fetches a URL it did not configure, which makes a public endpoint an SSRF surface. It denies by default: `https:` only; the hostname must be `oaiusercontent.com` (apex or **any** subdomain) or match `oaisdmntpr<azure-region>.blob.core.windows.net`; no credentials in the URL; no non-default port; redirects refused outright; the 7 MiB cap enforced from `content-length` **before the body is read** *and* again mid-stream; a bounded total budget; no headers sent; non-2xx refused. **The two host rules are asymmetric on purpose — don't "harmonize" them.** The `oaisdmntpr` prefix is required, never optional, *only* because `blob.core.windows.net` is multi-tenant (any Azure customer can register under it, and a literal list is dead — one user produced three different Azure regions in one afternoon). `oaiusercontent.com` is OpenAI's own locked domain, so there is no "any customer" hazard for a prefix to filter, and narrowing it just queues up the next outage: the boundary originally allowed only `files.oaiusercontent.com` and refused every attachment the day serving moved to `sdmntpr<region>.oaiusercontent.com`. Two rules to keep when editing: **fetch the already-parsed `URL` object, never re-parse the raw string** (re-parsing at the fetch is how an allowlist gets walked past), and remember that these hosts are undocumented vendor infrastructure that changes without notice — **the host check is a filter, not the defence**, so the cap, the timeout, and the no-redirect rule must each hold on their own.
- **The artifact download path is a write-side security boundary — treat `capabilities/artifacts.ts`'s `resolveSaveDir` call and its plain-http rule like `workshop/src/files.ts`.** It is the one place this server writes files it did not create for itself, into the user's workspace. The writing of the produced files is the SDK's `downloadArtifacts`, which names each file after the field it fills in the output, the storage key supplying only the extension, and never after a caller argument, and opens the file with `wx` so "never overwrite" cannot race; what this repo must keep is the containment: the directory is real-path-checked on its deepest existing ancestor *before* `mkdir` (a check only after `mkdir` lets a symlinked ancestor create directories outside the workspace) and again after, and only the resulting real directory is handed to the SDK. The plain-http opt-in is derived, never defaulted on: `allowHttp` is true only when `PIPELEX_BASE_URL` is itself `http:` or the explicit override says so. The download link comes from our own API, so the fetch is not the SSRF surface the attachment boundary guards, but the cap, the timeout and the no-redirect rule hold on their own regardless of who named the URL.
- **The tools that write into the user's workspace share containment and must never share policy.** `capabilities/workspace-boundary.ts` holds the whole of what they have in common — `isInsideRoot` and `resolveSaveDir`. Above that the rules are **inverted, deliberately**: `mthds_download_artifacts` never overwrites (`wx`, numeric suffix on collision — its own `main_stuff.json` and the SDK's files alike), because a collision there means two different files; `mthds_codegen` must overwrite its own previous output and only that, because its paths come from the engine and the lock hashes them, so regeneration has to land on the same names; `mthds_validate`'s method graph page takes codegen's side, since every validation regenerates it under the same name. One shared "write a file" helper would either suffix a regeneration or let a download clobber. Three rules to keep in `codegen-writer.ts` when editing: destinations are inspected with **`lstat`**, so a symlink is foreign by construction (an overwrite through one writes wherever it points; the download tool never had this exposure, because `wx` refuses an existing path outright); the stamp predicate is a **one-function mirror** of the SDK's internal one, kept to one function so the swap is one line once the SDK exports it (`pipelex/pipelex/codegen/stamp.py` is the source of truth); and the lock's ownership test pins the **`# codegen.lock` prefix, not the engine's full header sentence** — the SDK's lock parser ignores that trailing prose entirely (`LOCK_KEYS` is `lock_version`, `crate_fingerprint`, `engine_version`, `artifacts`), so nothing anywhere fails if someone rewords it, while a verbatim match would turn every regeneration into a "foreign file" refusal on a file this tool wrote itself.
- **A codegen response is preflighted through the SDK's own check before EITHER arm hands its bytes anywhere.** `runCodegenCheck` runs in memory over the response — not only on the write path — because without `output_dir` the bytes go to a model that will write them, and a report the write arm would refuse is one the inline arm must not hand over either. One notion of a valid report is what keeps the arms from diverging. Corollary for the tests: a hand-written artifact stub can no longer stand in for a valid arm anywhere `generateMthdsCode` runs, since the check verifies content hashes. Use the recorded engine response (`capabilities/codegen-fixture.ts` over `capabilities/__fixtures__/codegen-ts-zod/`, stored as real `.recorded` files precisely so byte-exactness is self-evident); synthetic reports stay only for the pure projection tests, which never preflight.
- **The `pipelex_upload_attachments` description is mechanism, not documentation, and cannot be hot-fixed.** ChatGPT gates the attachment substitution on the description as well as the schema (a defensive wording measurably yields empty calls that look like a host failure), *and* it caches a connector's tool list at add-time and never refreshes it — so a description defect leaves every existing installation broken until each user re-adds the connector. Review changes to that text with the same rigour as a schema change, and say "re-add the connector" in the release notes.
- **Every model-facing text is budgeted, and each fact goes in the last layer that still reaches the model when it needs it.** `check:tool-texts` holds each shell's `instructions` and every tool `description` to 1,800 code points (`scripts/tool-text-budget.ts` says why). The layers each have one job: **server instructions are the map** — what the server is for, the three ways to name a method stated once, the order of the steps, and the few rules that apply everywhere; **a tool description says when to call the tool**, plus the contract rules the model must know before calling it; **a field description carries parameter detail**, such as an address grammar or a per-value file list; **a result summary carries what matters only after a call**, such as a withheld-for-size note or a link's expiry. Front-load each text, since a host that cuts keeps the head. The failure this prevents is additive: each campaign appended its tool's usage to the instructions as well as to its description, and the instructions outgrew the cap without anyone seeing it. A result summary is also the only layer that reaches an existing ChatGPT install, whose tool list was cached when the connector was added.
- **No image content block this server emits may carry `annotations`, ever.** The MCP standard's `annotations` hint (audience, priority) is optional and looks harmless; the host probe behind the image tools found that **Codex refuses an annotated image block outright** with `tool call error … Unexpected response type`, against a control proving the identical block without them is accepted and the picture reaches the model. Shipping with annotations would have broken the feature entirely on one of three named workshop hosts, diagnosable only from production. The `ContentImage` type in `shared.ts` does not declare the field, and `images.test.ts` asserts on the emitted block's exact key set — keep both. The study is `wip/mcp-image-results/host-probe.md` in the workspace, which also records what the probe settled about cost: a host bills an image block at the model's **native vision price** (pixels), and its **base64 size is free** — so the byte caps are a transport guard, not a cost control, and the reason the feature is a deliberate tool is that a picture in context is **permanent**, not that it is expensive.
- **Never log request `_meta`.** ChatGPT attaches `openai/userLocation` (city, region, country, timezone, latitude/longitude) plus stable `openai/subject` / `openai/session` / `openai/organization` identifiers to **every** `tools/call`. That is PII arriving on a surface we did not ask for, on every route.
- **Branding:** keep MTHDS-standard concepts neutrally named inside the Pipelex-branded envelope (`bundle_blueprint`, `graph_spec`, `pipe_io_contracts`, `input_form`) — see `../CLAUDE.md` "Brand boundaries".
- **Every Pipelex API client is built by `createPipelexApiClient` (`capabilities/shared.ts`), never with `new`.** The factory passes the context's `appInfo`, which is how every request names itself `pipelex-mcp/<version> (<workshop|console>; host=<host>)` in its `User-Agent`, the version being the shell's own package version, since the two servers are versioned apart and is attributed to the `mcp` surface. Each shell sets that identity on every context of its own table through the patch helper beside its context set — `patchHostedApiContexts` in `hosted/tools.ts`, `patchLocalApiContexts` in `workshop/src/tools.ts` — the console per request from the connector's `User-Agent`, the workshop lazily from the `initialize` handshake's `clientInfo`, which is only known after the contexts exist. The `pipelex/sdk-client-factory` and `pipelex/no-raw-fetch` lint rules (`eslint-rules/pipelex-api-boundary.mjs`, pinned by `tests/api-boundary-lint.test.ts`) refuse a direct construction or a bare `fetch` elsewhere; pass a subclass to the factory as its second argument, and keep third-party fetches (which must not carry the header) in the exempted `attachment-fetch.ts`. See `docs/client-identification.md`.
- `no-console` is an **error** in ESLint — don't leave `console.*` calls.
- **Each package's `dependencies` carries exactly what its own entrypoint reaches at runtime, and nothing else.** The workspace gives the two surfaces the separate manifests their opposite needs call for. The workshop's tarball ships `dist/main.js` alone, so every `npx @pipelex/mcp` user downloads the whole of `packages/workshop`'s `dependencies` closure before a single tool call; it therefore declares only what that bundle leaves external — `@modelcontextprotocol/sdk`, `@pipelex/sdk`, `mthds` and `zod` — and nothing of the console's. **The core is a devDependency of both servers and is inlined by both builds**: tsup externalizes only a package's `dependencies` and `peerDependencies`, so it bundles the core's source into `dist/main.js`, and the core's own imports then resolve from the workshop's manifest — which is why the workshop re-declares every runtime dependency of the core at the same range, and `tests/workspace-manifests.test.ts` fails when it does not. The console's `package.json` declares what its server and its views reach, `skybridge`, React and the view packages included; `packages/console/vite.config.ts` bundles the views into `dist/assets`, and the build toolchain (`vite`, `@vitejs/plugin-react`, `@tailwindcss/vite`, `alpic`, `@skybridge/devtools`) stays in its devDependencies. None of that can reach a workshop install any more, whatever block it sits in: the console is never published. **`skybridge` belongs to the console alone**, and the manifest test holds that too: as a dependency of the published package it had put its **non-optional** peers (`react`, `react-dom`, `vite`, `nodemon`, `@skybridge/devtools`) into every `npx @pipelex/mcp` install. **The console never resolves a workspace package at runtime**: it starts from `dist/server.bundle.js`, the esbuild bundle of the whole server that `skybridge build` emits for Vercel and `npm run build` copies into `dist/` (`packages/console/scripts/emit-server-bundle.mjs`), named as the start command in the root `alpic.json` and in the `Dockerfile`. That bundle is not optional: Alpic's runtime image carries the root `node_modules` from its install stage and the build output directory, and the core's entry there is a workspace symlink to a directory the image does not hold, so anything that imported `@pipelex/mcp-core` at runtime would crash. The bundle's path is Skybridge's Vercel output and not a promised interface, so `check:bundle` boots it from an empty directory on every `make check` (see Commands) — **start the console any other way, from `dist/__entry.js` say, and it crashes on Alpic**. **`check:bundle` pins the console's side of this boundary and nothing else**: it proves the console's bundle needs nothing from `node_modules`. On the workshop's side, a runtime import of a package its manifest does not declare still builds green, because tsup inlines whatever is not external; the manifest test catches the core's dependencies, and anything else is by hand — when you add a package, the question is which entrypoint reaches it and whose manifest it therefore belongs in. The dependency switches follow the same rule: `make use-local-ui` / `make use-npm-ui` install `@pipelex/mthds-ui` into the console alone, and the SDK switches install `@pipelex/sdk` into each of the three members, never into the root; npm keeps an entry in the block it already sits in.
- **The input form's kernel, `@pipelex/mthds-form`, is NEVER declared here — it is reached through `@pipelex/mthds-ui/form`, which re-exports it whole.** This inverted at mthds-ui 0.20.0, and the old reasoning is worth knowing because it reads so plausibly: the kernel used to be an *optional peer* of mthds-ui, never installed transitively, so the view could not build without our own entry and a direct (dev) dependency was the only way to get one. Since 0.20.0 it is an ordinary **dependency** of mthds-ui, so declaring it here buys nothing and costs a **second copy** in the tree — and the kernel ships React contexts (`FieldStringsProvider`, `FieldPresentationProvider`), so two copies mean a provider mounted above the panel silently resolves to defaults inside it. That is not theoretical: this repo pinned `^0.5.0` while mthds-ui pins `^0.8.0`, and a sub-1.0 caret cannot bridge a minor, so the bump to 0.24.0 really did install both until the direct entry was dropped. If you ever need the kernel's own helpers, import them from `@pipelex/mthds-ui/form` (`getPipeInputForm`, `getPipeIOContract`, `InputForm`, `PipeIOContracts` all come through). Styling follows the same inversion: `packages/console/src/index.css` carries **no** `@source` glob for the kernel and imports none of its stylesheets. It does carry one `@source`, for `@alpic-ai/ui`'s components, and that path is relative to the stylesheet rather than a package name: the workspace hoists the package into the root `node_modules`, three levels above the stylesheet, so it reads `../../../node_modules/@alpic-ai/ui/src`. Tailwind drops an `@source` that names nothing without a word, which would silently purge every alpic utility, so `check:cascade` refuses an `@source` that is missing or that does not sit inside the package Node resolves. The glob was once required — the controls are Tailwind classes and the build purged the unused ones — but since mthds-ui 0.21.0 the kernel ships a prebuilt sheet that `@pipelex/mthds-ui/form/react` imports itself, so a glob would only duplicate those utilities into our own `@layer utilities` and buy nothing but bytes. **Do not take the rest of that package's framing on trust, because it does not hold here.** Its changelog explains the layer as protection — layered rules lose to unlayered ones regardless of source order — and that is true only of an **unlayered** host. Tailwind 4's host is layered, so the protection never applied, and layer precedence follows the order the names are first **declared**: the kernel's sheet is bundled after `packages/console/src/index.css`, so left alone `mthds-form` is declared last and **outranks** every host layer. Measured on the built stylesheet, that inversion cost us the kernel's `.rounded-md` beating the host's, its nested `theme` sublayer replacing `--font-sans` and `--font-mono` for the whole console, and its `.hidden` beating our `.sm:inline` — the exact bug the layer is advertised to prevent, happening through it. **The cure is NOT simply to declare the kernel's layer first, and getting that wrong shipped a worse bug than the one it fixed.** `@layer mthds-form;` alone puts the kernel under *every* host layer including `base`, which is Tailwind's preflight — and `bg-input` and `border-input` exist ONLY inside the kernel's layer, because `@alpic-ai/ui/theme` defines no `--color-input` and so our own Tailwind cannot generate them. Layer rank is compared **before** specificity, so preflight's `button,input{background-color:#0000}` at specificity 1 beats `.bg-input` at specificity 100: every control in `RunPanel` renders with no surface, inside a panel whose own chrome is unlayered and still looks right. The cure is the **whole order**, declared up front — `@layer properties, theme, base, components, mthds-form, utilities;` — which puts the kernel above `base` and below `utilities`, and keeps `properties` (Tailwind's `@property` fallback for older Safari and Firefox) at the bottom, since promoting it resets every `--tw-*` on those engines. The two font tokens the kernel would otherwise take are pinned unlayered in the bridge block instead, which is what frees the layer to sit where the controls need it. For the same reason the explicit `@pipelex/mthds-ui/form/react/RunPanel.css` import is gone — that entry imports it itself. **What `packages/console/src/index.css` does carry instead is a token bridge**, and it is load-bearing: the kernel's prebuilt sheet reads the bare shadcn names (`var(--primary)`, `var(--background)`, `var(--radius)`, …), while `@alpic-ai/ui/theme` defines the Tailwind 4 `--color-*` names, so nothing resolved until each bare name was aliased to its `--color-*` counterpart (`--input` and `--radius` have no counterpart and map to `--color-border` and `--radius-md`). The glob had been covering for this by accident, because our own Tailwind compiled the controls against our own theme. Alias rather than copy literals, so re-theming alpic moves the form with it. The failure mode if a token goes missing is **silent**: an undefined custom property makes the browser discard the declaration, so the control falls back to `transparent` or `canvastext` while the build stays green and the token inspects correctly in devtools — it reads as a contrast bug, not a stylesheet one. So when the form looks wrong, run **`npm run check:cascade`** rather than eyeballing the panel or reaching for a glob. **Never verify any of this by reading the layer order back out of the build.** That check passes in the state where every control is invisible, and it cannot even read what it claims to: lightningcss *deletes* the `@layer a, b, c;` statement and honours it by hoisting the blocks, so the names the source writes never reach the output. `packages/console/scripts/check-cascade.mjs` resolves the winning declaration for each property that matters — `!important`, then layer rank, then specificity, then document order, with longhand and logical-property expansion so `*{padding:0}` is weighed against `.px-5{padding-inline:…}` — and it asserts the pinned font literals still match `@alpic-ai/ui`'s own `tokens.css`, so a theme bump that moves them fails the gate instead of going quiet. Its `CHECKS` list is the contract; a new kernel-only utility nobody asserts on is a gap, so extend it rather than trusting it wholesale.
- The SDK dependency is the **published `@pipelex/sdk` npm package** (public on npm), not a `file:../pipelex-sdk-js` link. CI just runs `npm ci` — there is no sibling repo to check out. To develop against local `../pipelex-sdk-js` (or `../mthds-ui`) changes, use the Makefile switches — `make use-local-sdk` / `make use-local-ui` (or `make use-local` for both) point the dep at the sibling repo via a `file:` link in every manifest that declares it (the SDK in all three packages, the UI in the console's), and `make use-npm-sdk` / `make use-npm-ui` (or `make use-npm`) switch back to npm; `make check` refuses to run while a `@pipelex` dep in any manifest is a local link (the `check-no-local-deps` guard), so don't commit the link. Bump the `^x.y.z` range once the change is published. `mthds` **is** a direct dependency again, and deliberately: `catalog-write.ts` imports `serializeMethodFiles` / `parseMethodFiles` from `mthds/protocol`, and that module exists precisely so the platform, `@pipelex/sdk` and this server agree on the stored-source shape instead of each re-porting it. It is imported by the core, so the core and the workshop that inlines it both declare it; relying on it arriving transitively through `@pipelex/sdk` would leave the version it resolves to outside the published package's control.
- Keep `SPEC.md`'s declared input/output shapes, the Zod schemas in `capabilities/`, and `docs/tools.md` (the tool-by-tool reference) in sync when a tool contract changes, and the one-line tool table in `README.md` too when a tool is added, removed, renamed or moves between shells. The README stays at the repository root, where it is the repository's front page, and the workshop's `prepack` copies it into the package, so it is the npm front page too: per-host registration lives in `docs/hosts.md`, the development notes in `docs/development.md`, and every link in the README is absolute, because npm renders it where a relative link breaks.

## Versioning & changelog

`pipelex-mcp` ships two servers on two release tracks, each following [Semantic Versioning](https://semver.org) with its own version, its own changelog in the [Keep a Changelog](https://keepachangelog.com) format and its own tag prefix:

| Server | Version (source of truth) | Changelog | Release branch | Tag |
|---|---|---|---|---|
| The workshop, `@pipelex/mcp` on npm | `packages/workshop/package.json` | [`packages/workshop/CHANGELOG.md`](packages/workshop/CHANGELOG.md) | `release/vX.Y.Z` | `vX.Y.Z` |
| The console on Alpic | `packages/console/package.json` | [`packages/console/CHANGELOG.md`](packages/console/CHANGELOG.md) | `release/console-vX.Y.Z` | `console-vX.Y.Z` |

The workshop keeps the plain `v` because it is the published package, and its existing tags, its npm versions and the workspace's release landing all read that form already; the console takes the prefix so that its tags can never be read as the workshop's. Up to and including 0.20.0 both servers shipped together at one version, so a `vX.Y.Z` tag up to `v0.20.0` marks a release of both, and the workshop's changelog carries their joint history; the console's version continues from 0.20.0. The root `package.json` carries no version, and the core's `0.0.0` never moves, since the core is never released. A change to the core belongs in the changelog of each server it changes.

- Work in progress accumulates under each changelog's `## [Unreleased]` — don't mint a new `## [x.y.z]` heading per commit. Mint it (and the tag) only when you actually release that server at that version; the newest versioned heading must then match its `package.json`'s `version`. To cut a release, use the **`/release` skill** (`.claude/skills/release/`): it asks which server ships, promotes that changelog's `## [Unreleased]` to `## [x.y.z]`, bumps that server's `package.json`, regenerates `package-lock.json`, and opens the release PR into `main` that the CI gates expect. Note the version-string split: the `v` and `console-v` prefixes are on the branch name, git tag, and PR title only — never in `package.json` or the `## [x.y.z]` changelog heading.
- `0.1.0` is the first tagged release. It **retires the `v0.x` prototype-increment track** (`../docs/mcp/archive/2026-06-design/02-delivery/v0.x-prototype-plan.md`): the milestones once called v0.1 / v0.2 / v0.3 were build increments, not package versions, and all shipped together as `0.1.0`. Use the changelog + semver from here on, not the v0.x numbering. `../docs/mcp/cold-start.md` remains the cold-start brief for resuming work; the two changelogs are the source of truth for what has shipped.
