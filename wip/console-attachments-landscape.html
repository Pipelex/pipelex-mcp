Can the console see the user's uploaded files?

Host attachment channels on ChatGPT and claude.ai, the MCP standard in flight, and what it would take to lift the hosted console out of pass-through-only.

Shipped — this is now the record of a built feature Recorded 2026-07-30 Sources verified same day Outcome folded back 2026-07-31

BUILT AND VERIFIED 2026-07-31. This document is no longer a proposal. The channel was probed live, designed into SPEC.md, implemented, and smoke-tested against real ChatGPT. Read the sections below as the research that led to a shipped feature — the design sketch in §06 in particular is not what shipped. What actually landed:

  • A dedicated tool, mthds_upload_attachments — not an attachments argument on mthds_prepare_inputs as §06 sketches. The ~305 s URL life forced ingest-during-the-call, which left no pass-through design to weigh against a separate tool; a separate tool also means no binding convention has to be invented (Q1 below dissolves), prepare.ts is untouched, and the console's "pass-through only" property stays a true statement rather than an exception. The returned pipelex-storage:// URIs are filled into the mthds_inputs_template output and handed to mthds_run; mthds_prepare_inputs can be skipped entirely.
  • Registered on the hosted console only — Q5 below is settled the other way round from both options it offers. The host gates substitution on the declared schema, so on the workshop the tool would be structurally unreachable, and advertising it would cost every workshop user tokens on every tools/list.
  • A named attachment fetch boundary shipping with the first fetch (Q2, answered properly): https-only, the required oaisdmntpr host prefix, no redirects, no credentials, a cap enforced before the body is read and again mid-stream, a bounded timeout.
  • A 7 MiB cap, forced by the transport — see the measured box below. Not a product judgement.
  • Live smoke on real ChatGPT passed: unprompted fill, end-to-end to mthds_run, the oversize refusal, and — closing the last open cell — an image on iOS.
TL;DR

The question. Since 0.8.0 the local workshop uploads files, but the hosted console is pass-through only. On chatgpt.com and claude.ai the console is all a user has — and both let people drop a PDF into the chat. Can we get at those files?

  • ChatGPT — yes, and it already works this way today. A tool that declares _meta["openai/fileParams"] receives conversation attachments as { download_url, file_id, mime_type?, file_name? } inside its arguments: a signed HTTPS URL the server fetches. Bytes never enter the model's context. Skybridge 1.3.2 — which we already ship — wraps both halves (FileRef server-side, useFiles() in views).
  • claude.ai — no channel at all. No file id, no signed URL, no host-injected reference ever reaches a connector. Uploads become model context only. The realistic path stays "user pastes an https URL", which our pass-through already accepts.
  • MCP spec — nothing shipped, not even in the brand-new 2026-07-28 revision. The standard-in-waiting is SEP-2631 (authored by OpenAI, under an Anthropic-led File Uploads WG). It is a draft with no committed date.

Why this matters to us. SPEC.md defers console upload explicitly "until a proper out-of-band attachment channel exists." On ChatGPT that condition is now met — and it clears both original objections at once: bytes stay out of the model's context, and BYOK already settled whose storage an upload targets. One bounded increment turns the console into a real file-taking surface on ChatGPT, degrading silently to today's behavior everywhere else.

And we are already shaped for the endgame. SEP-2631 standardizes exactly the pattern mthds_prepare_inputs already implements: upload out-of-band, pass an opaque URI in the tool call. Our pipelex-storage:// design is the thing the ecosystem is converging on, not a detour from it.

01 · Where we wereThe console's pass-through wall

The workshop and the console share one capability core and one tool table; they differ at deliberate seams. For files there are two of them: resolver (who may read a { path } from disk) and allowUpload (who may turn a file-bearing input into storage). The console has neither — it accepts http(s) URLs and pipelex-storage:// references and refuses anything that would need an upload.

That refusal was reasoned, not lazy. Two objections stood behind it, recorded in SPEC.md:

O1Context cost

Inline data: bytes in a tool argument are emitted token by token by the model. That is precisely the cost the workshop's { path } arm exists to avoid — we measured the through-host penalty scaling roughly 100× with bundle size.

O2Whose storage?

An upload has to land in someone's Pipelex storage under someone's key. Before BYOK the console held no per-caller key, so the question had no answer.

O3Never read the server's filesystem

A related hazard we already designed around: handing raw inputs to the SDK's prepareInputs would make it readLocalPath a bare-path value on the server — LFI read, DoS, path-existence oracle on a public endpoint. Hence the console's own pass-through walk.

BYOK (0.5.0) already killed O2. Each console caller now supplies their own plx_sk_ key on the transport. What remained was O1 — and O1 is a statement about inline bytes, not about files as such. A channel that hands the server a reference instead of the bytes does not trip it. That is exactly what we went looking for.

03 · ChatGPTThe mechanism that already exists

A tool opts in by listing its file-typed input fields in _meta. At call time ChatGPT resolves the user's attachment — or even a file the model itself generated at /mnt/data/… — into a concrete file object, shows the user a permission dialog, and only then delivers it to the server. The server fetches the bytes itself over plain HTTPS.

sequenceDiagram
  autonumber
  actor U as User
  participant C as ChatGPT host
  participant M as Model
  participant S as pipelex-mcp console
  participant P as Pipelex API
  U->>C: drops invoice.pdf into the chat
  U->>M: "run my extraction method on this"
  M->>C: tool call mthds_prepare_inputs
  C-->>U: permission prompt "share file with app?"
  U-->>C: allow
  C->>S: args include download_url + file_id
  Note over M,S: the model emitted a URL, not the bytes
  S->>C: GET signed download_url
  C-->>S: file bytes
  S->>P: uploadFile (caller's BYOK key)
  P-->>S: pipelex-storage://...
  S-->>M: prepared inputs, ready for mthds_run

The ChatGPT file-params round trip. The only thing crossing the model is a URL and an id; the payload travels host → server → storage out of band.

That out-of-band property is the whole point, and it is what makes this compatible with objection O1:

Objection O1 was never about files — it was about inline bytes. A reference-passing channel sidesteps it entirely.

The contract, exactly

The schema is rigid, and the app-review "Scan Tools" step enforces it. Each field named in openai/fileParams must declare exactly four properties: download_url (required), file_id (required), mime_type (optional), file_name (optional). Omit one, require an optional one, or add a fifth, and submission is rejected. Arrays are allowed via items. Skybridge exposes this as the FileRef zod schema; on the view side, useFiles() gives a widget upload, selectFiles (ChatGPT's own file-library picker) and getDownloadUrl.

Why we cannot simply tag our existing inputs field

openai/fileParams lists top-level input fields, and each must match the four-property shape. Our inputs is a z.record(z.string(), z.unknown()) whose file-bearing values sit at arbitrary depth, discovered by resolving the pipe's declared signature. It cannot be a file param.

So the increment needs a separate top-level attachments array, plus a convention binding each attachment to an input slot. And that binding cannot live on the file object either — a fifth field like input_key would fail the scan. It has to live on the inputs side, as a marker value the model writes (e.g. "attachment:file-abc123") that we resolve against the array. That indirection is forced by the platform, not chosen by us — worth knowing before anyone reviews the schema and asks why it looks roundabout.

Known defects in the mechanism (all currently open)
  • Mobile is broken — did not reproduce; closed 2026-07-31. The iOS/Android native apps were reported to send placeholder strings — {"images": ["chat_upload"]} or "chat_upload://image_0" — instead of file objects. Reported January 2026, no vendor response. Our own probe did not reproduce this with a PDF on iOS (ChatGPT/1.2026.202, iOS 26.5.2): the attachment arrived as a correct four-field object and fetched fine. The remaining image-on-mobile cell — the exact case the defect reports describe — was then smoked against the shipped tool on iOS and also worked. No mobile-specific handling was built, and none is needed.
  • Duplicate calls. Cases of the same file_id arriving twice with different download_urls; and cases where the permission dialog never appears and the call never lands. Acknowledged by OpenAI support in March 2026, no documented fix.
  • imageIds round-tripping is buggy. Files a view pushes back to the model via setWidgetState({ imageIds }) are documented but reportedly not actually seen by the model. Acknowledged February 2026. Only relevant if we later want a view-side attach flow.
  • Undocumented: download_url TTL, size limits, and permitted MIME types. The docs imply expiry by offering a "mint a fresh URL" call. The TTL is now measured — ~305 s from the tool call (Azure SAS se, confirmed by an observed 403); see the box below. The vendor's own size ceiling is still undocumented and irrelevant to us: it hands over at least 19.6 MB, far more than our upload leg accepts (7.5 MiB, see the ceiling box), so our cap binds first in every case.

MEASURED 2026-07-30 — this section's unknowns are partly resolved. A live probe (throwaway rig on branch probe/openai-fileparams-phase0) confirmed the channel end-to-end on ChatGPT desktop web and iOS — five captures, three Azure regions, 140 KB to 19.6 MB — and corrected several assumptions made here:

  • The TTL is ~305 seconds (5 min) measured from the tool call. The download_url is an Azure SAS URL carrying its own expiry in the se query parameter. Confirmed empirically: 206 at +288 s, 403 at +328 s, bracketing the declared expiry exactly. This settles the design: ingest, never forward. A ~5-minute URL cannot survive to a durable run's workers.
  • The storage host is not files.oaiusercontent.com, and it changes between calls. Two samples from one user, one session: oaisdmntprnznorth.blob.core.windows.net and oaisdmntprkoreacentral.blob.core.windows.net (Azure Blob, x-ms-* headers, server: Windows-Azure-Blob/1.0). The pattern is oaisdmntpr<azure-region>. The "host allowlist" sketched further down is wrong as written. Note the trap: a suffix-only rule (*.blob.core.windows.net) is not safe — any Azure customer can create a storage account there — so the OpenAI-owned oaisdmntpr prefix must be required, and the byte cap and timeout must hold independently of it.
  • Size is not the obstacle we expected. A 19.6 MB PDF passed the handoff untruncated, and pulling the whole file took 6.2 s — 2% of the SAS window. So the expiry will not be what stops a large ingest; our own byte cap and the hosted request timeout will be.
  • The substitution only fires where the model writes a reference. The host rewrites a model-supplied reference into the four-field object; it never injects into a field the model left alone. A first attempt whose tool description told the model not to touch the field produced an empty call and measured nothing.
  • Every tools/call carries openai/* request _meta — including openai/userLocation with latitude/longitude, and stable openai/subject / session / organization ids. The handshake itself is plain. Production must not log this.
  • ChatGPT caches a connector's tool list and never refreshes it. Across a whole probing session it issued initialize four times and tools/call five times — and tools/list zero times, still quoting a tool description that had been deleted from the server. Shipping consequence: a tool-description change does not reach existing users; their connector keeps whatever it cached when they added it. Since the description is load-bearing mechanism rather than documentation (see above), a description defect is effectively not hot-fixable — it needs the same review rigour as the schema, and release notes must tell users to re-add the connector.
  • The four-field schema is a runtime gate, not just an app-review rule. The host will only hand a file to a field whose declared JSON Schema is the four-field object. A deliberately permissive twin tool was never invoked once across the whole session — the model reported being instructed to pass file references only to tools whose schema expects a file parameter. Practical consequence: a "lenient" production schema is not an option, and malformed payloads must be caught at the protocol layer (before validation) rather than by loosening the contract.
  • iOS mobile works with documents. Same two-call pattern as desktop — first call omitted the field, an explicit "pass the PDF in the attachments field" produced a correct object. A schema rejection comes back as an isError tool result whose Zod text the model reads and self-corrects from, so the strict schema is less brittle in practice than it looks on paper.

Both remaining unknowns closed 2026-07-31. The image on mobile cell was smoked against the shipped tool on iOS and works. The ~20 MB ingest timing question turned out to be moot — see the ceiling box below. Full record in TODOS.md.

MEASURED 2026-07-31 — the ingest ceiling is ~7.5 MiB, and the transport picked it, not us. Synthetic byte assets uploaded through the SDK against the live API: 1 / 5 / 7 / 7.3 / 7.4 MiB all succeed (~2.9 s at the top end, ~2.5 MB/s); 7.5 / 7.6 / 8 / 12 / 20 MiB all fail fast with 413. The wall is exactly AWS API Gateway's 10 MiB request quota divided by base64's 4/3 inflation — POST /v1/upload is a base64 JSON body behind an HTTP API integration. The app-level 50 MiB MAX_UPLOAD_MIB is unreachable through the public gateway and must not be quoted as the limit anywhere. Three consequences:

  • Synchronous ingest is comfortably feasible. At the cap: ~2.3 s fetch + ~2.9 s upload ≈ 6 s, against a ~305 s signed-URL window. Timing was never the constraint; payload size is. No async/job design is needed.
  • The byte cap was never a product decision. The console caps an attachment at 7 MiB, leaving headroom for the JSON envelope.
  • Oversize is an ordinary case, not an edge case — ChatGPT hands over 19.6 MB PDFs happily, so users will meet the refusal. It fires before any bytes are fetched, names the limit, and gets a release note. Raising the ceiling means bypassing the gateway for uploads (a presigned direct-upload redesign) — cross-repo, out of scope here.

Same measurement exposed a pre-existing bug in the shipped workshop: mthds_prepare_inputs hit the same wall via a wasted 10 MiB round-trip and a server message that could not name the real limit. Fixed in the same increment with a size-guarded client shared by both upload paths.

04 · claude.aiThe wall, and the tempting workaround

The answer here is a clean no, confirmed from the connector docs, the uploads help article, and the MCP spec itself. Every candidate path is closed:

  MC -.->|"no signed URL"| X1
  MC -.->|"no host-injected reference"| X1

  AR["Artifacts / Projects / Skills"] -.->|"no third-party-fetchable URL"| X1

  UU["User pastes an https URL"] ==>|"WORKS today"| OK2["our pass-through accepts it"]
  SB["Code-execution sandbox holds the file"] ==>|"works, but needs domain allowlisting"| OK3["curl to an upload endpoint"]
  style X1 stroke-dasharray: 5 5

Solid arrows are paths that actually work; dashed arrows are the ones people assume exist and do not.

Two details worth internalizing. First, MCP resources on claude.ai flow server → client only; there is no reverse channel, and Roots — the closest primitive — was formally deprecated in the July 2026 spec, with migration guidance that literally says to pass files via tool parameters instead. Second, the Anthropic Files API does not bridge: it is a platform-API feature, its ids are scoped to the uploading workspace, and user-uploaded files there are not even downloadable by their own owner.

The sandbox-curl workaround, and why we should not build on it

Conversation attachments do land on the code-execution sandbox filesystem, and Claude can curl them out to an HTTP endpoint — so if we exposed an upload route and users allowlisted our domain, files could reach us. This is a documented community pattern, not an Anthropic feature.

Reasons to leave it alone: it requires each user to add our domain under Settings → Capabilities → additional allowed domains (a Team/Enterprise-gated setting, so most users simply cannot); Anthropic's own docs pair that setting with an explicit prompt-injection exfiltration warning; and it depends on undocumented sandbox behavior that can change without notice. It would be an onboarding cliff attached to a security caveat, sold to users as a feature. Not worth it while "paste a URL" works for everyone.

05 · The standard in flightWhy our architecture is already the target shape

At protocol level there is still nothing. Tool arguments remain plain JSON matching inputSchema; resource_link is defined only as a tool result type; elicitation accepts primitives only. The newest revision, 2026-07-28, adds none of it.

The work is real but unlanded. A File Uploads Working Group was chartered in April 2026 — led by Anthropic, with OpenAI at the table — and its current anchor is SEP-2631, "File Objects and Transfer" (open draft, authored by OpenAI). Its design: file inputs are URI strings annotated x-mcp-file, plus a files/authorizeUpload control-plane call that returns an out-of-band upload descriptor so the client pushes bytes over HTTPS and the tool call carries only the resulting URI. An earlier attempt (SEP-2356, data-URI based) was closed in June in favor of it; a still earlier one (SEP-1306, binary elicitation) died in March.

  2026-06 : SEP-2356 closed in favor of SEP-2631
  2026-07 : Spec 2026-07-28 ships without file input : Roots deprecated

Three years of demand, three proposals, nothing in the spec yet. ChatGPT shipped its own in the meantime.

The strategic read: SEP-2631's shape — upload out of band, pass an opaque URI as the argument — is what mthds_prepare_inputs already does with pipelex-storage://. We are not going to have to rethink the tool when the standard lands; we will have to add a second way of filling the same field. That is a good position to be in, and it is worth saying out loud in review: the ChatGPT increment is not a detour, it is the same pattern with a vendor-specific intake.

06 · The incrementWhat it would take, minimally

Superseded by what shipped — read this section as the reasoning, not the design. The sketch below hangs ingest off mthds_prepare_inputs's PrepareContext. The measured ~305 s URL life then removed pass-through from the table entirely, and once ingest had to happen during the tool call, a dedicated mthds_upload_attachments tool was strictly better: no binding convention to invent (Q1), no change to prepare.ts's walk, and the console's "pass-through only" property preserved. The instinct that the change is bounded held; the seam it hangs on did not.

The change is bounded because the seam already exists. PrepareContext is where per-deployment asset policy lives (resolver, allowUpload); this adds a third mode: the console may ingest a host-supplied URL — fetch the bytes and upload them under the caller's BYOK key — while still never touching a filesystem.

Ingest, not pass-through. Handing the raw download_url through to the runner would be a smaller change, but the URL is short-lived and a durable run's workers may fetch it minutes later. Ingesting to pipelex-storage:// at prepare time makes the reference outlive the host's signature. Since measured: the TTL is ~305 seconds (Azure SAS se, measured from the tool call), so this is no longer a judgement call — pass-through is not viable at all.

Open questions for the design session — all five answered; each card carries its resolution

Q1The binding convention

How does the model say which attachment fills which input slot? A marker string ("attachment:file-abc") is the obvious candidate, but positional or filename matching are alternatives. Whatever we pick has to be explained in the tool description well enough that the model gets it right unprompted.

Dissolved, not answered. A dedicated tool returns pipelex-storage:// URIs, which are already ordinary pass-through values — the model fills them into the inputs template like any other string. No convention exists to get wrong.

Q2SSRF surface

We would be fetching a caller-supplied URL from a public endpoint. That needs a host allowlist, a size cap, and a timeout — the same care we took with readLocalPath, applied to the network instead of the filesystem. Corrected 2026-07-30: this paragraph originally named files.oaiusercontent.com as the host to allowlist. The measured host is oaisdmntprnznorth.blob.core.windows.net — Azure Blob, apparently region-scoped — so a literal host allowlist would both fail legitimate users and be weaker than it looks. Re-derive around a suffix rule, and lean on the byte cap, the timeout, and a no-cross-host-redirect policy for the real defence.

Do not ship the fetch without the allowlist. An unrestricted server-side fetcher on a public MCP endpoint is a worse hazard than the filesystem read we already refused.

Answered — and the suffix rule this card proposes is unsafe. Any Azure customer can create a storage account under *.blob.core.windows.net, so the OpenAI-owned oaisdmntpr prefix is required, never optional. Shipped as a named boundary in its own module: https-only, the host pattern, no credentials in the URL, no non-default port, redirects refused outright, the 7 MiB cap enforced from content-length before the body is read and again mid-stream, a bounded timeout, no headers sent. The advice to lean on the cap and timeout was right and is now doctrine — the prefix is undocumented vendor infrastructure, so the host check is a filter, not the defence.

Q3Failure texture for broken hosts

ChatGPT mobile sends placeholder strings. That must classify as an instructive input_domain at attachments — telling the user to try desktop — rather than surfacing as a fetch error.

Answered: nothing to build, and it could not have been built as written. The premise did not reproduce — iOS works with both documents and images. And a malformed payload never reaches the capability layer at all: the MCP SDK rejects it at its own boundary, surfacing to the model as an isError result carrying the raw validation text, from which the model was observed to self-correct on the next call. Loosening the schema to catch it is not an option either — the host would then never populate the field.

Q4Does mthds_run get it too?

mthds_run also takes inputs. Leaning no: keep one door for file intake so the prepare → run sequence stays the single story we teach.

Answered: no, and the lean was right for a better reason than it knew. Ingest is its own tool, so mthds_run needed no change whatsoever — it receives storage URIs like any other input value.

Q5Workshop posture

The schema is shared, so attachments exists on the workshop too. Simplest: ignore it there (no host populates it over stdio). Alternatively accept it — the workshop can already upload — for one uniform behavior.

Answered: neither. The tool is not registered on the workshop at all — the first documented exception to "both shells register the same table". The host gates substitution on the declared schema, so there the tool is structurally unreachable, not merely unused; advertising it would spend every workshop user's tokens on every tools/list for a capability that cannot fire. The invariant that survives: no tool name means different things on the two shells.

07 · Scope disciplineWhat we are deliberately not doing

  • No sandbox-curl intake on claude.ai. Allowlist-gated, injection-adjacent, undocumented. Users keep pasting URLs until the standard lands.
  • No view-side attach flow yet. useFiles() would let a widget run its own picker, but the imageIds round-trip is a known-broken path and views are ChatGPT/Cowork-only anyway. Tools-first.
  • No speculative SEP-2631 implementation. It is a draft that already replaced one predecessor. We adopt when it lands in a host.
  • No change to the pass-through contract. http(s) and pipelex-storage:// keep working exactly as they do; attachments are an additional intake, not a replacement.

If we take the increment, SPEC.md's Non-Goals paragraph on deferred console byte-upload needs rewriting rather than deleting: the deferral was conditional, the condition is now met on one host, and that nuance is the thing worth preserving in the record.
