# Pipelex MCP

This specification states one contract, the workshop's. The first sections say what the product is and how it stands beside the hosted Pipelex connector, a separate product; "The workshop's contract" then states its tools, shapes and behaviour.

## Value Proposition

Pipelex MCP lets people reach their Pipelex methods from inside an MCP host. It ships as **the workshop**, the Pipelex plugin's local stdio server (server name `pipelex-plugin`, npm `@pipelex/mcp`), for coding agents such as Claude Code, Codex and Cursor. Its tools are `mthds_*`, and besides naming a method by reference it takes a method as files on disk, which is what writing, repairing and integrating one needs.

The target user is a developer, or the coding agent working for them, who is authoring a method, repairing it, integrating it into a codebase or running it from the project it lives in. Before the workshop existed, validating a method meant leaving the assistant flow, knowing the local OSS `pipelex-api` or the SDK, and mapping diagnostics back to file content by hand.

Core actions:

- List the saved methods visible to the API key's organization (`mthds_list_methods`) as bounded, source-free catalog metadata, so an assistant can resolve a user's name or intent to a canonical `method_id` without leaving the conversation.
- List the files the organization already holds (`mthds_list_files`): its members' uploads, the test inputs made for a method and its runs' final outputs, newest first, each with its `pipelex-storage://` address, so an assistant can run a method on "the invoice uploaded this morning" by putting that address in the run's inputs, with nothing to upload.
- Validate a method given as files, a published address or a catalog id (`mthds_validate`), returning valid, invalid, pending-signature and no-verdict failure states in a stable structured result the assistant can use to fix issues.
- Look up the model references a method's pipes can name (`mthds_models`): list the deck's presets, aliases and waterfalls by category, or check one reference before it is written into a method, with the nearest names and the right sigil when it does not resolve. This gives the CLI-free skills in `../pipelex-plugins` what `mthds-agent models` and `mthds-agent check-model` used to.
- Project a pipe's declared inputs as a fill-in template (`mthds_inputs_template`), so an assistant can prepare inputs for a run without leaving the conversation. This unblocks the CLI-free skills in `../pipelex-plugins` (`pipelex-inputs`, `pipelex-design`) that used to shell out to `mthds-agent inputs bundle`.
- Generate typed code for a method (`mthds_codegen`): project its concept set into typed models — TypeScript (`ts-zod`) or Python (`python-pydantic`, `python-structures`), the target chosen from the project's context — stamped and locked by the Pipelex codegen engine, so an assistant working in a project writes the generated files and the lock verbatim and the offline check passes on the tree. Passing `output_dir` writes that tree straight into the project, so the bytes never enter the conversation at all.
- Prepare a pipe's *filled* inputs for a run (`mthds_prepare_inputs`): upload file-bearing values (local paths, `data:` URLs, bytes) to Pipelex storage and rewrite them to `pipelex-storage://`, so the inputs are run-ready, using the user's key, and record the uploads as the organization's files or as the method's test files. The method is named the same ways as everywhere else, so a **published** method with a file-bearing input now has a path to a run that does not require every asset to already be a URL.
- Start a durable run of a method on the hosted Pipelex API (`mthds_run`), then check on it and how far it has got (`mthds_run_status`) and report its results (`mthds_run_results`) and show its pictures (`mthds_show_images`) by durable run id — the run outlives any single tool call and even the conversation.
- Save a completed run to disk (`mthds_download_artifacts`): the main output verbatim as `main_stuff.json`, and every `pipelex-storage://` reference in it resolved to a fresh link through the API and saved beside it, under `runs/<run_id>/` in the server's working directory by default. This is the download counterpart of `mthds_prepare_inputs` — the output and a generated image or PDF land where the user is, instead of living in the conversation or behind a presigned link that expires within the hour.
- Carry a bundle between the workspace and the organization's catalog (`mthds_save_method`, `mthds_get_method`, `mthds_publish_method`): save the files on disk as a method's draft, creating the method or writing the draft of the one the directory is linked to; bring a saved method's draft, or one of its published versions, back; and, when the user asks for it, publish the draft as the method's next version.

## Why LLM?

**Conversational win**: The user can say "validate this method" while the assistant already has the relevant file contents and can immediately iterate on fixes.
**LLM adds**: The assistant can choose the files to submit, explain validation results, modify source content, and repeat validation until the bundle is usable.
**What LLM lacks**: The assistant does not have Pipelex validation semantics, access to local OSS `pipelex-api`, or structured verdicts such as pending signatures, validation errors, and graph specs. It also cannot resolve a pipe's effective input contract (needs of the pipe minus what upstream pipes produce) — that projection is computed by the API from the parsed closure.

## Product Context

- **Existing products**: Pipelex, MTHDS, `@pipelex/sdk`, and the Pipelex API (local OSS `pipelex-api` during development).
- **Server**: `pipelex-mcp` is one package at its root that builds the workshop, a plain MCP-SDK stdio server published on npm as `@pipelex/mcp`, over a capability core. The core (`src/capabilities/`) holds the API calls, the projections, the problems it relays and builds, the run lifecycle and the image walk. The workshop owns its tool table, its schemas and its descriptions (`src/tools.ts`) and its instructions (`src/server.ts`).
- **Runtime API**: the hosted Pipelex API, defaulting to `https://api.pipelex.com` (point `PIPELEX_BASE_URL` at a local OSS `pipelex-api` on `http://localhost:8081` during development).
- **SDK dependency**: the `@pipelex/sdk` npm package (`PipelexApiClient`, published from the `js/` directory of `Pipelex/pipelex-sdk`). It re-exports the `mthds/protocol` surface, so the MCP imports one SDK and still reaches the open protocol routes. `mthds` is also a direct dependency, for `mthds/protocol`'s stored-source helpers and its inputs-template projection.
- **Auth**: the workshop reads a `plx_sk_` platform key from `PIPELEX_API_KEY` in the host-supplied process env, and when the host passes none, from the key saved in the home `.env` (`~/.pipelex/.env`, the file the workshop's own `login` command writes, as `pipelex login` does), read afresh on every tool call; against a local runner started without authentication its files-based validation, inputs template and codegen calls work without one, while the catalog, every `method_id` call and the run family need one, and a missing or invalid key is a no-verdict carrying the credential problem (`auth.missing_credential` or `auth.invalid_credential`), whose summary says which key was sent and names the command that saves one, `npx -y @pipelex/mcp@latest login` (see What the workshop registers).
- **Primary environment variable**: `PIPELEX_BASE_URL`, defaulting to `https://api.pipelex.com`.

## The workshop and the Pipelex connector

This document is the contract of the workshop, the MCP server published to npm as `@pipelex/mcp`, which reports the server name `pipelex-plugin`. The hosted Pipelex connector for chat hosts, reached at `https://mcp.pipelex.com/mcp`, whose tools are named `pipelex_*`, is a separate product with its own contract, and nothing in this document specifies it.

A host needs one of the two, not both: a chat host takes the connector, and a coding agent takes the workshop through the Pipelex plugin. A Claude user with the plugin can still find both in one session, since a claude.ai connector syncs into Claude Code. Their tool names do not collide, and the workshop's instructions tell the model to use its `mthds_*` tools for all method work whenever the connector's `pipelex_*` tools are also present, and never to mix the two servers: each can be signed in to a different organization. For the same reason, a method saved from the workshop is visible from the connector only when the workshop's key and the connector's sign-in select the same organization.

## Naming Conventions

Tools are the contract; the `../pipelex-plugins` skills are the manual. The naming follows that split:

- **Server name: `pipelex-plugin`.** The workshop reports `pipelex-plugin` in the `initialize` handshake, following the public words "the Pipelex plugin". The workshop's name is slightly off when it runs outside the plugin, through `npx` in Cursor, and that is accepted; `pipelex-workshop` was rejected because a server name can appear in a host's server list, where "workshop" is not a public word. The flattened tool names a host shows come from the key the server was registered under, not from the handshake name: the plugin registers the workshop as `pipelex`, so Claude Code shows `mcp__plugin_pipelex_pipelex__mthds_validate`, and a hand registration chooses its own key (the snippets in `docs/hosts.md` use `pipelex`, which yields `mcp__pipelex__mthds_validate` on Codex).
- **Tool names: `mthds_<stem>`, snake_case.** The workshop keeps the `mthds_` prefix its tools always had, because the plugin's skills call them verbatim (`allowed-tools` pins included). The workshop's catalog tools (`mthds_list_methods`, `mthds_save_method`, `mthds_get_method`) are Pipelex services rather than MTHDS-language tooling, so a strict reading of the brand rule would rename them; they keep `mthds_*` deliberately, since a `pipelex_*` name would match the connector's tools and put one name on two servers that can be signed in to different organizations. A prefix stays on every tool even where the server's own key could be argued to cover it: some hosts display or match bare tool names, and generic verbs (`validate`, `run`, `upload`) collide across servers in a multi-server session.
- **Lifecycle families share a stem prefix** — `mthds_run`, `mthds_run_status` and `mthds_run_results` sort and display adjacently, so hosts and models see them as one family.
- **Names state what you get** — a noun-only name must name the artifact it returns (`mthds_inputs_template`, renamed from the ambiguous `mthds_inputs`); otherwise lead with the operation (`mthds_validate`).
- **Catalog listing is deliberately `mthds_list_methods`** — the repeated English word is acceptable: the prefix is the stable product-family prefix, while `list_methods` is the clearest operation/resource stem and stays recognizable when a host displays the bare tool name. The files listing, `mthds_list_files`, follows it, so the two listings sort and read as one family.
- **The file-moving tool leads with its direction** — `mthds_download_artifacts` (a run's produced files come *down* to disk) names the direction and the thing moved, and does not borrow the run family's `_run_` stem even though it is keyed on a `run_id`: a noun-only `mthds_run_artifacts` would read as a listing, and "names state what you get" wins over family adjacency.
- **Parameter names mirror the route each tool wraps.** The same pipe selector is `pipe_ref` on `mthds_inputs_template` and `mthds_prepare_inputs` (`POST /v1/pipe-io` and the SDK's `prepareInputs` say `pipe_ref`) and `pipe_code` on `mthds_run` (`/v1/start` says `pipe_code`); both take the same qualified `domain.pipe_code` value. This is the workspace convention applied — `_code` is the default and may be qualified, `_ref` is reserved for where "always namespaced" genuinely matters — and neither name is wrong under it, so neither is renamed away from its route. What the surface owes the caller is that the two names must not surprise it: each parameter's description names the other tool's parameter as the same value, so an agent copying a pipe selector from the template call into the run call is told it can.
- **Tools are self-sufficient; the dependency on skills is one-way** — tool names, descriptions, and the server `instructions` never reference the plugin skills, because many consumers (hosts that run the workshop without the plugin, and raw MCP hosts) will never see them. The skills reference tool names verbatim, and where a skill is the manual for one tool the two share a stem (`pipelex-inputs` ↔ `mthds_inputs_template`); that side of the convention is recorded in `../pipelex-plugins/docs/decisions.md`.

## The workshop's contract (`pipelex-plugin`, the Pipelex plugin's server)

### What the workshop registers

The workshop is an npm-distributed stdio server (`@pipelex/mcp`, bin `pipelex-mcp`) that the Pipelex plugin spawns via `npx` on Claude Code and Codex, and that coding-agent hosts without the plugin (Cursor, Cowork-as-builder) are registered to spawn by hand. It is built on the plain MCP SDK (`McpServer` + `StdioServerTransport`) over the capability core. Auth is a per-user `plx_sk_` platform key, supplied as `PIPELEX_API_KEY` through the host's MCP server config env or saved in the home `.env` by the login — per-user auth for free. The key determines the active organization and therefore the entire visible catalog.

**Where the key comes from.** The workshop decides its key and base URL at the start of every tool call. A non-empty `PIPELEX_API_KEY` from the host is used with the environment's `PIPELEX_BASE_URL`, or the hosted API, and nothing else is read: a key a user typed into a host's configuration means what it says. When the host passes none, or passes it empty, the workshop reads the home `.env`, the file its `login` command writes, as `pipelex login` does: `.env` in `PIPELEX_HOME` when that is set and not empty, else `~/.pipelex/.env`. The file's `PIPELEX_API_KEY` is the key, and its base URL is the environment's `PIPELEX_BASE_URL` when set, else the file's, else the hosted API, so a key saved beside a development base URL is sent there and not to production. A base URL in the file applies only with the file's key: it never redirects the host's key, and a call with no key in either place goes out keyless to the environment's base URL or the hosted API. An empty value counts as unset, in the environment and in the file alike. The file is read afresh on every call and never cached, so a key saved while a session runs is used from its next call with no restart, and a file that cannot be read counts as holding no key. `PIPELEX_HOME` must be an absolute path or start with `~/`: a relative value is refused, and the file is then not read. The working directory's `.env` is never read either. Both rules exist because the working directory is the project the host spawned the server in, so a credential or a base URL taken from there would let a cloned repository decide where the user's bundles and inputs are sent. A credential failure is the problem the platform or the SDK reports (`auth.missing_credential`, `auth.invalid_credential` or `auth.credential_expired`), relayed as is, and its Markdown adds which case it is, naming the API by its origin alone: no key anywhere, the file unreadable or `PIPELEX_HOME` relative, the host's key refused, or the saved key refused, each with the command that saves a key, `npx -y @pipelex/mcp@latest login` (see Verdicts and errors). Every failure the base URL can cause (an unreachable API, a route the deployment does not serve, a capability it lacks, a base URL the client refused, a credential refused) adds a sentence naming the API in use by its origin and where its base URL was set: by the host's `PIPELEX_BASE_URL`, to be fixed in the host's configuration; by no one, so the hosted API, with the variable that names another; or by the file beside the saved key, naming the file and saying that a `PIPELEX_BASE_URL` set in the host's configuration overrides it.

**Saving a key.** The package's bin has one subcommand, `login`, always given as `npx -y @pipelex/mcp@latest login`, since a copy `npx` cached before the command existed ignores the argument and starts the server. A first argument of `login` always runs it, and any other argument list starts the stdio server. The browser flow listens once on `127.0.0.1` and opens the Pipelex app's `/auth/cli` page (`PIPELEX_APP_URL`, from the environment or the home `.env`, else `https://app.pipelex.com`), which mints a key for the signed-in account's current organization and hands it back to the listener with the login's `state`, which must match; the login waits up to five minutes, reporting each refused callback, one that arrives while the browser is still being opened included, and when no key arrives it says that a key the page may have minted went unused and should be revoked. The link is printed first, naming `--paste` for SSH and containers, and where the opener is `xdg-open` it is launched only when `DISPLAY` or `WAYLAND_DISPLAY` is set, as Python's `webbrowser` does, so a session with no display says no browser could be opened. `login --paste` reads a key created in the app from a terminal instead, without showing it, and refuses a standard input that is not one. Either way the key must start with `plx_sk_`, is checked with `GET /v1/me` against the base URL a call pairs with a saved key (the environment's `PIPELEX_BASE_URL`, else the file's, else the hosted API, the line saying so naming the file when it is the file's), and is saved as `PIPELEX_API_KEY` in the home `.env`, every other line kept and the file written whole at mode `0600`. When the base URL the key was checked against differs from the one the file alone yields (its own, else the hosted API), it is saved beside the key in the same write, and the success message says so, naming the API by its origin alone and saying that a host that does not pass the shell's environment, which reads the file alone, and the pipelex CLI, which loads that file over its environment, now send the key to it, a sentence that stays true when the key could not be checked. The comparison is made with the checked base URL as the file reads at the save, so a `PIPELEX_BASE_URL` another program wrote in the file during the check is put back to the one the key was checked against; with no `PIPELEX_BASE_URL` in the environment and no such change, nothing about the base URL is written. A key the API refuses, read from the problem's code (`auth.missing_credential`, `auth.invalid_credential` or `auth.credential_expired`, which the SDK also reads a bare `401` or `403` as), is not saved, and a browser login then says the key it received went unused and should be revoked in the app; one it could not check is saved with a warning, and the key is never printed. A relative `PIPELEX_HOME`, a home `.env` the login could not write, a base URL the key would be checked against that is not host-only (an http or https URL with no path, credentials, query or fragment, the rule the API client holds a base URL to, whether the environment or the file sets it), or a `PIPELEX_BASE_URL` to save beside the key that a `.env` file cannot hold unquoted, is refused before any key is minted, naming where the value was set. The command exits `0` when the key is saved (and on `--help`), `1` when nothing was saved, `2` on any argument other than `--paste` or `--help`, and `130` on an interrupted prompt.

The workshop registers, in this order: `mthds_list_methods`, `mthds_list_files`, `mthds_models`, `mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`, `mthds_run`, `mthds_run_status`, `mthds_run_results`, `mthds_show_images`, `mthds_download_artifacts`, `mthds_save_method`, `mthds_get_method` and `mthds_publish_method`. It is the server for building and integrating a method: every method-taking tool takes the method's folder (`method_dir`) and `files` beside the two selectors, it reads the working directory the host started it in, and it writes into it. Its instructions say that its `mthds_*` tools are the ones to use for all method work when the connector's `pipelex_*` tools are present too (see The workshop and the Pipelex connector).

**It registers no views.** Tools-first is the empirically verified V1 posture: view-rendering workshop hosts penalize localhost asset origins, and the text summaries carry the flow on their own in text-only hosts. None of its results carries the graph or the form's artifacts on `_meta`, and `available_view_specs` is always empty on every tool that declares it. The text summaries carry the whole flow, and the one picture a builder needs, the method's flowchart, reaches them as a file: `mthds_validate` writes it into the method's folder or beside the `{ path }` files it validates, as a standalone HTML page (see The method graph page).

Three of its tools turn on the working directory:

- **`mthds_download_artifacts`.** It saves a run — its main output and its produced files — under the server's working directory (see Artifact Download Scope).
- **`mthds_save_method` and `mthds_get_method`** (see Catalog Write Scope). The filesystem is not optional on either side of these two: the save reads the method's folder from disk and finishes by writing the link file, `.pipelex/method.json`, that makes the next save an update rather than a duplicate, and the get exists to bring a method's tree to disk.

**Client identification.** Every request the workshop sends to the Pipelex API names this server in its `User-Agent`, so the platform attributes it to the `mcp` surface and records the AI host behind it: `pipelex-mcp/<version> (workshop; host=<name>/<version>) pipelex-sdk-js/<v> node/<v> (<os>; <arch>)`, where the host is the `initialize` handshake's `clientInfo`, sanitised to header-safe characters and read when each tool call builds its client. The server passes this as the SDK's `appInfo` through one client factory, and a lint rule refuses any other way of reaching the API. The header is analytics only and never gates anything. The product token is `pipelex-mcp`, whatever name the server reports in its handshake. `docs/client-identification.md` has the sanitising rule, the guard and what it does not catch.

### Method Selectors (`method_dir` / `files` / `method_ref` / `method_id`)

Every method-taking tool selects the method it operates on in one of these forms, stated once here so the per-tool sections carry only their own mechanics: a folder or files, which the workshop reads and sends, or an address or an id, the platform's addressing contract, which the server resolves. The method-taking tools (`mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`, `mthds_run`) take every one of them.

- **`method_dir`** — the method's folder on disk, the form to prefer for a method there: the workshop sends the folder's whole tree, every file the MTHDS standard's membership rule keeps, its templates, Python modules and data beside its `.mthds` files, and lists every file it sent in the result's `files_sent`, so none can be forgotten and none slips in unseen (see The method folder). It is a separate top-level argument, not a third arm of the files union, since a folder is not a file.
- **`files`** — the method's files, listed: the submitted-files shape (`{ content, uri? } | { path }` — see The files union), sent as one tree in which each `{ path }` item keeps where it sits relative to the others, the template files its `PipeDocGen` steps name among them (see Template files), and listed in `files_sent` as well.
- **`method_ref`** — a published method's address: `github.com/<owner>/<repo>[/<selector>][@<tag>]`, e.g. `github.com/Pipelex/methods/documents@v0.1.0`. Resolved **server-side by the runner**: the repository is fetched at the tag, the package is located by manifest identity, and the resolved commit SHA is recorded — no bundle ever enters the conversation. The registry form (any non-address reference) is reserved and answers `501`.
- **`method_id`** — a registered method's hosted catalog id (`mt_…`), org-scoped, from `mthds_list_methods`. Resolved server-side by the hosted platform wherever the platform supports it, and always requires a credential. It may carry a version suffix: a bare `mt_…` names the method's latest published version, `mt_…@<n>` version n, and `mt_…@draft` its draft (see Method versions, below).

Two uniform rules govern how the selectors combine — there is no per-tool precedence folklore:

1. **Tooling tools (`mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`): exactly one selector.** Give a folder, files, an address, or an id — never several. A second selector is an instructive no-verdict, a `client.argument_invalid` problem whose `reason` is `mutually_exclusive` (mirroring the API's own 422), located at a fixed field for each pair whichever came second: `files` beside a folder is refused at `method_dir`, `method_ref` beside a folder or files at `method_ref`, and `method_id` beside any of the others at `method_id`. A pairing with a folder is refused before the folder is read. These operations are stateless: there is no Run row, so "linkage" has no referent, and an extra selector could only be ignored — the worst contract of the three. This retires the old "files win, `method_id` is ignored" behavior, which was exactly the folklore the rule replaces.
2. **`mthds_run`: a folder or inline files win, and `method_id` beside them demotes to run-history linkage.** `files` + `method_id`, or `method_dir` + `method_id`, is legal — the files run and the id is recorded on the platform's Run row (the webapp's "run the editor's unsaved buffer, file it under its method"). A folder and files never pair: `method_dir` + `files` is refused at `method_dir`. `method_ref` is a complete run source of its own and pairs with **nothing**: `method_dir` + `method_ref`, `files` + `method_ref` and `method_ref` + `method_id` are all rejected — an address run carries its own provenance and needs no linkage id.

Where each selector is accepted, and who resolves it:

| Tool | `method_dir` | `files` | `method_ref` | `method_id` |
| --- | --- | --- | --- | --- |
| `mthds_validate` | yes — read by the workshop | yes | yes — server pass-through (`POST /v1/validate` resolves it) | yes — server pass-through (the hosted platform resolves it; hosted-only) |
| `mthds_inputs_template` | yes — read by the workshop | yes | yes — server pass-through (`POST /v1/pipe-io` resolves it) | yes — server pass-through (the hosted platform resolves it; hosted-only) |
| `mthds_codegen` | yes — read by the workshop | yes | yes — server pass-through (`POST /v1/codegen` resolves it) | yes — server pass-through (the hosted platform resolves it; hosted-only) |
| `mthds_prepare_inputs` | yes — read by the workshop | yes | yes — server pass-through (`POST /v1/pipe-io` resolves it) | yes — server pass-through (the hosted platform resolves it; hosted-only) |
| `mthds_run` | yes — read by the workshop | yes | yes — server pass-through (`POST /v1/start` resolves it; provenance returned) | yes — server pass-through (native on `/v1/start`) |

#### Method versions, on two platforms

A saved method has a **draft**, which every `mthds_save_method` writes and which may be invalid, and **published versions**, numbered from 1, immutable, and made only by `mthds_publish_method`. The method-taking tools accept every form of `method_id` above. On `mthds_run`'s linkage form (a folder or files beside `method_id`) the id must be bare, since the files are what runs and a suffix would claim a version that did not; the workshop refuses one there before the wire, as the platform would with a 422. The catalog tools address the method itself rather than a content: the save and the publish take the bare id, read `@draft` as the same thing, and refuse a version, and the pull reads the draft for a bare id and version n for `@n` (see Catalog Write Scope).

**The workshop is released before every platform resolves the suffix**, so it is right on two. It reads `GET /v1/version` and looks for `method_versions` in its `extensions` (`src/capabilities/method-versions.ts`):

- **On a platform that lists it**, a bare id reads the latest published version, or is refused with a 409 `method_not_published` for a method never published.
- **On one that does not**, a bare id reads the method's stored content, which is its draft, and a suffixed id is refused: the run route's body pattern refuses the `@` with a 422 `validation_failed` naming `method_id`, and the tooling routes look the id up literally and miss it with a 404 `not_found`.

**Every selector is sent exactly as given, on both.** The workshop never rewrites a selector or refuses one by its own reading of the platform, because that reading can be stale while a release reaches the platform's tasks unevenly: `@draft` rewritten as the bare id would then read or run the latest published version, and every method existing when the platform started resolving versions was published as version 1, so that version almost always differs from an edited draft. A platform that does not resolve a suffix refuses it loudly, and the refusal is read by what such a platform sends, as the SDK reads it: a miss (`pipelex.catalog.not_found` of anything but a version, or `request.not_found`, a `404` with no problem document) and a `422` the SDK could not read (`client.response_unreadable` with that status, how the run route's body pattern refusing the `@` reads) contradict nothing, since a platform that resolves suffixes also misses a method that does not exist, and leave the memory alone. For an addressed suffix the answer in memory, or one asked then, decides the note the workshop adds to the problem's `message`, its code, domain and retry staying the platform's: none where suffixes resolve, the explanation that the platform does not resolve suffixes yet and that a bare id reads the draft there where they do not, a hedge where the workshop cannot tell. Any other refusal says nothing about the suffix. The answer itself is asked only for a bare id whose result says what it read, and for that note, and a bare id's is asked beside its request, never before it: what is sent never depends on it, so only the result's closing sentence waits for it. Awaited first, it held every bare-id request for a handshake, up to the deadline, where the platform does not resolve versions and so never caches its answer.

The answer lives in one memory the server's tools share, one answer per base URL, since the workshop decides its base URL on every tool call (see What the workshop registers) and one platform's answer must never stand for another's, and only `supported` is kept, for ten minutes. `unsupported` is asked afresh by every call that depends on it, because it is the answer that goes stale misleadingly: once the platform resolves suffixes, a bare id reported as the draft is the published version, for as long as a cached `unsupported` was believed. A fresh handshake narrows that window to the time between the handshake and the request, which a rolling deploy can stretch while old and new platform tasks answer side by side; a run's acknowledgement catches it there, and a tooling route has no such answer to check. A failed handshake is never cached either, and one that misses its three-second deadline is released the moment it answers `unknown`, so the next call asks again while the late request is still running. A run acknowledgement that names a version, and a refusal only a resolving platform sends (`pipelex.catalog.not_published`, or `pipelex.catalog.not_found` of a version), prove `supported`; a run by bare id whose acknowledgement names no version drops it, which only a platform that does not resolve versions sends, so the tooling tools stop reading that bare id as `latest` the moment a run has shown it runs the draft; a handshake that was in flight across either cannot restore it. The handshake is never asked for an opaque id, a suffix, or a run by bare id, whose acknowledgement says which version ran. This mirrors the webapp's own capability check without its per-instance concerns, since one workshop process serves one user; the webapp, which holds the draft's source, sends it inline where the platform does not resolve `@draft`, and the hosted console sends the selector as the workshop does.

**Every by-id result says which content it read or ran**, in a field and in a closing sentence. The tooling tools carry `method_version`: a version number, `"draft"`, or `"latest"` for a bare id on a platform that resolves versions, since their routes do not say which number they read; for a bare id this server could not place, the field is absent and the sentence says it could not tell. `mthds_run` carries the acknowledgement's `method_version` (a number, or `"draft"`), and `"draft"` when the acknowledgement names none, which is how a platform that does not resolve versions answers. An accepted suffix ran what it named even when the acknowledgement names no version, since a platform that does not resolve suffixes refuses them before a run exists. `mthds_run_status` carries `method_version` when the platform records it.

**The version failures** are the platform's problems, relayed as it sends them. A bare id of a method never published is a 409 `pipelex.catalog.not_published`, to which the workshop's note names the method's own `mt_…@draft` and a publish, the latter only when the user asks for one. A version the method never had is a 404 `pipelex.catalog.not_found` whose `params.resource` is `version`. A method whose erasure is running and a stale draft token are refused by the platform under its own codes, the stale token at the token field of the route that took it (`expected_updated_at` on the save, `expected_draft_updated_at` on the publish), as `pipelex.catalog.update_conflict`.

**Nothing is expanded client-side.** Every selector in the table but the folder and the files, which the workshop reads and sends as a tree, is resolved by a server. `mthds_inputs_template` and `mthds_prepare_inputs` both read `POST /v1/pipe-io`, which takes every selector on the hosted API — the template tool directly, the preparation through `@pipelex/sdk`'s `prepareInputs` — so neither expands a catalog id into files through the SDK's `getMethodClosure` any more, as both did while they read routes that took no `method_id`.

**Verdict discipline on selector resolution.** A selector-resolution failure — an unknown or foreign-org `method_id` (404), a `method_ref` that does not parse or cannot be fetched (422), no package matching the address (404), an ambiguous address (422), either refusal from the execution-locus gate (a `501` or a `422` — see below), a registry-form ref (501) — is a **no-verdict** `status: "error"`, never `is_valid: false`, which stays reserved for a verdict about actual MTHDS content. Each failure is the server's problem, relayed as is with the location the server gave it. A runner too old to serve a route — the case on `POST /v1/pipe-io`, the route of `mthds_inputs_template` and `mthds_prepare_inputs` — answers a bare 404, which the SDK reads as `request.not_found`, and the Markdown then names the API in use and where its base URL was set.

**The execution-locus gate's refusals are the runner's own problems.** The runner decides where caller-supplied Python would execute, and refuses on two grounds, each under a registry `code`: a method shipping *any* `.py` is refused by a deployment that is not sandbox-hosted (`pipelex.deployment.custom_code_requires_sandbox`, a `501`), and a package declaring `StructuredContent` subclasses is refused on every hosted deployment (`pipelex.deployment.python_structures_refused`, a `422`) because structures import into the runner's own process. The workshop relays both as the runner sent them, with the runner's domain, retry and next step, and never reads them as a route the deployment lacks nor as a credential failure. The two differ in what the caller can do: a structures refusal is fixed only by expressing the types as MTHDS concepts, while custom Python is legal MTHDS and the same method runs on a sandbox-hosted deployment. `mthds_save_method` reads either code on its validation as no reason to refuse the save (see Catalog Write Scope).

**Which routes apply the gate, and which do not.** A selector resolved through `POST /v1/validate` or `POST /v1/start` travels `fetched_method_source`, which loads the package's non-`.mthds` files, so the gate applies — `mthds_validate` and `mthds_run`. `POST /v1/codegen` and `POST /v1/pipe-io` resolve an address through `fetch_method_mthds_files`, which takes only the `.mthds` files and loads no Python, so no execution locus is ever decided and the gate cannot fire — `mthds_inputs_template`, `mthds_codegen` and `mthds_prepare_inputs` therefore answer an address that the other tools refuse. `/v1/start` also applies the gate to a submitted tree and to a stored method's injected source, which is why the locator follows the request shape rather than always naming `method_ref`. A tree sent from a folder carries the method's Python modules with its `.mthds` files, so a folder holding Python meets the gate at `method_dir` on a deployment that is not sandbox-hosted, where a `.mthds`-only request used to pass.

**Availability.** `method_ref` resolution is served by any pipelex-api ≥ 0.21.0 deployment, bare or hosted. On `api.pipelex.com`, hosted `method_ref` support and the tooling-route `method_id` selector land with the platform deploy the addressing campaign tracks as its Checkpoint 3; until that deploy is live, a selector-shaped call there answers a no-verdict error rather than a verdict, and the tools surface it as such.

### Verdicts and errors

A *produced* verdict is always `status: "ok"`, whatever it says about the method: a tool that judges a method discriminates on `is_valid` (and, where it matters, `is_runnable`), the run tools on `state`, and a walk over several items on its own completeness flag. A successful catalog page is `status: "ok"` with no `is_valid` field, since a listing is not a verdict about a method. `status: "error"` is reserved for **no verdict could be produced** — a bad request shape, an unreachable or misconfigured API, a runtime fault — and says why in one member, `problem`.

**`problem` is the MTHDS problem document in the caller's view.** It is the RFC 9457 problem the MTHDS protocol defines: `type`, `title`, `status` when an HTTP answer gave one, `detail`, `code`, `domain` (who must act: `input`, `method`, `account`, `operator` or `runtime`), `retry` (`no`, `yes`, or `outcome_unknown` when the operation may already have taken effect), `retry_after` beside a `retry` of `yes` when the server gave one, `next_step` (`{ kind, detail }`, its kind one of the protocol's closed list, such as `change_input`, `check_credentials`, `read_run` or `fix_configuration`), the code's `params`, a structured `location` (`pipe`, `path`, `input`, `field`, `item`, `attempt`, `file`, `line`, `column`), `errors` (problem items, each a `code`, a `detail` and its own `location`) and `pipeline_run_id`, plus the Pipelex members the platform adds, `request_id` among them, and the client's own `message` when it says something the `detail` does not. The caller's view is `mthds`' `reportedProblem` with any operator-only `diagnostics` member dropped. One result carries one problem, never an array, and the member is named `problem` so that it never collides with a verdict's `errors`, which on `mthds_validate` are problem items. Every output schema declares the problem **open**: the members above are typed, and a member a newer platform or SDK adds passes through, so a consumer branches on `code`, then on `domain`, `retry` and `next_step.kind`, and never on the Markdown.

**The workshop classifies nothing.** Every error `@pipelex/sdk` throws carries a problem: the server's own problem document when it sent one, else the SDK's reading of the status or the transport failure (a `401` is `auth.missing_credential`, a `403` `auth.invalid_credential`, a bare `404` `request.not_found`, a `5xx` `runtime.unexpected` or `runtime.unavailable`, an unreachable API `client.unreachable`, a start whose answer was lost `client.outcome_unknown`). The workshop relays that problem as it is, through one helper (`problemOf`), and overrides none of its code, domain, retry or next step: a refusal by role is the platform's `auth.forbidden`, naming the caller's role in its `detail`; the execution-locus gate's refusals are the runner's `pipelex.deployment.custom_code_requires_sandbox` and `pipelex.deployment.python_structures_refused`; a start the SDK could not confirm is `client.outcome_unknown`, which no client repeats on its own. The one problem the workshop replaces is that of a method create that may have reached the catalog, which the SDK cannot yet send with an idempotency key: `mthds_save_method` reports it as `client.outcome_unknown` itself, the SDK's reading kept in `message` (see "A create that may have happened reads as an unknown outcome"). A failure the SDK did not raise is `runtime.unexpected`, with the error's own sentence as its `message`. The workshop reads a problem's code only where its own behaviour depends on it, such as `mthds_save_method` storing a draft unvalidated when the deployment refuses its Python, never to reword or reclassify it.

**A failure the workshop detects itself is a problem it builds**, with `mthds`' `buildProblem` and a code of the protocol's core registry, before anything is sent: `client.argument_invalid` for a request it refuses, its `params` naming the `argument` and a stable `reason` (such as `mutually_exclusive`, `missing`, `empty`, `outside_workspace`, `wrong_extension`, `not_a_directory`, `file_too_large`, `tree_too_large`, `secret_suspected` or `version_suffix`) and its `location.field` the argument's path (`method_dir`, `files[1].path`, `inputs_path`); `client.file_unreadable` for a file it could not read, `client.workspace_busy` for one that changed while it was read, `client.write_failed` for a write that failed, `client.target_exists` for a destination it will not overwrite, `client.not_configured` for a working directory it cannot resolve, and `client.response_unreadable` for an answer it cannot use. Its own sentence, with what to do, is the problem's `message`. **Several faults in one request are one problem**: a `client.argument_invalid` whose `reason` is `several_faults`, located at the first, whose `errors` hold one problem item per fault. A fault a retry can clear, its `retry` other than `no`, such as a file that changed while it was read (`client.workspace_busy`), is the exception: it is reported on its own, ahead of the others, since a problem item carries no retry verdict and the wrapper's `no` would hide it, and its `message` names each other fault by its code and where it is, its `location.field` or the argument or path its `params` name, so none is lost from the account. What was read while files were changing cannot be trusted, so the retry reads them again and reports whichever faults remain.

**A failure inside a produced result is a full problem at its item.** An image `mthds_show_images` could not fetch, an artifact `mthds_download_artifacts` could not save, a graph page `mthds_validate` could not write, a rename `mthds_save_method` could not make and the validation a deployment refused before a save each carry a caller-view problem at the member that reports them, never a problem item, since each needs its own `retry`. A failed run carries the run's own problem (see the run family).

**The Markdown summary of a no-verdict result is the problem rendered**, by `mthds`' `renderProblemMarkdown`, so every tool says the same things in the same order: the title as a heading, the detail, the client's message when it differs, the next step with its kind, then the code, the request id, the run id and the location, and for several faults one line per item. This is shared by every tool (`problemSummary` within `toolResultContent`): the agent reads `content`, so the actionable detail must reach that stream, while `structuredContent.problem` stays the untouched machine contract. **Where the key and the base URL came from is said in the rendering**, never in the problem's `location`, since the environment is no argument of the call: a credential the platform refused or found missing (`auth.missing_credential`, `auth.invalid_credential`, `auth.credential_expired`) adds which key was sent — none, the host's, the saved one or an unreadable file — with the command that saves a key, and a failure the base URL can cause (those codes, `client.unreachable`, `client.not_configured`, `client.response_unreadable`, `request.not_found` and `runtime.unsupported`) adds which API was in use and where its base URL was set (see What the workshop registers).

### The result streams

A tool result carries up to three independent streams, each with its own reader, and nothing belongs in two of them by accident:

- **`structuredContent`** is the machine contract the model reads. A consumer branches on its fields, never on the transport.
- **`content`** is the Markdown summary a model or a person reads. Each tool states what its summary carries: `mthds_validate`'s is the API's rendered Markdown, deliberately not duplicated into `structuredContent`, while the tools whose payload the model must act on deliberately repeat it in a fenced block — the template of `mthds_inputs_template`, the prepared inputs of `mthds_prepare_inputs`, the generated files of `mthds_codegen` when they are not written to disk, and the bounded output of the results tool — since some hosts read prose more reliably than structured fields. A summary is also the one layer that reaches a host whose copy of the tool list is cached, so a presentation rule that must reach existing installs is written there.
- **`_meta`** carries large data that **never reaches the model's context**: what a completed run holds beyond the model's bounded copy, the full output and the per-call usage records with their per-pipe rollup. It still travels on the raw MCP result, so a programmatic consumer can read it off the wire; it is withheld from the model, not from the transport.

Because the model never sees `_meta`, a result that fed a view would say so in `structuredContent`, in `available_view_specs`; the workshop registers no views, so that list is always empty (see What the workshop registers). A request's own `_meta` is treated as untrusted and is never logged, since a host may attach the user's location and stable identifiers to every call.

### The main pipe's signature (`main_pipe`)

`mthds_validate` returns the signature, read by one projection (`mainPipeSignatureOf`) from three artifacts of its `POST /v1/validate` report. It is the entry pipe's.

```ts
main_pipe?: {                                    // present on every valid verdict with a settled pipe
  pipe_ref: string;                              // namespaced domain.pipe_code
  inputs: Array<{                                // ordered — authored order where the descriptor states it
    name: string;
    concept_ref: string;                         // fully-qualified, multiplicity suffix stripped
    multiplicity: "single" | "variable" | "fixed";
    item_count?: number;                         // present exactly on the fixed arm
    required: boolean;                           // presence !== "optional"
  }>;
  output: {
    concept_ref: string;
    multiplicity: "single" | "variable" | "fixed";
    item_count?: number;
    optional: boolean;
    images?: string[];                           // where images sit, in `$` notation; absent = unknown, [] = none
  };
};
```

**The main pipe's signature rides `structuredContent`.** An agent integrating a method it cannot read — a `method_ref` or `method_id` source, where no bundle enters the conversation by design — needs the call site's types, and the alternative is guessing the produced concept by heuristic. `main_pipe` states them compactly: the main pipe's namespaced ref, each declared input with its fully-qualified `concept_ref`, multiplicity and `required` flag, and the produced concept with its own multiplicity and `optional` flag. The decisions behind that shape:

- **Source of truth is `pipe_io_contracts[main_pipe_ref]`**, a required field on every valid report and not gated by the `views` token. The input-form descriptor is consulted for exactly one thing, **input order** — the contract's `inputs` map deliberately contracts none, the descriptor states authored order — and when the descriptor (or its entry) is absent the map's own order stands. A descriptor naming the same field twice costs the repeat rather than duplicating the slot — the contract's map is what declares the inputs, the descriptor only orders them, and a signature listing one slot twice is wrong in exactly the plausible way a partial one is. The signature never depends on the descriptor being present.
- **Present on every valid verdict, pending signatures included.** The workshop has no views and is precisely the deployment the integrating agent uses, so the signature never depends on a view; a pending-signature verdict has a fully determined signature, and knowing the shape before the signatures resolve is useful. Absent when nothing settles an entry pipe — see the next bullet.
- **The entry pipe is the report's `default_pipe_ref`; the blueprint derivation stands only behind an absent field.** `default_pipe_ref` is the API's statement of the pipe a selector-less run of that same request would execute, and it is the only signal that knows a `method_ref` package's manifest (`METHODS.toml`), whose `main_pipe` outranks the bundle-level declaration on the run and build routes. Reading `bundle_blueprint.main_pipe` instead is manifest-blind, so a package where the two differ got a signature typing a call site the run would not execute. Three arms, and `null` is deliberately not `undefined`: a non-empty string is the stated default; a stated `null` (or any unreadable value) is the server reporting that it determined **none** — no `main_pipe` anywhere, or a manifest naming a pipe the closure does not declare or declares in several domains — which is precisely when a selector-less run would fail to resolve one too, so no signature is emitted and the blueprint is *not* consulted behind it; the field being **absent** means the runner predates it, and only there does the blueprint derivation (its primary blueprint's `main_pipe`, qualified by its domain) stand. A JSON body cannot carry an own property holding `undefined`, so reading the field is the whole absence test.
  - *Live coverage is no longer gated*: the field landed on `pipelex-api` after its 0.21.0 release and `validate.e2e.ts` carried a skipped assertion against an unseamed client — the one check the fallback cannot stand in for — waiting on a deployment that served it. Measured on 2026-09-21, the live suite's default target (`api-dev`) returns the field, so that assertion now runs. It matters more than when it was parked: since `@pipelex/sdk` 0.19.0 a stated `null` is a refusal rather than a fall-through, so the field's presence changes behaviour rather than only sharpening it.
- **Naming follows the standard's own artifact** (`concept_ref`, the `IOMultiplicity` vocabulary) per the brand boundary — MTHDS concepts inside a Pipelex envelope. `item_count` is absent off the fixed arm (this repo's "the unused field is absent" convention; the contract's `null` is the contract's own), and the three-valued `presence` collapses to `required` the way the standard recommends for a consumer that only needs "may this be absent?" — the plain/force distinction is lint- and graph-facing and does not bear on a call site. Inputs are an **array**, not a map, because order must be expressible.
- **Defensive narrowing, whole-signature omission.** Every member is checked against what actually arrived (strings non-empty, multiplicity in the closed vocabulary, `item_count` an integer of at least two exactly on the fixed arm and the literal `null` the contract states on every other arm — `Concept[1]` reports `"single"`, so a fixed count of one is a producer violation, and an omitted or non-null `item_count` off the fixed arm is drift — presence in the marker vocabulary). Any malformed member, or no contract entry for the declared main pipe, omits the **whole** signature rather than emitting a partial one — half a signature actively misleads the agent typing against it, where an absent one just sends it to the inputs template. The verdict is never affected.
- **No JSON Schemas.** The per-slot `json_schema` is the token-heavy part and stays behind the inputs template and `mthds_codegen`.
- **`output.images` says whether a run will produce pictures, and where they will sit.** The capability requests the standard's **output-form descriptor** alongside the input form (`views: ["input_form", "output_form"]`) and walks the entry pipe's single output node for `kind: "image"`, recursing into an `object` node's `fields` and a `list` node's `item`. The result is a list of paths from the output's root: `$` is the output itself, `$.name` a field of it, `$[]` an element of a list, `$[].name` a field of one — so a top-level `Image` output is `["$"]`, an `Image[]` is `["$[]"]`, and "this method produces pictures" is `images.length > 0`. Three rules matter. **An empty array and an absent member are different answers**: `[]` means the server described the **whole** output and it holds no image, absence means the question is unanswered — no descriptor arrived (an older runner, or an entry that did not narrow), *or* the walk met something it could not read — and the agent must not read silence as "no". **A `document` node is not a picture** and is deliberately not reported here; a `documents` member is a later increment rather than a silent inclusion. And **`kind: "unknown"` is opaque**: it is the standard's escape hatch for a producer that could not map a node honestly, so there may be an image inside it and no way to know.

  **The walk therefore reports its own completeness, and that decides whether the member rides at all.** Opacity and emptiness are not the same answer, but they collapsed into the same emitted value: an `unknown` root, a `kind` string this build does not know, a record carrying no `kind`, a field with no usable name and the depth ceiling each yielded `[]` — "described and holds none" — for a descriptor that said no such thing, and a consumer applying the documented `images.length > 0` rule read a confident **no** off a node nobody had looked into. So the walk returns `{ paths, complete }`, and the projection publishes the member only when it is a truthful answer: an incomplete walk that found **nothing** withholds it, which is the unanswered reading. An incomplete walk that **did** find an image still publishes — those positions really do hold pictures, and downgrading a known yes to "unknown" would lose the signal the member exists for, so a non-empty array is exhaustive unless part of the description was opaque. Only kinds the walk fully understands and that hold no picture (`text`, `prose`, `date`, `number`, `boolean`, `enum`, `document`) keep it complete; a `document` is an **answer**, not a failure to look, and must not poison completeness. The walk is a total map over the standard's own `FIELD_KINDS`, so a kind a later version adds fails this repo's build instead of quietly reading as "no images". The rendered signature line says it too, as a trailing ` (produces images)`, for agents that read prose more reliably than fields.
- **One rendered signature line is appended to the `content` summary** on the same verdicts, under its own `## Main pipe` heading, in MTHDS-flavoured notation — `demo.main(document: legal.Contract, notes?: native.Text, tags: native.Text[]) -> analysis.Report[2]`, where `?` marks an input the caller may omit (and an output a successful run may resolve absent), `[]` a variable list and `[N]` a fixed one. The two marks never meet on an input — the standard pins a plural slot to `presence: "plain"`, so an optional list is not a shape a caller can be offered — and only the output can carry both. Agents read prose more reliably than structured fields.

### Catalog Discovery Scope (`mthds_list_methods`)

`mthds_list_methods` lists the registered methods visible to the API key's organization through `@pipelex/sdk`'s `PipelexApiClient.listMethods()` (`GET /v1/methods`). Catalog listing uses the same org-bound credential as the by-id catalog paths, `PIPELEX_API_KEY`: the credential determines the active organization and therefore the entire visible catalog, and no catalog data is embedded in static server instructions. It is a plain, read-only tool with no view and no `_meta` payload: the assistant needs bounded names, descriptions, and canonical ids to choose a method, and a human catalog-management flow does not exist in this increment. Listing executes no method and spends no inference credit.

**The catalog is searched reactively.** The tool description carries the reactive triggers alone — the user asked what exists, or named a saved method without its id. The workshop's `instructions` state the reactive triggers and stop there — a coding-agent session is driven by skills, and a proactive clause in text that reaches every session had it searching the catalog in the middle of work no skill had asked it to leave, `/pipelex-design` included.

The public MCP input is:

```ts
{
  query?: string;  // case-insensitive substring, matched server-side over name and description
  limit?: number;  // integer 1..50; default 20
  cursor?: string; // opaque next_cursor from a previous call
}
```

`query` is trimmed and blank means no filter — the trimmed-away case omits `q` entirely rather than sending an empty string, which the API treats as bad input rather than as "no filter". Search, ordering and paging are all applied server-side: `q` matches across the whole catalog rather than one page, and rows arrive ordered newest first by the immutable `created_at` the catalog pages on. The MCP re-sorts and re-filters nothing — re-sorting would reorder a page against the cursor that produced it, and re-filtering would search only the rows the server already selected. A cursor is opaque and is passed back verbatim to continue.

Success projects exactly:

```ts
{
  status: "ok";
  returned_count: number;
  next_cursor: string | null;
  methods: Array<{
    method_id: string;
    name: string;
    name_truncated: boolean;
    description: string | null;
    description_truncated: boolean;
    created_at: string;
  }>;
}
```

The model-facing `name` is bounded to 200 Unicode code points and `description` to 500, with explicit truncation flags; the server's search examines their full stored values. `created_at` is reported rather than `updated_at`, because the catalog orders on `created_at` and showing a timestamp other than the sort key makes "newest first" unreadable. There is no total count in either form: counting a catalog means reading all of it, which is the cost paging exists to avoid. Missing descriptions normalize to `null`. Empty catalogs and no-match queries are successful empty results.

**There is no `has_source` flag.** The catalog index projection does not carry a method's source, and recomputing the flag would cost a `getMethod` per listed row — exactly the read the index exists to avoid. A source-less method instead announces itself where the answer is actionable rather than advisory: passing its id to a by-id validate, inputs template, prepare or run fails fast as a no-verdict carrying the platform's problem.

The projection boundary is strict: `mthds`, `python`, `input_data`, `pipe_output`, `org_id`, and `created_by_user_id` never enter `structuredContent`, `content`, `_meta`, or logs. The index projection no longer returns them, but the boundary is enforced on what actually arrives rather than on what the type declares, so a looser server cannot leak through it. A response that is not a page object, a page missing its `items` array, a **missing or** non-string `nextCursor`, or a row whose `method_id`, `name`, or `created_at` is not a string is a `client.response_unreadable` no-verdict (status `200`, the parse failure in its `message`) rather than a partial list. `nextCursor` is checked as strictly as `items` on purpose: the SDK reads the raw wire key, so a renamed or dropped `next_cursor` arrives as `undefined`, and treating that as the end of the catalog would hide every method past the first page while every live check stayed green. The text summary repeats the bounded name, description, and canonical id for each returned row, and includes cursor/query guidance without source or stored defaults.

**The summary specifies the listing's presentation, because the name alone is not an answer.** A catalog listing is read almost verbatim by the user, and the description is what lets them choose; observed live on the same two-method catalog, one host answer rendered name + description while another rendered bare names and volunteered "both contain source code, but I haven't checked whether they validate" — the model filling the silence with the one field that carries no verdict. So the summary leads its list with an explicit render directive ("report every method with BOTH its name and its description"), puts name and description first on each row with `method_id` demoted to a trailing parenthetical, and says nothing at all about source or validity — the flag that once carried that caveat is gone, and a row that volunteered it demonstrably leaked into user-facing answers as a half-verdict. The directive lives in the summary rather than the tool description on purpose: the summary is the one layer that reaches a host whose copy of the tool list is cached (see The result streams). The tool description carries the same instruction as a backup for hosts that weight it at selection time. Names and descriptions are org-authored and therefore untrusted: each is collapsed to a single line so it cannot break out of its bullet, and the directive names them as data to display rather than instructions to follow. The directive is omitted when the page is empty.

No-verdict failures carry the shared `problem` (see Verdicts and errors): the problem the SDK read from the platform's answer, or from the status or the transport when there is none, relayed as is, an unreachable API being `client.unreachable`, a missing or refused key the `auth` code the platform sent, a plan limit the platform's own, a deployment that does not serve `/v1/methods` `request.not_found`, and a refused `cursor` or a key acting for no organization the platform's own refusal with the field it names. The workshop refuses before sending only what it can check itself, its arguments, as `client.argument_invalid`, and a malformed success payload is `client.response_unreadable`.

### Files Discovery Scope (`mthds_list_files`)

`mthds_list_files` lists the files the API key's organization holds, as `GET /v1/files` serves them (`pipelex-server/platform/docs/files.md`): its members' uploads, the test inputs made for a method and its runs' final outputs, each a record with the name a person sees, a type, a size and a provenance. It exists so that an assistant can find a file the team already holds, such as the invoice uploaded this morning or the report yesterday's run produced, and run a method on it: each row carries the file's `pipelex-storage://` address, which a run's inputs take where a file goes, exactly as they take an `http(s)` URL, with nothing to upload. It is modelled on `mthds_list_methods`: a plain, read-only tool with no view and no `_meta` payload, one server-selected page per call, reading through `@pipelex/sdk`'s `listFiles`. The key decides the organization, and every role of it reads every file. Listing reads no file's content and spends no inference credit.

**It is called reactively.** Its tool description carries the trigger: the user means a file the organization already has rather than one on disk. The server instructions do not name the tool. They are the map of the method flow and sit at their budget (see Server instructions and the text budget), and a file the team holds is one way into that flow among several, which the description covers when the host chooses a tool.

The public MCP input is:

```ts
{
  query?: string;                            // case-insensitive search, server-side, in each file's name and original name; at most 200 characters
  kind?: "uploaded" | "generated" | "test";  // what made the file
  format?: string[];                         // 1..20 format keys: a file's lowercase extension, "image" for any picture
  method_id?: string;                        // a saved method's bare catalog id: that method's files
  limit?: number;                            // integer 1..50; default 20
  cursor?: string;                           // opaque next_cursor from a previous call
}
```

- `query` is trimmed and blank means no filter: a blank query sends no `q` at all. A trimmed query longer than 200 code points, the route's own bound on `q`, is refused as `client.argument_invalid` at `query` (reason `too_long`) before anything is sent, rather than sent for a refusal the route would answer with a 422.
- `format` keys are normalized before they are sent: trimmed, one leading dot dropped, lowercased and each sent once, since the platform writes a key as the file's lowercased extension and so `.PDF` and `pdf` name one format. An empty key, one holding whitespace or one longer than 64 characters is refused as `client.argument_invalid` at `format.<index>` (reason `not_a_format`), several such keys folding into one problem. The cap of 20 keys is the tool's, a handful being what a model needs; the route takes more.
- `method_id` is the method's bare id, because a method's list is the method's whatever version took or made its files, and the route refuses anything else. An id with an `@` suffix is refused as `client.argument_invalid` at `method_id` (reason `version_suffix`), with the bare id to pass in its message, rather than stripped, since a selector is never rewritten behind the caller's back. `mthds_prepare_inputs` makes the same check, with the same words, on the method a test upload names (see What an upload is recorded as). An id that cannot be one (empty, longer than 128 characters, or holding anything but letters, digits, `_` and `-`) is refused at the same place before anything is sent. An id the organization does not hold is no refusal: the route lists nothing for it, and the summary says so.
- `limit` takes the method list's bounds, 20 by default and at most 50, below the route's 200.
- The route's other filters, a run, a member, media types and a date range, are not offered. A run's files reach a model through that run's own results, a member's user id is nothing a model can act on, and a format key covers a type.

Every filter and the paging are applied by the server across all of the organization's files, newest first. The tool re-sorts and re-filters nothing: re-sorting would reorder a page against the cursor that produced it, and filtering a page here would search the rows one page happened to read and call it a search.

Success projects exactly:

```ts
{
  status: "ok";
  returned_count: number;
  next_cursor: string | null;
  files: Array<{
    file_id: string;
    uri: string;                              // pipelex-storage://…, ready for a run's inputs
    name: string;                             // bounded to 200 code points
    name_truncated: boolean;
    media_type: string;
    format: string;
    size: number;                             // bytes
    kind: "uploaded" | "generated" | "test";
    origin: {
      surface: string | null;                 // the client an upload came through
      run_id: string | null;                  // the run that made the file, or that was given it inline
      method_id: string | null;               // the method whose run made it, or the method a test file is for
      method_version: number | "draft" | null;
    };
    created_at: string;
  }>;
}
```

**Only a null `next_cursor` ends a listing.** The server applies a filter to the rows a page reads and never refills the page, so a filtered page can hold fewer files than asked, or none, and still carry a cursor. The field description says so, and when an empty page carries a cursor the summary says in words that the listing is not finished, since read as "no match" it would end a search halfway. A continuation repeats the listing's own filters beside the cursor, because the route binds a cursor to the filters that issued it.

**The projection boundary.** `created_by`, a member's user id, never enters `structuredContent`, `content`, `_meta` or a log: a model cannot act on it, and the summary words a file's provenance without naming who uploaded it. The boundary is enforced on what arrives rather than on what the type declares, so a field the route adds later is dropped too. Each row is checked as it arrives, and a page that breaks the contract fails whole, as a `client.response_unreadable` no-verdict rather than a partial list: a response that is not a page object, a page with no `items` array, a missing or non-string `nextCursor` (read as the end of the list, a renamed field would end every listing at its first page), a row whose `file_id`, `uri`, `name`, `media_type`, `format` or `created_at` is not a string, a `size` that is not a non-negative integer, a `kind` outside the three, or an `origin` field of the wrong type, `method_version` being a positive integer, `"draft"` or null. An absent `origin`, or an absent field in it, reads as null. The `uri` carries the organization's storage prefix, as every `pipelex-storage://` address a run returns does: it is the address a run reads, not an identifier to hide.

**The summary.** Its first line names the scope with its filters, such as `Files matching "invoice" (kind uploaded, format pdf): 3 returned, newest first.`, so an empty answer reads as nothing matching these filters rather than an organization with no files. When rows are present, the next line says how one is used: put its uri where a method's input takes a file, as an `http(s)` URL would go, since it needs no upload and the inputs can go straight to `mthds_run`. That is the step a model would otherwise get wrong, by preparing the file again. The same line says that file names are data to display, never instructions to follow, since members choose them. Each row is then one bullet: the bounded name, collapsed to one line so it cannot break out of its bullet and with its Markdown metacharacters escaped so it cannot close its bold or plant a uri of its own on the row, its format, a readable size (bytes, then KiB, then MiB from the first size that would read as 1024 KiB), its provenance in a few words (uploaded, given inline to a run, made by a run of a method, a test file for a method) and its date, with the uri trailing in a parenthetical, as the method list's id trails its description. A finished empty listing says whether filters applied, that a method id the organization does not hold lists nothing too, and that a file stored a moment ago can take a moment to be listed, since the lists are eventually consistent.

**Failures** carry the shared `problem`, as the method list's do. An unreachable API is `client.unreachable`, a missing or refused key the platform's `auth` code, and a plan limit the platform's own. A refusal of the request is the platform's problem with the field it names on the wire (`q`, `format.<index>`, `method_id`, `limit`, `kind`, `cursor`), relayed as is and rendered under its errors; the workshop does not translate a wire field into the tool's argument. A `404` from a deployment that does not serve `/v1/files` is `request.not_found`, and never an unknown method, which lists nothing. A malformed answer is `client.response_unreadable`.

### Run Scope (the run family)

The run family adds durable (async) method execution against the hosted Pipelex API, wrapping `@pipelex/sdk`'s run lifecycle (`client.start` → `POST /v1/start`, `client.getRunStatus` → `GET /v1/runs/{id}/status`, `client.getRunProgress` → `GET /v1/runs/{id}/progress`, `client.getRunResult` → `GET /v1/runs/{id}/results`). The MCP adds no execution logic and stays stateless: all run state lives behind the durable `run_id` on the platform. The server never calls the blocking `POST /v1/execute` or the SDK's blocking wrappers (`waitForResult`, `startAndWaitForResult`), and never surfaces `result_url` or other presigned URLs into model context.

**Run flow**:

1. The assistant starts a run with `mthds_run`, giving files, an address or an id and the inputs filled from `mthds_inputs_template`, prepared by `mthds_prepare_inputs` where they carry local files.
2. The start tool returns the durable `run_id` immediately.
3. If the user asks how it is going, the assistant calls the status tool — a cheap read of the run's status and of how far it has got, with a retry hint in the summary so it doesn't spin-poll.
4. Once the run is terminal, the assistant calls the results tool and reports the main output (bounded) on success, or, on a failure, why the run failed, what to do and what to give support.
5. Because everything is behind the durable id, the flow survives conversation gaps: days later, "what did that run produce?" is a single results call.

**Starting a run.** The start tool is `mthds_run`. It is not read-only: its description states that it executes the method on the hosted API and spends inference credit. Its inputs are stated in the `mthds_run` section; its result is:

```ts
// structuredContent
{
  status: "ok" | "error";
  run_id?: string;             // the durable pipeline_run_id — the handle for everything else
  run_status?: RunStatus;      // initial state from the ack, when the server includes one
  created_at?: string;
  method_provenance?: {        // method_ref runs only — what was actually fetched
    address: string;
    tag: string | null;        // null for a bare address (default branch at HEAD)
    commit_sha: string;        // the honest cache key; what keeps the run explainable when a tag moves
  };
  available_view_specs: Array<"live_run_status">;  // always [] on the workshop
  files_sent?: string[];       // method_dir and files runs — every file of the tree sent (see The files union)
  problem?: Problem;           // no-verdict only — why the run was not started (see Verdicts and errors)
}
```

`RunStatus` is the hosted lifecycle set: `PENDING | STARTED | RUNNING | COMPLETED | FAILED | CANCELLED | TERMINATED | TIMED_OUT`. The `content` summary states the run was accepted, gives the id, and spells out follow-up etiquette for the model (check with the status tool, fetch with the results tool when terminal, don't poll in a tight loop). Deliberately not exposed in v1: `output_name`, `output_multiplicity`, `dynamic_output_concept_ref`, `extra`, webhooks, client-supplied run ids. Binary inputs (PDFs, images) ride reachable https URLs or `pipelex-storage://` references inside `inputs`: `mthds_prepare_inputs` turns a local path or bytes into a storage reference (see Prepare Inputs Scope).

**Run-by-reference (`method_id`)**: `mthds_run` starts a registered method by its catalog id, so the model never carries the bundle — a run of a registered method is a tens-of-tokens call from any host. The platform resolves the id natively on `POST /v1/start`, with no fetch round-trip and no bundle on the wire. A bare id runs the method's latest published version, `mt_…@<n>` pins one and `mt_…@draft` runs the draft, and the result says which ran (see Method versions, on two platforms), so agents do not assume a run executes what they previously looked at. The catalog is org-scoped, so a by-id start needs a credential: an unauthenticated call is the credential problem (`auth.missing_credential`), whose summary says which key was sent, and an id the caller's organization cannot see is the catalog's miss, `pipelex.catalog.not_found` with `params.resource` `method`, which reads exactly like an id that does not exist. Id format beyond non-blank stays server-owned, the same stance as `run_id`.

**Run-by-address (`method_ref`)**: `mthds_run` also starts a published method by its address — `github.com/<owner>/<repo>[/<selector>][@<tag>]`, e.g. `github.com/Pipelex/methods/documents@v0.1.0` — as a **server pass-through**: the SDK's typed `method_ref` start option rides `POST /v1/start`, the runner fetches the repository at the tag, locates the package by manifest identity, and runs it. A `method_ref` is a complete run source and pairs with nothing (`files` + `method_ref` and `method_ref` + `method_id` are both refused before the wire as `client.argument_invalid` — see Method Selectors); a `pipe_code` beside it is legal and overrides the manifest's `main_pipe`. The start ack's `method_provenance` (`{address, tag, commit_sha}`) is surfaced in `structuredContent` and echoed in the summary — the resolved SHA is what keeps the run explainable when a tag moves. A ref that does not resolve is a no-verdict result carrying the runner's problem as it answered it, with the location the runner gives (a registry-form ref, for one, is `request.unsupported` at `method_ref`), and either execution-locus refusal is the deployment's own problem (see Run verdict discipline below); each is refused before anything executes, so no inference credit is spent on a failed resolution.

**The status tool** (`mthds_run_status`) — check on a run. Read-only, plain tool (no view).

```ts
// input
{ run_id: string }

// structuredContent
{
  status: "ok" | "error";
  run_id?: string;
  run_status?: RunStatus;      // the coarse lifecycle state
  is_terminal?: boolean;       // convenience so the model needn't know the status set
  degraded?: boolean;          // true → status is last-known, not freshly derived
  retry_after_seconds?: number | null;
  created_at?: string;
  finished_at?: string | null;
  error?: RunError;            // terminal statuses other than COMPLETED, when the run stored the problem it ended with — see below
  progress?: RunProgress;      // the run's progress snapshot, when the progress read answered — see below
  progress_invocations_omitted?: number;  // how many invocations progress.invocations leaves out; absent when none
  problem?: Problem;           // no-verdict only
}
```

The `content` summary while non-terminal includes "check again in ~Ns" from the retry hint.

**A run says how far it has got.** After the status read, the status tool reads the run's progress snapshot once, `client.getRunProgress` → `GET /v1/runs/{id}/progress`, whatever the status, pending and ended runs included. The snapshot is the one the hosted progress contract defines (`conformance/specs/pipelex-platform-api.md`, "Run progress"): which invocations of which pipes have started, ended or been skipped, how far each batch has got, which outcome each condition took, where the run is retrying or stuck, and a one-line `summary` the contract words from the snapshot alone. The tool relays it as `progress`:

```ts
interface RunProgress {
  pipeline_run_id: string;
  mode: string;                 // "live" on the hosted API
  status: string;               // pending, running, succeeded, failed or canceled; an open set
  version: number;              // of two snapshots of a run, the higher version is the newer
  assembled_at: string;         // when the platform projected it
  summary: string;              // the platform's one line, as it sent it
  degradation?: ProgressDegradation;    // the run status's, when the run reads degraded
  invocations: ProgressInvocation[];    // at most MAX_PROGRESS_INVOCATIONS (50) — see below
}

interface ProgressInvocation {
  path: string;                 // the entry pipe's pipe_ref, then step_<n>, branch_<n>, item_<n>, outcome_<key> or default per level, joined by "/"
  pipe_code: string;
  pipe_ref: string;
  pipe_type: string;            // an open string, such as "PipeLLM"
  status: string;               // scheduled, running, succeeded, failed, skipped or canceled; an open set
  started_at: string | null;
  ended_at: string | null;
  step_count?: number;          // a sequence's steps
  branch_count?: number;        // a parallel's branches
  skip_reason?: string;
  batch?: { total: number; done: number; running: number; failed: number };   // a batch that has fanned out
  condition?: { selected_outcome: string | null };                              // a condition that has resolved; null for its default
  attempts?: number;            // health: how many times its work has been tried, when more than once
  last_failure?: { problem: RunError; at?: string };                           // health: the latest failure of its work, as a problem
  degradation?: ProgressDegradation;    // health: the run is stuck at this invocation
}

interface ProgressDegradation {
  reason: string;               // "workflow_task_failing" or "status_unavailable"; an open set
  message?: string | null;      // the platform's account
  failed_attempts?: number | null;
  failing_since?: string | null;
  ends_at?: string | null;      // when the platform ends the run as failed if it is still failing then
}
```

- **The summary is the platform's, relayed.** The `content` summary gives it a paragraph of its own right after the status, after the whole account of why an ended run ended: exactly `Progress: <summary>`, a line break in the summary collapsed to a space. This server words no progress of its own, so that the workshop and the hosted console's run status say the same progress the same way.
- **The contract's known members, each with its type.** `root_path` and `chain`, which describe a snapshot of part of a run and which the hosted plane never sets, are dropped, and so is any member a later platform adds. An optional member is kept only when it has its type, since the MCP server checks `structuredContent` against the tool's output schema and a mismatch would fail the call; a snapshot whose required members do not have theirs, its own or an invocation's, is relayed as no snapshot at all. `last_failure` is read as the contract states it, `{ problem, at }`: its `problem` is checked as a problem document and carried as a run's own problem is, the operator's `diagnostics` dropped and its texts bounded (see "A failed run says why"), and a `last_failure` holding no problem document is left out. The other texts the runtime and the platform write freely are bounded too, `degradation.message` to `FAILURE_MESSAGE_MAX_CODE_POINTS` and `skip_reason` to `FAILURE_FIELD_MAX_CODE_POINTS`; the summary is not, being the contract's own line.
- **At most fifty invocations, those worth reading first.** A wide batch gives the snapshot one invocation per item and every invocation below each, so `invocations` lists at most `MAX_PROGRESS_INVOCATIONS` (50) of them. Those running, failed or carrying a health annotation (`attempts`, `last_failure`, `degradation`) are kept first, each with its ancestors, then the others in snapshot order while room is left, and the list keeps snapshot order, so each invocation still follows its ancestors. When the invocations needing attention alone pass the cap, the first fifty of them in snapshot order are kept. `progress_invocations_omitted` counts what was left out.
- **Best effort.** The read is bounded by `PROGRESS_READ_TIMEOUT_MS` (5 s), far under the SDK's own poll timeout. A read that fails for any reason, a server older than the route (which the SDK reports as `RunLifecycleUnavailableError`), a `404`, a `5xx`, an answer the SDK cannot read or the deadline, leaves the status to go out alone, with no `progress` and no word about it: the progress never turns the status into an error and never holds it back. It is read after the status, so it can be a moment ahead of it.
- **The progress and the degradation never contradict each other.** A degraded status read gets the reassurance that its status is the last one recorded and that the run itself is unaffected only when the platform could not read the run (`degradation.reason` `status_unavailable`, or no `degradation`, which is how a platform older than it says the same), and never beside a snapshot reporting the run stuck, a `degradation` for any other reason, which the progress read made a moment later can carry. A run whose workflow task keeps failing (`workflow_task_failing`), or degraded for a reason this server does not know, is not reassured: its progress paragraph says that it is not progressing and at which invocation.

**A failed run says why.** When a run ends without success, the platform stores on it the problem it ended with, under the run's own code (`run.cancelled`, `run.timed_out`, or the code of what failed, such as `model.unavailable`) and with its own `domain`, `retry` and `next_step`: the runner's problem for a failure it raised, or the platform's own for an ending no runner reported (a workflow that kept failing, a timeout, a workflow that vanished). The platform serves it on the status read (`RunRead.error`), and the results read's `409`, a `run.failed` problem, nests it as `run_error`, which the SDK's failed arm carries as `error`. Every failed arm of the run family carries that problem, in the caller's view, as one member: `error` on the status tool for a terminal status other than `COMPLETED`, and `run_error` on the `failed` state of the results tool, the image tool and `mthds_download_artifacts`. The `run.failed` problem around it is not carried, since it says only that the run did not succeed, which `state` and `run_status` already say.

**The platform serves the problem through its strict disclosure**: what only an engineer needs, the provider's raw answer among it, rides in the operator's `diagnostics` member, and this server drops `diagnostics` whatever served the problem, so a deployment serving it verbose, such as a local loop, keeps it from the model too. The model reads the problem the platform words for the caller, and the people who run the platform find the rest on the run itself, by the run id and the code the support line gives.

```ts
type RunError = Problem & {   // the caller's view of the run's own problem (see Verdicts and errors), its texts bounded
  errors_omitted?: number;    // how many of the run's faults `errors` leaves out
};
```

The problem is checked as it arrives, since the runtime and the platform write it: a value that is no problem document, as the SDK's `isProblem` reads it, is no problem, so a run that ended with none, or with a value of another shape, carries its status alone. **Every text is bounded**, because the runtime bounds none it writes, one problem can run to hundreds of kilobytes (a bundle that failed validation can list every fault in it), and every text reaches the model twice, in the summary and in `structuredContent`: `detail`, `message` and `next_step.detail` to `FAILURE_MESSAGE_MAX_CODE_POINTS` (2,000 code points), `title` to `FAILURE_FIELD_MAX_CODE_POINTS` (300), and `errors` to its first `RUN_ERROR_MAX_ITEMS` (20) faults, each `detail` cut to `RUN_ERROR_ITEM_MAX_CODE_POINTS` (500), with `errors_omitted` counting the faults left out. The structured members are bounded too, the problem's `params` and `location` and each fault's `params`, `location` and `suggestions`: a text to `RUN_ERROR_ITEM_MAX_CODE_POINTS`, or `FAILURE_FIELD_MAX_CODE_POINTS` in a location or a member's name, an object to `RUN_ERROR_MAX_ITEMS` members and a list it holds to as many entries, so a typed list such as `missing_blobs` holds nothing but its entries, what either left out counted in one text member of that object named `…`, or `……` and so on when the object already has a member by that name, so the count never takes a member's place, and anything nested deeper than `RUN_ERROR_VALUE_MAX_DEPTH` (4) levels replaced by a text saying it was left out. A fault's `suggestions` keep `RUN_ERROR_MAX_ITEMS` names with `suggestions_omitted` counting the rest. A location's `path`, the pipes from the run's main pipe down to the failing one, is carried whole, since a path cut anywhere names another pipe. A fault's `suggested_fix` is a patch applied as written, so it is never cut: it is carried whole while its JSON fits `FAILURE_MESSAGE_MAX_CODE_POINTS`, and otherwise left out with `suggested_fix_omitted`. Each cut says what it left out, and every other member is kept as served, so what the arm carries is still an open problem document. **Nothing is inferred**: whether running it again can help is the problem's `retry`, and what to do is its `next_step`. The results, image and download tools take the problem from their failed arm when it carries one and otherwise from one status read of the same run that follows the arm, which is also where the time the run ended comes from. That read is bounded by `FAILED_RUN_READ_TIMEOUT_MS` (5 s), far under the SDK's own poll timeout, since it only adds to an answer already in hand; a status read that fails or runs out of time leaves the failure to what the arm carried, and never turns the verdict into an error or holds it back.

Each failed summary says that the run ended and with which status, renders the problem the way every tool renders one (`renderProblemMarkdown`: the title as a heading, the detail, the client's message when it differs, the next step with its kind, the code with its domain and retry verdict, and one line per fault), and closes with **For support**, the run id, the problem's code and the time the run ended (`Run run_… · model.unavailable · ended 2026-09-23T15:16:37.856067+00:00`). A run with no problem says that its status is all that is known, and still gives the support line; when the failed arm carried no problem and the status read that should have followed it failed, the summary says instead that the reason is unknown for now and that reading the run's status again returns it, since nothing then shows the run stored none.

**The results tool** (`mthds_run_results`) — report the results. Read-only.

```ts
// input
{ run_id: string }

// structuredContent
{
  status: "ok" | "error";
  run_id?: string;
  state?: "running" | "completed" | "failed";   // mirrors the SDK's RunResultState
  retry_after_seconds?: number | null;          // state=running only
  run_status?: RunStatus;                       // state=failed only (terminal status)
  run_error?: RunError;                         // state=failed only, when the run stored the problem it ended with — see the status tool above
  main_stuff?: unknown;                         // state=completed only — bounded, see below
  truncated?: boolean;                          // state=completed only; true when main_stuff was bounded down
  image_candidates?: string[];                  // state=completed only, and only when the output references stored files — the free image shortlist, see below
  image_candidates_omitted?: number;            // state=completed only, and only when the shortlist left some out
  usage?: RunUsage;                             // state=completed only, always present there — RUN-LEVEL token & USD-cost totals; per-pipe rollup + full per-call list ride _meta (see below)
  available_view_specs: Array<"run_graph">;     // always [] on the workshop
  problem?: Problem;                            // no-verdict only
}
```

On `completed`, `content` composes a Markdown summary with the main output in a fenced code block (the `mthds_inputs_template` duplication pattern: the payload the model must read is deliberately repeated in the prose), bounded by the same cap as `structuredContent`. The **full** (unbounded) `main_stuff`, the **full** per-call `tokens_usages` record list, and the per-pipe usage rollup ride the `_meta` channel (keys mirror the API field names where they exist: `_meta.main_stuff`, `_meta.tokens_usages`, plus our own `_meta.usage_by_pipe`), never model context. A `state: "running"` result is a produced verdict ("no result *yet*" is an answer): `status: "ok"` with the retry hint. On `failed`, the summary says why the run failed, what to do, whether running it again can help and what to give support (see "A failed run says why" above), and states plainly that no graph exists for failed runs.

**A completed result reports what the run stored, and fetches none of it.** A run that produced an image, a PDF or a document carries it in `main_stuff` as content with a `pipelex-storage://` reference in `url` beside a presigned `public_url` that expires within the hour. The results summary is the moment the agent decides what to do with that, so the projection walks the **full** output (not the bounded copy — a reference pruned out of the model-facing copy is still a real file) and reports two things:

- **`structuredContent.image_candidates`**: the bare `pipelex-storage://` reference of each stored file whose storage key passes an extension prefilter (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, or no extension at all — the runtime does store extensionless keys, and only a fetched content type can settle those). The member is **absent**, not empty, when the output references no stored file, so a consumer can tell "nothing was produced" from "nothing looked like an image". The walk is `collectArtifacts` plus a string test: no link is resolved and no byte is read. It is a **shortlist, never a verdict** — the content type at fetch time is what decides, which is the image tool's job.
  **Bounded, and bare.** "Nothing reaches the model but a handful of short strings" was the intent and nothing enforced it: the walk reads the **full** output deliberately, so a method emitting a large `Image[]` put an arbitrarily long list into model-facing `structuredContent` — outside the `MAIN_STUFF_CAP` discipline the output beside it obeys, and capable of exceeding it several times over. So the list is capped at `MAX_IMAGE_CANDIDATE_ENTRIES` (32) and the remainder counted in **`image_candidates_omitted`**, absent when nothing was left out. The cap is a **prefix**, so an index into this list means to the image tool exactly what it means here, and that tool still walks the whole set — an omitted picture is reached by naming its reference. Entries are bare strings rather than `{ uri, key }` pairs: the key was a fixed-prefix strip of the reference beside it, so it doubled the list's cost and told a consumer nothing the reference did not. A reference the output names more than once is one candidate, deduplicated at the walk — otherwise the same picture would be fetched twice, billed twice and given two positions.
- **One merged sentence in the prose**: how many stored files there are, how many look like images, the image tool (`mthds_show_images`) to see one (with the standing warning that a shown picture stays in the conversation), and `mthds_download_artifacts` to save the run, the output as `main_stuff.json` and the full files beside it, with the `public_url` expiry stated.

**Every completed result says how to keep it.** When the output references no stored file, the summary still ends with one sentence naming `mthds_download_artifacts` as the way to keep the output on disk, verbatim as `main_stuff.json`, and telling the model never to retype it into a file itself. That is the failure it answers: in the proof lab of 2026-09-24 a model asked for the results as files rewrote each output with its own file tool, which costs output tokens in proportion to the result and can alter it silently.

**The results tool returns no image content block, and takes no flag that would make it.** That is a decision, not an omission — see Image Display Scope.

**Bounding `main_stuff`**: an output can be huge. The structured copy (and the fenced summary block) is bounded to a serialized cap (~32KB, tunable constant): JSON trees are pruned deterministically (deepest levels and longest collections first, with an ellipsis marker); plain text keeps head+tail. When bounded, `truncated: true` and the summary says the output was cut. The full output always rides `_meta`. The same sentence names `mthds_download_artifacts` as the way to read the rest: it writes the whole output to disk as `main_stuff.json`, where the agent reads it with its own file tools, so a cut output is never the last word.

**Run usage & cost**: on a `completed` result, `structuredContent.usage` carries **run-level** token and cost totals over the SDK's `RunResults.tokens_usages` — the per-inference-call record list (token counts by category, server-computed USD `cost`, and the `pipe_code` that made the call). The arithmetic is the SDK's: `usage` is a **projection of `summarizeUsage`** (`@pipelex/sdk`), which folds the list and its `usage_assembly_error` into one null-aware reading, and this server adds no totals of its own. The projection keeps this tool's established field names — the SDK's `total_cost_usd` is `cost_usd` here, and its separate `input` / `output` token totals are added into the one `tokens` figure the model has always been given. It is a small, fixed-shape totals object; there is deliberately **no per-pipe breakdown in the model-facing usage** (the agent gets the run's bottom line, not a table). The per-pipe rollup and the **full** per-call `tokens_usages` list ride the `_meta` channel (`_meta.usage_by_pipe`, `_meta.tokens_usages`) — never model context, exactly like `main_stuff` — where a future detailed-cost tool/view can read them. Usage is also **never rendered into the `content` prose**: the totals live only in `structuredContent.usage`.

```ts
usage: {
  state: "records" | "no_inference" | "unavailable";  // the SDK summary's state — read it first
  cost_usd: number | null;      // the SDK's total_cost_usd: Σ priced calls' cost; null under "records" when NO call was priced (own-GPU/mock/dry-run), 0 under "no_inference", null under "unavailable"
  cost_partial?: boolean;       // present (true) only when some calls were priced and some not — cost_usd is a lower bound
  tokens: number | null;        // the SDK's input total + its output total; null only when both are null. input_cached / output_reasoning are documented subsets and never counted
  calls: number;                // number of inference calls (0 outside "records")
  assembly_error: string | null; // the SDK's usage_assembly_error; non-null only when usage assembly broke for this run
}
```

`usage` is present on **every** completed result, and `state` says which of the SDK's three readings it is. `records`: `tokens_usages` is a non-empty list and the totals are folded from it. `no_inference`: the list is `[]` (assembly ran, no inference happened), so `cost_usd` is `0`, `tokens` is `0` and `calls` is `0`. `unavailable`: the list is null or absent, so the totals are null — and `assembly_error` is the only thing that says why, being non-null when assembly broke and null when usage was off or the run predates the artifact (all three leave the list null, so nothing else can tell them apart). Cost is null-aware: a `null` per-call `cost` means the model had no rate table (own-GPU/mock/dry-run) and `0` means it was priced at zero, so a `records` total of `null` ("no priced call") is deliberately distinct from `0` ("no inference"), and `cost_partial` flags a mix. The per-pipe rollup on `_meta.usage_by_pipe` is the SDK summary's `by_pipe`, projected row by row onto `{ pipe_code, cost_usd, tokens, calls }` with the same renaming and the same token figure, in the SDK's order: priced pipes by cost descending, unrated pipes after every priced one, ties broken by call count descending and then by pipe code, and the runtime-unattributed calls (a `null` `pipe_code`, one group of their own) after the named pipes when everything else ties. It is carried whenever the run reported a usage list (`[]` for `no_inference`, absent for `unavailable`), unbounded (it rides `_meta`, not the model's context), so a programmatic consumer keeps it.

Moving onto the SDK's summary changed three observable things. `usage` used to be **omitted** when the run reported no list and no assembly error; it is now present with `state: "unavailable"`, null totals and `assembly_error: null`. `assembly_error` is therefore always present, `null` where it used to be absent, and `state` is new. And on a tie in cost and calls, the unattributed (`null` `pipe_code`) group of `_meta.usage_by_pipe` used to sort **first** and now sorts **last**. The `tokens` figure is now the SDK's input and output totals added rather than a sum this server folded itself; the rule — only `input` and `output`, null when no call reported either — and therefore every value it takes are unchanged.

**Run verdict discipline**: `status: "ok"` means the API answered the question about the run — including "it failed" and "not done yet". A FAILED/CANCELLED/TIMED_OUT run is a produced verdict (`status: "ok"` with the terminal `run_status`), and so is a `state: "running"` results lookup. `status: "error"` with one `problem` is reserved for no-verdict conditions, and the problem is the one the call met, built or relayed as Verdicts and errors says:

- **Refused before anything is sent**, a problem the workshop builds: an empty or blank `run_id`, a blank pipe selector (`pipe_code`), no run source supplied, a blank selector and an illegal selector pairing (`files` + `method_ref`, `method_ref` + `method_id`) are each `client.argument_invalid` located at the argument, and several in one call are one problem with an item per fault.
- **Refused by the platform or the runner**, relayed with the code, location and next step it came with: a request-shape refusal at start (such as `request.invalid` or `request.pipe_not_found`), an unknown `run_id` (`run.not_found`), an unknown `method_id` (`pipelex.catalog.not_found`, the caller's to change; the catalog is org-scoped, so a method of another organization reads exactly like a miss), a `method_ref` that does not resolve, a registry-form ref (`request.unsupported` at `method_ref`), an organization out of credit (`pipelex.billing.credit_exhausted`, the account's to fix), a start refused by role (`auth.forbidden`, its `detail` naming the role, which a runner meets on a start of anything but a published version: `mt_…@draft`, a folder, files or an address), and inputs referencing a file another organization stored (the platform's problem, the input's to change, which a key changed since the inputs were prepared meets, after a login to another organization for instance). The execution-locus gate refuses a *submitted bundle* that ships `.py` on a deployment that is not sandbox-hosted, and a stored method's injected source on an id-only start, as `pipelex.deployment.custom_code_requires_sandbox`, and a method declaring its structures as Python classes as `pipelex.deployment.python_structures_refused`.
- **Read by the SDK** from an answer that is no problem document, or from a transport failure: a missing or rejected credential (`auth.missing_credential`, `auth.invalid_credential`), whose summary says which key was sent; an unreachable API (`client.unreachable`); a server without the run routes, such as a bare runner the base URL points at (`runtime.unsupported`, since durable runs need the hosted API); a `5xx` on a read (`runtime.unexpected` or `runtime.unavailable`; a start's is below); and an answer it cannot use, such as a completed result missing `main_stuff` (`client.response_unreadable`, naming the run).

**The SDK tells a missing route from a missing run.** A server without the lifecycle routes is `runtime.unsupported`, whose summary says which API was in use and where its base URL was set, while an unknown run is the platform's `run.not_found` and an unknown method the catalog's `pipelex.catalog.not_found`. A refusal keeps the location the API gave it, whether the start named its method by folder, files, address, id or a mix, since the workshop rewrites no location by request shape.

An unknown `run_id` on the status, results, image and download tools is the platform's `run.not_found`, relayed with its own next step. Runs are org-scoped and live on the deployment that started them, so another organization's run, or one started against another base URL, reads exactly like a miss, which is what a key changed since the run started meets, after a login for instance; the workshop adds no wording of its own about that, and the platform's problem is what the caller reads.

Whether the same call may succeed again is the problem's `retry`, the server's or the SDK's verdict and never the workshop's. An edge's `429`, and its `408` on any call but a start, are `runtime.unavailable` with `retry` `yes` and the `Retry-After` the answer gave, since they refuse a call for its timing rather than its content, while a server without the run routes is `runtime.unsupported`, which running the call again does not fix.

**A start that may have reached the server is never repeated on its own.** A start creates a durable run that spends inference credit, and the hosted `/v1/start` honours an `Idempotency-Key` that `@pipelex/sdk` cannot send yet, so a start retried after a lost acknowledgement starts a second run. Whether a failed start may have created a run is the SDK's reading, stated as `client.outcome_unknown`, whose `retry` is `outcome_unknown` and whose next step (`read_run`) is to look for the run before starting another. The SDK reads it from a transport failure that does not prove nothing was sent (a connection refused or a name that did not resolve proves it), from a `2xx` it could not read (a start the server accepted whose acknowledgement was lost), and from a `408` or a `5xx` other than a `501` whose body is no problem document, which a gateway or a proxy may answer for a request it forwarded. A problem document is the server's own word on the start and is relayed as it came, so the platform's `503` refusing a start before the runner is reached keeps its `retry` of `yes`, as an edge's `429` and a refused connection do. The workshop reads that `retry` alone, never the wording: a failed start whose problem's `retry` is `outcome_unknown` opens its summary with "Run may have started", saying to look for the run before starting it again, which would spend credit a second time, ahead of the problem's own rendering, since a host may show the agent that line alone. When the SDK can send the key, these failures can be retried and this paragraph goes.

**Start-time rejection on the hosted API**: `/v1/start` reports runner-rejected submissions — an invalid bundle, missing required inputs — as a `422` problem carrying the real rejection reason; earlier platform builds answered a generic `503` "Failed to start pipeline". A `503` that still occurs is relayed as the platform's problem, with no advice of the workshop's own, and the `mthds_run` tool description is what nudges validating first — validation gives a structured, repairable verdict, where a start-time rejection only reports the failure.

### Image Display Scope (`mthds_show_images`)

The image tool, `mthds_show_images`, puts the pictures a completed run produced in front of the model, as MCP **image content blocks**. It is the deliberate counterpart to the results tool's free inventory: the results tool says what is there and fetches nothing, and this one fetches and shows. It is a plain tool — no view, no `_meta` channel, no `available_view_specs`.

**Why a tool and not a flag, and why the results tool never inlines.** An image block is cheap to send and **permanent to keep**. The host probe behind this feature (L-260920-fc66db in the workspace ledger) measured a workshop host billing an image block at the model's own native vision price — about 360 tokens for 512×512, 1,400 for 1024×1024 — with its base64 size costing nothing at all; the widely-repeated claim that base64 image data in a tool result is billed as text did not reproduce. But the same probe established the thing that decides the design: once a picture is in a conversation it is in **every prompt that follows**, and nothing takes it back. One picture is a rounding error; an agentic loop that generates twenty is twenty images of permanent context nobody chose to buy. So the cost that matters is not per-call, and no default can be safe. Seeing a picture is an act, with a name a person can say out loud, that nothing fires by accident.

The public MCP input shape is:

```ts
// input
{
  run_id: string;        // the durable run id from the start tool
  images?: string[];     // OPTIONAL selection: pipelex-storage:// references from image_candidates
  indices?: number[];    // OPTIONAL selection: zero-based positions in image_candidates
}
```

`images` and `indices` are mutually exclusive (both supplied is a `client.argument_invalid` no-verdict at `images`, reason `mutually_exclusive`), and an empty array on either is refused rather than read as "all" (reason `empty`). Omitting both shows every candidate, up to the per-call attempt cap.

```ts
// structuredContent
{
  status: "ok" | "error";
  run_id?: string;
  state?: "running" | "completed" | "failed";   // the same reading the results tool reports
  retry_after_seconds?: number | null;          // state=running only
  run_status?: RunStatus;                       // state=failed only
  run_error?: RunError;                         // state=failed only, when the run stored the problem it ended with — as on the results tool
  images?: Array<{                              // state=completed only — one entry per candidate CONSIDERED, in the order considered; bounded, see omitted
    uri: string;
    mime_type?: string;                         // the store's own content type, once the object was fetched — present on the withheld arm too
    bytes?: number;                             // once measured
    inlined: boolean;                           // true ⟺ this picture is one of the image blocks in content
    withheld?: "size" | "budget" | "count" | "type" | "deadline" | "empty";
    error?: Problem;                            // this picture could not be read at all — a full problem, with its own retry
  }>;
  omitted?: number;                             // state=completed only, and only when something was left out — THIS LISTING's truncation, not the run's surplus
  all_inlined?: boolean;                        // state=completed only; about the RUN, so false when a narrowed call left a candidate unconsidered; vacuously true for an empty walk
  problem?: Problem;                            // no-verdict only
}
```

**A machine consumer branches on `images[i].inlined`, never on the presence of a block.** A not-inlined entry always says why: `withheld` names the cap or the gate that stopped it, and `error` carries a per-reference failure as a problem of its own, with its own `retry`. Leaving "no error" to mean both "too big" and "not an image" would be a contract a consumer cannot act on, which is why the vocabulary is closed and exhaustive.

**The order is the order considered, not discovery order.** A selection is answered in the caller's own order — that is what makes `indices: [3, 0]` mean something — and only an absent selection walks in discovery order. The entries and the image blocks follow the same order as each other either way.

**`images` is bounded exactly as the inventory is**, at `MAX_IMAGE_CANDIDATE_ENTRIES`, with the remainder in `omitted` (absent when nothing was left out) and one prose line rather than one entry each. One entry per candidate was itself unbounded output: a run holding hundreds of pictures produced hundreds of `withheld: "count"` entries, and a prose line for each, from a call that fetches six.

**`omitted` counts this listing's truncation, and `all_inlined` answers for the run — they are about different sets, and conflating them was a defect in both.** `omitted` is what the candidates *this call considered* lost to the cap, so it equals the run's own surplus only when the call considered the whole run; a hundred-candidate run with forty named reports `omitted: 8`, not 60. Its guidance is `indices` and not `images`: the references past the cap are exactly the ones nothing enumerates — the results tool truncates at the same 32 and a large run's `main_stuff` is pruned — so there is no reference to name, while `indices` is positional over the run's **full** candidate list, which the selection never caps, and always reaches them. `all_inlined` answers "is everything this run produced now in front of me", so **every** way a candidate can fail to be in front of the caller counts against it: withheld, failed, past the listing's cap, and — the one the walk could not see, since it is handed only the selection — never selected at all. A narrowed call therefore reports `false` whenever the run holds a picture it did not ask for, even where everything it asked for arrived.

**A repeated selection is deduplicated, not refused.** Naming the same picture twice is a plausible slip and refusing the whole call over it helps nobody; obeying it literally is worse than either, since a shown picture is permanent context — a duplicate would spend two of the six attempts, two shares of the byte budget, and put the same picture in every later prompt twice.

**The walk.** Read the run through the results route first, so a `running`, `failed` or candidate-free run is a produced verdict that fetches nothing. Then `collectArtifacts` over the full `main_stuff`, the same key prefilter `image_candidates` uses, and the caller's selection intersected with what the run actually produced — an unknown reference or an out-of-range index is a `client.argument_invalid` no-verdict at `images` / `indices` (reason `not_a_candidate` or `out_of_range`), refused before any network call rather than fetched and reported as missing. Each surviving candidate is then fetched through the SDK's own bounded `fetchArtifact` (fresh presigned link, `redirect: "manual"`, no credentials forwarded, the byte cap checked from `Content-Length` before a byte is read and again per chunk), with the plain-http rule the download tool derives (see Artifact Download Scope) and a 30-second per-image budget.

**The walk carries its own deadline, because a per-image timeout is per image.** The walk is sequential, so six stalled objects accumulated their timeouts into a call of three minutes and more, and a host whose deadline is shorter then failed the *whole* call, losing the pictures that had already arrived along with the reasons for the ones that had not. So `INLINE_IMAGES_DEADLINE_MS` (60s) bounds the walk: a candidate reached with none of it left is `withheld: "deadline"` without being attempted, and partial results always come back.

**It is applied two ways, and the second is the one that is easy to miss.** A per-fetch `timeoutMs` alone does not bound the walk end to end: the SDK resolves the storage reference *before* arming that timer, and the resolve runs under a fixed 30-second budget of its own that only an `AbortSignal` reaches. So a candidate started with 30s left could spend 30s resolving and then a full 30s fetching — **90s of walk against this 60s**, and about 120s of tool call once the run lookup ahead of it is counted, which is squarely inside the range of host deadlines the bound exists to stay under. Each fetch is therefore given both: whichever timeout is smaller, its own or the time left, **and** a signal for the time left. Because the SDK re-throws a caller's abort untouched, this tool's own deadline arrives as a raw `DOMException` rather than an `ArtifactFetchError`, so both catch sites recognise their own abort and withhold with `deadline` — left to the whole-request arm it would report the tool's own time budget as a failure of the request, and as a no-verdict when nothing had yet been inlined.

**A zero-byte object is withheld, not emitted.** Every gate clears for nothing — the declared type is an image type and no cap can be crossed by no bytes — so the block came out as `data: ""`, reported as a picture successfully shown. Hosts and model APIs refuse an empty image, and an image block is permanent, so one that can never render would sit in every later prompt rather than failing once. It is reachable rather than theoretical: nothing between an upload and a stored object enforces a minimum length (`/v1/upload` declares a maximum only, the SDK derives the content type from the filename, and the storage interface stores what it is handed), so a zero-byte `empty.png` prepared as an input and echoed by a run is enough. `withheld: "empty"` says so in the vocabulary a caller already branches on.

**The content-type gate is the store's answer, not the route's guess.** `ResolvedArtifact.content_type` is documented by the SDK as the platform's guess from the reference's *extension*; the object store's own `content-type` header is what the runtime stored with the object. So the gate reads the fetched response's header, accepts exactly `image/png`, `image/jpeg`, `image/gif` and `image/webp`, and cancels the body of anything else unread (`withheld: "type"`, with `mime_type` saying what it actually was). **No SVG**: it is not a model-accepted image type, and it is a script-bearing document in a renderer.

**The caps, and what each one is measuring.** Three named constants, all in `capabilities/shared.ts` with the probe's provenance in their comments:

| Constant | Value | What it bounds, and why that number |
| --- | --- | --- |
| `MAX_INLINE_IMAGE_BYTES` | 4 MiB | One picture. **Not a cost control** — bytes are free and pixels are billed. It is a transport guard (Claude Code's stdio transport carried an 8 MiB PNG and died on a 12 MiB one with `Connection closed`, taking the tool call with it) and a point of diminishing returns (above roughly a megabyte every host measured re-encodes the image anyway). |
| `INLINE_IMAGES_BUDGET` | 6 MiB | One call's total, so a whole tool result stays well under the message size that killed the 12 MiB rung. |
| `MAX_INLINE_IMAGES` | 6 | **Attempts**, not successes — one call makes at most this many network exchanges whatever the run produced, and buys at most this much permanent context. |

The walk stops *attempting* at the count, stops *inlining* at the first picture that does not fit the per-image cap or the remaining budget, and keeps walking to report the rest — a smaller sibling later in the list still gets its chance. Oversize means withheld and named, **never resized**: an image library in `dependencies` is install weight every `npx @pipelex/mcp` user pays on every session, and `mthds_download_artifacts` already brings the full file to disk.

**The emitted block, and the one thing that must not change.** Each inlined picture is `{ type: "image", data, mimeType, _meta: { uri } }`, appended to `content` after the text block so a host that renders in order shows the summary and then the pictures. `_meta.uri` is the storage reference, so a programmatic consumer can correlate a block with the `main_stuff` value it came from; `_meta` never reaches the model, so it costs the conversation nothing.

**No `annotations`, ever.** The MCP standard's optional `annotations` hint (audience, priority) looks harmless and is not: the host probe found that **Codex refuses an annotated image block outright**, with an opaque `tool call error … Unexpected response type`, against a control proving the identical block without them is accepted and the picture reaches the model. Shipping with annotations would have broken the whole feature on one of three named workshop hosts, diagnosable only from production. A unit test asserts that no emitted block carries the key.

**And the `_meta` the block does carry is measured, not assumed.** `_meta` is an optional field the standard permits on an image block — and so was `annotations`, so nothing about the first followed from the second. The probe's original variants (`full`, `bare`, `text`) never sent a block-level `_meta`, which left the shape this server actually ships untested on every host. A fourth variant, `meta`, closes that: run against codex-cli 0.153.4 it was **accepted**, and the model described the picture correctly, so the shipped block is measured on the host that refused the other optional field. Keep the variant — the next host, or the next version of this one, is measured the same way.

**Verdict discipline, and where a whole-request refusal falls.** Once the walk has run the result is produced (`status: "ok"`, `state: "completed"`), discriminated on `all_inlined`. Partial success is a produced verdict: pictures that arrived are never discarded because a sibling failed, and a whole-request refusal part-way through (the resolve route rejecting the credential, say) lands on the entry being worked, stops the walk, and reports the untouched rest as `withheld: "count"`. `status: "error"` keeps its usual meaning — a bad request shape, an unreachable or misconfigured API, a malformed report.

**Those two sentences used to contradict each other, and the tie is broken on whether anything was shown.** A whole-request refusal is not about any one picture, so when it stopped the walk before **any** picture arrived there is no partial answer to report: nothing was produced, which is precisely what `status: "error"` means here. Answering `status: "ok"` there told a consumer the call had succeeded on a deployment where every call fails deterministically — a 402 plan limit, a 403, a 404 from a runner with no bulk-resolve route, an unreachable host — and it buried the cause, an exhausted plan or a refused key above all, under a generic "no picture could be shown" line. It also diverged from `mthds_download_artifacts`, which answers `status: "error"` for the identical class. So: **a whole-request refusal that showed nothing is a no-verdict**, carrying the refusal's own problem and its rendering; once one picture has arrived, partial success is a produced verdict as described above and the refusal rides its own entry.

**The summary** names how many pictures follow and that they are now part of the conversation, lists any withheld candidate under `## Withheld` with its reason, or its problem on one line (its detail, the client's sentence when there is one, its code and its next step), the `mthds_codegen` pattern,, and reminds the caller the full files can be saved. A completed run with no candidate at all is one sentence and no blocks.

### Server instructions and the text budget

**Server instructions**: The workshop sets a short MCP `instructions` string that hosts surface to the model. It is the map, not the manual, and it is front-loaded, because a host that cuts keeps the head: it opens with what the server is for and the order of the steps, states the ways to name a method once, and ends with the rules that hold everywhere — a run spends inference credit, and a picture the image tool returns stays in the conversation for every turn that follows, so it is shown when someone wants to look at it rather than by reflex. The instructions embed no catalog, because a host may cache instructions. They tell the model to use its `mthds_*` tools for all method work when the connector's `pipelex_*` tools are also present, and never to mix the two servers (see The workshop and the Pipelex connector). Right after the flow, they say where a method stops, in one sentence: a method only turns the inputs it is given into results, and fetching from mail, drives or business systems, running on a schedule and writing back are up to whatever calls it. The instructions are the one text an agent reads without calling a tool or loading a skill, so this is where a model that goes straight to the tools learns that "read my mail every morning and post the digest" is a method plus the read, the schedule and the post around it. Concretely, they open with "This is the Pipelex plugin's local workshop…", give the flow — `mthds_list_methods`, `mthds_validate`, `mthds_inputs_template`, `mthds_prepare_inputs`, `mthds_run`, the status and results tools, then `mthds_show_images` or `mthds_download_artifacts` — name `mthds_codegen`, the catalog pair and `mthds_models`, state the ways to name a method once for every method-taking tool, prefer the `{ path }` file form, prompt a catalog search reactively only, and say there are no views. They do not name `mthds_list_files`, whose own description carries its trigger (see Files Discovery Scope).

**The selector sentence names every method-taking tool and every selector it takes**, because a sentence that named `method_id` and omitted `method_ref` told the model a published method could not be validated, templated, prepared or run — so the by-address flow was never offered, however fully the tools supported it. The same sentence names the method's folder (`method_dir`) as the form to prefer for a method on disk, then `{ path }` files over inline content, since a folder sends every file of the method, which a hand-made list can forget. The workshop's contract test holds that, and holds that the step order is complete, in order, near the head of the text. Everything per-tool stays out: when to call a tool, and the contract rules needed before calling it (which forms may be combined, what an absent `method_id` means to a save), live in the tool `description`; parameter detail, such as the address grammar, lives in the field descriptions.

**Text budget**: The workshop's `instructions` and every tool `description` are held to 1,800 Unicode code points, measured on what the server emits by `npm run check:tool-texts`, which `make check` and CI run. Claude Code cuts each of those texts at 2,048 characters, so a text over the cap reaches the model with its tail missing; the ceiling leaves room for one added sentence and a margin for hosts whose cap has not been measured. A fact goes in the last layer that still reaches the model when it needs it: the instructions carry the map (what the server is for, the ways to name a method, the order of the steps, the rules that apply everywhere), a tool description says when to call that tool and states the contract rules needed before calling it, a field description carries parameter detail, and a result summary carries what matters only after the call.

### The files union and the path trust boundaries

**A method named by its folder or its files travels as one method tree.** Every method-taking tool (`mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`, `mthds_run`) sends the method it reads from `method_dir` or `files` as a tree, every file at its path inside the tree with its exact bytes, through the `tree` form `@pipelex/sdk` gives each route: a `MethodTreeSource`, the listing, its digest and a reader over the bytes the workshop already holds, which is also the form `mthds_save_method` sends a draft in. The SDK reads the deployment's version to learn which form it takes, then sends the tree as the MTHDS protocol's `files` map from tree path to file entry: a small tree inline, each file as its text, or as `{ base64 }` when it is not UTF-8 text, and a larger one by hash, each file as `{ sha256, size }`, after uploading the blobs the organization's storage lacks; which it does is the SDK's decision, never the workshop's. No route is sent a list of `{ content, source }` items, which the runner refuses, nor `resources`: a file a step reads rides the tree. So a folder validated, run and saved is one tree, its `.mthds` files, its templates, its Python modules and its data alike: what a validation checks is what a run runs and what a save keeps.

Every method-taking tool takes `files` as one per-item union, inline content or a file path:

```ts
type SubmittedFileInput = { content: string; uri?: string | null } | { path: string };
```

- The **workshop reads `{ path }` from disk** before invoking the capability — this is its headline feature: near-constant token cost, byte-accurate reads, and real provenance, since each file is sent under its path in the tree, so diagnostics locate to files the agent can open and edit. Inline `{ content, uri? }` items stay accepted, for a `.mthds` file the agent holds only in the conversation.

An item is one arm or the other; on a malformed item carrying both keys, `content` wins (first-match union semantics) and `path` is ignored.

A `{ path }` item is read through the resolution seam, not by the schema: each capability's context carries an optional file resolver, which the workshop sets, and the resolution runs ahead of the request-shape checks, which see the tree as a method named. A context built without a resolver rejects every `{ path }` item as `client.argument_invalid` at `files[i].path` and every `method_dir` at `method_dir`, with the reason `not_readable_here`; the workshop never builds one.

**The tree a list of files makes.**

- **Where each file sits.** The `{ path }` items keep where they sit relative to one another. Listed alone, the tree is rooted at the deepest directory holding them all, and each file's tree path is its path from there, written with `/` and taken in Unicode NFC. That is the name the runner's diagnostics give the file and the path a step's `template_file` leads to, so `[{ path: "invoice/invoice.mthds" }, { path: "invoice/templates/invoice.xlsx" }]` sends `invoice.mthds` and `templates/invoice.xlsx`, and a step of `invoice.mthds` whose `template_file` is `templates/invoice.xlsx` finds its template. The root is decided on the paths the caller wrote, resolved against the working directory without following a link. **Beside an inline item**, which has no directory of its own, the tree is rooted at the working directory instead, and each `{ path }` item is sent under its path from there, so `[{ content, uri: "invoice.mthds" }, { path: "templates/invoice.xlsx" }]` sends `invoice.mthds` and `templates/invoice.xlsx`, where a lone `{ path }` rooted at its own directory would have lost the `templates/` a step of the inline file names; a `{ path }` item outside the working directory cannot be sent beside an inline item. A path given twice, under any spelling that resolves alike, is one file of the tree.
- **The inline items** are `.mthds` files at the tree's top, each under its `uri`'s last segment when that names a `.mthds` file a tree may hold and no other file of the tree takes or collides with, else under `bundle.mthds`, `bundle-2.mthds` and on. The `uri` is provenance: it may name the file, never a directory, so an inline item cannot place a file anywhere else in the tree.
- **What is refused before anything is sent.** First, a list holding no `.mthds` file, neither an inline item nor a `{ path }` item with that extension, makes no method: it is refused as `client.argument_invalid` at `files` (reason `no_method_file`) before any item is stated, read or hashed, as a folder with no `.mthds` file at its top is, so none of its files reaches the SDK, which would upload a heavy one to the organization's storage before the runner refused the tree. Then, each a `client.argument_invalid` at the item, its `reason` naming the rule: a blank path at `files[i].path`, empty content at `files[i].content` and a blank `uri` at `files[i].uri`, and once the files are read, a `{ path }` item that is a `.mthds` file holding nothing but whitespace, at `files[i].path`, naming it as `<path> is empty.`; a tree path the MTHDS standard refuses, one no machine keeps alike, through `mthds`' own `treePathViolation`; a name the standard never admits to a method's tree, a segment starting with a dot, a `__pycache__` or `node_modules` directory or a run's inputs file, since the folder form would never send it either; two paths that collide, once case is ignored or by one naming the other's directory, at each item involved; and two different paths that name one tree path once Unicode-normalized, at the second, since every machine reads them as one name. A list of files holds none of the exclusions a folder's `.gitignore` files and `METHODS.toml` state: the caller chose each file.
- **In what order, and how much.** No byte of a file is read before the whole list has passed every check that needs none. Each `{ path }` item is first stated through the resolver: its extension, where it lies, that it is a regular file, and its size. Then the tree paths and their refusals above, then the deployment's limits on a method's tree, the ones a folder is held to (see The method folder), asked for every list, an inline-only one included: the limit on one file at the item, on its stated size or an inline item's text, then the file count and the total at `files`, on the sizes known before any read. Only then are the files read, one at a time, each held to the limit on one file and the running total held to the limit on all, so a file that grew since its stat stops the reads at the limit rather than past it. A refusal names the limit, its number and whose it is, the deployment's or the workshop's own.
- **What the result says.** `files_sent` lists every file of the tree, in tree path order: each `{ path }` item as the caller gave it, and each inline item under the tree path it was sent at, so the caller sees which name an inline item took.

**Path trust boundary (read side).** `{ path }` values resolve relative to the server's working directory — the host spawns the server in the workspace. Two bounds apply, both on the submitted item before a byte of it is read. **What** it reads: the `{ path }` arm of `files` is contracted to a fixed list of extensions, chosen where the server builds its resolver and never by the caller — `.mthds`, and the template suffixes `.html`, `.xlsx`, `.docx` and `.pptx` that pipelex's `DocGenFormat.template_file_suffix` names, one per format, every file read as bytes — and the resolver rejects any other extension (case-insensitive) *before touching the filesystem*, so it never opens a `.env`, `.git/config`, or key file a prompt-injected path could point at. A method needing any other file, a Python module or a data file, is sent as its folder, where the standard's membership rule decides what belongs. **Where** it reads: containment is enforced by real-path check — the resolved target (symlinks followed) must live inside the working-directory subtree — and the target must be a regular file, read to at most one byte past the size its stat gave, so a file that changed while it was read is refused rather than sent. A wrong extension (reason `wrong_extension`), an escape (`outside_workspace`) and a file over the deployment's limit for one file (`file_too_large`) are `client.argument_invalid` problems located at `files[i].path`; a missing file and a file that is not a regular file are `client.file_unreadable`, naming the path and the reason (`not_found`, `not_a_file`, or the system's error code), and a file that changed while it was read is `client.workspace_busy`. MCP client roots are deliberately not consulted — cwd containment is the simple, correct core; honoring host-declared roots is a possible later widening.

Both bounds are checked on the *submitted* items, before any read, which is what closes the prompt-injection vector: an injected request is the only thing that threat controls, and it can choose neither the kind of file nor a target outside the workspace. Two residuals require a local process with **write** access to the workspace and are accepted, not mitigated: (a) a symbolic link inside the workspace, named with an extension the arm takes and pointing at another file inside the workspace, since the extension gate reads the submitted name and not the resolved target, and (b) a TOCTOU symlink swap between the real-path check and the read. Both demand an attacker who already holds direct read access to those same files, and the secret guard below still reads every byte such a link leads to before any is sent.

**The secret guard.** Before a byte of a method's tree leaves the machine, every tool that sends one — the method-taking tools, from `method_dir` or `files`, and `mthds_save_method` — refuses a tree holding what looks like a secret (`src/capabilities/secret-guard.ts`): a file whose name is a known secret file's, matched on its last segment ignoring case (a `.key` file whose bytes are not a zip archive, since a Keynote deck is one while a DER key, binary and holding no PEM block, is not, key and certificate stores such as `.p12`, `.pfx`, `.jks` and `.keystore`, a PuTTY `.ppk`, a KeePass `.kdbx`, an SSH key under its default `id_rsa`, `id_dsa`, `id_ecdsa` or `id_ed25519` name, a `credentials` or `credentials.json` file, an OAuth `client_secret…json` export), whatever it holds, or a file whose bytes hold a well-known key format, in whatever encoding: every format is ASCII, so the bytes are read as Latin-1, which keeps every ASCII run of a UTF-8, Latin-1 or cp1252 file and of a binary one, and a file holding NUL bytes is read once more without them, which is how a key reads in UTF-16, with or without its byte order mark: a PEM private key block, an AWS access key id, a GitHub, GitLab, Slack or npm token, a Stripe live key, a Google, Anthropic, OpenAI or Hugging Face API key, or a Pipelex API key (`plx_sk_`). Each format is the prefix its provider puts on its keys so scanners find them, with enough of the key's body after it that prose mentioning the prefix does not match. A `.pem` file is no name rule, since one is as often a public certificate: a private key in one is a PEM block, which the text search refuses. Inline items are read too: their text came through the conversation, but the guard is what keeps a key from reaching the organization's storage. The refusal is a `client.argument_invalid` no-verdict whose `reason` is `secret_suspected`, naming each file as the caller finds it and what it matched, **never the matched text**, since a refusal is shown to a model and may be logged: one problem at `method_dir` naming every file for a folder, and for a list of files one fault at each item holding one, `files[i].path` or `files[i].content`, several faults folding into one problem whose `errors` list them. Its message says a key belongs in the environment, that a method's files are kept in the organization's storage where every member can read them, how to keep the file out of what is sent — for a folder, a `.gitignore` line inside it or a name starting with a dot, and for a list of files, leaving the file off the list, since the list names each file it sends and refuses a name starting with a dot — and that a file refused for its name alone that is no key can be renamed. The membership rule already keeps the commonest secret files out by construction, since `.env`, `.ssh/` and every other dotfile start with a dot. The guard runs on the bytes the tool read, after every other refusal of the tree and before anything is sent, so a refused call sends nothing of the method: the only request it may have made is the limits handshake, `GET /v1/version`, a metadata read that carries no file, which the listing needs before it reads. It is a tripwire for the well-known shapes, never a promise that a tree holds no secret: a password in prose, a scanned contract or a payslip goes through it.

**Template files.** A `PipeDocGen` step fills a template file its method carries — an HTML template for a PDF, the workbook, document or deck itself for a spreadsheet, a Word document or a slide deck — named by the step's `template_file`, a path from the `.mthds` file holding the step. The runner finds it in the tree it was sent, where that path leads, so a template travels as any file of the tree does: a folder sends it with everything else, and a list of files carries it as a `{ path }` item beside the `.mthds` files, keeping where it sits relative to them. No file is keyed by the step that names it, and a step whose template the tree does not hold makes the method invalid, which the runner reports. A template file has no inline form: an inline item always carries a `.mthds` file's text, so binary bytes never travel through the conversation. The template's bytes are not in `structuredContent`, `content` or `_meta`, where `files_sent` lists its path alone, and the method graph page does not embed it.

**What the platform refuses of a tree.** A refusal of a tree the request carried is relayed as the platform answered it, with the location it gave, which names the request's own field (such as `tree.files`) and is never rewritten to the argument the caller passed, `files` or `method_dir`; the result's `files_sent` says which files left the machine. A map the standard refuses, a path that is no tree path or two that collide, which the workshop refuses before sending, so this is a rule the receiver holds that the workshop does not, and a tree past one of the deployment's limits, which the SDK has already sent once more on a fresh handshake, are `method.package_invalid`, its `params` naming the path or the limit. A hash entry stating another size than the blob the organization holds is `request.invalid`, which no argument of the caller's fixes, since the workshop states the sizes of the bytes it read. A blob gone between its upload and the request is `request.blobs_missing`, which the SDK answers once by uploading the blobs it names and sending the request again, handing a second such answer back. A `413` is relayed as the deployment answered it, a `request.too_large` problem naming the limit when the deployment sends one, its code, domain, retry and next step kept, and the workshop adds to its `message` what it can tell of which part of the call made it too large, which neither the answer nor the SDK says. It first tells which step answered the `413`, from the route the SDK names in its error's message: a `413` from `POST /v1/blobs/missing`, or a file's upload refused with a `413` (`MethodFileTransferError`), came while the method's files were prepared, before the request itself, so it names the method's files and never the inputs. A `413` from the tool's own route (`/v1/validate`, `/v1/codegen`, `/v1/pipe-io`, `/v1/start`) is weighed by what rode that request: the tree's inline map, measured once as the SDK measures it, a file that is not UTF-8 text as its base64, and a start's inputs as JSON; how the tree travelled is asked of the version handshake and decided as the SDK decides it, inline to a deployment keeping no blob store, and otherwise inline when its weight is within the lower of `INLINE_TREE_MAX_BYTES` and the `max_inline_bytes` the handshake announces, by hash past it. A tree that travelled inline is named as the cause, with its weight and why it went inline, only when nothing else of any size rode the request, with the cure: keep what is not part of the method out of its folder, or send fewer or smaller files. A start's inputs are named alone only when none of the method's files rode it, the method named by `method_ref` or `method_id` or its files gone by hash, with the cure of uploading large file inputs through `mthds_prepare_inputs` or passing them as URLs. A start whose inputs rode beside an inline tree names both causes with the weights measured, and so does one whose handshake did not answer, which leaves how the tree went unknown; with no inputs, that tree is named with the same hedge. A `413` neither step can be told for, and one on a request that carried neither files nor inputs, such as a start by reference with none or a tree gone by hash, is relayed with nothing added. A file the platform's storage would not take is the SDK's `MethodFileTransferError`, whose problem carries no link: `runtime.unavailable` for a transfer that can succeed later, `client.response_unreadable` for a refusal or for bytes that are not the file named. A request that named its method by `method_ref` or `method_id` sent no tree, and every refusal of it is the route's own.

**The method folder (`method_dir`).** Every method-taking tool takes the method's folder as a source beside `files`, and `mthds_save_method` takes nothing else (see Catalog Write Scope). **Every tool sends the folder's whole tree**, the tree a save stores: a validation checks, and a run runs, every file a save would keep, and a file the folder holds that the caller did not think of is seen in `files_sent` rather than sent unseen. The request carries the tree and nothing else, with no manifest and no package identity, and an address or an id is resolved as before.

- **Where.** `method_dir` resolves against the working directory, and its real path, symlinks followed, must lie inside it, be a directory, and hold a `.mthds` file at its top. A folder that is missing, outside, not a directory, or that holds its `.mthds` files only further down is refused, the last naming the deeper files so the caller can point at the right folder.
- **Which files belong to it.** The MTHDS standard's membership rule, through `mthds`' own lister, `listMethodTree`, which is held to the standard's conformance corpus, read with the folder as the tree's root (never a `METHODS.toml` further up): a file under the folder belongs to it unless a segment of its path starts with a dot (`.git/`, `.venv/`, `.env`, and the folder's own `.pipelex/`), it sits under a `__pycache__/` or a `node_modules/` directory, it sits under a directory holding a `pyvenv.cfg` file, which marks a Python virtual environment whatever its name (a folder whose top holds one is a virtual environment, none of it a method's, and is refused), it sits under a directory below the folder's top holding a `.git` entry, which marks a nested repository, a submodule's `.git` file included, or under one holding a `METHODS.toml`, which marks a nested package, or the `.gitignore` files inside the folder exclude it, read with git's own matching, or the folder's `METHODS.toml` excludes it in its `[package] exclude`. A `.gitignore` above the folder and the user's global excludes do not count, so one folder yields the same files on every machine. A symbolic link refuses the folder, naming its path, and so does a socket, a FIFO or a device; it is never followed and never skipped silently. Tree paths are taken in Unicode NFC, and two names that collide once normalized or case-folded refuse the folder. **One file is left out on top of the standard's rule**, by the workshop's wrapper (`src/capabilities/method-tree.ts`): the method graph page `mthds_validate` writes, a `method-graph.html` at the folder's top carrying the page's generator mark, so a validation never changes what the folder sends or saves; a `method-graph.html` without the mark is the user's file and belongs. A run's inputs file, a file named exactly `inputs.json` or `inputs.toml` at any depth, holds one run's data and never the method's, and the standard's own `run_inputs` rule leaves it out (`mthds` 0.33): it is neither listed, counted nor read, and a symbolic link of either name is left out with it rather than refusing the folder. A folder holding nothing but those files is an empty tree, refused as the standard refuses one, never given the digest of nothing.
- **The deployment's limits bind every tool**, since every tool sends the whole tree. The workshop asks the platform it talks to for the limits it holds a method's tree to (`GET /v1/version`'s `limits.method_tree`, through the SDK's `methodTreeLimits()`), keeps one answer per base URL for ten minutes, in one memory every tool that sends a tree shares, and waits at most three seconds for it; a handshake that failed or timed out is remembered for a minute, so the calls that follow do not each wait again, and an answer arriving late is still kept. The limits are held exactly on the files kept, so the graph page, which the wrapper leaves out and never sends, never counts against them; since `mthds`' walk counts every member the standard keeps, the walk itself takes each limit widened by an allowance for that page, 1,000 files and 64 MiB, and stops at the first widened bound crossed, before a file is hashed. Either refuses the folder as `client.argument_invalid` at `method_dir` (reason `too_many_files`, `file_too_large` or `tree_too_large`), naming the limit, its number and whose it is: a limit the deployment announced is the deployment's, while one the deployment did not announce is worded as the workshop's own scan limit, never blamed on the deployment. A walk stopped at a widened bound is reported against the limit under it, with that limit's owner and its own number, and says that the walk stopped past that limit plus the allowance. Every limit the deployment does not announce, and every limit when the handshake failed or timed out, takes the workshop's own value: at most 10,000 files, 32 MiB for one file and 64 MiB in all, the byte limits being the runner's defaults, which the hosted platform takes as its own. So a tool pointed at a home directory costs a refusal rather than a long scan, never reads an unbounded tree into memory, and the platform, which enforces its limits whatever a sender read, refuses what is too large for it. A sample PDF beside a `main.mthds` is part of the method and is sent; a file that is not belongs outside the folder, or behind a `.gitignore` line inside it.
- **How it reads.** Everything is decided on the listing before a byte is read, and the listing carries each file's size and SHA-256. Each file is then read once, opened without following a final symbolic link (`O_NOFOLLOW` where the platform has one), read to at most one byte past its listed size, and checked against both, so a link swapped in after the listing is refused rather than followed and a file that changed since is refused rather than sent. A file whose name is held on disk in another Unicode normalization than the NFC tree path, which a file system that keeps names byte for byte does not find under the tree path, is found by matching each segment against its directory's entries and read with the same bound, never read whole first; a link swapped into a directory component in between is the read side's accepted residual. The bytes read are the bytes the secret guard checks and the SDK sends, never read again. An empty `.mthds` file is refused: on the method-taking tools, a `.mthds` file of the tree holding nothing but whitespace, which no runner loads as a bundle, refuses the folder before anything is sent, naming it as `<method_dir>/<path> is empty.` Every refusal of the folder is a problem at `method_dir`, `client.argument_invalid` for a rule the folder breaks and `client.file_unreadable` for one it cannot read, whose message names a `.gitignore` inside the folder wherever keeping a file out would fix it.
- **What the result says.** A result produced once the request was sent carries `files_sent`, every file of the tree, each as `method_dir` joined with its tree path, in tree path order, on a no-verdict error too, since the files left the machine either way; the Markdown summary closes with the same list under `## Files sent`. A refusal of what was sent keeps the location the route gave it, which names the request's own field and is never rewritten to `method_dir`. A failure before sending carries no `files_sent`, whether the folder was refused, the secret guard refused it, the client could not be built or the SDK refused an argument before the request left the machine.
- **A run's files beside the method.** Nothing in the rule knows a run-artifacts directory by name, so one inside the folder is part of it unless a `.gitignore` keeps it out: its files would be sent and listed, and a symbolic link in it would refuse the folder. `mthds_download_artifacts` marks a directory it creates with a `.gitignore` of `*`: for the default location the topmost directory the call creates, `runs/` on a first download or `runs/<run_id>` under an existing `runs/`, and for a `dir` the caller names the directory the run lands in (see Artifact Download Scope), so a run it saves into a method's folder stays out of the method; a directory made before that, or by another tool, needs the same file.

**The inputs file (`inputs_path`).** `mthds_run` and `mthds_prepare_inputs` take their inputs as an inline `inputs` object or as `inputs_path`, the path of a `.json` file holding the same object, so an agent whose inputs a script computes, or that run to tens of kilobytes, never retypes them into the conversation. It is a separate argument, mutually exclusive with `inputs`, and deliberately **not** a `{ path }` shape inside `inputs`: an inputs map may legitimately declare an input named `path`, and overloading the map would make that input unpassable. It is read under the read-side bounds above, by its own resolver: the extension gate is `.json` (case-insensitive), checked before the filesystem is touched, so an injected path cannot make the workshop open a `.env` and send it as a run's inputs; the target must be a regular file whose real path, symlinks followed, lies inside the working-directory subtree; and it is capped at 1 MiB (`MAX_INPUTS_FILE_BYTES`), checked on the stat before the read, because inputs ride a request's JSON body and a set past that size is an asset that belongs in a file input. Inputs are no part of a method's tree, which may not come from disk at all, so no rule of the tree applies to the file, but the working-directory containment does. So a method folder's own `inputs.json`, which the standard's membership rule keeps out of what `method_dir` sends, is read as the run's inputs when `inputs_path` names it, a symbolic link of that name followed under the same containment. The content must parse as JSON and be one object; a leading UTF-8 byte-order mark, which some Windows editors and PowerShell write, is skipped first. Every refusal — both forms supplied, a blank path, a wrong extension, an escape, a missing or non-regular file, a file over the cap, invalid JSON, a value that is not an object — is a problem at `inputs_path`: `client.argument_invalid`, its reason naming the rule (`mutually_exclusive`, `empty`, `wrong_extension`, `outside_workspace`, `file_too_large`, `not_json`, `not_an_object`), or `client.file_unreadable` for a file that is missing or cannot be read. Once read, the object takes the inline path unchanged: `mthds_prepare_inputs` uploads its file-bearing values, and a relative local path inside it is read by the SDK's walk exactly as the same path given inline would be. As with `{ path }`, the resolution is a seam: the run and prepare contexts carry an optional `inputsResolver`, which the workshop sets, and a context built without one refuses `inputs_path` instructively and asks for inline `inputs`, so a deployment that cannot read the user's disk — the hosted console — never reads one.

**Path trust boundary (write side).** The tools that write into the user's workspace — `mthds_download_artifacts` saves a run, `mthds_codegen` writes a generated tree under `output_dir`, the catalog pair pulls a method's tree and leaves a link file, `mthds_validate` writes the method graph page beside the files it read — share one containment routine, on real paths, enforced on both sides of the one `mkdir`. A lexical check refuses `..` escapes and absolute paths before the filesystem is touched; then the deepest *existing* ancestor of the target directory is real-path-checked **before** `mkdir`, so a symlink inside the workspace pointing outside cannot have directories created at its target; then the created directory is real-path-checked again, which closes the window between the two. Refusals are `client.argument_invalid` at the caller's own field (`dir`, `output_dir`), with the reason `outside_workspace` or `not_a_directory`, and a destination that cannot be used is `client.write_failed`. Containment is also available *without* creation, which is what lets a writer contain every destination before deciding whether to write any of them.

**What the writers do NOT share is policy, and they must not.** `mthds_download_artifacts` never overwrites — neither the `main_stuff.json` it writes itself nor the files the SDK downloads beside it — because a collision there means two different files. `mthds_codegen` must overwrite its own previous output and only that, because its paths come from the engine and the lock hashes them. The method graph page takes codegen's side, for the same reason: it is regenerated on every validation and must land on the same name. One shared "write a file" helper would either suffix a regeneration or let a download clobber. Each scope states its own policy; the boundary above is all that is common.

### Model Deck Scope (`mthds_models`)

`mthds_models` answers for the model references a method's pipes can name in their `model` field. Without `reference` it lists the model deck, read through `@pipelex/sdk`'s `models()` (`GET /v1/models`, the MTHDS Protocol's `ModelDeck`); with `reference` it asks the runner to check that reference, through the SDK's `checkModelReference()` (`GET /v1/models/check`, the Pipelex API's reference check, whose contract is `pipelex-models-api.md` in the `conformance` repository). It is read-only, has no view and no `_meta`, and spends no inference credit. It replaces what the CLI era's `mthds-agent models` and `mthds-agent check-model` gave an authoring agent, which the CLI-free plugin reaches only through this server.

The public MCP input is:

```ts
{
  category?: "llm" | "extract" | "img_gen" | "search" | "judgment" | "doc_gen"; // for a PipeLLM, PipeExtract, PipeImgGen, PipeSearch, PipeJudge, PipeDocGen; doc_gen only with reference
  reference?: string; // $preset, @alias, ~waterfall, a bare handle, or a preset:/alias:/waterfall:/handle: prefix
}
```

Without `reference` the tool lists the deck; with it, it checks that reference. **The `category` filter is closed and what the tool reads is open.** The filter takes the categories the runner's check covers and nothing else, since a runner refuses any other value on `?type=`: the protocol's, which are `mthds`'s `MODEL_CATEGORIES`, then `doc_gen`, the family of `PipeDocGen`, which is `@pipelex/sdk`'s `ModelCheckCategory`. The table of the pipe type that names each category is total over that set, so a category the protocol or the SDK gains or drops fails this repository's build until the tool is taught to describe it. The deck it reads is held to the protocol's reader rule, "A client reading a model list MUST NOT fail it because an entry carries a category it does not recognize; it keeps that entry with its raw value or leaves it out.", and the tool keeps it: a category of the deck it does not know, which a runner of a later protocol may report, is listed and checked under the runner's own name. A check without a category covers every category the runner checks in, `doc_gen` included. The protocol does not define `doc_gen`, so the deck has no such category and the listing leaves it out: `doc_gen` without `reference` is a `client.argument_invalid` refusal at `category` (reason `not_listed`), while a check takes it like any other category.

**What the deck holds.** On the Pipelex runner, the protocol's flat `models` list carries the presets, each stamped with its category, and two extensions keyed by category carry the rest: `aliases` (an alias's name to its model handle) and `waterfalls` (a waterfall's name to the handles it tries in order). The same alias name can exist in several categories pointing at different models, which is why the extensions are keyed by category and why the tool answers per category. **The deck lists no model handle as such**: a handle appears only as an alias's target or a waterfall's step.

**Listing.** A listing asks the route for the category when one is given, and projects one entry per category in scope: the protocol's, in its order, each present even when it is empty, then, when no category was named, each category the tool does not know that holds a preset, an alias or a waterfall, in the order the deck first names it:

```ts
{
  status: "ok";
  category?: ModelCategory;
  deck: Array<{
    category: string; // a ModelCategory, or a category the tool does not know under the runner's name
    presets: string[];
    aliases: Array<{ reference: string; target: string }>;
    waterfalls: Array<{ reference: string; fallbacks: string[] }>;
  }>;
}
```

Every reference is written as it is typed in a method (`$writing-factual`, `@best-gpt`, `~robust-llm`), in the runner's order. The summary repeats the deck by category, names each category's pipe type or says that the tool does not know the category, says what each kind of reference is for and that presets are the ones to prefer, and ends with how to check a reference.

**Checking.** A check sends the reference as the caller wrote it, with the category when one was given, and relays the runner's verdict. The runner parses the reference as a validation does (a sigil, else a spelled-out namespace, else a bare handle), resolves it against every name its deck holds and every model it can call, and draws its suggestions by the rule a failing validation follows. So the tool parses nothing, ranks nothing and reads no deck for a check: a reference the runner finds `resolved` in a category is one a validation accepts there, and one it finds `not_found` is one a validation refuses. The tool answers:

```ts
{
  status: "ok";
  category?: ModelCheckCategory; // the category asked, absent when none was: the protocol's or doc_gen
  reference: string;        // the caller's, trimmed by the runner
  kind: "preset" | "alias" | "waterfall" | "handle";
  name: string;             // the reference without its sigil or namespace
  resolution: "resolved" | "not_found";
  matches: Array<{
    category: string;
    resolves_to: string | null;  // what a run through the reference calls now; null when it reaches no model
    target?: string;             // preset, alias: the deck's binding, which may itself be a reference
    description?: string | null; // preset
    fallbacks?: string[];        // waterfall: its steps, in order
    via?: string[];              // handle: the presets, aliases and waterfalls whose binding names it
  }>;
  suggestions: string[];
  other_kinds: string[];
  other_categories: string[];
}
```

- `resolved`: the reference resolves in at least one category in scope. `matches` has one entry per such category, in the runner's order of categories, each carrying the fields of the reference's kind and no other. A match whose `resolves_to` is `null` is a name the runner holds whose binding reaches no model it can call (a backend it has not enabled, a waterfall none of whose steps it serves, an alias cycle): a validation accepts it, but a run through it fails, so the summary flags it as a warning.
- `not_found`: the reference resolves in no category in scope. This is definitive for every kind, a bare handle included, since the runner knows every model it can call. A resolution the tool does not know, which a later runner may send, reads as `not_found`, under the check's reader rule that such a reference is treated as unresolved.

On `not_found`, `suggestions` holds the nearest names the runner offers, `other_kinds` the same name under another sigil (`best-gpt` exists as `@best-gpt`) and, when a category was named, `other_categories` the categories where the same reference resolves (`$gen-image` checked as `llm` resolves in `img_gen`). All three are empty on `resolved`, and every name in them is written as a method writes it. The summary puts the wrong sigil first, since it is the likeliest fault. Every category a verdict names is read open, as on the listing: one the tool does not know is relayed under the runner's name and labelled as one it cannot place on a pipe type.

**The verdict is checked, then relayed.** The SDK hands it back as parsed JSON, so the tool checks its shape before relaying it: a verdict that is not an object, a `kind` outside the four, a match missing its `resolves_to` or a field of its kind, and a list that is not a list of strings are a `client.response_unreadable` no-verdict. A field the shape does not name is dropped, so `structuredContent` holds exactly what the output schema declares.

**The deck is not the account.** The deck is what the runner can route to, not what the caller's account may use: a gateway can refuse a listed model when a run starts, after validation has passed. The tool description and every summary say so. An account-level check belongs to hosted validation, not to this tool.

**Malformed and failed reads.** A listing checks the deck rather than trusting it: a deck that is not an object, a missing `models` list, an entry without a name, a category that is present but is not a non-blank string, and an extension that is present but shaped wrong are a `client.response_unreadable` no-verdict. An entry whose category is absent or null is skipped, since it has no category to be listed under, an unknown category is kept as described above, and an absent extension reads as empty, since `aliases` and `waterfalls` are the runner's rather than the protocol's. A refusal of either route is the problem the runner or the platform sent, relayed as is: a runner older than the protocol that defined a category refuses it (a runner before protocol 0.7.0 refuses `judgment`), and a check's reference the runner cannot read (a blank reference, a sigil or a namespace with nothing after it, or one past the runner's length limit) is refused with the runner's own reason and the field it names, since the tool checks no reference itself and the runner's rule is the only one. A bare 404 is a runner too old to serve the route, which pipelex-api serves from pipelex 0.78.0, and reads as `request.not_found`, the Markdown naming the API in use. An unreachable API, a refused credential, a paywall and a server fault are relayed the same way, on either route.

### Validation Scope (`mthds_validate`)

The public MCP input shape is:

```ts
{
  method_dir?: string;          // the method's folder, read by the workshop — see The method folder
  files?: SubmittedFileInput[]; // { content, uri? } | { path } — see The files union
  method_ref?: string;          // published method address — github.com/<owner>/<repo>[/<selector>][@<tag>]
  method_id?: string;           // catalog id (mt_…) of a registered method
  graph_page?: boolean;         // default true — write method-graph.html into method_dir or beside { path } files (see The method graph page)
}
```

Exactly one of (`method_dir`, non-empty `files`, `method_ref`, `method_id`) is required — the tooling rule from Method Selectors: no selector is `client.argument_invalid` at `files`, a second selector is `client.argument_invalid` at the fixed field for its pair (`files` beside a folder at `method_dir`, `method_ref` beside a folder or files, `method_id` beside any of the others), and a supplied-but-blank selector is `client.argument_invalid` at that selector. Both selector forms are **server pass-throughs** carried on `POST /v1/validate` itself via `@pipelex/sdk`'s `validate({ method_ref })` / `validate({ method_id })`: the runner resolves an address through the same fetch path as a `method_ref` run, the hosted platform resolves an id against the org's catalog and injects the stored source before the runner sees the request. Nothing is expanded client-side, and diagnostics get their source labels from the package's (or the stored method's) real file names rather than an MCP-side `uri` relabel. Selector-resolution failures are no-verdict results per Method Selectors, each the platform's or the runner's problem with the location it gave: an unknown or foreign-org id or no package at the address (404), a ref that does not parse or fetch (422), either execution-locus refusal (a `501` or a `422`), a registry-form ref (501); an organization whose credit does not cover the call is the account's problem the platform states, such as `pipelex.billing.credit_exhausted`, as on every route. A credential is required for by-id calls.

The result carries no graph and none of the form's artifacts, because the workshop registers no views: those are view-only data.

The capability always permits pending signatures, always requests rendered markdown, and always requests the `input_form` and `output_form` views from the Pipelex API, the second being what feeds `main_pipe.output.images`.

The structured output is:

```ts
{
  status: "ok" | "error";
  is_valid: boolean;
  is_runnable: boolean;
  pending_signatures: string[];
  available_view_specs: Array<"dry_run_graph" | "input_form">;  // always [] on the workshop
  main_pipe?: MainPipeSignature;   // present on every valid verdict with an effective entry pipe — see The main pipe's signature
  graph_page?: {                   // present when the method came from method_dir or every file came as { path }, and graph_page was not false
    path: string;                  // where the page is, or would have been, relative to the working directory
    written: boolean;
    error?: Problem;               // why it was not written, as a full problem — never a change to the verdict
  };
  warnings?: ProblemItem[];        // a valid verdict's advisory findings, one problem item each, as the API sent them; absent when there are none
  errors?: ProblemItem[];          // is_valid false only — the faults, one problem item each, as the API sent them
  files_sent?: string[];           // method_dir and files — every file of the tree sent (see The files union)
  problem?: Problem;               // no-verdict only (see Verdicts and errors)
}
```

`warnings` relays the valid verdict's advisory findings, which never change `is_valid`, so a consumer that branches on them, such as a template authoring skill, reads them from the contract rather than from the Markdown, which lists them too. A finding of a `PipeDocGen` step's template check in the template file it was sent, a field that matches no input of the step for instance, is a `pipelex.docgen.template_warning` item located at its pipe (`location.pipe`), whose `params` carry `template_file` (the file as the step names it) and `template_location` (the place in the file, in the engine's words). `errors` carries an invalid verdict's faults the same way, one problem item each with its own code, detail and location, and a `suggested_fix` when the API has one: they are the verdict's findings about the method, never a no-verdict `problem`. The check runs on the template the tree carries, so a method whose tree lacks a step's template has no such findings and no valid verdict.

The MCP `content` text is the API's rendered Markdown, which is not duplicated in `structuredContent`, with the signature line appended under its own heading when `main_pipe` was produced, and a `## Method graph` section last when the page was written or tried, after any error details.

#### The method graph page (`graph_page`)

A builder in a host that renders no views never saw the method's flowchart; the `pipelex` CLI used to give one as a local HTML file, and the CLI-free plugin had lost it. So when the method comes from its folder, or every item of `files` is a `{ path }`, `mthds_validate` also writes `method-graph.html` into the directory holding the `.mthds` files — the deepest directory holding them all, when they span several, each file then named by its path relative to it, which for a folder is the folder itself, since it holds a `.mthds` file at its top — and reports it as `graph_page`. A folder leaves the page out of the tree it sends, by the page's generator mark (see The method folder).

- **What the page is.** A standalone HTML file that embeds the method's `.mthds` files, exactly as validated, and none of its other files, in the `mthds-sources` element `@pipelex/mthds-ui`'s standalone viewer reads, and loads that viewer and elkjs from jsDelivr, each pinned by exact version and by Subresource Integrity with `crossorigin="anonymous"`. The viewer builds the static graph in the browser, the way a Mermaid page carries its diagram's text and loads the renderer. So the page opens from disk with no server and no Pipelex install, costs no API call to draw, and draws a method that does not validate as well, with the notes reading its source turned up on the viewer's toolbar. It needs a network connection: offline, or when a CDN file fails its integrity check, it shows a line saying so. Every `<` in the embedded text is written `\u003c`, so no method text can close the element or change how the page parses. The embed is written by mthds-ui's own `serializeMthdsSourcesEmbed`, from the release this repository installs, and the page loads the viewer of that same release, so the writer and the reader of the element cannot drift apart; the build inlines the serializer, so the published package gains no dependency.
- **When it is written.** On every call whose method came from `method_dir` or whose files all came as `{ path }`, whatever the verdict and even when the API produced none, since the page draws from the files and not from the report; so it never shows an older version of the method than the one on disk last validated. Nothing is written for inline `{ content }` files, a mix of the two arms, `method_ref`, `method_id`, a request refused before the API call, or `graph_page: false`. `mthds_save_method`'s validation leg writes none either: its result never reports a page.
- **How it is written.** Through the write-side boundary, on real paths, and with `mthds_codegen`'s policy: a missing page is created exclusively, and an existing one is replaced only when it carries the page's own generator mark (`<meta name="generator" content="@pipelex/mcp method-graph">`). A file without it, a symlink or a directory at that name is left untouched and reported as `graph_page.error`, a `client.target_exists` problem at `graph_page`. A directory that vanished or a page that appeared while it was being written is `client.workspace_busy`, a write that failed `client.write_failed`, a page that could not be inspected `client.file_unreadable`, and a file whose directory resolves outside the working directory `client.argument_invalid` (reason `outside_workspace`), each at `graph_page` too; a working directory the server cannot resolve is `client.not_configured`. The summary's `## Method graph` section says why on one line, with the problem's code. A page that could not be written never changes the verdict, and the call's `status` and `isError` are the validation's alone.
- **What the summary says.** Where the page is; on its first write, also that it opens in a browser, loads its viewer from the CDN, is rewritten on every validation, and is a generated file a project under version control may want to ignore.
- **Annotations.** `mthds_validate` is therefore not read-only. It stays non-destructive, because the only file it ever replaces is a page carrying its own mark, whose whole content derives from the files beside it, and because Codex asks for confirmation before every destructive call, which would put a prompt on the call a design loop makes after every edit.

### Inputs Template Scope (`mthds_inputs_template`)

`mthds_inputs_template` projects a pipe's declared inputs as a fill-in template. It reads one `POST /v1/pipe-io` through `@pipelex/sdk`'s `pipeIo()` for the one pipe, with no dry run, and projects the template client-side from that pipe's input-form descriptor. It is a plain tool: no view, no `_meta` channel, no `available_view_specs` field — the template is small structured data the model must read, so it belongs in `structuredContent`.

The public MCP input shape is:

```ts
{
  method_dir?: string;          // the method's folder, read by the workshop — see The method folder
  files?: SubmittedFileInput[]; // { content, uri? } | { path } — see The files union
  method_ref?: string;          // published method address — github.com/<owner>/<repo>[/<selector>][@<tag>]
  method_id?: string;           // catalog id (mt_…) of a registered method
  pipe_ref?: string;
  explicit?: boolean;
  format?: "json" | "toml";
}
```

- Exactly one of (`method_dir`, non-empty `files`, `method_ref`, `method_id`) is required — the tooling rule from Method Selectors, with the same `client.argument_invalid` refusals at the same locations (no selector at `files`; a second or blank selector at that selector). Every selector is a **server pass-through** on `POST /v1/pipe-io`: nothing is expanded or fetched client-side.
- `method_dir` and `files` mirror `mthds_validate`'s: the method is sent as one tree, through `pipeIo`'s `tree` form, and the result lists it in `files_sent` (see The files union).
- `method_ref` projects a published method by its address: the runner fetches the package's `.mthds` files at the tag and resolves the closure, so a package that ships Python is answered here on any deployment (see the execution-locus gate above). The registry form stays a 501. Selector-resolution failures are no-verdict results per Method Selectors, each the runner's problem with the location it gave.
- `method_id` projects the content its selector names (see Method versions, on two platforms): the hosted platform resolves the id against the key's organization and forwards the stored files, so a key is required. An unknown or foreign-org id is the catalog's 404 miss, `pipelex.catalog.not_found` (the catalog is org-scoped, so a foreign-org method reads exactly like a miss), and a stored method the platform cannot resolve into files, such as one with no MTHDS source yet, is a 422 problem the platform states; both are relayed as they came. A bare pipelex-api runner has no catalog and does not resolve the selector.
- `pipe_ref` is the pipe to project, as a qualified `domain.pipe_code` — the same value `mthds_run` takes as `pipe_code` (the names mirror their routes; see Naming Conventions). Optional; the route's selection chain then settles the method's entry pipe: a fetched package's manifest `main_pipe`, else the closure's single `main_pipe` declaration — the pipe `mthds_prepare_inputs` prepares and a run naming none executes. A `pipe_ref` the closure does not declare, and a method that settles no entry pipe or several, are refused by the route with a 422 problem, `request.pipe_not_found` or `request.pipe_ambiguous`, which the tool relays as a no-verdict with the route's own location and params, the pipes it suggests among them, whatever named the method.
- `explicit` defaults to **true** (the ceremonial `{concept, content}` envelope per input — each input's declared concept ref plus its canonical content shape, which is what an agent needs to fill the template correctly); `false` requests the light template shape (bare example values). The default was flipped from `false` to `true` for agent UX (concept refs and canonical shapes by default); the light shape stays one flag away.
- `format` defaults to **"json"** (parsed template object in `inputs`); `"toml"` returns raw TOML text in `inputs_toml`, preserving concept comments and key order.

**The projection.** The route's valid arm is keyed by exactly the `pipe_ref` it resolved, and the template is projected from `input_form[pipe_ref]` by `inputsTemplateFor` (`src/capabilities/inputs-template.ts`, over `mthds/protocol`'s `projectInputsTemplate` and `renderInputsTemplate`). `explicit` and `format` are the projection's options and never travel to the route. The TOML text and the summary's JSON fence are the standard's own rendering, byte-identical with the Python twin; the `inputs` object is the same projection as plain JSON. A method with pending signatures still gets its template, since the route reports runnability without refusing and the template describes the pipe's declared inputs.

The structured output is:

```ts
{
  status: "ok" | "error";
  is_valid: boolean;
  pipe_ref?: string;
  format?: "json" | "toml";
  explicit?: boolean;
  inputs?: Record<string, unknown>;
  inputs_toml?: string;
  files_sent?: string[];           // method_dir and files — every file of the tree sent (see The files union)
  errors?: ProblemItem[];          // is_valid false only — the closure's faults, one problem item each
  problem?: Problem;               // no-verdict only (see Verdicts and errors)
}
```

Verdict discipline is identical to `mthds_validate`: any *produced* verdict is `status: "ok"`, discriminated on `is_valid`. On the valid arm the tool returns the resolved `pipe_ref` (always qualified), the echoed `format`/`explicit`, and the template on exactly one of `inputs` / `inputs_toml` (chosen by `format`; the unused field is absent). A closure that does not load is a produced verdict: the route's invalid arm becomes `is_valid: false` with its faults as `errors`, one problem item each, and its `message` in the summary, and consumers branch on the field, never on transport. `status: "error"` with one `problem` is reserved for no-verdict conditions, each built or relayed as Verdicts and errors says: a bad request shape (`client.argument_invalid` at the argument), an unreachable or misconfigured API or a refused credential, a refused pipe selection (the route's `request.pipe_not_found` or `request.pipe_ambiguous`), a selector-resolution failure, the route's refusal of what was sent, such as too many files or an oversized one, at the location the route gave, a deployment that does not serve `/v1/pipe-io` (a runner's bare 404, which the SDK reads as `request.not_found`, its summary saying which API was in use and where its base URL was set; the hosted gateway answers an unlisted path with a 403, which the SDK reads as `auth.invalid_credential`), a valid answer carrying no descriptor the projection can walk for the resolved pipe (`client.response_unreadable` of the `200` it came on), and server faults (`runtime.unexpected` or `runtime.unavailable`).

The route returns no `rendered_markdown`, so the capability composes its own `content` summary: the resolved pipe, the template itself in a fenced code block (` ```json ` or ` ```toml ` to match `format`), and after it the next step — call `mthds_prepare_inputs` once the template is filled, or go straight to `mthds_run` when every file value is already an http(s) URL or a `pipelex-storage://` reference; on the TOML arm it first says to convert the filled template to a JSON object, since both tools take `inputs` as one. The next step rides the summary rather than the tool description because the model reads it exactly when it has a template in hand, and because the description and the instructions are held under the length a host shows. Unlike validation, the template is deliberately duplicated between `structuredContent` and the summary — it is the payload the model must read, and some hosts read prose more reliably than structured fields. An invalid closure's summary carries the route's `message` and one line per fault.

### Codegen Scope (`mthds_codegen`)

`mthds_codegen` projects a method's concept set into typed artifacts in the language the calling context needs, wrapping `POST /v1/codegen` through `@pipelex/sdk`'s `codegen()`. It is a plain tool: no view, no `_meta` channel, no `available_view_specs` field — decided on 2026-08-29: the summary's fenced blocks already carry the artifacts to every host. It takes the same thin-front-end posture as every other tool here: the engine projects, the MCP selects the method, chooses nothing on the user's behalf that the model can choose from context, and hands the artifacts back verbatim so the codegen trust chain (stamps, `codegen.lock`, the offline check — `conformance/specs/pipelex-codegen.md`, in the `conformance` repository beside the tests that verify it) survives the trip through a conversation.

The public MCP input shape is:

```ts
{
  method_dir?: string;           // the method's folder, read by the workshop — see The method folder
  files?: SubmittedFileInput[];   // { content, uri? } | { path } — see The files union
  method_ref?: string;            // published method address — github.com/<owner>/<repo>[/<selector>][@<tag>]
  method_id?: string;             // catalog id (mt_…) of a registered method — resolved by the hosted platform
  target: "ts-zod" | "python-pydantic" | "python-structures";
  output_dir?: string;            // write the tree here instead of returning its content
}
```

- Exactly one of (`method_dir`, non-empty `files`, `method_ref`, `method_id`) — the tooling rule from Method Selectors, with the same locations. **Every selector is a server pass-through**: `method_ref` is resolved by the runner (the repository fetched at the tag), `method_id` by the hosted platform's tooling selector (`PipelexHostedToolingExtensions.method_id` on the SDK's `CodegenRequest`). There is no fetch-and-forward leg and no method source in the conversation; the tool is hosted-first for `method_id` exactly as `mthds_validate` is.
- `target` is **required and has no default** — the engine's flavor identifier, verbatim. There is no `language: "typescript" | "python"` alias layer: the codegen spec rejects a flat enum that mixes artifact kinds with output formats, the two Python targets differ by *audience* rather than language, and an alias would be a second vocabulary to keep in sync with the engine's. The enum is typed from the SDK's `CodegenTarget` and closed in both directions (`satisfies` rejects a target the SDK dropped; a `Record` over the union rejects one it gained), so a widened SDK widens the tool in a deliberate edit that also has to write the new target's profile. Picking the target is the tool's whole point, so the decision rule lives in the tool description and is derived from those profiles — the description states only who each target is for, while the `target` field description adds what each emits and the file names, which is parameter detail the length budget keeps out of the description: the user's explicit request wins; a TypeScript or JavaScript project wants `ts-zod` (`types.ts` — zod schemas and inferred types, depending only on zod — plus `binder.ts`, a parse/serialize pair per concept; keep both); a Python consumer with no Pipelex runtime wants `python-pydantic` (`models.py`, plain `BaseModel`s); a Pipelex host or a `@pipe_func` implementation wants `python-structures` (`structures.py`, runtime `StructuredContent` classes). File names are fixed per target; what varies per method is the type names inside them. Field keys are wire-native snake_case in every target, TypeScript included.
- `kind` is **not exposed**: the engine serves one kind (`types`, the crate's whole concept set), and a single-member enum on every `tools/list` spends tokens on a choice that does not exist. The capability always sends `kind: "types"` and never a `pipe_ref` (the route rejects one on `types` with a 422 rather than ignoring it). When per-pipe kinds ship (`docs`, `tools`, `tests`), `kind?` and `pipe_ref?` are added together as optional fields — additive, not a rename.

The structured output is:

```ts
{
  status: "ok" | "error";
  is_valid: boolean;
  target?: "ts-zod" | "python-pydantic" | "python-structures";
  kind?: "types";
  crate_fingerprint?: string;
  engine_version?: string;
  artifacts?: Array<{ path: string; bytes: number; content?: string; written_to?: string }>;
  lock?: { filename: string; bytes: number; content?: string; written_to?: string };
  truncated?: boolean;             // some content was withheld for size — whole files only, never a cut file
  // The written arm (output_dir was supplied and the write succeeded):
  output_dir?: string;             // the generated directory, relative to the working directory
  is_current?: boolean;            // the offline check's verdict over what landed on disk
  orphans?: string[];              // always present on this arm, empty when clean
  orphans_truncated?: boolean;     // a walk bound tripped, so orphan detection is partial
  drifts?: unknown[];              // present when non-empty — any drift that is NOT an orphan
  files_sent?: string[];           // method_dir and files — every file of the tree sent (see The files union)
  errors?: ProblemItem[];          // is_valid false only — one problem item per fault, the items mthds_validate lists
  problem?: Problem;               // no-verdict only (see Verdicts and errors)
}
```

**Verdict discipline** is `mthds_inputs_template`'s: a produced verdict is `status: "ok"` discriminated on `is_valid`; an unresolvable closure is `is_valid: false` with its faults as `errors`, one problem item each (the same items `mthds_validate` lists, so the assistant repairs through the validation flow and retries); `status: "error"` with one `problem` is reserved for no-verdict conditions. On the valid arm the tool echoes `target` and `kind`, the crate fingerprint and engine version the stamps carry, and the artifact set plus its lock.

**Artifacts and the lock are handed over verbatim, always.** No reformatting, no re-serialized lock, no trimmed trailing newline: any byte change breaks the stamp's content hash and the lock's artifact hash, and the point of the trust chain is that a tree written from this tool is byte-identical to a local `pipelex codegen types` run, so `pipelex codegen check` and the SDK's `runCodegenCheck` pass on it. `bytes` is each file's UTF-8 size and is present even when its content is withheld. Prettier and ruff settings that rewrite generated files are the user's concern. What arrives is checked rather than trusted, because what arrives is what gets written into a user's tree — and the check runs on **both arms**, not only the write path: without `output_dir` the bytes go to a model that will write them, so a report the write arm would refuse is one the inline arm must not hand over either. One notion of a valid report is what keeps the two arms from diverging.

The check is the SDK's own: every valid response is fed to `runCodegenCheck` in memory before anything is written or relayed. That one call establishes far more than a hand-rolled rule set would — the lock parses and its `lock_version` is readable, every path in the lock and in the artifact set is safe, canonical and unique (control characters and drive prefixes included), and every artifact's stamp and body hash agree with the lock. A `CodegenLockError` and a non-current verdict are equally contract violations, and both are no-verdicts, `client.response_unreadable` of the `200` the report came on, whose message says what did not hold together and that nothing was written. What remains hand-checked is only what the SDK cannot know: that `artifacts`, `lock` and `lock_filename` are present and typed, that every artifact path is one the check can verify (`isStampableArtifactPath`), that **the report answers the request that was sent** — `target` and `kind` are documented as an echo of the request's projection axes, and a report for another language is internally current and passes the offline check, so only comparing the echo catches it, which matters most on the write arm where `output_dir` would otherwise fill with another language's files and be reported as a current tree — and that **`lock_filename` is exactly `codegen.lock`** — the one name the SDK's own contract fixes, pinned rather than merely checked for being bare. That last rule is not decoration, and it earns three things at once: the writer joins the lock filename under the generated directory and the inline arm hands it to a model that will do the same, so a `lock_filename` of `../../…` is the one value in the whole path that would otherwise reach a write uncontained; the lock lands where the offline check looks for it, so `pipelex codegen check` finds the tree this tool says passes; and it cannot **alias an artifact path**, since an artifact must carry a stampable suffix to reach here and so can never be `codegen.lock` — which closes the one case the in-memory preflight structurally cannot see, `runCodegenCheck` taking the lock content separately and never learning its filename, where the writer would overwrite an artifact it had just written with lock text and report that as drift. Containment in the writer still stands on its own — canonical is not the same as contained — but the rule belongs where it holds for both arms.

**The streams rule is written for size.** The artifacts are the payload the model must act on and also the largest thing this server puts in a response. `content` is present on `structuredContent.artifacts[].content` and `lock.content`, and the Markdown summary repeats each file in a fenced block tagged for its language (` ```ts `, ` ```python `, ` ```toml ` for the lock; the fence grows past any backtick run inside the file), because some hosts read prose more reliably than structured fields and the model needs the exact bytes to write files itself. Both copies are bounded by one budget over the whole set (`CODEGEN_CONTENT_CAP`, 64 KiB of UTF-8 — sized so a small method never truncates and a large concept set degrades rather than breaks), applied **by whole file, in order, stopping at the first that does not fit**, with **the lock's bytes reserved off the top** and the artifacts filling what remains. Filling artifacts first and letting the lock fall off the end would drop the trust anchor to fit the code it anchors, leaving the model code it cannot check under an instruction promising the offline check will pass on what it writes; the lock is the smallest file in the set, so the reservation costs the artifacts almost nothing. A lock that alone exceeds the cap is the one remaining truncation of it, and nothing rides then. The withheld files carry `path` and `bytes` with `content` absent, and `truncated: true` names what happened. A half file is worse than no file (a partial `types.ts` neither compiles nor passes the check), and a `binder.ts` without its `types.ts` is no more useful than none. The summary of a truncated result lists the withheld files with their sizes and points at generating locally with the CLI. Nothing rides `_meta`: there is no view to feed, and a non-LLM consumer reading the raw MCP result sees exactly what the model sees.

**Errors are relayed, not classified**, as on every tool (see Verdicts and errors). A refusal of the request keeps the location the route gave it, whatever named the method, since the workshop rewrites none by request shape: on a files request an unresolvable closure is a produced verdict on this route and the client sends only `kind: "types"` with no `pipe_ref`, so a refusal there is about the projection axes, and a by-ref or by-id request's refusals are the runner's or the platform's problems about the selector. An organization whose credit or plan does not cover the call is the account's problem the platform states. A `401` the SDK reads as `auth.missing_credential` and a `403` as `auth.invalid_credential`, each with the note saying which key was sent. The hosted authorizer requires the `FF_PLAYGROUND` feature flag for `/v1/codegen` beside the plan checks, so a caller whose key every other tool accepts can still be refused here; the workshop adds no sentence of its own about that gate, and the platform's problem is what the caller reads. A `5xx` is `runtime.unexpected` or `runtime.unavailable`, and a malformed report `client.response_unreadable`. The credential is `PIPELEX_API_KEY`.

#### The write arm (`output_dir`)

Passing `output_dir` writes the generated tree to disk instead of returning its content, so the artifact bytes never enter the conversation at all. The directory is relative to the server's working directory, created if missing, and required to stay inside it — the write-side path trust boundary in The files union and the path trust boundaries.

**`output_dir` is advertised with `readOnlyHint: false` and `destructiveHint: true`** on the tool, because an annotation says what a tool *may* do, and a call with `output_dir` overwrites the stamped files a previous generation wrote.

**Overwrite policy is the inverse of `mthds_download_artifacts`'s, deliberately.** That tool never overwrites, because a collision there means two different files. This one *must* overwrite, because its paths come from the engine, the lock hashes them, and regeneration has to land on the same names. So it overwrites its own previous output and only that:

- A destination that does not exist is written.
- A destination that is a **regular file carrying a codegen stamp** — for an artifact, the file's text starts with the begin marker in its suffix's comment syntax; for the lock, the text starts with `# codegen.lock` — is overwritten. **Whether or not it was hand-edited**: the stamp says not to edit by hand, edits below it are discarded without warning, and a formatter run over the generated directory must not become a permanent block on regeneration. The lock's test pins the `# codegen.lock` prefix rather than the engine's full header sentence, whose trailing prose the lock parser ignores entirely — a verbatim match would turn a reworded header into a "foreign file" refusal on a file this tool wrote itself.
- **Anything else refuses the whole write**: an unstamped file, a **symlink whatever it points at** (destinations are inspected with `lstat`, because an overwrite through a symlink writes wherever it points), a directory, anything not a regular file. The refusal is `client.target_exists` at `output_dir`, names the file, and points at using a dedicated generated directory.

**"Whole tree or nothing" describes the refusal path, not a crash.** Every destination — the lock included — is contained *before* anything is created, and every existing one is inspected before anything is written, so a refusal leaves the tree byte-identical, directories included. There is no temp-and-rename dance: what matters is that a half-written tree is *detectable*, which the lock already makes true, so the guarantee is **detectable**, not atomic. A failure mid-write is `client.write_failed` at `output_dir`, its message naming what landed and saying to call again with the same `output_dir` — regeneration overwrites its own files, so the retry finds the stamped files it left and proceeds. The window between inspection and write is accepted: the workshop is one user in one working directory.

**After writing, the tree is checked against itself.** The directory is walked recursively — symlinks skipped, vendor and VCS directories pruned (`node_modules`, `.git`, `dist`, `build`, `target`, `.next`, `.venv`, `__pycache__`) — filtered with `isStampableArtifactPath`, decoded with a **strict** UTF-8 decoder (`readFile(p, "utf8")` substitutes U+FFFD and never throws, so a corrupted artifact could otherwise hash to the locked value and report current), and handed to `runCodegenCheck` with **the lock re-read from disk**, not the copy that was meant to be written — passing the in-memory copy would leave the one write the check exists to verify unverified. The walk is bounded by a file count and a decoded-bytes budget, because `output_dir: "."` is legal and would otherwise read a whole repository into a long-lived stdio process; the bounds apply to orphan candidates only, so the files just written are always read back and a tripped bound can never fabricate a `missing` drift. A tripped bound sets `orphans_truncated`, and the summary then says orphan detection was partial rather than reporting a clean tree it did not fully see.

**Orphans are reported and never deleted.** A stamped file the new lock does not list — left by an earlier generation into the same directory, a different target, or an engine version that renamed an artifact — comes back in `orphans` and stays on disk. Consequence, stated rather than discovered: **a directory holding more than one generation stays non-current by design.** The summary says what the orphans actually are and that a dedicated directory per generation is the fix; "delete them by hand" would be wrong advice the moment a user has generated two methods into one place.

**On the written arm, content is withheld from every stream.** `artifacts[]` carries `path`, `bytes` and `written_to`; `lock` carries `filename`, `bytes` and `written_to`; the summary names the files and the check verdict and carries **no fenced blocks**. `truncated` is always `false` — nothing rode, so nothing was withheld for size. **`output_dir`'s presence is the arm discriminator** (with `written_to` per file), not `truncated` and not a new field: a third encoding of one fact is a third thing to keep aligned.

**A refused or failed write is a no-verdict `status: "error"`, never a fallback to riding the content.** The caller asked for a write and none happened; silently inlining tens of kilobytes they did not ask for would both blow the budget and change the shape they expected, and the retry is one cheap call with a fixed `output_dir`. The problem is the writer's, located at `output_dir`: `client.target_exists` for a destination it does not own, `client.write_failed` for a write that failed part-way, and `client.file_unreadable` for a file of the tree it could not read back, one that is not UTF-8 among them. A lock the check could not read back is the SDK's own `client.file_unreadable`, whose message says the files are on disk and to verify them with `pipelex codegen check`, and an artifact path from the API that would land outside `output_dir` is `client.response_unreadable`, since the API broke its own contract. A **produced-invalid** verdict never touches disk at all, on either arm: it carries no artifacts, so the write arm is never reached.

### Prepare Inputs Scope (`mthds_prepare_inputs`)

`mthds_prepare_inputs` prepares a pipe's *filled* inputs for a run: it uploads the file-bearing values to Pipelex storage and rewrites them to the canonical content shape carrying `pipelex-storage://`, so the returned `inputs` can be handed straight to `mthds_run`. It wraps `@pipelex/sdk`'s `prepareInputs`. It is a plain tool: no view, no `_meta` channel, no `available_view_specs` — the prepared inputs are small structured data the model reads directly.

Where it sits in the flow: `mthds_inputs_template` produces the empty template → the agent fills it (with text, `http(s)` URLs, local file references, or inline bytes) → `mthds_prepare_inputs` turns the filled inputs into run-ready inputs → `mthds_run` executes them. The prepare step is what makes local/byte assets runnable; an inputs set that is already all pass-through (`http(s)` URLs, existing `pipelex-storage://` URIs) can skip prepare and go straight to `mthds_run`.

The public MCP input shape is:

```ts
{
  method_dir?: string;            // the method's folder, read by the workshop — see The method folder
  files?: SubmittedFileInput[];    // { content, uri? } | { path } — the method closure (signature source)
  method_ref?: string;             // published method address — github.com/<owner>/<repo>[/<selector>][@<tag>]
  method_id?: string;              // catalog id (mt_…) of a registered method
  pipe_ref?: string;               // qualified domain.pipe_code; omit for the method's entry pipe
  inputs?: Record<string, unknown>; // the caller's FILLED inputs (the mthds_inputs_template output, populated) — compact or the explicit {concept, content} envelope
  inputs_path?: string;            // or the path of a .json file holding that object — see The inputs file
  kind?: "uploaded" | "test";      // what the uploads are recorded as — see What an upload is recorded as
}
```

- Exactly one of (`method_dir`, non-empty `files`, `method_ref`, `method_id`) is required — the tooling rule from Method Selectors (no selector is `client.argument_invalid` at `files`; a second selector, or a blank one, is `client.argument_invalid` at the offending field). Every selector is a **server pass-through**: the selector rides `POST /v1/pipe-io`, which resolves an address on the runner and an id on the hosted platform. Nothing is expanded client-side, so this tool no longer carries a `getMethodClosure` leg of its own.

  **A `method_ref` here is not subject to the execution-locus gate.** `/v1/pipe-io` fetches a package's `.mthds` files alone, as the routes of `mthds_inputs_template` and `mthds_codegen` do, so a published package shipping `.py` prepares on any deployment; its run is refused at the start by `mthds_run` off a deployment that is not sandbox-hosted. Before `@pipelex/sdk` 0.27.0 the signature came from `/v1/validate`, which applies the gate, and such a package was a `403` here.

- `pipe_ref` is the pipe whose declared signature drives asset identification — the same qualified value as `mthds_inputs_template`'s `pipe_ref` and `mthds_run`'s `pipe_code`. Optional; it defaults server-side to the method's entry pipe, the one `/v1/pipe-io` settles (for a package whose manifest names a `main_pipe`, that pipe). A method that settles none, such as one whose domains declare several `main_pipe`s, and a `pipe_ref` the method does not declare are refused by the route, and the refusal is a no-verdict carrying the route's own problem, `request.pipe_ambiguous` or `request.pipe_not_found`. A bare `pipe_code` and an `alias->domain.pipe_code` ref, which the SDK's `prepareInputs` refuses before any request since preparation names a pipe by its qualified ref and covers the method's own pipes, are refused by the tool itself first, as `client.argument_invalid` at `pipe_ref` (reason `not_qualified` or `dependency_pipe`), so a folder's files are known never to have been sent. Unlike `mthds_inputs_template` there is no `format` / `explicit` — this tool returns prepared inputs, not a template.
- The filled inputs are **required** (they are the whole point), as exactly one of `inputs` or `inputs_path` (see The inputs file): neither is `client.argument_invalid` at `inputs` (reason `missing`), both is `client.argument_invalid` at `inputs_path` (reason `mutually_exclusive`). A loaded file is prepared exactly as the same object inline. An empty object `{}` is accepted (nothing to prepare); it passes through and uploads nothing. **Both filled template shapes are accepted**: the compact value, and the explicit `{concept, content}` envelope that `mthds_inputs_template` returns by default (`explicit: true`). An envelope's inner `content` is interpreted exactly as the compact value would be, and the envelope is **preserved on output** — the `concept` annotation rides through to the run, which the runtime accepts as a first-class explicit form. The envelope is recognized by the strict rule "a plain object whose keys are *exactly* `concept` and `content`", so a declared structured concept that merely happens to carry both fields is not misread as one. This matches `@pipelex/sdk`'s `prepareInputs` (0.9.0+).

**Signature-driven asset identification (inherited from the SDK).** The SDK resolves the pipe's declared signature from the **input-form descriptor** — one `POST /v1/pipe-io` for the one pipe, the MTHDS standard's own artifact — and walks the caller's `inputs` top-down against it. **The descriptor is the classifier, never the value's shape**: a `document` / `image` node marks a file position at any depth, an `object` recurses through `fields`, a `list` through `item`, and every other kind passes through. That is what makes an *optional* nested file field prepare like a required one, and a `text` field merely *named* `url` stay untouched — the two misclassifications the earlier rendered-template signature made, whose file signal was a `url`-bearing dict. Only values at descriptor-declared file positions are treated as assets; the identical bare string at a Text position is never touched. Per file-bearing value:

| Source at a file-bearing input | Action |
| --- | --- |
| Local filesystem path (Node) / `data:` URL / inline bytes | Uploaded to Pipelex storage → rewritten to `pipelex-storage://` |
| Existing `pipelex-storage://` URI | Already prepared — passes through unchanged |
| `http(s)` URL | Passes through unchanged |


**The asset boundary.** Uploading a local or byte asset means reading the caller's bytes, which only the server co-located with them can do. The workshop prepares local paths, `data:` URLs and bytes within its asset boundary, uploading with the user's `PIPELEX_API_KEY`, and it delegates the whole walk to the SDK's `prepareInputs`. It always uploads.

**The upload size ceiling is ~7.5 MiB decoded, not the documented 50 MiB.** Measured 2026-07-31 against the hosted API: 7.4 MiB uploads, 7.5 MiB is rejected `413`. `POST /v1/upload` takes a base64 JSON body behind an AWS API Gateway HTTP API integration, whose 10 MiB request limit is a hard quota; base64's 4/3 inflation puts the decoded wall at exactly 7.5 MiB. The app-level `MAX_UPLOAD_MIB` (50 MiB) is therefore unreachable through the public gateway and must not be quoted as the limit of any path that crosses it.

The ceiling is enforced client-side by `SizeGuardedPipelexApiClient` (`capabilities/upload-ceiling.ts`), a `PipelexApiClient` subclass overriding `upload` — the one seam the MCP owns, since the SDK's `prepareInputs` walk reaches the wire through `this.upload`. One override therefore covers the workshop's delegated walk. It throws the same `RejectedAssetError` the SDK maps a real `413` onto, `reason: "too_large"` included, carrying the problem of a refusal made before anything left: `client.argument_invalid` at `inputs`, the argument whose file it is, for the reason `upload_too_large`, whose message names the file, its size and the actual limit, which the gateway's bare `413` cannot, and says to shrink the file or reference it by an http(s) URL instead. The SDK wraps it in an `UploadTransportError`, which carries that problem. **What it does not do is skip reading and base64-encoding the asset first**: for a local path the SDK owns that step inside `uploadFile` (`readLocalPath`), so refusing before the read needs a pre-flight in `@pipelex/sdk` itself — a cross-repo item, carried alongside the presigned direct-upload redesign. The wasted network round-trip, the expensive half, is gone either way. `MAX_UPLOAD_BYTES` is derived from the gateway quota rather than hardcoded, so the derivation stays visible.

**What an upload is recorded as (`kind`).** Every upload is recorded among the organization's files (`POST /v1/upload`, `pipelex-server/platform/docs/uploads.md`), as `uploaded`, a member's own file, unless the upload says otherwise. `kind: "test"` records every upload of the call as a test input made for the method being prepared: the method's file list then holds it, and `mthds_list_files` lists it as that method's test file. The platform requires the method's bare saved id beside it, since a test file is the method's whatever version it tests. The workshop hands the kind and the id to the SDK's `prepareInputs` as its `upload` member, which sends them on every upload of the walk, and it settles the id before anything is sent:

- With `method_id`, the id is the selector's, which must therefore be bare. An id with an `@` suffix is refused as `client.argument_invalid` at `method_id` (reason `version_suffix`) before anything is sent, naming the bare id to pass, rather than stripped, exactly as `mthds_list_files` refuses it; so is an id that cannot be a catalog id (reason `not_a_catalog_id`). A draft's signature is prepared against by passing the method's linked folder as `method_dir`, which the refusal's message says.
- With `method_dir`, the id is the saved method the folder is linked to, read from its link file (see The link file — `.pipelex/method.json`). A folder that still holds the legacy `pipelex-method.json` is refused as `client.argument_invalid` at `kind` (reason `legacy_link`) straight away, with the command that moves the file into place, as the save and the pull refuse it.

Every other way of not knowing the method matters only when something is uploaded, since inputs that are all `pipelex-storage://` or `http(s)` addresses record no file at all. Those ways are a list of `files` or a `method_ref`, which name no saved method (reason `no_saved_method`); a folder with no link file (`unlinked`) or a link file that cannot be read (`link_unreadable`); a link file whose `method_id` is not a saved method's bare id (`link_damaged`), which the message calls damaged and says to repair by saving the folder again rather than by hand; and a link recorded against another API than the one the call goes to (`linked_elsewhere`), compared by host as the save compares it, which names both hosts. Such a request goes out with uploads disallowed (the SDK's `allowUploads: false`). If every input passes through, the inputs are prepared and nothing is recorded. If one needs an upload, the SDK refuses before reading or sending anything (`UploadNotAllowedError`), and the workshop answers `client.argument_invalid` at `kind`, for the reason above, its message saying why no method could be named and which input needed the upload; for `files` and `method_ref` it names `method_id` and a linked `method_dir`. `test_method_id` is echoed only when a test file was recorded, that is with `kind: "test"` and at least one upload.

`kind: "uploaded"`, like no `kind` at all, sends nothing, since it is what the platform records by default. A value that passes through is not uploaded and keeps whatever record it has. The platform refuses a test upload from a `runner` (a `403`), for a method it does not hold (a `404`) and for a method being erased (a `409`); the SDK raises each as a `TestFileRefusedError`, whose problem is the platform's own when it sent one, and otherwise `auth.forbidden` for the role and `client.argument_invalid` at `method_id` for the other two, relayed as it came.

The structured output is:

```ts
{
  status: "ok" | "error";
  is_valid: boolean;                 // true on the produced (success) arm — see verdict discipline below
  pipe_ref?: string;                 // echoed when the caller supplied it (the SDK does not return the resolved default)
  inputs?: Record<string, unknown>;  // the prepared (rewritten) inputs — ready for mthds_run
  uploads?: string[];                // the pipelex-storage:// uris of the assets uploaded this call ([] when all pass-through)
  kind?: "uploaded" | "test";        // echoed when the caller supplied it
  test_method_id?: string;           // with kind test and at least one upload: the bare id of the method the uploads are test files of
  files_sent?: string[];             // method_dir and files — every file of the tree sent (see The files union)
  problem?: Problem;                 // no-verdict only (see Verdicts and errors)
}
```

**Verdict discipline.** A produced result is `status: "ok"`, `is_valid: true`, carrying the rewritten `inputs` and the `uploads` uri list. Unlike `mthds_inputs_template`, `mthds_prepare_inputs` has **no produced-invalid arm**: an unresolvable closure (invalid bundle, unknown `pipe_ref`, unresolvable `main_pipe`) is a **no-verdict** `status: "error"`, the route's refusal of the pipe or the SDK's `method.invalid` whose `errors` are the closure's faults, because the SDK's `prepareInputs` throws on an invalid closure (`MethodLoadError`) rather than returning a verdict. The agent's recovery path is `mthds_validate` / `mthds_inputs_template`, which *do* produce the structured diagnostics — prepare sits downstream of them and delegates the verdict surface rather than duplicating it (re-fetching the list would cost a redundant `/v1/validate` round-trip).

`status: "error"` with one `problem` covers every failure, built or relayed as Verdicts and errors says:

- **Refused before anything is sent**, a problem the workshop builds, `client.argument_invalid` at the argument: a bad request shape (no selector, a second selector, a blank selector, a blank, bare or dependency `pipe_ref`, no inputs at `inputs`, both inputs forms at `inputs_path`); a `kind: "test"` whose `method_id` is not bare, at `method_id`; a `kind: "test"` from a folder holding the legacy link file, and a `kind: "test"` whose method cannot be named while an input needs an upload, each at `kind` (see What an upload is recorded as); an `inputs_path` the workshop refuses to read or parse (at `inputs_path`, see The inputs file, a file it cannot read being `client.file_unreadable`); and a file over the upload ceiling (at `inputs`, reason `upload_too_large`).
- **Raised by the SDK** before or during its walk, each with the problem it states (below), a deployment with no upload route (`UnsupportedUploadCapabilityError`, `runtime.unsupported`) among them.
- **Answered by the platform or its edge**, relayed as it came: a refused pipe selection (`request.pipe_not_found`, `request.pipe_ambiguous`); a selector the route refuses, such as an unknown or foreign-org `method_id` (`pipelex.catalog.not_found`); a refused or missing credential on either leg (`UploadAuthenticationError` carries the server's problem, else `auth.invalid_credential` or `auth.missing_credential`); a test upload the platform refuses (see What an upload is recorded as); an organization whose credit or plan does not cover the call, on the pipe I/O route and on the upload leg alike; an unreachable API on either leg (`client.unreachable`); a runner too old to serve `/v1/pipe-io` (a bare 404, `request.not_found`, its summary saying where the base URL was set); and a fault on the upload route, whose `retry` says whether asking again can succeed.

The SDK wraps whatever the upload leg meets, other than a refused credential or size, in an `UploadTransportError`, which carries the problem of the error it wraps, so a plan limit on the upload leg reads as the plan limit, the upload ceiling's refusal as its own and an unreachable API as `client.unreachable`, never as a passing transport fault. A refusal keeps the location the route gave it, whatever named the method, since the workshop rewrites none by request shape.

**The SDK's client-side refusals, by class.** The SDK raises its own refusals as `InputPreparationError` or one of its subclasses, each carrying its problem, which the workshop relays: the base class carries `client.argument_invalid` for an argument it refused, or the problem of the refusal it wraps, such as the route's refusal of the pipe; `InvalidInputValueError`, a value at a file position it cannot read as a file, a `data:` URL that does not decode or a value of a type no file input takes, is `input.invalid`, naming the input; `InvalidLocalSourceError`, a local path that is missing or unreadable, is `input.file_unreadable`, naming the path; and `MethodLoadError`, a closure that does not load (the pipe I/O answer's `is_valid: false`), is `method.invalid`, whose `errors` are the closure's faults, since the method must change and neither the pipe nor the inputs can fix it. An input walk whose answer the SDK could not read, such as a report carrying no `input_form` descriptor for the pipe, is `client.response_unreadable`, which is not the caller's to fix.

**Summary.** The build/prepare surface returns no `rendered_markdown`, so the capability composes its own `content` summary: the resolved pipe (when known), a one-line note of how many assets were uploaded vs passed through, naming the method they were recorded as test files of under `kind: "test"`, and the prepared `inputs` in a fenced JSON block (the `mthds_inputs_template` duplication pattern — the prepared inputs are the small payload the model must carry to `mthds_run`).

### Catalog Write Scope (`mthds_save_method`, `mthds_get_method`, `mthds_publish_method`)

Three tools carry a method between the workspace and the organization's catalog: `mthds_save_method` sends a method's folder to the catalog as a method's draft, creating the method or writing the draft of an existing one; `mthds_get_method` brings a saved method's draft, or one of its published versions, back; and `mthds_publish_method` makes the draft the method's next published version. They complete the loop `mthds_list_methods` opened — the listing says which methods exist, these say what a method *is* and let a workshop session change it.

**A saved method is a method tree.** Its draft and each published version hold every file of the method's folder the MTHDS standard's membership rule keeps (see The method folder, above): its `.mthds` files, its Python modules, its templates, its data, each at its tree path with its exact bytes. A save sends the folder's whole tree, and a pull writes a stored tree back to disk, file for file. There is no separate Python set and no list of `.mthds` files to name: the folder is the method.

**A save never changes what a caller of the bare id runs; a publish does.** On a platform that resolves version selectors, a bare id runs the latest published version, so the draft is a working copy that the save writes freely and the publish deploys. That is why the publish is a tool of its own, called only when the user asks for a publish, and never as a step of a save. On a platform that does not resolve them yet, a bare id still runs the draft, and the save's result says so rather than promise a protection that platform does not give.

**The save and the pull need the working directory** (see What the workshop registers). `mthds_save_method` reads the folder from disk and finishes by writing the link file that makes the next save write the same method's draft rather than create a duplicate, and `mthds_get_method`'s write arm has nowhere to write without a working directory; its inline arm exists for the single case of explaining a method to a workshop session that is about to work on it. The catalog's human surface lives in the webapp's editor.

#### `mthds_save_method`

One call reads the folder, validates it and saves those same bytes as the method's draft, with the verdict beside the save. Splitting it — validate in the skill, save in a second call — would read the files twice and the verdict would not be provably about the saved bytes.

The public MCP input shape is:

```ts
{
  method_dir: string;             // the method's folder, relative to the working directory
  name?: string;                  // required on a create; on an update, omitted keeps the name and a changed one renames
  method_id?: string;             // absent creates; present writes THAT method's draft (bare, or @draft)
  expected_updated_at?: string;   // the draft token this save believes it is overwriting
}
```

- **`method_dir` is required and names the method's folder**, held to everything The method folder says: inside the working directory on its real path, a `.mthds` file at its top, its tree listed by the standard's rule with the deployment's limits. Its whole tree is saved, and the folder's link file, `.pipelex/method.json`, is the one this save reads and writes. The order rule a list of files used to carry is gone: the platform derives the method's listed description from the first `.mthds` file, in tree path order, that declares a string `description`.
- **`name` is required on a create and optional on an update.** The name belongs to the method, not to a version, and the draft write does not carry it: an update that omits it keeps the method's name, and one that sends a different name renames the method through its own call (`renameMethod`, `PATCH /v1/methods/{id}`), made after the draft write, which changes the name alone and moves no token. The result says which it did (`saved: "renamed"`). The token the result and the link record is the draft write's, never the rename's: a save by somebody else landing between the two calls would otherwise be adopted as this one, and the next save from the folder would replace it unseen. When the rename reports a different `updated_at`, the summary says the draft moved right after this save, and the next save from the folder is refused until the user decides. A rename that fails leaves the draft saved, so the result is still `status: "ok"`, with `saved: "updated"`, the method's unchanged name and the rename's error in `rename_error`; the summary says to save again with the same name to retry it alone. **A name that is the one the link file records is not taken as a rename when the stored name differs.** It is the name an agent reads back out of `.pipelex/method.json`, and the stored name differs because the method was renamed elsewhere since, in the webapp or by a teammate, so renaming would quietly undo that rename. The stored name is kept, `saved` stays `"updated"`, and the summary says why; the link this save writes records the stored name, so saving again with the older name is then a rename the caller means, which the summary also says.
- **`method_id` is the arm discriminator**, as `files` versus `method_id` is on `mthds_run`. Absent, the tool calls `createMethod` (`POST /v1/methods`, the id minted by the server), which holds the tree as the new method's draft and publishes nothing. Present, it calls `writeDraft` (`PUT /v1/methods/{id}/draft`, which never creates). It takes the bare id; `mt_…@draft` is read as the same id, and `mt_…@<n>` is refused at `method_id` before anything is read, since a version never changes and a save writes the draft. There is no `create`/`update` flag and no second tool: the difference is the presence of one argument.
- **The draft is written with the link file's token.** The draft's `updated_at` is its token, and the link file records the one this folder last synced with as `synced_updated_at`. On an update the tool sends a token on `writeDraft` as the platform's own compare-and-swap: `expected_updated_at` when the caller gave one, and otherwise the link's `synced_updated_at`, the claim check having already proved that the link names this method. **The save's read is one local step, and its link write a compare-and-swap.** The save reads the folder's link, then the folder's whole tree, every file once, in one turn of a queue the whole workshop process shares (`inLinkTurn`), holding the workshop's write lock described below, and neither the turn nor the lock holds anything but that local work, never a call to the platform. A save that cannot take the lock for its read is refused before anything is sent, as a no-verdict at `method_dir`: `client.workspace_busy` while another workshop process holds the lock, which a later call can take, and `client.write_failed` when the lock cannot be had at all. Once the files are in hand it reads the link again and refuses when it moved, as `client.workspace_busy`, since a writer that takes no lock, an editor, a git checkout or an older workshop, may have written while the save read, leaving bytes no link vouches for. The validation, the draft write and the rename run outside any turn or lock, so a slow save delays no pull. The link is read before the files, so the token certifies the state the bytes were read against: two saves from one folder that overlap read the same token, the platform takes only one draft write under it, and the other is refused as stale rather than replace the newer draft with older bytes. At the end the link is written only while it still holds exactly the bytes this save read (`replaceMethodLink`): a link another save or a pull wrote meanwhile — a version pulled over the files, another save's token — describes what that call left in the folder, so it is left as it is, `link_file` says `written: false` with that reason, and the summary says to look at the folder before saving from it again. One queue for the process rather than one per folder, because a pull can write into a folder nested in another's and one folder has several spellings. **A create holds a turn of its own, from its claim read to its link write, its calls to the platform included**, in a second queue that only creates take: what claims a folder against a second create is the link the first writes last, so two overlapping creates from one folder both read it unclaimed and both minted a method, the second's link write then finding the first's link and writing nothing, which left a duplicate only an administrator can delete. Queued, the second reads the first's link and is refused; creates are rare and paced by a person, and an update never waits on one, and two workshop processes creating from one folder at the same moment are not covered. **Every write, and the save's read, also holds the workshop's write lock, across workshop processes** (`withLinkLock`): the save's read of its link and files, the save's compare-and-swap of its link, and the pull's whole landing. A compare-and-swap is a read and a write, and nothing else ordered them between processes: a version pull from a second workshop process could land between a save's compare and its write, the save then recorded its draft token over the version's files, and the next ordinary save replaced the draft with that version, its restore guard bypassed and the bytes the first save sent gone from the draft and from disk. There is one lock for every folder, the cross-process twin of the one in-process queue and for the same reasons: two pulls into a folder and a subfolder of it can write the same file, and with a lock per folder both landed it, each link then vouching for its own method's copy; under one lock the second landing finds the file changed since its plan read it and is refused. The save's read holds it too, because a second read of the link cannot stand in for it: a pull from another workshop process landing while the save read left it a mix of two contents, which a caller passing `expected_updated_at` sent past the `partial_pull` refusal, and a pull into a folder nested in the method's changes the method's files without touching its link. The lock is an exclusive SQLite transaction on a file in a directory private to the user under the home directory, `~/.local/state/pipelex-mcp/write-lock.sqlite` on POSIX and `~/AppData/Local/pipelex-mcp/write-lock.sqlite` on Windows, never in the user's working directory, which is committed. `XDG_STATE_HOME` is deliberately not read, and the lock is not under the OS temp directory, where it first lived: both can differ between one user's processes, and two processes computing two files exclude nothing; and a temp cleaner deletes old files, macOS's daily one included, after which a process still connected to the deleted file locks it while every process started later creates a new file and locks that one. So every acquisition first checks that the file at the path is still the one its connection opened, and reopens it when it was deleted or replaced. SQLite takes the lock with the operating system's file lock, which the kernel releases the moment the holder's process ends, so nothing is ever judged abandoned and no recovery can take a live holder's lock, which is what made a lock written as a file on disk unsound. The directory is created readable by its user alone, its missing parents as ordinary directories, and refused when it is not a directory or belongs to another user. The lock is held for a few file operations, never across a call to the platform. A call waits up to ten seconds for it. A save that cannot take it for its read is refused, sending nothing; one that cannot take it for its link write leaves its link unwritten and says why in `link_file`, its draft being already stored; and a pull that cannot take it is refused, writing nothing. Each refusal is `client.workspace_busy` while another process holds the lock and `client.write_failed` otherwise. A connection that fails with anything but busy, a damaged lock file for instance, is closed and opened afresh on the next call, and the refusal names the file, which can be removed when it is damaged. The lock binds the processes that share the home directory: one user's sessions on one machine. **A link that cannot vouch for the draft is refused, never read as no token**, since a save without one is last-writer-wins: a link that cannot be read, and one whose last pull never finished (`partial_pull`, or no recorded token), are refused at `method_dir`, the first as `client.file_unreadable` and the second as `client.argument_invalid`, and their messages say how to relink. A link recording `synced_version` holds a published version pulled over the draft, so a save from it without `expected_updated_at` is refused at that argument: replacing the draft with a version is a restore, made only when the user asks, by passing the token the refusal names. A draft that moved since is refused atomically by the platform with a 409 `pipelex.catalog.update_conflict`, relayed as is with the workshop's message naming both tokens and what to do, and nothing is written — not the draft, not the link file. The tool then reads the method to put both tokens in the message, best-effort, and says when the stale one was the link's, so the caller can tell a teammate's save, or the webapp's autosave, from its own save whose link write failed (a pull into the folder refreshes that link while the files match). So a save from a linked folder never replaces a draft somebody saved since the folder synced; to replace one knowingly, after asking the user, the caller passes the draft's current `updated_at`, which the refusal names. Only a save from an unlinked folder sends no token and is last-writer-wins. The argument is ignored on a create, where there is nothing to be stale against.
- **The folder's link is read before anything touches the catalog, and refuses there**, because both writes are irreversible in the same way and delete is admin-only. **A folder already linked to a different method is not re-pointed**: the link file is committed and shared, so a silent takeover would send a teammate's next save to this method instead of theirs. A create from a claimed folder is refused as a `client.target_exists` no-verdict naming the link file, at `method_id`, rather than minting a duplicate nobody can remove, and an update whose `method_id` is not the one the folder is linked to is refused at `method_id` rather than rewriting a different method with this folder's tree and name — a replaced draft cannot be given back. Copying the folder without its `.pipelex/method.json` is the deliberate fork for each, and the messages name it. **A link file that cannot be READ counts as a claim**, not as an empty slot: `readMethodLink` reports a malformed, truncated or symlinked link, or a `.pipelex` that is a symbolic link or not a directory, as `unreadable` precisely because something claims the folder, and treating that as "no link" is what let a create run and a duplicate appear. When a link write fails after a successful save, the result says which of the three states holds — linked and refreshed, linked but stale, or genuinely unlinked — and never the last about a folder where a link survives, since the advice that answer carries has itself overwritten the wrong method.

**The secret guard** (see The files union and the path trust boundaries) runs on the bytes the save read, inside the save's local turn, after the link's refusals and before the validation and the catalog write, so a refused save sends nothing of the folder: the only request it has made is the limits handshake, `GET /v1/version`, a metadata read that carries no file, which the listing needs before it reads. Its refusal is one `client.argument_invalid` no-verdict at `method_dir` whose reason is `secret_suspected`, naming every file and what it matched, never the matched text, and its message closes with saving again.

**Behaviour, in order.** Locate the folder on its real path; ask the deployment's limits; in one local turn holding the lock, read the link and make its refusals, list the folder's tree and read every file once, run the secret guard over those bytes, and read the link again. Then validate through the same capability `mthds_validate` uses, on the same bytes: the validation is handed the folder's tree as it was read and checked, so it reads nothing again, runs no second pass of the secret guard and asks no limits again, and it sends what a `method_dir` validation sends, the folder's whole tree. **The verdict rides beside the save and does not gate it**: a draft is never validated on write, an agent's work in progress is often invalid, and the verdict is what tells the agent so, while the publish is where validity is required. A validation that was sent and produced no verdict at all (an unreachable API, a rejected credential) refuses the save, since the tool could not say what it saved, and the summary quotes why no verdict came. **One no-verdict outcome saves all the same**: the execution-locus gate. A deployment that refuses to load the method for the Python it holds gives no verdict about it on any request, while nothing is wrong with the draft, so a folder holding a `.py` file would otherwise be unsaveable on a deployment that is not sandbox-hosted. The save goes ahead unvalidated, and the result carries the refusal as `validation_refused`, with no `is_valid`, `is_runnable` or `pending_signatures`; the summary says the method was NOT validated, that a publish validates it before publishing anything, and where it validates, the refusal's next step. No handshake announces whether a deployment is sandbox-hosted, so the save keys off the refusal itself. Then hand the SDK the tree as a `MethodTreeSource` — the listing, its digest and a reader over the bytes already in hand — which sends it inline or uploads the blobs the organization lacks and sends it by hash, so a method saved from the workshop opens in the webapp's editor as the same files. On an update, the draft write sends the tree and the token, and nothing else: the draft route keeps `input_data` on omission, so the form inputs a webapp user saved survive without being read back first. Then rename when the name changed, and write the link file of the section below, recording the draft's new token. The summary says when the method is invalid or does not run yet that it was saved anyway and that a publish will refuse it, says what callers of the bare id run now (the latest published version, which this save did not change, or on a platform that does not resolve versions yet, this draft), names `mt_…@draft` as the id that validates or runs what was just saved — or the bare id where the platform does not resolve versions, since a suffix is refused there — names `mthds_publish_method` with the new token for when the user asks for a publish, and names the graph page when the wrapper left it out.

**No file comes back.** The result carries the id, the name, whether the method was created, updated or renamed, the draft's new `updated_at`, the method's latest published version and how the draft stands against it, the API host, `files_sent` and the verdict's summary fields. The bytes are already in the caller's hands.

```ts
{
  status: "ok" | "error";
  is_valid?: boolean;                           // absent when validation_refused is present
  is_runnable?: boolean;
  pending_signatures?: string[];
  method_id?: string;
  name?: string;
  saved?: "created" | "updated" | "renamed";   // renamed = the draft written and the method renamed
  updated_at?: string;                          // the draft's new token
  latest_version?: number | null;               // null: never published
  publish_state?: "never_published" | "draft_unchanged" | "draft_ahead";
  api_host?: string;
  link_file?: { path: string; written: boolean; reason?: string };
  files_sent?: string[];                        // every file of the tree sent, as method_dir joined with its tree path
  rename_error?: Problem;                       // the draft was saved; the rename was not
  validation_errors?: ProblemItem[];            // the verdict's errors, present when non-empty
  validation_warnings?: ProblemItem[];          // the verdict's warnings, present when non-empty
  validation_refused?: Problem;                 // saved unvalidated: the deployment refused the method's Python
  problem?: Problem;                            // no verdict (see Verdicts and errors)
}
```

`publish_state` is derived from the method the platform returned: `never_published` when it has no version, `draft_unchanged` when the draft's `draft_digest` equals the latest version's `tree_digest`, and `draft_ahead` otherwise. It is absent when the platform's answer does not carry those fields, or either digest is unknown.

**Verdict discipline** is the family's: a produced verdict is `status: "ok"` discriminated on `is_valid`, an invalid method is `is_valid: false` with `validation_errors`, the verdict's problem items, and saved all the same, a method the deployment refused to load for its Python is saved with `validation_refused`, that refusal's problem, and no `is_valid`, and `status: "error"` + `problem` is reserved for no-verdict conditions — a folder refused, a secret found, any other validation that produced no verdict, a rejected credential, a write refused by role (the platform's `auth.forbidden`, its `detail` naming the role, and on a create no list-first caution, since a refusal minted nothing), a stale `expected_updated_at`, an unknown `method_id`, a file that could not be uploaded (the SDK's `MethodFileTransferError`, its problem carrying no link), a tree the platform refused, a failed write. Each is the problem the SDK read or the one the workshop built, relayed as is (see Verdicts and errors).

**A create that may have happened reads as an unknown outcome.** `POST /v1/methods` honours an `Idempotency-Key` and `@pipelex/sdk` exposes no way to send one, so a create whose response was lost cannot be replayed safely: the retry mints a second method. Whenever the create may have reached the catalog, the result's `problem` is therefore `client.outcome_unknown`, whatever the SDK read, so that a caller branching on `retry` never resends it: its `retry` is `outcome_unknown`, its `next_step` (`refresh`) says to list the catalog with `mthds_list_methods` before saving again and to save with the found method's `method_id`, and its `message` keeps the SDK's reading with its code, its `request_id` kept beside it. The create may have happened unless its failure proves otherwise, and only three proofs count, each keeping the SDK's problem: an argument the SDK refused before any request (`RequestArgumentError`); a failure of a step that comes before the create, which is then never sent, that is a file that could not be uploaded (`MethodFileTransferError`), or any answer from another route than the create's, the version handshake or `POST /v1/blobs/missing`, whatever its status, the route read from the error's message, where the SDK names it; and a refusal the create's own route answered, a `4xx` other than `408`, or a `501`. Everything else counts as may-have-happened: a `2xx` the SDK could not read, because the platform accepted the create, so the method exists; a `408` or any other `5xx` from the create's route, or from a route the error does not name; every transport failure, the SDK's test of one that proves nothing left not being exported; and an error the SDK did not raise, such as an abort or a wrapper's error, which proves nothing of what was sent whatever problem it reads as. A draft write has no such hazard — `PUT` replaces the draft and is idempotent by construction — so its failure keeps the SDK's problem. When the SDK gains the key, it reads a lost create as `client.outcome_unknown` itself and this rule goes.

**A failed link-file write does not fail the save.** The method is already stored by then, and answering `status: "error"` would tell the caller their save did not happen. The link file reports itself in `link_file` with `written: false` and the reason, and the summary says the folder is not linked, so the next save would create a second method unless the caller passes the id.

#### `mthds_get_method`

```ts
{
  method_id: string;     // bare or mt_…@draft: the draft; mt_…@<n>: version n
  output_dir?: string;   // write the tree here; omitted, the text files come back inline
  overwrite?: boolean;   // only meaningful with output_dir; see the linked-folder rule
}
```

**It reads the draft by default.** A bare id and `mt_…@draft` read the draft (`getMethod`), which is what the next save replaces and what a session works on; `mt_…@<n>` reads published version n (`getMethodVersion`, `GET /v1/methods/{id}/versions/{n}`), alongside the method itself, whose name a version does not carry. A version the method never had is the platform's `pipelex.catalog.not_found`, to whose message the workshop adds the versions the method has. The result's `version` says which was read, and it carries the method's `latest_version` and `publish_state` as the save does. Pulling a version into the method's folder and saving it with the draft's token as `expected_updated_at` is how a version is restored: the save replaces the draft's whole tree with the version's and publishes nothing. The pull's summary says so and names the token, and a save from that folder without it is refused, so a version pulled to be read is never saved over the draft by accident. **A version that is the draft, file for file, leaves the folder holding the draft.** When the version's tree holds the same paths with the same SHA-256 as the draft's, which the method read beside it already lists, the link records no `synced_version`, and the summary says the version is identical to the draft and that a save from the folder needs no token. The comparison is file by file rather than by digest, since restoring a version identical to the draft restores nothing, and a marker there would refuse an ordinary save for no reason.

**A read lists the tree; the bytes come from its links.** Each listed file carries its path, its size, its SHA-256 and a short-lived link to its bytes, and the SDK's `writeMethodTree` downloads them, checks each against its hash, and writes them under a destination that must be absent or empty, refusing a path that is not a tree path, or two that collide, before it downloads anything. **A link is a bearer credential**: it never reaches `structuredContent`, `content`, `_meta` or a log, and a failed download is reported by the SDK's `MethodFileTransferError`, whose message carries none. A method whose tree holds no file is a produced failure, not an empty success: `status: "error"`, a `method.package_invalid` problem the workshop builds — the row exists but holds nothing yet, which is a different answer from "no such method" (the platform's `pipelex.catalog.not_found`, since an id from another organization is indistinguishable from an unknown one).

**With `output_dir`** every file of the tree is written at its path, the link file is written in the folder, and the result returns the paths — no file passes through the conversation, which is the rule `mthds_codegen`'s write arm set. The folder is relative to the working directory under the shared write-side containment boundary. The tree is downloaded into a private directory under the system's temporary directory before the landing, so no download runs while the landing holds the workshop's lock, a download that fails leaves `output_dir` as it was, and the staging directory is removed whatever happens; a pull that only refreshes the link downloads nothing.

**What the pull may write at all.** A stored file's path comes from whoever saved the method, so the catalog is an untrusted source of paths while `output_dir` may be any folder the user is standing in. Containment is therefore necessary and not sufficient: every destination must also carry no path component beginning with a dot, which is where a workspace keeps what configures its tools and where the link file lives, and which no method tree holds under the standard, and be unique across the set after case folding (two paths landing on one file wrote one over the other and reported both). Without those, a stored method pulled into a workspace could leave a CI workflow or an agent's configuration behind it, since the occupancy guard only refuses destinations that already exist. Each refusal is a `method.package_invalid` problem, the offending stored path in its `location.file` — the request was fine and the stored method is not — and writes nothing.

**The refusal rule, and why it is not the codegen writer's.** `mthds_codegen` overwrites its own stamped output because the engine owns those filenames; a method's files are the *user's* and carry no stamp, so the only evidence of ownership is the link file. So: a folder with no link is written only when its tree, listed exactly as a save from it would list it, holds no file at all but those this pull lands, and none of those yet, since the link the pull writes claims the whole folder and the next save from it sends every file of its tree: pulled with `output_dir: "."` into a project, a method would otherwise take the project with it. A folder whose tree holds anything else is refused, naming the files, with a fresh folder as the cure, and one whose tree cannot be listed, past the limits or holding a symbolic link, is refused too, since the pull cannot tell it holds nothing else; dotfiles, a run's inputs file and the graph page are no part of the tree, so a fresh repository or a folder holding inputs is written; a folder whose `.pipelex/method.json` names this same method is compared destination by destination against the stored tree, each local file hashed and compared with the SHA-256 the listing carries, and three outcomes follow — identical means **nothing is written at all** and only the link's `synced_updated_at` is refreshed (rewriting identical bytes woke watchers and, with one read-only file, turned a pure link refresh into a mid-write failure); different while the draft's `updated_at` still equals the recorded `synced_updated_at` means the local files are work this folder has not saved, so the pull is refused and says it would be lost; different after the draft has moved means the tool cannot tell whose change it is looking at, so it refuses unless `overwrite: true`, which the caller sends only after asking the user. A destination whose local bytes the catalog already stores elsewhere is none of the three either, and is written: the draft's own file at the same path when the pull brings a version, or the file of the version the link says this folder last pulled (`synced_version`) when it brings anything else. Writing over a copy of stored bytes loses nothing, and without this a folder that pulled version 3 could never pull the draft back, its files reading as unsaved work against a draft that had not moved. The version is read only when a file is still in question, and a version that cannot be read stores nothing, so this narrows a refusal only on evidence. A destination that is simply **absent** is none of the three and is written: nothing is lost by creating a file that is not there, and counting it as a difference refused every pull that would have restored a file the user had deleted, with no flag to open it. A folder already holding any file this pull would land, or any `.mthds` file of its own at its top under other names, or a link naming another method, is refused outright: it is somebody else's work. **Every half of that rule is asked of the whole write set — every file of the tree, nested paths included — never of the `.mthds` files alone**: a guard that inspects a narrower set than the write loop lands is not a guard. The one exception is a link carrying `partial_pull`, which an interrupted pull of this same method leaves behind so that the retry it advertises is actually permitted — and it is an exception to the *ownership* question only: a destination whose bytes have **changed** since that pull landed is still refused without `overwrite`, because the marker says a pull was interrupted and nothing more, and it rides in a file the user is told to commit, so it can be stale or planted. Every destination, and every directory that already exists between `output_dir` and it, is also inspected with `lstat` before anything is planned, and again inside the landing before the provisional link, and a destination that is not an ordinary file, or a directory on its path that is a symbolic link, is refused for what it is: containment is decided on a joined path, and a write through a symlink lands at its target. A directory symlink inside the folder defeats both the dot-segment rule and containment, since `assets -> .claude` lets a stored `assets/settings.json`, whose path has no dot segment and whose real parent stays in the folder, land among an agent's configuration. The path the write would really take, from the deepest existing directory's real path on, is also held to the dot-segment rule. Every refusal is `client.target_exists` at `output_dir` and writes nothing at all. **A version pull whose interrupted-pull marker cannot be written writes nothing either**, as `client.write_failed` at `output_dir`: under the link left in place, which records the draft's current token and no version, the version's files would read as the draft's, and an ordinary save would replace the draft with them without the explicit token a restore takes. A draft pull over a link that records a version is refused the same way, since that link would go on saying the folder holds the version; any other draft pull carries on, since a link describing an older sync is refused as stale and a current one already describes the draft's own bytes. **The pull plans with no turn held, and lands in one.** It reads the folder's link before the method, so the link it plans against never records a sync newer than the content it read: read after it, a save landing in between handed the pull a link ahead of its method, which it reported as a moved draft and, under `overwrite`, answered by writing the older content back. It hashes each destination once, and lands only while every destination still holds what it read, since an edit made while the pull waited on the platform — for the version that recognises stored files, or for the download — moves no link, and the plan's verdict that the file held stored bytes would otherwise write over it; such a pull is refused as `client.workspace_busy` at `output_dir`, writing nothing. A folder with no link is listed again inside the landing, before the provisional link, and refused as it would have been at planning when its tree now holds a file the pull does not land: it was found holding nothing else before the download and outside the lock, and a file landing meanwhile would be claimed by the link and sent by the next save. Its reads of the platform, the version read and the download included, and its comparison of the destinations run first; the provisional link, the files copied from the staged tree and the final link then land in one turn of the save's queue, which holds no call to the platform. Both link writes are the save's compare-and-swap: the provisional one expects the link the pull planned against, so a save or a pull that rewrote it since has moved the folder under the plan, and the pull is refused as `client.workspace_busy` at `output_dir` before a file is written, a link-only refresh included; the final one expects the provisional link the pull wrote, and when another workshop process rewrote it meanwhile the files are written, that link is left, and the summary says to pull again before saving.

**Without `output_dir`** the text files come back inline, bounded by one budget over the whole tree, 256 KiB, applied by whole file in tree path order on the sizes the listing gives — the codegen streams rule, for the same reason: half a `.mthds` file is worse than none. Only the files that fit are downloaded; the first that does not closes the budget, and every file after it is withheld too, each carrying its path and byte size with no content, and `truncated: true` names what happened. A file that is not UTF-8 text carries `binary: true` and no content. This arm exists for the one case where the model has to read the method anyway, which is explaining a method it cannot see on disk; it writes nothing into the working directory, and a failed download is a no-verdict with no location, since it writes nowhere the caller named.

```ts
{
  status: "ok" | "error";
  method_id?: string;
  name?: string;
  version?: number | "draft";                   // which content was read
  updated_at?: string;                          // the draft's token, whichever content was read
  latest_version?: number | null;
  publish_state?: "never_published" | "draft_unchanged" | "draft_ahead";
  api_host?: string;
  files?: Array<{ path: string; bytes: number; content?: string; binary?: boolean; written_to?: string }>;
  output_dir?: string;                          // present on the written arm — the arm discriminator
  link_file?: { path: string; written: boolean; reason?: string };
  unmanaged?: string[];                         // written arm — files of the folder's tree that this method does not have
  unmanaged_truncated?: boolean;                // written arm — the folder could not be listed, so `unmanaged`'s absence is not "none"
  truncated?: boolean;                          // inline arm only; always false on the written arm
  problem?: Problem;                            // no verdict (see Verdicts and errors)
}
```

**A pull writes what the catalog holds now, which is not the same as making the folder match it.** A file somebody removed from the stored method is neither written nor deleted, and the link is refreshed regardless — so without saying anything the folder would certify a sync it does not have, holding a tree that validates and runs differently from the catalog's, and a later save from it would put the removed file back. The tool records no per-file state, so it cannot tell a file the catalog dropped from one the user simply keeps beside the method, and deleting on that guess is the one thing it must not do. So it names them in `unmanaged` and says in prose which two things they might be: the files of the folder's tree, listed exactly as a save from the folder would list it — the standard's rule, the wrapper's two exclusions, the deployment's limits — that the stored tree does not hold. Telling them apart needs the link file to record what it manages, which is a change to the link's format and is filed rather than guessed at. **It reports its own completeness in `unmanaged_truncated`**, because "nothing to report" and "I could not finish looking" are different answers that an absent list renders identically: a folder whose tree the rule refuses (a symbolic link, a name no tree takes, a directory it cannot read) or that is past the deployment's limits reports nothing at all rather than a partial list, sets the flag and says so in prose, since the line's whole claim is that it names everything, and a save from that folder would be refused for the same reason.

#### `mthds_publish_method`

```ts
{
  method_id: string;                  // bare, or mt_…@draft; a version is refused
  expected_draft_updated_at: string;  // the draft token the caller last saw — required
}
```

It publishes the method's draft as its next immutable version (`publishMethod`, `POST /v1/methods/{id}/publish`) and is called **only when the user asks for a publish**: its description, the save's summary and the server's instructions all say so. The token is required, so a publish never takes a draft its caller has not seen — which holds only for a token that came with the draft's content: the updated_at of a save, or of a pull of the draft. A read of a version reports the draft's token too, for a restore, without the draft's content, so the description, the field and that read's own text all say never to publish under it. A draft that moved since is the platform's 409 `pipelex.catalog.update_conflict`, relayed as a no-verdict, to whose `message` the workshop adds the draft's current token, read afresh, and the reminder that a publish under it is the user's call, and nothing is published. `mt_…@<n>` is refused as `client.argument_invalid` at `method_id` (reason `version_suffix`) before anything is sent, since a version is already published and a publish publishes the draft; its message says how to publish an old version's content again (pull it, save it as the draft, publish that). A caller whose role does not allow a method change is refused with the platform's `auth.forbidden`, relayed as is, whose `detail` names the caller's role and what the action needs.

The platform answers a `200` discriminated on `outcome`, and each arm is a produced verdict, `status: "ok"`:

- **`published`** — the new version's number, `published_at` and `crate_fingerprint`. The summary says `mt_…@<n>` now names it for good, and what callers of the bare id run from their next call, by what the platform resolves.
- **`unchanged`** — the draft's digest equals the latest version's, so no version was added and no runner was asked; the existing version's number comes back. A republish of the same draft is therefore harmless.
- **`refused`** — the draft does not validate (`reason: "invalid"`) or validates but does not run yet (`reason: "not_runnable"`). The runner's verdict is relayed in `is_valid`, `is_runnable`, `pending_signatures` and `validation_errors`, the verdict's problem items, read defensively, and the summary lists the first errors, one line each as `code: detail (location)`, or names the pending signatures.

```ts
{
  status: "ok" | "error";
  outcome?: "published" | "unchanged" | "refused";
  method_id?: string;
  name?: string;
  version?: number;                   // published and unchanged
  published_at?: string;
  crate_fingerprint?: string | null;
  reason?: "invalid" | "not_runnable"; // refused
  message?: string;
  is_valid?: boolean;
  is_runnable?: boolean;
  pending_signatures?: string[];
  validation_errors?: ProblemItem[];   // { code, detail, location? }
  updated_at?: string;                // the draft's token
  latest_version?: number | null;
  publish_state?: "never_published" | "draft_unchanged" | "draft_ahead";
  api_host?: string;
  problem?: Problem;                  // no verdict: the caller's view of the problem document
}
```

Its annotations are `readOnlyHint: false` and `destructiveHint: true`: a publish removes nothing, but it changes what every caller of the bare id runs, and a version once published is never taken back, so a host that asks before a destructive call should ask here. It needs no working directory and writes no file.

#### The link file — `.pipelex/method.json`

The save and the pull write it; no skill does, and nobody edits it by hand. It lives in the folder it describes, in a `.pipelex` directory the save or the pull creates there, so it sits outside the method's tree (a segment starting with a dot is never a member) and is never saved as one of the method's files. It is meant to be **committed**: a team shares an organization, and the link is what lets the second person update the method the first one saved rather than creating a second. An id grants nothing without the organization's key. A `.pipelex` that is a symbolic link or not a directory is never read or written through: the link reads as unreadable, which claims the folder, and no write follows it.

```json
{
  "comment": "Written by the Pipelex workshop (@pipelex/mcp). This directory is saved on Pipelex as the method below. Commit this file so that a teammate updates the same method instead of creating a second one. Do not hand-edit it.",
  "generator": "pipelex-mcp",
  "api_host": "api.pipelex.com",
  "method_id": "mt_…",
  "name": "Summarize PDF",
  "synced_updated_at": "<the draft's updated_at at the last save or pull>",
  "synced_version": 3
}
```

**Every write of it is a compare-and-swap on its own bytes.** A save or a pull decides what to write from the link it read, and writes only while the file still holds exactly those bytes; a link written by another call in between describes what that call left in the folder, so it is left as it is and the result says so. A file that cannot be read is never written over, and one that became unreadable after the call read it, a merge conflict landing in it for instance, is a change like any other, so a pull refuses on it before writing a file. Each compare and its write hold the workshop's write lock, so they are one step for every workshop process of the user on the machine, not only this one. That is what keeps the link truthful when two calls touch one folder, in this workshop process or another; the save's and the pull's paragraphs above say what each does when the compare fails, and what the lock does when it cannot be taken.

`synced_version` is present only after a pull of a published version whose tree differs from the draft's, and records which one the folder holds; a save, a pull of the draft, or a pull of a version identical to the draft drops it, since the folder then holds the draft. The pull reads it to recognise local files as a stored version's rather than as unsaved work, and the save reads it to refuse replacing the draft with a version unless the caller passed `expected_updated_at`. A value that is present but not a version number makes the whole link unreadable, as any other malformed field does: dropped, it would read as a folder holding the draft and switch that refusal off.

**The workshop writes it because the workshop is the only party that knows which API host it talks to.** `api_host` is the host of the configured base URL, and it is what makes an unknown id on a later update diagnosable: a link made against one plane, or with another organization's key, reports the host it records rather than reading as a vanished method.

**The name it had up to 0.25.0 is refused, never read.** A folder still holding `pipelex-method.json` at its top would read as unlinked, so a save from it would create a second method and upload the old file as one of the method's own, and a pull into it would judge it somebody else's folder. So a save whose folder holds an entry of that name is refused at `method_dir` before the limits handshake, and a pull into one is refused at `output_dir` before anything is planned, both `client.argument_invalid`, the message naming the command that moves it into place, `mkdir -p .pipelex && git mv pipelex-method.json .pipelex/method.json`. There is no legacy read, as there is no backward compatibility anywhere in the workshop.

**It records no file hashes**, deliberately. The cost is stated rather than hidden: with no record of the files as they were at the last sync, a pull into a linked folder cannot tell whose change it is looking at, which is why the three-outcome rule above ends in a question for the user in its last case instead of an answer. Inside a git repository `git status` answers that question for them.

`synced_updated_at` is known only at a save or a pull, because it costs a call. It is the draft's token whatever the pull brought. A save from the folder sends it as its compare-and-swap token unless the caller passed `expected_updated_at`, and refuses when the link records a version, an unfinished pull or no token at all; a publish takes it as `expected_draft_updated_at` only when the link records no `synced_version`, since a link holding a version vouches for the draft's token and not for its content; the save and the pull rewrite it with the new one, and a publish leaves it alone, since publishing moves no draft token.

### `mthds_run`

`mthds_run` starts a durable run on the workshop, with the start result, the lifecycle and the verdict discipline of Run Scope. It takes its method in any of the forms Method Selectors names, and its description nudges validating a folder or a files bundle first (see the start-time rejection note in Run Scope).

```ts
// input
{
  method_dir?: string;               // the method's folder, read by the workshop — see The method folder
  files?: SubmittedFileInput[];      // { content, uri? } | { path } — see The files union
  method_ref?: string;               // published method address — see run-by-address below
  method_id?: string;                // catalog id (mt_…) of a registered method — see run-by-reference below
  pipe_code?: string;                // pipe to run — the same qualified value mthds_inputs_template takes as pipe_ref; omitted → server resolves the bundle's (or the manifest's) main pipe
  inputs?: Record<string, unknown>;  // method inputs, as filled from the mthds_inputs_template template
  inputs_path?: string;              // or the path of a .json file holding them — see The inputs file
}
```

`inputs` and `inputs_path` are mutually exclusive — both is `client.argument_invalid` at `inputs_path` (reason `mutually_exclusive`) — and both are optional, since a method may declare no inputs. A loaded file starts the run exactly as the same object inline would.

**Beside files.** `method_id` is a separate optional top-level argument beside a now-optional `files` — deliberately **not** a third arm on the files union (a method id is not a file, and a mixed array would falsely suggest merging) and not a distinct tool (one run tool for the model; the lifecycle family keeps its stem). Request shape follows the run rule from Method Selectors: at least one source among (`method_dir`, non-empty `files`, `method_ref`, `method_id`) is required, else `client.argument_invalid` at `files`; a supplied-but-blank selector is `client.argument_invalid` at that selector; id format beyond non-blank stays server-owned (the same stance as `run_id`). Precedence mirrors the platform: **a folder or inline `files` win** — when both are supplied, the files run and `method_id` is recorded as the run-history linkage on the platform's Run row (the webapp's own semantics for saved methods); `method_id` alone runs the stored method, as Run Scope describes.

### Artifact Download Scope (`mthds_download_artifacts`)

`mthds_download_artifacts` saves a completed run to disk: its main output, and the files it produced. It is the workshop's download counterpart to its upload path: `mthds_prepare_inputs` pushes local files *into* Pipelex storage and rewrites them to `pipelex-storage://` references; nothing brought a run's outputs back *out*. A run that produces an image, a PDF or a document returns it in `mthds_run_results` as content carrying its `pipelex-storage://` reference in `url` beside a presigned `public_url` with a one-hour life — so every file a run produced reached the user as a link that dies within the hour, and whether it ever landed on disk depended on the agent thinking to fetch it in time (observed live: the generated image reached the user only because the agent happened to fetch the link before expiry, and first into a scratch directory rather than the workspace). This tool makes that outcome the default. It is a plain tool: no view, no `_meta` channel, no `available_view_specs` — the saved paths are small structured data the model reports directly.
**The output is saved too, always, as `main_stuff.json`.** A run's main output used to reach the disk only by the model retyping it: in the proof lab of 2026-09-24 a model asked for the results as files rewrote each output with its own file tool — thousands of characters of output tokens per run, with nothing to stop it altering the JSON on the way — and a long output was worse off still, cut at `MAIN_STUFF_CAP` in `mthds_run_results` with no tool to read the rest, until the session reached for curl. So every completed save writes the **full** `main_stuff`, exactly as the API returned it (the `pipelex-storage://` references and their expiring `public_url` links included — the file is a record of the run, and the verdict is what maps each reference to its saved file), as `JSON.stringify(value, null, 2)` plus a newline, to `main_stuff.json` — the name `pipelex run --save-main-stuff` writes and the one the hosted platform stores the same artifact under. There is no flag: the failure it answers is a model that does not know to ask. It is written **first**, before a single file is fetched, so it always takes its own name, and a stored file that would collide with it is the one suffixed. A run whose output references no stored file is saved all the same — that is the case that motivated it. Only JSON is written: the CLI's Markdown and HTML renderings need the runtime's content classes, which the hosted API does not relay.
**Why a companion tool and not an option on `mthds_run_results`.** Two shapes were plausible: a `save_artifacts` flag on the results tool, or this companion. The companion keeps the tool contract simplest on three counts. First, the results tool is annotated read-only; writing files to the user's disk is not a read. Second, the results projection is already the busiest surface in the repo (bounding, usage, three `_meta` channels); a filesystem write does not belong inside it. Third, a separate tool answers the durable case on its own terms — "save the files from run X" days later is one call with the id, no re-projection of a result the agent already read. The cost is one more tool on the workshop's list. The same three counts settled where the output write went when the need for it surfaced (2026-09-24): an `output_path` on the results tool was proposed, and the output was given to this tool instead, which keeps its name — `main_stuff.json` is a run artifact in Pipelex's own vocabulary, beside `graphspec.json` and `working_memory.json`.

**Why it is keyed on the run id, not on a list of URIs.** The run id is the durable handle the whole family already uses, and the agent holds it. Taking `uris` instead would have the agent copy references out of a bounded result (a pruned copy could have dropped one) and would invite misspelled schemes; taking the id lets the tool walk the run's **full** main output, find every reference, and resolve each through the API to a **fresh** presigned link — so the hour-long life of the `public_url` embedded in the results never matters, and the same call still works days after the run. Finding the references is a contract, not a heuristic: the scheme is unambiguous, so every string that *is* a `pipelex-storage://` reference anywhere in the output is a produced file (or an input the output echoes — accepted, and harmless). Nothing is guessed from field names.

**The mechanics are the SDK's; the tool is thin over them.** The walk, the fresh links, the filenames, the never-overwrite rule and the download bounds are `@pipelex/sdk`'s artifact stack — `locateArtifacts` (the pure walk, which also says where each reference sits; `collectArtifacts` is its references alone), `resolveArtifacts` (one call to the platform's bulk resolve route, `POST /v1/resolve-storage-url/bulk`, for the whole set) and `downloadArtifacts` (resolve, fetch and write under a directory, returning a produced verdict), documented in the SDK's [`docs/artifact-download.md`](https://github.com/Pipelex/pipelex-sdk/blob/main/js/docs/artifact-download.md). What this tool keeps is what is the workshop's own: the tool envelope and its run-state verdicts, the containment of `dir` against the working directory, the deployment gate, the plain-http rule below, the reading of the download's own item codes into problems, every other failure being the SDK's problem relayed, and the prose summary. It carries no walker, filename rule or downloader of its own.

The public MCP input shape is:

```ts
{
  run_id: string;   // the durable run id from mthds_run
  dir?: string;     // where to save, relative to the server's working directory; created if missing, and marked with a .gitignore of * when this call created it; must stay inside it; omitted → runs/<run_id>; "." → the working directory itself
}
```

- `run_id` follows the run family's stance: non-blank is the only client-side check, format is server-owned.
- `dir` is optional and relative. A blank value, an absolute path, a lexical escape (`../x`) and a symlink inside the workspace that points out of it are all refused as `client.argument_invalid` at `dir` (reason `empty`, `absolute` or `outside_workspace`). The lexical half runs on the request, before the run is read, so a run that is still running or has failed refuses an escaping `dir` too rather than answering that there is nothing to save yet; the real-path half runs with the one `mkdir`, once the run has completed. Omitted, the run is saved into **`runs/<run_id>/`** under the working directory — one folder per run, so a second run's `main_stuff.json` never becomes a `main_stuff-1.json` that no longer says which run it came from, and it is the folder the `pipelex-run` skill already chose. The segment is built from the run id the API **answered**, never from the caller's argument, reduced to `[A-Za-z0-9_-]`; one with nothing left is a `client.argument_invalid` no-verdict at `dir` (reason `required`) whose message says to pass `dir`, and the containment above holds whatever the segment. `"."` saves into the working directory itself.

**Behavior.** The tool reads the run itself (`GET /v1/runs/{id}/results`, the same route and the same relayed problems as `mthds_run_results`) and branches on its state exactly as the results tool does: `running` and `failed` are produced verdicts (`status: "ok"` with `state`), since "nothing to save yet" and "a failed run produced nothing" are answers. On `completed`, it resolves the target directory under the containment rule and writes `main_stuff.json` into it; a directory that cannot take that one small file will not take the downloads either, so a failed output write stops the save there. It then walks the main output with `collectArtifacts`: a completed run with no reference is a produced verdict (`scope: "main_stuff"`, the `output`, `artifacts: []`, `all_saved: true`). Otherwise it hands the results it already holds to `downloadArtifacts` — the `results` form, so the run is never read twice — with that directory, the scope and the plain-http answer. The SDK resolves the whole set in one bulk call, downloads a bounded few at a time (four by default), re-resolves any link that has expired by the time its turn comes, and answers one entry per reference in discovery order; the tool turns each absolute path into one relative to the working directory and each per-item error into a full problem (see below). Per-item failures ride the item; the rest of the set still downloads. Reading the run here rather than through the SDK's `run_id` form is deliberate: a run that is still running or has failed never touches the disk.

**Scope.** The tool takes no `scope` input and always walks `main_stuff`, the SDK's default, naming it explicitly so the empty-walk check and the download agree. The verdict names what was walked: `scope: "main_stuff"` on every completed verdict, beside `artifacts`, whose length is the count of references found there, errors included. That is what makes an empty verdict read as "this run's main output references no stored file" rather than as an unexplained success. The SDK's other scope, `working_memory` (echoed inputs and every intermediate), is not offered here.

**The plain-http rule.** The SDK refuses a plain `http:` download link unless its caller opts in, and this tool opts in exactly when the configured API is itself plain http: `PIPELEX_BASE_URL` with the `http:` scheme is the local compose stack, whose object store mints plain-http presigned links, so a download there must accept them; a deployment reached over `https:` mints `https:` links, so a plain-http one from it is refused rather than followed silently. The explicit override is **`PIPELEX_MCP_ARTIFACTS_ALLOW_HTTP`**: `true` (or `1`) accepts plain-http links from any deployment — the case of an `https:` tunnel in front of the local stack — and `false` (or `0`) refuses them from every deployment, the local stack included. Unset or blank, the rule derives from the base URL. Any other value refuses, so a misspelled override can only make the tool stricter. A refused link is that item's error, the SDK's `client.link_refused` with the reason `plain_http`, relayed with the SDK's own sentence; the problem does not name the override, which this section and the tool reference do.

**Write policy.** Containment is the shared write-side boundary described in The files union and the path trust boundaries, and it stays this tool's own: the directory is real-path-checked on its deepest existing ancestor before it is created and again after, before the SDK writes a byte into it. The *filename* and the *collision rule* are the SDK's (`artifactFilename` and its exclusive create), and both follow from where the names come from. The filename is never taken from anything the caller typed: each file is named after the field it fills in the main output, the first path in its `found_at`, so the picture at `$.rooms[3].staged_photo.url` is saved as `rooms-3-staged_photo.png`. A final `url` key is dropped, each key is reduced to `[A-Za-z0-9_]`, the segments are joined with `-`, a name over the length cap keeps its tail, and a stem Windows reserves for a device gets a trailing `_`; a reference that is the whole output takes the scope's name, so an output that is one image is saved as `main_stuff.png`. The storage key supplies only the extension, and the object's content type supplies one when the key carries none (an unknown type gets no extension rather than a guessed one). The result is a bare filename, never empty and never starting with a dot, so no traversal survives. The full rule is the SDK's, in its `docs/artifact-download.md`. **Files are never overwritten**: the file is created exclusively (`wx`) and a name collision gets a numeric suffix (`name-1.ext`). Two fields can reduce to the same name (`staged photo` and `staged-photo`), and since a few files download at once, which of the two takes the suffix is not fixed. A collision here means two *different* files, so suffixing is the right answer — the exact inverse of `mthds_codegen`'s write arm, whose paths come from the engine and whose regeneration must land on the same names. The two writers share containment and nothing above it.

`main_stuff.json` is the one file of the run this tool writes itself, and it follows the same rule: an exclusive create, `main_stuff-1.json` and on when the name is taken, and the file removed again if the write fails. Saving the same run twice into the same folder therefore adds copies of everything rather than replacing anything. Because it is written before any download starts, the output has first claim on its name: a produced file that would also be called `main_stuff.json` — an output that is itself one stored JSON document — is the one that takes the suffix. The write is a few lines here rather than an SDK function because writing one JSON value is not the network work the SDK's artifact stack exists for, and the SDK's suffixing helper is internal to it.

**The mark on a directory it creates.** When resolving the target creates directories, one of them gets a `.gitignore` holding `*` before anything else is written into it. For the default location it is the topmost one created, `runs/` on a first save or `runs/<run_id>` when `runs/` already existed, so one mark covers every run saved there. For a `dir` the caller names it is the directory the run lands in, and only that one: an ancestor the save created on the way stays the caller's, unmarked, so a file put there later is not hidden. A run saved beside a method lands inside the method's folder, and the folder's membership rule reads the `.gitignore` files inside it, so the mark keeps the run's files out of the method `method_dir` sends, and out of git, without the rule knowing `runs/` by name (see The method folder). Only a directory this call created is marked, never one it found, `"."` included, and an existing `.gitignore` is never overwritten (an exclusive create, like every write of this tool), so a directory the user made stays theirs to mark. The mark is not a file of the run: it is not in `saved_paths`, and the summary says in one line which directory it marked. A mark that cannot be written refuses the save as `client.write_failed` at `dir`, as the output file's failure does, since a directory that cannot take it will not take the run either, and the save first removes the empty directories it created, from the target up to the topmost one, so a retry creates and marks them again rather than finding them unmarked.

**Download boundary.** The link is the configured API's own answer, so this is not an SSRF surface — but a download that writes to the user's disk is bounded regardless of who named the URL, and the bounds are the SDK's, taken at their defaults: `http(s)` only (plain `http:` under the rule above), no credentials in the URL and none of ours forwarded, redirects refused outright, a timeout covering the whole exchange (120 s per file), a byte cap enforced from `content-length` before a byte is written and again mid-stream (1 GiB per file), and a cap on the bytes the whole call writes (4 GiB), past which the file that would cross it and every file not yet started are item errors. The caps are accident guards against filling the disk, not product limits: run outputs are produced server-side, so a user cannot shrink one the way they can shrink an upload, and a low ceiling would leave them with no recourse but the expiring link. A refused or failed download leaves no partial file behind.

Each per-item error is a full problem, its `message` the SDK's sentence about that file. The resolve route's per-reference codes and the fetch boundary's are the SDK's to read, and the tool relays its reading: a reference the API rejected as found in the output (`invalid_storage_uri`), one belonging to another organization than the key's (`forbidden`) and a vanished object (`not_found`, a `404`/`410` from the store) are `input.reference_not_found`; a link the tool does not fetch (`unsupported_url` — not http(s), or carrying credentials), a refused plain-http link and a refused redirect are `client.link_refused`, its `reason` saying which; a store refusing a *fresh* signature (`store_refused`, a `401`/`403` — clock skew, a signing misconfiguration) and any other store status (`store_error`) are the SDK's reading of the store's status, or `runtime.unavailable` when no status came; a timeout and a network fault are `runtime.unavailable`; and a code the SDK cannot place is `runtime.unexpected`. The download's own codes, which the SDK reads as `runtime.unexpected`, are read here into the core codes they are: an oversized file (`too_large`) and one past the call's total cap (`total_limit_exceeded`) are `client.download_limit_exceeded`, naming the limit this call passed; a failed write is `client.write_failed` at `dir`; a file the download stopped before is `client.aborted`; and an expired link that could not be re-resolved (`resolve_failed`) is `runtime.unavailable`, since every call mints new links.

The structured output is:

```ts
{
  status: "ok" | "error";
  run_id?: string;
  state?: "running" | "completed" | "failed";   // mirrors mthds_run_results
  retry_after_seconds?: number | null;          // state=running only
  run_status?: RunStatus;                       // state=failed only
  run_error?: RunError;                         // state=failed only, when the run stored the problem it ended with — as on the results tool
  scope?: "main_stuff" | "working_memory";      // state=completed only — what was walked; always "main_stuff" here
  output?: {                                    // state=completed, and every refusal of the file download — the main output, saved first
    path: string;                               // where main_stuff.json was written, relative to the working directory
    size: number;                               // bytes written
  };
  artifacts?: Array<{                           // state=completed — one per storage reference, in discovery order; its length is the count walked. Also on a credential refused after some files were saved
    uri: string;                                // the pipelex-storage:// reference found in the output
    found_at: string[];                         // the $-rooted paths in main_stuff.json where the reference sits, in walk order, at most `MAX_FOUND_AT_PATHS` (8); the first named the file — on both arms
    found_at_omitted?: number;                  // how many further paths found_at leaves out; absent when it lists them all
    path?: string;                              // where it was saved, relative to the working directory — on success
    content_type?: string | null;               // the platform's content type from the reference; null when it has none
    size?: number;                              // bytes written
    error?: Problem;                            // per-item failure, a full problem with its own retry
  }>;
  saved_paths?: string[];                       // wherever output is — every file written: main_stuff.json first, then the saved artifacts
  all_saved?: boolean;                          // state=completed only — the output and every reference saved
  problem?: Problem;                            // no-verdict only (see Verdicts and errors)
}
```

**Verdict discipline**, consistent with the run family: once the run has been read, the result is produced (`status: "ok"`), discriminated on `state`; once the per-file walk has run, `all_saved` is the produced discriminator for the walk. **Partial success is a produced verdict, not an error** — the output and the files that landed are on disk and useful, and a sibling's failure must not hide them. The output itself is always saved by the time a verdict exists, so `all_saved` turns on the files. `status: "error"` with one `problem` is reserved for no-verdict conditions: a blank `run_id` or a bad `dir` (`client.argument_invalid`), an output that could not be written (`client.write_failed` at `dir`, and nothing downloaded), an answered run id that cannot name the default folder (`client.argument_invalid` at `dir`, reason `required`), no working directory to save under (`client.not_configured`), an unknown `run_id` (the platform's `run.not_found`), a missing or rejected credential, an organization whose credit or plan does not cover the call, an unreachable API or a bare runner without the run lifecycle (`client.unreachable`, `runtime.unsupported`), and a malformed report (`client.response_unreadable`). The bulk resolve route adds its whole-request refusals, which are about the caller or the deployment rather than any reference: each relayed as it came: a deployment that does not serve the route (a `404` — the bare `pipelex-api` runner has no resolve route at all, and a hosted deployment that predates the bulk route answers the same — which the SDK reads as `request.not_found`, its summary saying which API was in use and where its base URL was set), a key acting for no organization (a `400`, whose problem is the platform's, with no sentence of the workshop's own about minting a key in the run's organization: the platform's problem is what the caller reads), a credential the route refuses (`auth.invalid_credential` or `auth.missing_credential`, like every credential failure), a plan or credit limit, and a signing failure (a `5xx`, `runtime.unexpected` or `runtime.unavailable`). Every one of those refusals — and any other failure of the download itself, an unreachable API included — arrives after the output was written, so each carries `output` and `saved_paths` beside the `problem`, and its summary, the problem rendered, is followed by a paragraph naming what was saved before the failure. A credential refused part-way through a download — possible only when a link expires mid-set and its re-resolution is refused — also leaves the files saved before it on disk: the SDK hands them back on the error, and they ride the result as `artifacts` and in `saved_paths`, with the summary naming them too. A credential refused before any file was saved carries no `artifacts`: the SDK's verdict there is nothing but aborted items, each inviting a retry the refusal itself rules out. `state` and `all_saved` stay absent, because no verdict was produced and nothing here may read as one; a consumer that could only parse the prose would otherwise call again and get suffixed copies of files it already has. Per-item errors are read as above.

**Summary.** The saved paths are deliberately repeated in the prose (the `mthds_inputs_template` pattern — they are what the agent must report), with the working directory named once so the paths read as locations, `main_stuff.json` first with its size, each file's content type, size and the field it fills (its first path, with a count of any others), and the never-overwrite rule stated. A file that failed is named by its field and its reference. It ends by telling the model to read the output from the file rather than retype it. Per-item failures ride here too, each on one line (its detail, the SDK's sentence about the file, its code and its next step), since they are not the top-level `problem`. A completed run whose output references no stored file says that the output is the whole run.

**Live coverage.** The hermetic suite runs the tool over a mocked SDK client — a fake `getRunResult` and a fake `downloadArtifacts` that writes into the directory it is handed — against a real temp working directory, so the containment, the directory creation, the relative-path reporting and the reading of every SDK outcome are exercised on disk. The fake names and locates each file with the SDK's own `artifactFilename` and `locateArtifacts`, so its names and `found_at` are the released SDK's rather than a copy of them. The download boundary itself, the filename rule, the never-overwrite rule and the caps are the SDK's, proven there on the wire and on disk. The live leg, `artifacts.e2e.ts`, has a free half that refuses an unknown run id before anything is written, and a paid half, in the run family's tier, that saves a completed run of the published `text_stats` package and compares `main_stuff.json` with the unbounded output the platform holds. That run references no stored file, so the bulk resolve route is not reached there: a run that produces one costs an image generation, which the suite does not buy on every paid run.

### Workshop tools at a glance

**Tool: `mthds_list_methods`**

- **Input**: `{ query?, limit?, cursor? }` — trimmed case-insensitive search applied server-side, bounded page size, opaque continuation cursor (see Catalog Discovery Scope).
- **Output**: `{ status, returned_count?, next_cursor?, methods?, problem? }` in `structuredContent`, plus a bounded text summary that opens with a render directive (report each method with its name **and** description) and then repeats names, descriptions, ids, and cursor guidance. No method source, stored inputs/outputs, org/user ids, `_meta`, or view payload.
- **Behavior**: Asks the platform for one page of the active key's organization catalog through the SDK, immediately validates and projects the rows it returns, and treats empty catalogs and no-match queries as success. Listing executes nothing; a returned id can be passed to `mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs` and `mthds_run`.
- **Annotations**: Read-only, non-destructive, no open-world publishing.
- **View**: none — bounded catalog metadata is read directly by the model.

**Tool: `mthds_list_files`**

- **Input**: `{ query?, kind?, format?, method_id?, limit?, cursor? }` — a server-side name search, the file's kind, format keys, a saved method's bare id, a bounded page size and an opaque continuation cursor (see Files Discovery Scope).
- **Output**: `{ status, returned_count?, next_cursor?, files?, problem? }` in `structuredContent`, each file with its `uri`, plus a text summary that names the scope with its filters, says to put a file's uri where a run's input takes a file with nothing to upload, and lists each file's name, format, size, provenance, date and uri. No member id, `_meta` or view payload.
- **Behavior**: Asks the platform for one page of the organization's files through the SDK (`GET /v1/files`), checks and projects the rows it returns, and treats an empty page as success, saying so in words when it still carries a cursor. Listing reads no file's content; a returned uri goes straight into `mthds_run`'s inputs.
- **Annotations**: Read-only, non-destructive, no open-world publishing.
- **View**: none.

**Tool: `mthds_models`**

- **Input**: `{ category?, reference? }` — a category narrows either use; without `reference` the tool lists the deck, and with it, it checks that reference (see Model Deck Scope).
- **Output**: `{ status, category?, deck?, reference?, kind?, name?, resolution?, matches?, suggestions?, other_kinds?, other_categories?, problem? }` in `structuredContent`, plus a text summary that repeats the deck by category or states the check's answer, and says that the deck is what the runner can serve rather than what the account may use. No `_meta`, no `available_view_specs`.
- **Behavior**: A listing reads `GET /v1/models` through the SDK, passing the category. A check asks the runner through `GET /v1/models/check`, passing the reference as written and the category when one was given, and relays its verdict after checking its shape: `resolved` or `not_found`, definitive for every kind, a match per category with what a run through the reference calls now, and on a miss the nearest names, the same name under another sigil and, when a category was named, the categories where the reference resolves. A reference the runner cannot read is its `422` problem, relayed with the runner's own reason and the field it names.
- **Annotations**: Read-only, non-destructive, no open-world publishing.
- **View**: none.

**Tool: `mthds_validate`**

- **Input**: `{ method_dir?, files?, method_ref?, method_id?, graph_page? }` — exactly one of `method_dir` / `files` / `method_ref` / `method_id` (see Method Selectors and Validation Scope)
- **Output**: `{ status, is_valid, is_runnable, pending_signatures, available_view_specs, main_pipe?, graph_page?, warnings?, errors?, files_sent?, problem? }` in `structuredContent`, plus a text summary in MCP `content` carrying the rendered signature line and, when the page was written or tried, a `## Method graph` section. The workshop renders no views, so no graph or form artifact rides `_meta` and `available_view_specs` is always empty. `main_pipe` is the main pipe's typed signature, the one thing a valid verdict puts in the model's context beyond the verdict itself (see Validation Scope).
- **Behavior**: Validates request shape, calls the Pipelex API against `PIPELEX_BASE_URL` or `https://api.pipelex.com` with signatures and markdown enabled, and maps produced validation verdicts into flattened structured content, projecting the main pipe's signature from the report's per-pipe IO contracts. A `method_ref` or `method_id` is a server pass-through on `POST /v1/validate` itself — the runner resolves the address, the hosted platform resolves the id; nothing is expanded client-side. When every file came as `{ path }`, it writes `method-graph.html` beside them unless `graph_page` is false (see The method graph page).
- **Annotations**: Not read-only (it writes the method graph page), non-destructive (it replaces only a page carrying its own mark), no open-world publishing.
- **View**: none — the flowchart is the page on disk.

**Tool: `mthds_inputs_template`**

- **Input**: `{ method_dir?, files?, method_ref?, method_id?, pipe_ref?, explicit?, format? }` — exactly one of `method_dir` / `files` / `method_ref` / `method_id` (see Method Selectors and Inputs Template Scope)
- **Output**: `{ status, is_valid, pipe_ref?, format?, explicit?, inputs?, inputs_toml?, errors?, files_sent?, problem? }` in `structuredContent`, plus a text summary in MCP `content` that includes the template in a fenced code block and, after it, the next step: fill it in (converting a TOML template to a JSON object) and call `mthds_prepare_inputs`, or go straight to `mthds_run` when every file value is already a URL or a storage reference. No `_meta`, no `available_view_specs`.
- **Behavior**: Validates request shape, calls `POST /v1/pipe-io` against `PIPELEX_BASE_URL` or `https://api.pipelex.com` for the one pipe, a folder or files sent as one tree, projects the template client-side from that pipe's input-form descriptor, and maps the produced verdict into flattened structured content with the same `status`/`is_valid` discipline as `mthds_validate`. Every selector is a server pass-through — the runner resolves an address, the hosted platform resolves an id; nothing is expanded client-side.
- **Annotations**: Read-only, non-destructive, no open-world publishing.
- **View**: none — the template is small structured data the model reads directly.

**Tool: `mthds_codegen`**

- **Input**: `{ method_dir?, files?, method_ref?, method_id?, target, output_dir? }` — exactly one of `method_dir` / `files` / `method_ref` / `method_id`, plus the required `target` and an optional `output_dir` (see Method Selectors and Codegen Scope)
- **Output**: `{ status, is_valid, target?, kind?, crate_fingerprint?, engine_version?, artifacts?, lock?, truncated?, output_dir?, is_current?, orphans?, orphans_truncated?, drifts?, errors?, files_sent?, problem? }` in `structuredContent`, plus a text summary in MCP `content`. Without `output_dir` the summary repeats every artifact and the lock in fenced blocks tagged for their language; on the written arm it carries no content and no fenced blocks, only where the files landed and the check verdict. No `_meta`, no `available_view_specs`.
- **Behavior**: Validates request shape, calls `POST /v1/codegen` with `kind: "types"` and the requested `target` (never a `pipe_ref`), and projects the produced verdict with the same `status`/`is_valid` discipline as `mthds_inputs_template`. Every selector is a server pass-through — the runner resolves an address, the hosted platform resolves an id. Every valid response is preflighted through the SDK's `runCodegenCheck` before it is written or relayed. Without `output_dir`, artifacts and the lock ride the response verbatim, bounded by whole file with the lock's bytes reserved first. With `output_dir`, the tree is written to disk — stamped files overwritten, anything else refusing the whole write — and content is withheld from every stream.
- **Annotations**: NOT read-only (`readOnlyHint: false` — it can write) and **destructive** (`destructiveHint: true`) — regeneration overwrites the stamped files it wrote before and discards hand-edits below the stamp, which is a destructive update rather than an additive one, and this is the hint a host reads to decide whether to confirm before calling. No open-world publishing. Contrast `mthds_download_artifacts`, which stays non-destructive because it never overwrites.
- **View**: none — decided out; the fenced blocks in the summary serve the copy-out case on every host.

**Tool: `mthds_prepare_inputs`**

- **Input**: `{ method_dir?, files?, method_ref?, method_id?, pipe_ref?, inputs?, inputs_path?, kind? }` — exactly one of `method_dir` / `files` / `method_ref` / `method_id` (see Method Selectors), plus exactly one of the filled `inputs` or `inputs_path`, a `.json` file holding them (see Prepare Inputs Scope and The inputs file), and optionally what the uploads are recorded as, `uploaded` or the method's `test` files
- **Output**: `{ status, is_valid, pipe_ref?, inputs?, uploads?, kind?, test_method_id?, files_sent?, problem? }` in `structuredContent`, plus a text summary in MCP `content` that repeats the prepared `inputs` in a fenced code block. No `_meta`, no `available_view_specs`.
- **Behavior**: Resolves the pipe's declared signature from the input-form descriptor (one `POST /v1/pipe-io` for the one pipe, with no dry run, whatever the selector), uploads file-bearing input values to Pipelex storage, and rewrites them to `pipelex-storage://` (wrapping `@pipelex/sdk`'s `prepareInputs`); `http(s)` / `pipelex-storage://` values pass through unchanged. Uploads with the user's key. An unresolvable closure is a no-verdict error (the SDK throws without a structured verdict).
- **Annotations**: NOT read-only (`readOnlyHint: false` — it uploads), non-destructive, no open-world publishing.
- **View**: none — the prepared inputs are small structured data the model reads directly.

**Tool: `mthds_run`**

- **Input**: `{ method_dir?, files?, method_ref?, method_id?, pipe_code?, inputs?, inputs_path? }` — at least one run source, and at most one of `inputs` / `inputs_path` (see The inputs file); `method_ref` pairs with nothing, `method_dir` or `files` + `method_id` is legal, and `method_dir` + `files` is not (see Method Selectors and Run Scope)
- **Output**: `{ status, run_id?, run_status?, created_at?, method_provenance?, method_version?, available_view_specs, files_sent?, problem? }` in `structuredContent`, plus a start-ack text summary in MCP `content` with the run id and follow-up etiquette (and the resolved provenance on a `method_ref` run, and which content runs on a by-id run).
- **Behavior**: Validates request shape, then starts a durable run via `POST /v1/start` (fire-and-forget 202) — from a method folder or inline files, from a published method's address by `method_ref` (server-resolved at the tag, provenance returned), or from a registered method by `method_id`, whose selector names the content that runs (see Method versions, on two platforms) (files win when both are supplied; the id then rides as run-history linkage — see Run Scope). Never blocks on the result.
- **Annotations**: NOT read-only (`readOnlyHint: false`), non-destructive, no open-world publishing. The description states it executes the method on the hosted API and spends inference credit.
- **View**: none; `available_view_specs` is always empty here.

**Tool: `mthds_run_status`**

- **Input**: `{ run_id }`
- **Output**: `{ status, run_id?, run_status?, is_terminal?, degraded?, retry_after_seconds?, created_at?, finished_at?, method_version?, error?, progress?, progress_invocations_omitted?, problem? }` in `structuredContent`, plus a text summary with a check-again hint while non-terminal, why the run failed once it ended without completing, and the platform's one-line progress summary as `Progress: …` when the progress read answered.
- **Behavior**: One cheap self-healing status read (`GET /v1/runs/{id}/status`), then one best-effort read of the run's progress snapshot (`GET /v1/runs/{id}/progress`), bounded at 5 s and left out when it fails (see "A run says how far it has got"). A terminal non-COMPLETED status is a produced verdict, not an error, and carries the problem the run ended with as `error` (see "A failed run says why").
- **Annotations**: Read-only, non-destructive, no open-world publishing.
- **View**: none.

**Tool: `mthds_run_results`**

- **Input**: `{ run_id }`
- **Output**: `{ status, run_id?, state?, retry_after_seconds?, run_status?, run_error?, main_stuff?, truncated?, image_candidates?, usage?, available_view_specs, problem? }` in `structuredContent`, plus a text summary that on `completed` repeats the bounded main output in a fenced code block. The workshop carries no executed graph, and `available_view_specs` is always empty.
- **Behavior**: One-shot result lookup (`GET /v1/runs/{id}/results`), discriminated on `state`: `running` (with retry hint), `completed` (bounded `main_stuff` + `truncated` flag), `failed` (terminal status and the problem the run ended with as `run_error`, read from a status read of the run when the arm carries none; no graph exists for failed runs). On `completed` it also reports the free stored-file inventory — `image_candidates` and one merged prose sentence naming `mthds_show_images` — walking the full output in memory and **fetching nothing**; the summary also names `mthds_download_artifacts` on every completed result, as the way to keep the run and, when the output was truncated, to read the rest. The read names the artifacts it wants (`?artifacts=`), so the platform reads and re-signs only what the tool projects: the main output and the usage records; the working memory is never read.
- **Annotations**: Read-only, non-destructive, no open-world publishing.
- **View**: none.

**Tool: `mthds_show_images`**

- **Input**: `{ run_id, images?, indices? }` — the selection fields are mutually exclusive; omitting both shows every candidate (see Image Display Scope)
- **Output**: `{ status, run_id?, state?, retry_after_seconds?, run_status?, run_error?, images?, omitted?, all_inlined?, problem? }` in `structuredContent`, plus a text summary and, after it, one MCP **image content block** per inlined picture: `{ type: "image", data, mimeType, _meta: { uri } }` and **never `annotations`** (Codex refuses an annotated block). No view, no `_meta` on the result itself, no `available_view_specs`.
- **Behavior**: Reads the run through the results route, asking for the main output alone, prefilters the stored references by storage key, intersects the caller's selection with what the run produced, then fetches each surviving candidate through the SDK's bounded `fetchArtifact` under a per-image cap, a per-call budget and a per-call attempt count. The content-type gate is the object store's own header. A picture that does not fit is `withheld` with its reason; a per-reference failure is its `error`, a full problem; partial success is a produced verdict.
- **Annotations**: Read-only (it writes nothing anywhere — what it changes is the conversation, which the description says), non-destructive, no open-world publishing (the link it fetches is the configured API's own answer).

**Tool: `mthds_download_artifacts`**

- **Input**: `{ run_id, dir? }` — the durable run id, and optionally a directory relative to the server's working directory to save into; omitted, `runs/<run_id>`, and `"."` for the working directory itself (see Artifact Download Scope).
- **Output**: `{ status, run_id?, state?, retry_after_seconds?, run_status?, run_error?, scope?, output?, artifacts?, saved_paths?, all_saved?, problem? }` in `structuredContent`, plus a text summary that repeats the saved paths (relative to the working directory, which it names once) and any per-file failure. No `_meta`, no `available_view_specs`.
- **Behavior**: Reads the run (`GET /v1/runs/{id}/results`, asking for the main output alone, the one artifact it writes and walks) and branches on its state like `mthds_run_results`; on `completed`, writes the full main output verbatim as `main_stuff.json` in the target directory, then walks it for `pipelex-storage://` references and hands the results to the SDK's `downloadArtifacts`, which resolves them to fresh presigned links in one call to `POST /v1/resolve-storage-url/bulk` and streams the bytes into files under the working directory within the SDK's download boundary (http(s) only with plain http under the base-URL rule, no redirects, bounded timeout, per-file and per-call byte caps, no partial file left behind). Each file is named after the field it fills (the first path in its `found_at`, the storage key supplying only the extension) and never overwrites an existing file; the directory is real-path-contained on both sides of `mkdir` before the SDK writes into it. Partial success is a produced verdict.
- **Annotations**: NOT read-only (`readOnlyHint: false` — it writes files), non-destructive (it never overwrites), no open-world publishing (it fetches only links the configured Pipelex API minted).
- **View**: none — the saved paths are small structured data the model reports directly.

**Tool: `mthds_save_method`**, **Tool: `mthds_get_method`** and **Tool: `mthds_publish_method`** — stated in full in Catalog Write Scope.

## Non-Goals

The server must not add Pipelex Hosted API deployment behavior, blocking execution (`POST /v1/execute` or the SDK's blocking wrappers), run cancellation, MCP resources (the protocol's `resources/*` methods, not a method's template files, which travel in its tree), logs, package publishing (of MTHDS method packages to a registry — not this server's own npm distribution, which is how the workshop ships), subprocess fallbacks, or a production validation UI. Filesystem access is scoped: the workshop reads exactly the `{ path }` items, the `method_dir` folders and the `inputs_path` file submitted to it and writes only saved runs — a completed run's main output and the files it references (`mthds_download_artifacts`) — generated trees (`mthds_codegen`'s `output_dir`), a pulled method's sources (`mthds_get_method`'s `output_dir`), the link file both catalog-write tools leave beside a bundle, and the method graph page `mthds_validate` leaves beside the files it validated, within its trust boundaries. The workshop registers no views at launch (tools-first — see What the workshop registers); local view delivery is a later increment gated on self-contained view bundles. `mthds_prepare_inputs` (see Prepare Inputs Scope) now covers turning file-bearing inputs into run-ready `pipelex-storage://` references, from local paths/bytes/`data:` URLs using the user's key. What stays out of scope beside it:

- **Inline asset bytes in tool arguments remain out of scope.** Nothing may **accept** base64 as an argument, because bytes in an argument pass through the model's context. Per-user auth settles *whose* storage an upload targets; it never settled the context-cost concern. Returning base64 has one deliberate exception, the image tool (see Image Display Scope): an MCP image content block is base64 in the result, it is the only way a host can show a model a picture, and it is the reason the gesture is a tool of its own rather than a default on any other surface — the caller chooses the permanent context cost, it is bounded by named caps, and the results tool is not changed by it.
- **Opt-in `http(s)`→storage ingest** for ordinary user-pasted URLs stays parked — an `http(s)` URL at a file position passes through unchanged, and ingesting it is a later, additive SDK feature.

The organization's files are in scope as a listing alone (`mthds_list_files`, see Files Discovery Scope): renaming a file, a file's detail and uses, links to read one, archives of several and adding one to a method's draft stay the app's, and a run reads a listed file through its address without the workshop fetching it.

Method access by selector is in scope (`method_ref` and `method_id` per the Method Selectors table), server-resolved on every tool that takes them. Catalog listing is in scope through `mthds_list_methods`, and **three of the exclusions that stood beside it have ended**: method source retrieval, catalog create/update, and a save tool are served by `mthds_save_method` and `mthds_get_method`, and publishing a method's draft as a version by `mthds_publish_method` (see Catalog Write Scope). Listing a method's versions is not a tool: the pull and the save report the latest version, and `mt_…@<n>` reads any one of them. What remains out of scope for this increment: **delete** — the platform makes it admin-only, it erases every run the method produced, and it stays a webapp gesture; **dynamic per-method tool projection**; and **stored-`input_data` defaulting**, which the save tool preserves on an update precisely so that it never has to read it. The catalog's human surface is still the webapp's: these tools exist so that a bundle authored on disk can reach the catalog and come back, not so that the catalog can be administered from a conversation. Code generation is in scope through `mthds_codegen` (see Codegen Scope), and only that: no `mthds_resolve` tool (the crate itself is not something a model reads), no `codegen check` tool (the check is offline by design — a workshop agent runs `pipelex codegen check` or the SDK's `runCodegenCheck` directly), no per-pipe kinds until the engine serves them, no JSON Schema target until the engine has one (a cross-repo cascade, not an MCP composition of the per-pipe `build/output` schemas), no reformatting of artifacts, no deletion of orphaned generated files (they are reported and left on disk), and no detection or reporting of hand-edits before an overwrite (a stamped file is this tool's, edited or not).

Repository quality gates are in scope: ESLint, Prettier, TypeScript type checking, Vitest unit tests, and a combined `npm run check` command should remain available locally.

The prototype should call the Pipelex API (local OSS `pipelex-api` during development) only through `@pipelex/sdk`'s `PipelexApiClient`; it should not expose API internals such as `mthds_contents` or `mthds_sources` in the MCP schema.

## UX Flows

Discover a registered method:

1. When the user asks what saved methods exist or names one without an id, the assistant calls `mthds_list_methods`, with a focused `query` when possible.
2. One strong match supplies its canonical `method_id`; several plausible matches are presented by bounded name/description for the user to choose; no matches are reported without inventing an id.
3. A listed row is never presented as a validation or runnable verdict — the listing carries no such signal. A method whose stored source is missing surfaces that at the point of use, as the platform's refusal located at `method_id`, a no-verdict from a by-id validate, template, prepare or run.
4. The chosen id feeds the flow: optionally `mthds_validate`, then `mthds_inputs_template` → fill and prepare the inputs → `mthds_run`.

Validate MTHDS files:

1. The user asks the assistant to validate one or more `.mthds` files.
2. The assistant submits the files to `mthds_validate` — `{ path }` items, or inline contents with optional provenance URIs (see The files union).
3. The tool returns structured validation facts plus a text summary that the assistant can use to repair the files. For `{ path }` files it has also written the method's flowchart, `method-graph.html`, beside them, and says where; the assistant tells the user where to open it when they want to see the method.
4. The assistant may repeat the same flow after editing the submitted source content, which rewrites the page.

Name a model in a method:

1. The user names a model while the assistant writes or edits a method, or asks which models a pipe can use.
2. The assistant calls `mthds_models` with the pipe's category to see the deck and offers a preset where one fits; a pipe the user named no model for keeps no `model` field.
3. For a reference the user typed, the assistant calls `mthds_models` with `reference`. On `not_found` it offers the right sigil, the right category or the nearest names; on a match that reaches no model it warns that a run through it would fail.
4. The assistant validates the method, which checks every reference by the rule the check applied. A run can still be refused a listed model by the account's gateway, which the tool has said.

Prepare inputs for a method:

1. The user asks the assistant to prepare inputs for a `.mthds` method (or a skill needs the method's input schema).
2. The assistant submits the files (and optionally a qualified `pipe_ref`) to `mthds_inputs_template` — the same file forms as validation, or the method's `method_ref` or `method_id`.
3. The tool returns the fill-in template plus the resolved pipe, which the assistant fills with user data, synthetic data, or placeholders.
4. On an invalid closure, the tool returns the closure's faults instead (`errors`, one problem item each); the assistant can repair via the validation flow and retry.

Generate typed code for a method:

1. The user asks for types or models for a method in their project, or an assistant building a consumer needs them — a TypeScript app reading run results, a Python service, a Pipelex host.
2. The assistant picks the target from the project (the user's explicit request wins: a TypeScript or JavaScript project wants `ts-zod`, a Python consumer `python-pydantic`, a Pipelex host or `@pipe_func` implementation `python-structures`) and calls `mthds_codegen` with the files, a `method_ref` address, or a `method_id`.
3. **It passes `output_dir`** — a dedicated generated directory such as `src/generated/<method>/`. The tool writes the artifacts and `codegen.lock` there verbatim, reports where each landed and whether the offline check finds the tree current, and returns no file content at all. Regeneration into the same directory overwrites the stamped files it wrote before; a foreign file there refuses the whole write instructively.
4. **Without `output_dir`**, when the assistant wants the bytes, the tool returns the stamped artifacts and `codegen.lock`; the assistant writes each artifact at its path and the lock beside them, verbatim, into a dedicated generated directory. `pipelex codegen check` (or the SDK's `runCodegenCheck`) then passes on that tree.
5. On an unresolvable closure the tool returns the closure's faults instead (`errors`, one problem item each); the assistant repairs via the validation flow and retries. A set too large for the response is withheld by whole file (`truncated: true`); the assistant passes `output_dir`, or generates locally with the CLI, rather than writing a partial file.

Prepare filled inputs for a run:

1. After filling the `mthds_inputs_template` output, the assistant calls `mthds_prepare_inputs` with the same selector it templated from — the same files, the same `method_ref` address, or the same `method_id` — plus the pipe and the filled `inputs`.
2. File-bearing values (local paths, `data:` URLs, bytes) are uploaded with the user's key and rewritten to `pipelex-storage://`; `http(s)` and `pipelex-storage://` values pass through unchanged.
3. The assistant passes the prepared `inputs` straight to `mthds_run`. An inputs set that is already all pass-through can skip this step. An unresolvable closure is a no-verdict `problem`; the assistant repairs via the validation flow and retries.

Run a method on a file the team already holds:

1. The user names a file the organization already has rather than one on disk, such as "the invoice I uploaded this morning" or "the report yesterday's run produced".
2. The assistant calls `mthds_list_files`, narrowed server-side by a `query` on the name, a `kind`, a `format` or a saved method's `method_id`, and keeps asking with the returned cursor while the listing carries one and the file has not appeared.
3. One clear match supplies its `uri`; several are presented by name, format, size, provenance and date for the user to choose; none is reported without inventing an address.
4. The assistant puts the uri where the method's input takes a file, as it would an `http(s)` URL, and passes the inputs straight to `mthds_run`: nothing is uploaded, so `mthds_prepare_inputs` is skipped unless another value still needs uploading.

Record a method's test files:

1. The user prepares inputs to try a saved method and wants the files kept as the method's test files rather than as loose uploads.
2. The assistant calls `mthds_prepare_inputs` with `kind: "test"` and the method by its `method_id` or by its folder linked to the saved method.
3. The uploads are recorded as that method's test files, the result says which method, and `mthds_list_files` with that `method_id` lists them for the next run.

Run a method durably:

1. The user asks the assistant to run a `.mthds` method (usually after validating it and filling the inputs template).
2. The assistant submits the files (or an address or an id), the pipe to run, and the filled inputs to `mthds_run`; the tool returns the durable `run_id` immediately.
3. The assistant checks on the run with `mthds_run_status` when asked, reading its one-line progress (honoring the retry hint rather than spin-polling); once the run is terminal it reports through `mthds_run_results`, and `mthds_show_images` shows a picture the run produced when someone asks to see it.
4. Days later, the same `run_id` still answers `mthds_run_status` / `mthds_run_results` — the run is durable and the MCP is stateless.

Save a run's produced files to disk:

1. A completed run's results carry its main output, and any produced image, PDF or document in it as content with a `pipelex-storage://` reference beside a presigned `public_url` that expires within the hour. The results summary names `mthds_download_artifacts` as the way to keep the run, and counts those references when there are any.
2. The assistant calls `mthds_download_artifacts` with the run id (optionally a `dir` relative to the working directory; by default the run lands in `runs/<run_id>/`). The tool writes the full output as `main_stuff.json`, walks it for references, resolves them to fresh links through the API, and saves the files beside it — never overwriting, suffixing on collision.
3. The assistant reports the saved paths. Days later, the same call with the same run id still works; no presigned link is ever the thing the user has to catch in time.

Run a registered method by reference:

1. The user names a registered method. If no catalog id (`mt_…`) is supplied, the assistant resolves it in-band with `mthds_list_methods` and disambiguates by name/description when necessary.
2. The assistant may first call `mthds_validate` with `method_id` (no files) to confirm the version it is about to run still validates — e.g. after a suspected edit — getting the same structured verdict as a files-based call, with no bundle entering the conversation.
3. The assistant calls `mthds_inputs_template` with `method_id` (no files) and fills the returned template with user data.
4. The assistant calls `mthds_run` with `method_id` and the filled `inputs` — no bundle ever enters the conversation, the run executes the method's latest published version (or, with `mt_…@draft`, its draft), and the result says which.
5. Everything downstream is unchanged: `mthds_run_status` and `mthds_run_results` operate on the durable `run_id` and don't care how the run started.

Run a published method by address:

1. The user pastes or names a method address — `github.com/<owner>/<repo>[/<selector>][@<tag>]`, e.g. `github.com/Pipelex/methods/documents@v0.1.0`. Nothing needs discovering: the address is the reference, no catalog and no id.
2. The assistant calls `mthds_inputs_template` with `method_ref` (no files) and fills the returned template with user data. It may first call `mthds_validate` with `method_ref` for a structured verdict — the server fetches the package either way, so no bundle enters the conversation.
3. The assistant calls `mthds_run` with `method_ref` and the filled `inputs`. The start ack carries `method_provenance` — the address, the tag, and the commit SHA that was actually fetched — which the assistant can report so the run stays explainable if the tag later moves.
4. Everything downstream is unchanged: `mthds_run_status` and `mthds_run_results` operate on the durable `run_id`.
