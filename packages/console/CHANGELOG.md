# Changelog

This is the changelog of the hosted console: the Pipelex MCP that chat hosts reach at `https://mcp.pipelex.com/mcp`, deployed to Alpic. Up to and including 0.20.0 the console was released together with the workshop, `@pipelex/mcp`, under one version, and those releases are recorded in [the workshop's changelog](../workshop/CHANGELOG.md). After 0.20.0 the console has its own version, this changelog, and `console-vX.Y.Z` tags.

## [Unreleased]

### Changed

- **`pipelex_show_method` and `pipelex_run`'s input check read `POST /v1/pipe-io`, with no dry run**: A show and a run's input preparation each read the method's signature and forms from one call that loads the method without validating it, so neither waits for the dry run of every pipe any more, and the console calls `/v1/validate` nowhere. The method's graph is now drawn on the server from the method's own files by `@pipelex/mthds-ui`'s static builder, one node per pipe call, for a saved method and a published address alike; only the graph reaches the view, never the source, and a method whose graph would pass 2,000 nodes is shown without one. The graph starts at the pipe the show is for, the named `pipe_ref` or else the entry pipe, so a named pipe shows as itself and the pipes it calls, with a caption naming the entry pipe; a method with no single entry pipe is drawn from the first `main_pipe` its files declare, with no caption, so a pipe clicked there still opens a form. A method with pending signatures is still reported as not runnable, but a method whose dry run would fail is now reported runnable and fails when it runs, and a published package that ships Python now shows, its run being refused at the start as before. A named `pipe_ref` the method does not declare, or a method with no single entry pipe, is refused at `pipe_ref` with the route's own reason during a run's input check. The deployment must serve `/v1/pipe-io` (pipelex-api 0.33.1 or later): a runner too old to serve it answers a bare `404`, reported as a `config` error at `PIPELEX_BASE_URL` naming the route rather than as a missing package or method, and the hosted gateway answers a `403`. The tool list is unchanged, so no connector needs re-adding.
- **`@pipelex/sdk` moves from 0.26.0 to 0.27.0**, the release that carries `pipeIo()`, which the show and the run's input check call.

### Fixed

- **A click on an image or a file's name saves the file on claude.ai**: On a host that takes download requests, a click on an output image, or on a file's name, now saves that file just as its download button does, under the same name, so the host asks to confirm a named file. Before, it opened the file, and claude.ai's confirmation showed a long link full of encoded signature instead of a name. A file in the executed graph's data panel is named after its stored file, and a file too large to save that way still opens in a new tab. On ChatGPT, which takes no download request, the click still opens the file in a new tab.
- **A stalled file read no longer holds a download for good**: The view reads a stored file's bytes before handing them to the host, and that read had no time limit, so a read that stalled without failing left the file's download button spinning and disabled until the view reloaded. The view now gives a read up after two minutes, which is enough for the largest file one download request carries on a slow connection. The button then settles on a failure that can be retried, and a click on the file's name or image opens it in a new tab instead.
- **Both views fill the fullscreen frame on claude.ai**: In fullscreen, `run-graph` and `run-follow` laid themselves out in 600 pixels and cut off there, with the rest of the frame empty, because the frame's height claude.ai states never reached them. They now take the frame's own height in fullscreen, keep the host's safe-area insets once rather than twice, and `run-graph`'s Collapse button sits inside those insets rather than at the frame's edge. This changes the views' code, so ChatGPT shows it only once the connector is removed and added again.

## [0.20.1] - 2026-09-28

### Highlights

- **A run's output lives in the view.** A run started from the method's form shows its results in place, through the form kernel's result viewer, with images and documents that now load, and every file in the output can be saved.
- **A failed run says why.** The run tools and both views give the reason, the next step and a support line, from the error report the runner stored on the run.
- **Remove and re-add the Pipelex connector in ChatGPT after this release.** ChatGPT keeps a connector's tool list and its views from the moment it was added, and this release changes both: the run tools' output schemas gain `failure`, and the views' code and content security policy moved.

### Added

- **A failed run says why, what to do and what to give support**: `pipelex_run_status` on a terminal status other than COMPLETED, and the `failed` state of `pipelex_run_results` and `pipelex_show_images`, now carry a `failure` object from the error report the runner stored on the run, and their summaries say why the run failed, what to do next, whether running it again can help and a support line with the run id, the error type and the time. Both run views show the person the reason, the next step and that support line with a Copy button, never the report's raw message or the provider's text, where they used to show only the ending status. The tools' output schemas gain the field; if an existing ChatGPT connector keeps the old tool list, remove and re-add it.
- **A run's output in the method form's view**: A run started from the `run-graph` view's form now shows its results in the form's place once it completes, with the executed graph replacing the dry-run one and the form folded behind "Edit inputs and run again". The user no longer has to ask the assistant to fetch the results. The view keeps the run in host-persisted view state, so reopening the conversation shows the run's results again, with the form on the pipe that ran; each press of Run clears that state first, so a failed start never brings an older run back. Run stays disabled until the results are read, or until their fetch gives up after a little over two minutes of reads and says so.
- **A run's output can be saved from the view**: The results panel's Download saves the output and every file in it, and each image, document or HTML page carries its own download button, in the fullscreen graph's data panel too. What it saves is named after the pipe that ran, so a method whose output is one image saves it as `generate_portrait.png`, and a richer output's JSON copy is `generate_portrait.json`. The files go through the host's own download request, one confirmation for the whole output, on a host that takes one, with each stored file's bytes read by the view and carried in the request; on a host that does not, each stored image or document opens in a new tab through a page the console serves, which keeps its signed link intact, as does a click on an image preview or a file's name on any host, and the whole-output Download, which always includes the JSON copy, is not drawn. An output too large for the view to render, which it shows in part as JSON, gets a "Download the whole output" of its own that saves all of it.

### Changed

- **The console's instructions say what a method leaves to whatever calls it**: Both variants now say, right after the flow, that a method only turns the inputs it is given into results, and that fetching from mail, drives or business systems, running on a schedule and writing back are up to whatever calls it, so a model asked to automate a task fetches the inputs and delivers the results with the host's other connectors. To stay within the text budget, several sentences are shorter without changing what they say. Only the instructions changed, not the tool list.
- **`@pipelex/sdk` 0.25.1 → 0.26.0 and `mthds` 0.25.0 → 0.28.0**: The SDK's failed results read now carries the run's stored error report, which the failed state of `pipelex_run_results` and `pipelex_show_images` reads before falling back to a status read of the run. `mthds` moves with it, since this SDK requires 0.28.0.
- **`@pipelex/mthds-ui` 0.24.0 → 0.27.0**: The views take the form kernel 0.12.1, so a result table shows five columns and moves the rest into the row's detail, and a graph marks a list-valued stuff as `Document[]` wherever the runtime that drew it records that the stuff is a list. The console now compiles the kernel's controls with its own Tailwind build, which mthds-ui 0.25.0 made the host's job, instead of ranking a second, prebuilt stylesheet under its own. The tools' output schemas now state a nullable field as a type list (`"type": ["number", "null"]`) rather than an `anyOf`, the same schema as `zod` 4.6 writes it; no input schema or description moved, so an existing ChatGPT connector keeps working without being re-added.
- **The console is released on its own track**: Its version, this changelog and the `console-vX.Y.Z` tags now describe the console alone. A console release deploys to Alpic without publishing to npm, and a workshop release no longer deploys the console.
- **Both run views render the output with the form kernel's result viewer**: `run-graph` and `run-follow` share one results panel, which shows the run's duration and cost on its header line and the full output through `StuffViewer` (a structure as a grid, a list as a table, images and document previews in place, with its Rendered / JSON switch), in place of the JSON dump or single image `run-follow` used to show. The executed graph moved to fullscreen in `run-follow`. An output over 256 KiB serialized shows its bounded copy as JSON instead.
- **The form's run sends the assistant no completion message**: A run started from the form no longer hands the conversation to the model when it ends, since the user reads the output in the view; "Summarize in chat" sends the same request on demand. A run the assistant started still hands the conversation back.
- **Both views' content security policy names the storage buckets for images and frames**: `run-graph` gains the app buckets as `resourceDomains`, and both views gain them as `frameDomains` for a document's preview; `run-follow` also gains them as `connectDomains`, which `run-graph` already had for uploads, so the results panel can read a file it hands to the host's download request. Every source is one bucket's own host, in the global and the regional virtual-hosted forms. This changes the view resources, not the tool list; if an existing ChatGPT connector keeps the old policy, remove and re-add it.

### Fixed

- **A start that failed with a 500 is no longer marked retryable**: The platform now relays a runner's failed start as an HTTP 500 rather than a 502, and the runner can fail after Temporal has already recorded the start, so a `pipelex_run` that fails with a 500 comes back not retryable, with the hint to check whether the run started before starting it again. A 500 from any other route stays retryable. Every start that may have run (a timeout, a lost connection, a 500, 502, 504 or 408) now also opens its result with "Run may have started" instead of "Run could not be started", and the run views say the run may have started instead of that it did not start.
- **A run started from the form no longer renders blank on ChatGPT**: ChatGPT drops the `null` values of the results it hands a view, and the executed graph's validator refused the missing value and threw, which unmounted the whole view, output included. Each graph, the output and the input form now sit under an error boundary, so a part that fails shows one line saying so and the rest stays; the output falls back to its JSON view. The executed graph itself now draws on ChatGPT too, since `@pipelex/mthds-ui` 0.26.0 reads a missing value as `null`.
- **A throttled or timed-out request no longer stops a follow**: An HTTP 429 or 408 from the Pipelex API is now a retryable error, so `run-follow` and the form's run keep following through a throttled status read instead of stopping for good. A start that failed with a 408 is not retryable, since the run may exist anyway.
- **A run's output images never loaded in the views**: The runtime signed a file's link path-style on the shared regional S3 endpoint (`s3.us-west-2.amazonaws.com/<bucket>/…`), which the policy never allowed, and a bucket there can be scoped only by path, which a host does not keep. From `pipelex` 0.66.0 it signs on the bucket's regional host, which the policy allows, so a picture a method writes into an HTML output paints too, for the hour its link lives. The console now resolves a fresh link for each stored file when it reads a completed run's results, through the platform's bulk resolve route, which signs on each bucket's own host, and both views paint images and preview documents from those links (`_meta.resolved_urls`). The same fix means a conversation reopened more than an hour after its run shows its pictures again, since each read mints new links, where the link baked into the result had expired. The links are asked for a hundred files at a time within a few seconds of each read. When a request for them fails in a way that may pass, or runs out of time, the view says some files may not show and reads the results again a few times, so the pictures appear if the platform recovers within the minute; a remount reads them again.

## [0.20.0] - 2026-09-25

Released together with the workshop as `@pipelex/mcp` 0.20.0, the release that made the console the Pipelex connector, with its own `pipelex_*` tools. Its entry in [the workshop's changelog](../workshop/CHANGELOG.md#0200---2026-09-25) records this release and every earlier one.
