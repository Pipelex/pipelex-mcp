# Changelog

This is the changelog of the hosted console: the Pipelex MCP that chat hosts reach at `https://mcp.pipelex.com/mcp`, deployed to Alpic. Up to and including 0.20.0 the console was released together with the workshop, `@pipelex/mcp`, under one version, and those releases are recorded in [the workshop's changelog](../workshop/CHANGELOG.md). After 0.20.0 the console has its own version, this changelog, and `console-vX.Y.Z` tags.

## [Unreleased]

### Added

- **A failed run says why, what to do and what to give support**: `pipelex_run_status` on a terminal status other than COMPLETED, and the `failed` state of `pipelex_run_results` and `pipelex_show_images`, now carry a `failure` object from the error report the runner stored on the run, and their summaries say why the run failed, what to do next, whether running it again can help and a support line with the run id, the error type and the time. Both run views show the person the reason, the next step and that support line with a Copy button, never the report's raw message or the provider's text, where they used to show only the ending status. The tools' output schemas gain the field; if an existing ChatGPT connector keeps the old tool list, remove and re-add it.
- **A run's output in the method form's view**: A run started from the `run-graph` view's form now shows its results in the form's place once it completes, with the executed graph replacing the dry-run one and the form folded behind "Edit inputs and run again". The user no longer has to ask the assistant to fetch the results. The view keeps the run in host-persisted view state, so reopening the conversation shows the run's results again, with the form on the pipe that ran; each press of Run clears that state first, so a failed start never brings an older run back. Run stays disabled until the results are read, or until their fetch gives up after a little over two minutes of reads and says so.

### Changed

- **The console is released on its own track**: Its version, this changelog and the `console-vX.Y.Z` tags now describe the console alone. A console release deploys to Alpic without publishing to npm, and a workshop release no longer deploys the console.
- **Both run views render the output with the form kernel's result viewer**: `run-graph` and `run-follow` share one results panel, which shows the run's duration and cost on its header line and the full output through `StuffViewer` (a structure as a grid, a list as a table, images and document previews in place, with its Rendered / JSON switch), in place of the JSON dump or single image `run-follow` used to show. The executed graph moved to fullscreen in `run-follow`. An output over 256 KiB serialized shows its bounded copy as JSON instead, and the kernel's Download control is hidden, since a host's sandboxed frame blocks it.
- **The form's run sends the assistant no completion message**: A run started from the form no longer hands the conversation to the model when it ends, since the user reads the output in the view; "Summarize in chat" sends the same request on demand. A run the assistant started still hands the conversation back.
- **Both views' content security policy names the storage buckets for images and frames**: `run-graph` gains the app buckets as `resourceDomains`, and both views gain them as `frameDomains` for a document's preview. Every source is one bucket's own host, in the global and the regional virtual-hosted forms. This changes the view resources, not the tool list; if an existing ChatGPT connector keeps the old policy, remove and re-add it.

### Fixed

- **A run started from the form no longer renders blank on ChatGPT**: ChatGPT drops the `null` values of the results it hands a view, and the executed graph's validator refused the missing value and threw, which unmounted the whole view, output included. Each graph, the output and the input form now sit under an error boundary, so a part that fails shows one line saying so and the rest stays; the output falls back to its JSON view. On ChatGPT the executed graph still shows that line until `@pipelex/mthds-ui` reads a missing value as `null`.
- **A throttled or timed-out request no longer stops a follow**: An HTTP 429 or 408 from the Pipelex API is now a retryable error, so `run-follow` and the form's run keep following through a throttled status read instead of stopping for good. A start that failed with a 408 is not retryable, since the run may exist anyway.
- **A run's output images never loaded in the views**: The runtime signed a file's link path-style on the shared regional S3 endpoint (`s3.us-west-2.amazonaws.com/<bucket>/…`), which the policy never allowed, and a bucket there can be scoped only by path, which a host does not keep. From `pipelex` 0.66.0 it signs on the bucket's regional host, which the policy allows, so a picture a method writes into an HTML output paints too, for the hour its link lives. The console now resolves a fresh link for each stored file when it reads a completed run's results, through the platform's bulk resolve route, which signs on each bucket's own host, and both views paint images and preview documents from those links (`_meta.resolved_urls`). The same fix means a conversation reopened more than an hour after its run shows its pictures again, since each read mints new links, where the link baked into the result had expired. The links are asked for a hundred files at a time within a few seconds of each read. When a request for them fails in a way that may pass, or runs out of time, the view says some files may not show and reads the results again a few times, so the pictures appear if the platform recovers within the minute; a remount reads them again.

## [0.20.0] - 2026-09-25

Released together with the workshop as `@pipelex/mcp` 0.20.0, the release that made the console the Pipelex connector, with its own `pipelex_*` tools. Its entry in [the workshop's changelog](../workshop/CHANGELOG.md#0200---2026-09-25) records this release and every earlier one.
