# Testing

This page is how `pipelex-mcp` is tested: the hermetic suite every change runs, the live suite and smoke test that catch what the hermetic suite cannot, the fixtures those need, and the conventions a new test follows. [`development.md`](development.md) has the commands in brief; this is the account behind them.

## The hermetic suite and the live suite

**Two suites, two jobs — and the second exists because the first mocks the boundary that actually breaks.** The default suite (`*.test.ts`, `vitest.config.ts`) fakes every client, so it proves the projections and never touches the wire; that is what keeps `make all` and CI hermetic. The live suite (`*.e2e.ts`, `vitest.e2e.config.ts`, run by `make test-e2e`) does the opposite: it builds each capability's context from `liveApiConfig()` and supplies **no** `client` seam, so the real `PipelexApiClient` reaches the real API. Selection is by suffix — the default `include` is `*.test.ts`, so an e2e file can never be picked up by the hermetic run. When a live run reveals behavior that contradicts a unit fake, fix the fake in the same change: a fake that has drifted from the wire is how the mocked suite goes green over a broken client. Shared fixtures, the fixture-method lookup and the API config guard live in `src/capabilities/e2e-support.ts`.

## Testing conventions

Tests are colocated with the code they test under `src/` (`*.test.ts`, Node environment); the tests that belong to no module live in the root `tests/`, among them `tests/manifest.test.ts`, which holds what the manifest promises npm (see [What the manifest declares](architecture.md#what-the-manifest-declares)) and drives the publish guard through a real `npm publish --dry-run --offline`. Each capability is tested by **injecting a fake client** via its context's `client` field (`CatalogContext.client`, `ModelsContext.client`, `ValidationContext.client`, `InputsContext.client`, `CodegenContext.client`, `PrepareContext.client`, `RunContext.client`, `ImagesContext.client`) — the capability uses `context.client` when present and only constructs a real `PipelexApiClient` otherwise. Use this seam to test API behavior without a live `pipelex-api`. The **resolver seam works the same way**: inject a fake `FileResolver` via the context's `resolver` field to test `{ path }` handling without touching the filesystem (leave it absent to test the fail-closed rejection); the real `localFileResolver` is tested against actual temp directories in `src/files.test.ts`. The artifact download capability runs over a **mocked SDK**: inject a fake `ArtifactClient` (`getRunResult` plus `downloadArtifacts`) via `ArtifactsContext.client`; the fakes in `artifacts.test.ts` write into the directory they are handed and answer the SDK's verdict shape, and every walk runs against a real temp working directory, so containment, directory creation, relative-path reporting and the classification of every SDK outcome (per-item codes, thrown errors) are exercised on disk. The download boundary, the filename rule and the never-overwrite rule are the SDK's and are tested there. **The two writers deliberately have no injected write seam**: `ArtifactsContext.saveRoot` and `CodegenContext.saveRoot` are directories, and a real `mkdtemp` directory is the better test double — `codegen-writer.test.ts` runs entirely against real temp trees with the recorded engine response, so containment, the overwrite rule, the orphan walk and the strict decoder are all exercised on disk. The image tools run over the same client seam: inject a fake `ImagesClient` (`getRunResult` plus `fetchArtifact`) via `ImagesContext.client`, answering real `Response` objects with chosen headers and bodies — a real `Response` rather than a stub, because the capability reads `content-type`, reads `content-length`, cancels a body it will not use, and errors a stream mid-read to exercise the cap. Its picture is a real 1x1 PNG's bytes for the same reason `e2e-support.ts`'s is: the tests assert the base64 that reaches the block. **The workshop has one contract test, and a file snapshot is at its heart**: `src/server.test.ts` pins, byte for byte, everything the workshop shows a host before a tool call — the `initialize` result and `tools/list` — in `src/workshop.contract.json` (`shell-test-support.ts` reads it, with the package version replaced by a placeholder). A diff to that file is a contract change, so update the snapshot with `npx vitest run -u` only for a change you meant, and say so in the release notes. Beside the snapshot, the test asserts the properties worth naming: the dispatch through the real stdio entrypoint and the **absence** of the console-only tools. Pure projection/classification functions (`projectCatalog`, `validationResult`, `inputsResult`, `classifyError`, `validateMethodSelectorRequest`, `validateInputsRequest`, `resolveSubmittedFiles`) are exported specifically so they can be tested in isolation; the shared ones are covered in `shared.test.ts`.

`scripts/` and `tests/` are dev tooling, not shipped code: they are linted and Prettier-checked with `src/`, and the one `tsconfig.json` typechecks all three as one program, so `make check` covers them all. `tests/` holds what belongs to no single module: the Makefile recipe tests, the API-boundary lint test and the manifest test. The `*.e2e.ts` files and `e2e-support.ts` sit under `src/`, so they are linted, formatted and typechecked with everything else — they are excluded from the _default_ suite by suffix and from the bundle by reachability (nothing the workshop's entrypoint imports reaches them).

## The live targets

The live targets — `smoke`, `test-e2e`, `test-e2e-run`, `seed-e2e-fixture`, `test-all` — are **the only ones that touch the network**, and all of them are deliberately outside `make all` / `make check` so the local gate and CI stay hermetic. They share one gate (`live-preflight`): it resolves the live targets' own pair, `PIPELEX_E2E_BASE_URL` / `PIPELEX_E2E_API_KEY`, once (make command line, then `.env`, then the shell, then the default), prints where each value came from, probes `/v1/version`, and refuses to start without a key. **They never read `PIPELEX_BASE_URL` / `PIPELEX_API_KEY`**, and refuse either name on the make command line: those belong to every other tool and to the server itself, and sharing them is how a shell profile exporting the production pair for other tools sent `make test-e2e` to production, where no fixture is seeded, and failed every by-id leg with a miss that read like drift. With the shell clear, the old resolution followed `.env` instead, which named whatever the local server was pointed at. So `.env` carries the dev key for the live targets under their own name, `PIPELEX_E2E_API_KEY`, and `PIPELEX_E2E_BASE_URL` is also the name `@pipelex/sdk`'s live suite uses, in `pipelex-sdk/js`. **Their default is `https://api-dev.pipelex.com`, not production** — dev is the hosted plane the addressing campaign ships to, and it is the deployment that advertises the selectors, so defaulting to production meant the suite's by-selector coverage skipped on every default invocation. This is the live targets' default only; the server's own `PIPELEX_BASE_URL` default in `buildApiConfig` is still the production API. Calling the underlying npm script directly skips those guards, which is what a keyless local OSS runner needs. See "Detecting API drift" below for why they exist.

- `make smoke` (= `npm run smoke`) — spawns the workshop stdio server the way a host does, completes the MCP handshake, and calls the read-only tools against a live Pipelex API, asserting on their `structuredContent`. Read-only; spends no inference credit.
- `make test-e2e` / `make te` (= `npm run test:e2e`) — the live capability suite (`src/**/*.e2e.ts` under `vitest.e2e.config.ts`). Free of inference credit: the run family skips itself unless `PIPELEX_E2E_RUN=1`. **Not free of side effects**, and the writes are of two kinds. Storage: `prepare.e2e.ts` uploads a 1x1 PNG on every run, ungated and unremovable (the SDK exposes no delete), because it is the only live proof the upload path still rewrites a local path to a `pipelex-storage://` reference, and `prepare-by-address.e2e.ts` uploads another for the by-address leg — gated only on the deployment advertising the selectors, which the live targets' default `api-dev` target does, so in practice it is not skipped either. Catalog: `catalog-write.e2e.ts` performs real **updates** against the seeded write fixture, in its setup and again in the tests that save, ungated because its whole subject is a write. What no `make test-e2e` run does is CREATE a catalog row — that stays behind `make seed-e2e-fixture`, for the reason recorded under "Detecting API drift".
- `make test-e2e-run` — the same suite **including** the run family, which executes the fixture method for real and therefore **spends inference credit**. Its own target so nothing reaches it by accident.
- `make seed-e2e-fixture` (= `npm run seed:e2e-fixture`) — **writes**: creates or refreshes the durable fixture methods the by-id legs and the catalog-write suite need, in whichever organization the API key selects. Idempotent; run it once per organization.
- `make test-all` — **every test in the repo**, in cost order: the hermetic suite, then `smoke`, then the live suite _including_ the run family, so it **spends inference credit**. That is why it is `test-all` and not folded into `make all`, which stays the hermetic gate. It runs `live-preflight` first, so a missing key fails in a second rather than after the unit suite, and it deliberately does **not** seed — a catalog write stays hand-invoked, and an unseeded organization already fails the by-id legs with the seed command in the message.

Run a single test with Vitest directly: `npx vitest run src/capabilities/validate.test.ts` or filter by name with `npx vitest run -t "projects pending signatures"`. The same works for the live suite with `--config vitest.e2e.config.ts`, as long as the environment already carries the `PIPELEX_E2E_BASE_URL` / `PIPELEX_E2E_API_KEY` pair that `make test-e2e` would have resolved (`vitest.e2e.config.ts` loads `.env` for it, without overriding the shell).

## Detecting API drift

The unit suite cannot see the failure mode that actually breaks this server. Every capability reaches `@pipelex/sdk` through a hand-written narrow interface (`CatalogClient`, `RunClient`, …) and every test injects a fake satisfying that interface, so `tsc` catches a **type** change on the SDK side and nothing at all catches a **wire-shape** change. That is not hypothetical: `mthds_list_methods` failed every real call with `wire.map is not a function` — the platform had reshaped `GET /v1/methods` into a page object while the pinned SDK still called `.map()` on it — and the whole suite stayed green. There is no OpenAPI schema to diff against (`/v1/openapi.json` is 403), so a live call is the only available detector.

There are two live detectors, at two different altitudes, and they are complementary rather than redundant.

**`make smoke`** drives the real shell over stdio, so it covers the whole path a host exercises: handshake, `tools/list`, then `mthds_list_methods` (row shape plus the projection invariant — method source, stored inputs/outputs and org fields must appear nowhere in the result), `mthds_models` (the LLM presets it lists, and the first of them checked back as resolved), `mthds_validate`, `mthds_inputs_template`, and `mthds_codegen` (the canonical bundle as `ts-zod`: both artifact paths, the lock filename, every artifact carrying its content, nothing on `_meta`). Its assertions live in `scripts/smoke.ts`. It carries two inline fixtures because one is not enough: the canonical `quick_start` bundle validates, but declares no inputs, so its template is `{}` and would pass just as happily if the projection dropped every field — the second fixture declares one input so the template check proves something.

**`make test-e2e`** goes wider and one layer down: one `*.e2e.ts` per capability, calling the capability functions with a context that has **no `client` seam**, so the real `PipelexApiClient` runs against the real API. That is the layer the drift lives at. It covers the catalog (`catalog.e2e.ts` — paging, server-side search, the projection invariant, and the fixture row's server-derived `description`), validation (`validate.e2e.ts` — including that an invalid bundle is a _produced_ verdict, never an error), the inputs template (`inputs.e2e.ts` — free, one `POST /v1/pipe-io` per case: both formats, the `explicit` shape switch, an invalid bundle as a _produced_ verdict, an unknown `pipe_ref` and a method with several entry pipes refused at `pipe_ref`, and, wherever the API advertises the selectors, a published package by address, one naming its entry pipe only in its manifest, the seeded fixture by id and an unknown id), code generation (`codegen.e2e.ts` — the target loop over every SDK target, each artifact set fed to the SDK's offline `runCodegenCheck` to prove the trust chain survived the wire, an invalid bundle as a produced verdict, the **write arm** against a real temp working directory (write, regenerate over it, then a second target into the same directory to produce the orphan case D7 describes — the hermetic writer suite runs on a recorded response, so this is what proves a CURRENT engine still writes a checkable tree), and the two selector legs, which run wherever the API advertises them), input preparation (`prepare.e2e.ts` — the workshop really uploads a 1x1 PNG), the run lifecycle (`run.e2e.ts`), the run-saving tool (`artifacts.e2e.ts` — an unknown run id refused before anything is written, free; in the paid tier, a completed by-address run saved into a temp working directory, its `main_stuff.json` compared with the unbounded output the platform holds, and no stored file in it, so the bulk resolve route stays unexercised live), the model deck (`models.e2e.ts` — read-only and free: presets still stamped with their category, the `aliases` extension still sent, each category's filtered listing equal to its share of the whole deck, and a listed preset and an alias's model resolved live), and the method graph page's CDN files (`graph-page.e2e.ts` — each pinned file fetched from jsDelivr and its SRI hash recomputed, since a wrong hash leaves every page blank while the hermetic suite, which cannot fetch, stays green; it calls no Pipelex API).

**The by-selector legs are gated on the live API, not on a date.** Every leg that needs the platform to resolve a `method_id` or a `method_ref` server-side asks `/v1/version` first — `apiAdvertisesExtension` in `e2e-support.ts` — and skips itself where the deployment does not advertise `method_ref`, the marker for the platform build that brought the whole three-selector surface (an API on the previous build advertises `[runs, method_id]`). That replaced a row of hardcoded `it.skip("… (gated)")` calls naming a checkpoint in a plan document, which is a gate nobody re-reads: the dev API served the surface while the tests stayed dark and said nothing.

**A skip is only allowed to mean one thing, so the probe asserts its own inputs.** `extensions` is an untyped extension field riding `VersionInfo`'s index signature — nothing types it in any repo, so a rename breaks no build — and every unexpected shape collapses to "advertises nothing", which is exactly what a deployment that legitimately serves no selectors looks like. Left alone that makes the suite skip its way to green through the wire drift it exists to catch. So the deployment decides which rules apply: on a hosted `implementation` (`pipelex-hosted`, which always declares `extensions` and always carries `runs`) an absent, non-array or `runs`-less value **throws**; on a bare runner, which declares no `extensions` at all, absence is the protocol's documented "protocol only" answer and yields an empty set, while a malformed value still throws. What survives that is a skip that really is a statement about the deployment. Note it is a statement you have to go looking for: vitest's default reporter prints per-file counts, not a line per skipped test.

One leg had no extension to probe and so stayed a hardcoded skip: `validate.e2e.ts`'s `default_pipe_ref` assertion, where the assertion IS the probe. It is live as of the `@pipelex/sdk` 0.19.0 bump — measured against the live suite's default target, which serves the field carrying the fixture's own ref — so the gate is now the assertion itself, and a deployment that stops serving the field fails the suite rather than skipping past it. Production could not be measured in the same pass: it answers this key with a 403. And `validate.e2e.ts`'s by-address leg keeps its own Python-free address instead of the shared `PUBLISHED_METHOD_REF`: `/v1/validate` resolves an address through the execution-locus gate, so a fetched package shipping any `.py` is a 403 there off a deployment that is **not** sandbox-hosted.

**`run.e2e.ts` is split on cost, and the split is what keeps the suite schedulable.** Its free half always runs and spends nothing: reading the status and results of a run id that does not exist proves the two lifecycle routes are reachable and still classify as `input_domain`@`run_id`, and one start on an unknown `method_id` — refused before anything executes — proves `/v1/start` still accepts the run source the way this client sends it. That last check exists because `method_id` is a named SDK option the client reserves on `extra` with a **runtime** throw, so sending it the wrong way compiles and passes the mocked suite; the free tier could not reach the start path at all until it was added, which is how the 0.14.0 bump's break stayed invisible. Its paid half executes the fixture for real and runs only under `PIPELEX_E2E_RUN=1` (`make test-e2e-run`), so `make test-e2e` and any future scheduled canary cannot reach it by accident. That half also runs a published package **by address** — `github.com/Pipelex/methods/text_stats` pinned at a tag, a PipeFunc method that buys no model call — and asserts the reported provenance down to the commit the tag resolved to. It sits in the paid tier despite spending no inference credit because the tier is about executing, not about the bill: `make test-e2e` must remain a suite that starts nothing.

**The by-id legs need a durable fixture method, seeded once per organization.** The SDK had no method delete when this was designed; since 0.14.0 `deleteMethod` exists but is an **asynchronous acceptance** (a resolved promise means "deletion accepted", never "gone"), so a create-per-run suite would still be racing its own cleanup. Instead `make seed-e2e-fixture` stores one method named `pipelex_mcp_e2e_fixture` (its bundle and every other fixture live in `src/capabilities/e2e-support.ts`), and the suites resolve its catalog id **by name at run time** rather than hardcoding a `mt_…` — an id belongs to one organization, this repo is public, and a scheduled canary would run under a different key from a developer's. A missing fixture fails loudly with the seed command in the message, so "not seeded" and "wrong organization" read the same and both point at the fix. **That lookup follows the cursor, and a one-page read is a bug rather than a shortcut.** The platform applies `q` as a post-read filter over a bounded slice of the index per request, so a sparse match legitimately answers `{items: [], nextCursor: "…"}`; the index is keyed on the immutable `created_at`, so a fixture sinks monotonically as its organization accumulates methods and no update lifts it back. A lookup that stopped at the first page would therefore start reporting a seeded fixture as missing, permanently — and because that message sends the operator to `make seed-e2e-fixture`, whose own lookup is the same helper, the miss would route them into creating a second row the platform makes admin-only to delete. `catalogRowNamed` in `e2e-support.ts` is the one helper all three sites use, over the SDK's `iterateMethods`.

**The catalog-write suite takes a second seeded row, and never creates it.** `catalog-write.e2e.ts` exercises `mthds_save_method` against the real catalog, so it is the one suite whose subject is a write. It only ever **updates** `pipelex_mcp_e2e_catalog_write`, because a create is check-then-act across two round trips with no compare-and-swap: two concurrent first runs in one organization would each read no row and each create one, and the duplicate is permanent — the platform makes delete admin-only — after which every later run updates whichever row the server lists first. Seeding it by hand, once, is what takes that race out of the suite, and it keeps `make test-e2e` free of catalog _creates_, which is the reason the seed target exists as a separate gesture at all. The consequence to know is that `POST /v1/methods` — the tool's create arm — has no live coverage from the suite; what exercises it live is the seed script, through the SDK rather than through the tool.

**`make test-e2e` cannot pass vacuously**, and that guarantee is the fixture's: it keeps the catalog non-empty, so `catalog.e2e.ts`'s row assertions always execute rather than looping zero times, and a missing key **fails** the suite instead of skipping it. `make smoke` deliberately does not share it — being fixture-free and seed-free is what keeps it read-only and runnable in an organization nobody has seeded. On an empty catalog it still proves the page envelope survived the wire, which is the reshape that motivated it; it withholds its row-shape PASS and says out loud that row projection was not exercised. Non-vacuous row coverage is `make test-e2e`'s job, not smoke's.

A failure in either detector means the _shipped_ client disagrees with the _live_ API; the fix belongs in `../pipelex-sdk/js`, then a bump here through the `bump-sdks` skill — never a patch that papers over it in this repo. Anything a live run reveals that contradicts a unit-test fake gets folded back into the fake in the same change, so the two layers cannot disagree silently.

## The Makefile's own tests

**Makefile logic that reads configuration is untested by construction, so the live targets' resolution has a hermetic test of its own, `tests/make-live-recipe.test.ts`**: it runs `make -f` from a temp directory holding its own `.env`, reads the preflight's target line under `make -n`, and checks that the ambient `PIPELEX_BASE_URL` / `PIPELEX_API_KEY` change nothing, the precedence of the `PIPELEX_E2E_*` pair, that the key is never printed, and the refusal of the old names on the command line. It spawns `make` with a minimal environment so a parent `make test` cannot leak `MAKEFLAGS` or the variables under test into it.
