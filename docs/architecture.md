# Architecture

This page is the account of how `pipelex-mcp` is built and why each piece is shaped the way it is: the two shells, the capability core, the console's views, and the rules the code keeps between them. [`SPEC.md`](../SPEC.md) is the contract the code implements and [`tools.md`](tools.md) the tool-by-tool reference; this page is the layer beneath both. **Read a module's entry before changing the module**, and when a change makes an entry wrong, fix the entry in the same change.

Rules that must hold while particular files are open also live in `.claude/rules/`, where Claude Code loads each one only when a file it names is read: the attachment fetch boundary, the workspace writers, the console's contract, its views and stylesheet, the package manifests and the live suite.

## Two shells over one core

The repo ships two thin shells over one capability core: the Skybridge HTTP console (the Pipelex connector) for chat hosts and the plain MCP-SDK stdio workshop (the Pipelex plugin's server) for coding agents. **Each shell owns its tool table** — `packages/workshop/src/tools.ts` for the workshop, `packages/console/src/hosted/tools.ts` for the console — built from the capability functions in `packages/core/src/capabilities/`, and each shell's emitted contract is pinned byte for byte (see [Testing conventions](testing.md#testing-conventions)). The console's table also carries each tool's view and host metadata. Each table module builds its own capability contexts too, and states its shell's settings there rather than receiving them as options: the workshop's `buildLocalToolContexts` sets the cwd-bound `{ path }` resolvers, the working directory as every writer's `saveRoot`, `artifactDownloadAvailable: true` and `viewsAvailable: false`; the console's `buildHostedToolContexts` sets views on, no resolver and no write root, and states `CONSOLE_TOOL_NAMES` on every context whose texts name a tool. **Every tool name a text both shells produce names comes from `capabilities/tool-names.ts`**: `WORKSHOP_TOOL_NAMES` and `CONSOLE_TOOL_NAMES` each carry only their shell's tools, discriminated by `shell`, and a text naming a tool only one shell has is written per shell, the compiler saying where. Contexts default to `WORKSHOP_TOOL_NAMES`, except `startPipelexRun`, the console's run, which defaults to `CONSOLE_TOOL_NAMES`. Workshop-only capabilities, and the workshop's own table, write `mthds_*` names literally. `hosted/server.test.ts` fails on a workshop tool name in the console's instructions or in any tool description or schema; result summaries and hints are checked capability by capability in the core's tests.

**The tables share no tool name, and differ by more than the names.** A chatbot runs methods rather than authoring them, so the console has no validate, inputs template, codegen or prepare tool and no `files` argument (`validateMethodReferenceRequest` in `shared.ts` is its selector rule): `pipelex_show_method` and `pipelex_run` cover what a chat user needed from those. Beyond that each shell holds what only it can serve: the console's `pipelex_upload_attachments` takes a host-substituted reference the host gates on the declared JSON Schema, which no stdio host performs, and its `pipelex_request_upload` has a view as its one caller; the workshop's `mthds_download_artifacts`, `mthds_save_method` and `mthds_get_method` turn on a working directory the console does not have. On the wrong shell each would be *structurally unreachable*, and registering it would spend every user's tokens on every `tools/list`. **One tool name means one contract** (L-260923-d3c264 in the workspace ledger, D1): a name both shells registered would have to carry the same input schema, output schema and annotations on both; no name is shared since the console became `pipelex_*`, and `tests/tool-names.test.ts` guards the next one. The description is deliberately outside that test, because it is how each shell tells its own audience when to call the tool. **The workshop's table is registered in a loop; the console's is not.** `workshop/src/server.ts` iterates `localToolDefinitions`, while `hosted/server.ts` chains one `.registerTool` per tool, because the chain is what types `AppType`, which the views' `useToolInfo` / `useCallTool` read. So a tool added to the console is a definition in `hosted/tools.ts` and a link in that chain, and `hosted/server.test.ts` fails when a definition the module exports has no link, since nothing else would notice: the snapshot does not move and no linter flags an unused export.

The whole of it is a thin MCP front-end over the existing Pipelex validation stack — it does no validation itself. It forwards file contents to a **Pipelex API** (`POST /v1/validate`, `POST /v1/build/inputs`, `POST /v1/codegen`) through the `PipelexApiClient` from the `@pipelex/sdk` npm package (published from `../pipelex-sdk-js`), then projects the API's reports into MCP output. `@pipelex/sdk` is the Pipelex hosted-platform SDK — the same one `pipelex-app` uses, and the only one carrying the durable run lifecycle the later run-backed tools need; it re-exports the open `mthds/protocol` surface. It is the one API client, but the core also imports `mthds/protocol` directly (`catalog-write.ts`, `inputs-template.ts`), so the core and the workshop declare `mthds` as well.

## Modules

The code is a handful of small files in three packages, and the list names each by its path inside its package's `src/`: `capabilities/…`, `tool-definition.ts` and `shell-test-support.ts` are the core's, `server.ts`, `helpers.ts`, `hosted/…` and `views/…` are the console's, and the workshop's files, which sat under `src/local/` before the split, sit at the top of its `src/` and are written `workshop/src/…` here, from `packages/`, since their bare names would collide with the console's.

A module this page does not list carries its account in its own header comment: `catalog-write.ts` and `catalog-link.ts` (the catalog pair and the `pipelex-method.json` link file, whose contract is SPEC.md's Catalog Write Scope), `inputs-template.ts`, `client-identification.ts` (see [`client-identification.md`](client-identification.md)), `start-outcome.ts`, `tool-names.ts`, and the views' smaller helpers.

### The console shell

#### `server.ts` and `hosted/server.ts`, `hosted/tools.ts`

Thin Skybridge entrypoint; `hosted/server.ts` owns the console shell and registers the console's table through Skybridge's typed chain. It also chains two `.mcpMiddleware` handlers: `initialize` picks the instructions per handshake (`hostRendersViews`: the MCP Apps extension or a ChatGPT `User-Agent` gets the form variant, every other client the no-views one the snapshot pins), and `tools/call` answers the `RETIRED_TOOL_NAMES` — the console's pre-rename `mthds_*` names, which a cached ChatGPT tool list still calls — with an `isError` telling the user to remove the Pipelex connector and add it again. `hosted/tools.ts` is the table: the console's capability contexts (`HostedToolContexts`, `buildHostedToolContexts`) and every console tool's definition with its `view` and `_meta`. `tool-definition.ts` is the shape both tables are written in (`ToolDefinition`, `defineTool`), not a table, and it stays Skybridge-free because the workshop's bundle reaches it.

#### `hosted/contexts.ts`

The console's per-request capability contexts, and the whole of its auth posture on this side of Skybridge. **Auth is per-user OAuth and nothing else** (bring-your-own-key has been removed — there is no second posture, no keyless mode, and no shared-key fallback). Skybridge's `workosProvider` verifies the caller's AuthKit token and the MCP SDK transport surfaces it as `extra.authInfo`; `contextsForRequest` lifts that token into `apiKey` on **every** capability context, which `@pipelex/sdk` then sends upstream as `Authorization: Bearer`. The override is unconditional — a server-held `PIPELEX_API_KEY` must never fund a signed-in caller's work, since the credential picks the active org and therefore the whole visible catalog. The tokenless branch is unreachable in production (no console tool allows anonymous, so Skybridge mounts `requireBearerAuth` server-wide) and exists only to **fail closed** — note it sets `apiKey` to the **empty string, not `undefined`**: `PipelexApiClient`'s constructor reads `options.apiKey ?? process.env.PIPELEX_API_KEY`, so an absent key silently borrows the deployment's env key, which is the precise opposite of the intent. `contexts.test.ts` pins this on the wire (no `Authorization` header goes out) rather than by asserting the field, because the field alone does not prove it. The token rides the transport only — never a tool argument, so it never enters the model's context. The workshop doesn't import this: its per-user credential is a `plx_sk_` key in the host-supplied `PIPELEX_API_KEY` env. `../server.ts` refuses to boot unless both `WORKOS_AUTHKIT_DOMAIN` and `PIPELEX_MCP_RESOURCE_INDICATOR` are set, and `createHostedServer` takes the resolved `OAuthConfig` as its **required first argument** — a console that cannot authenticate a caller is unrepresentable.

#### `helpers.ts`

`generateHelpers<AppType>()` exposes `useToolInfo`/`useCallTool` for the views.

### The workshop shell

#### `workshop/src/server.ts`, `workshop/src/tools.ts`, `workshop/src/main.ts`

Constructs the plain MCP SDK server and registers the workshop's table. `workshop/src/tools.ts` is that table: the workshop's capability contexts (`LocalToolContexts`, `buildLocalToolContexts`, which binds the cwd-bound file resolvers and the working directory) and `localToolDefinitions`, in the order a host lists them. It must import nothing from Skybridge: tsup bundles it into the npm package, and the workshop's `package.json` does not declare Skybridge at all, which `tests/workspace-manifests.test.ts` holds. `workshop/src/main.ts` owns stdio transport and graceful shutdown; `workshop/src/log.ts` keeps diagnostics on stderr so stdout remains protocol-only.

#### `workshop/src/files.ts`

The local workshop's filesystem-backed `FileResolver` (`localFileResolver`): resolves `{ path }` items relative to the server's working directory, rejects any path whose extension is not the resolver's own *before touching the filesystem* (`.mthds` for a bundle's files, `.py` for `mthds_save_method`'s `python` — this keeps a prompt-injected `.env`/`.git/config`/key path from ever being opened), enforces the realpath containment boundary, and maps non-`.mthds` paths / escapes / missing files / non-regular files / read failures to `FileResolution` failures (never throws). Consumed by the local stdio shell; the hosted server never imports it.

### The capability core: reading and listing

#### `capabilities/catalog.ts`

The list capability (`pipelex_list_methods`, `mthds_list_methods`) and its narrow `CatalogClient.listMethods()` test seam. It calls only the SDK's `listMethods`, validates the rows of the one page it gets back, and bounds names/descriptions by Unicode code point. **Search, ordering and paging belong to the server** (`q` / `limit` / `cursor`): filtering a returned page locally would be searching fifty rows of ten thousand and calling it a search, and re-sorting would reorder a page against the cursor that produced it. A blank query omits `q` rather than sending `""`, which the API rejects as bad input. **Non-negotiable projection invariant:** `mthds`, `python`, `input_data`, `pipe_output`, `org_id`, and `created_by_user_id` must never reach `structuredContent`, `content`, `_meta`, or logs — the index projection stopped returning them, but keep validating what *arrives* rather than trusting the declared type, so a looser server cannot leak through. There is deliberately no total count (counting means reading the whole catalog) and no `has_source`: recomputing it would cost a `getMethod` per row, so a source-less method now surfaces at the point of use, as an `input_domain` no-verdict at `method_id`. **The summary carries a render directive on purpose**: a listing is read near-verbatim by the user, so `catalogSummary` tells the model to report each method with name **and** description, and puts the description before the demoted `method_id`. Keep that directive in the summary, not (only) in the tool description — ChatGPT caches a connector's tool list at add-time, so the summary is the sole channel where a presentation fix reaches existing installs. No view, no `_meta`.

#### `capabilities/models.ts`

The model deck capability (`mthds_models`, **workshop-only**, since a chatbot never writes a pipe's `model` field) and its narrow `ModelsClient.models()` seam over the SDK's `models()` (`GET /v1/models`). It lists the deck or checks one reference against it. **The deck names no model handle as such**: on the Pipelex runner the protocol's `models` list holds the presets, each stamped with its category, and the category-keyed `aliases` and `waterfalls` extensions name handles only as targets and steps, so a bare handle nothing names is `unconfirmed`, never `not_found`, and the summary sends it to validation, which checks handles against the runner's full model list. A listing passes the category to the route; **a check reads the whole deck** so that a miss in the category asked about can be placed in the category that holds it. `projectDeck` checks what arrives rather than trusting it (a missing `models` list, a nameless entry or a misshapen extension throws into a `runtime` no-verdict) but skips an entry or an extension key of a category it does not know, which the protocol allows. The category enum is closed against the protocol's `ModelCategory` both ways, `MODEL_CATEGORY_VALUES` by `satisfies` and `PIPE_TYPE_OF` as a total `Record`, as codegen's targets are. **The nearest names are ranked as the runner ranks them**: `closeMatches` and `similarity` port difflib's `get_close_matches` and `SequenceMatcher.ratio`, tie order included, and run at the cutoffs of `pipelex/cogt/models/model_suggestion.py`. For a preset, alias or waterfall checked in one category they agree with the "did you mean" of a failed validation of the same reference; a handle's candidates are only the handles the deck names, where the runner uses every model of the pipe's type, and a check with no category pools every category, so those can differ. The port was checked against Python's difflib over thousands of pairs, and the tests pin values Python printed. It leaves out difflib's junk heuristic, which applies to the word from 200 characters, and that is exact because `MAX_REFERENCE_LENGTH` caps a reference below it, which also bounds the match's work. The summary leads a miss with the same name under another sigil, the likeliest fault, and every summary, like the description, says the deck is what the runner can serve rather than what the account may use. No view, no `_meta`.

#### `capabilities/shared.ts`

The plumbing the capabilities share, including **the artifact fetch boundary's shared half**: `ALLOW_HTTP_ENV` / `parseAllowHttpOverride` / `allowsPlainHttp` / `buildArtifactFetchConfig` (the plain-http rule, derived from `PIPELEX_BASE_URL`'s scheme unless overridden), `BULK_RESOLVE_ERROR_OPTIONS` (the resolve route's whole-request refusals), and `ITEM_ERROR_TEXTURES` / `itemToolError`, which map the SDK's closed per-reference `code` vocabulary — shared by the download verdict's `ArtifactItemError.code` and the thrown `ArtifactFetchError.code`. All of it lives here rather than in `artifacts.ts` because the image tools need the same mapping on both shells and must not import the workshop-only download tool to get it; `itemToolError`'s `location` is therefore a parameter (`artifacts[i].uri` there, `images[i].uri` here). The image-inlining constants and the key prefilter (`imageCandidatesOf`, `looksLikeImageKey`, `storageKeyOf`) sit beside them, used by `run.ts` and `images.ts` alike. Also: the submitted-files input schema (a per-item union, `{ content, uri? } | { path }` — see "The files union and the resolution seam" below), the `ToolError` model, file resolution (`resolveSubmittedFiles` + the `FileResolver` seam), request-shape validation (`validateMethodSelectorRequest`, shared by every workshop method-taking tool — it enforces the two selector rules: strict one-of on the tooling tools, files-win-plus-linkage on `mthds_run`; the console's two reference-only tools use `validateMethodReferenceRequest`), the by-id fetch-and-forward leg (`fetchMethodFiles` + `MethodFetchClient`, narrowed to `mthds_inputs_template` alone — every other method-taking tool forwards its selector to the server, `mthds_prepare_inputs` since the SDK's `prepareInputs` grew all three), `blueprintMainPipeRefOf` (the blueprint's declared main pipe, qualified by its domain only when authored bare — shared by `validate.ts`'s `defaultPipeRefOf` and `console-inputs.ts`'s pipe selection), env-derived API config (`buildApiConfig` — `PIPELEX_BASE_URL`/`PIPELEX_API_KEY`), and `classifyError`. `classifyError` takes per-route `ClassifyErrorOptions` (the 400/422 class/locator/hint, the separate `preparation` locator for the SDK's client-side `InputPreparationError` base — which a route with a selector-shaped `badRequest` must set, or a client-side pipe failure reports the selector as the fault — and the route named in the 404 hint) so each capability points the agent at its own knobs; the class override lets catalog listing classify a missing active-org 400 as `config` without changing other routes, and catalog listing picks its 400 arm by request shape so a rejected `cursor` stays `input_domain`@`cursor` instead of telling the caller their key is wrong. It also maps the `@pipelex/sdk` `InputPreparationError` family (the upload/preparation errors `mthds_prepare_inputs` can raise) ahead of the generic `PipelineRequestError` arm.

#### `capabilities/validate.ts`

The validation logic. Zod input/output schemas, the API call (`validateFiles`), and projection of the API report into MCP `structuredContent` + the view-only `_meta` graph payload (`toolResult`). Also accepts `method_ref` (a published method address) and `method_id` as **server pass-throughs**: the selector rides the `/v1/validate` body (`ValidateMethodSelector`) and the hosted API resolves it — no fetch-and-forward, no method source in the conversation. The three source forms are mutually exclusive (`validateMethodSelectorRequest`, rule `one_selector`). It also projects the **main pipe's signature** (`mainPipeSignatureOf` → `structuredContent.main_pipe`, plus one rendered line in the summary): the ref, the ordered inputs with their concept refs and multiplicities, and the produced concept — read from `pipe_io_contracts[main_pipe_ref]` (a required field on every valid report, not gated by the `views` token), with the input-form descriptor consulted for input **order** alone. The ref itself is `defaultPipeRefOf`: the report's `default_pipe_ref` — the API's own statement of what a selector-less run would execute, and the only signal that knows a `method_ref` package's manifest — with `blueprintMainPipeRefOf(bundle_blueprint)` behind it **only when the field is absent** (an older runner), never behind a stated `null`, which means the server determined no entry pipe at all. It is deliberately **not** on the views branch — the workshop is the shell an integrating agent uses — and every member is narrowed against what arrived, with any malformed one omitting the whole signature rather than emitting a partial one. The signature's `output` also carries **`images`**, the produces-images signal: the capability requests the standard's output-form descriptor beside the input form (`views: ["input_form", "output_form"]`) and `imageFieldPaths` walks the entry pipe's single output node for `kind: "image"`, recursing into an `object`'s `fields` and a `list`'s `item`, yielding paths in `$` notation (`["$"]` for a top-level `Image`, `["$[]"]` for an `Image[]`, `["$.picture"]` for a field of a structure). Three things are load-bearing: **`[]` and an absent member are different answers** (described-and-none versus nobody-said), a `document` node is deliberately not a picture, and `kind: "unknown"` is opaque rather than empty. **The third only holds because the walk reports its own completeness**: `imageFieldPaths` returns `{ paths, complete }`, and `complete` is false for an opaque node, an unknown kind, a non-record, a nameless field and the depth ceiling — all of which used to yield a bare `[]`, i.e. a confident "produces no pictures" off a node nobody had read. The member is published only when the walk was complete **or** it found at least one image; an incomplete walk that found nothing withholds it, and a `document` stays `complete` because "not a picture" is an answer, not a failure to look. The walk is a **total `Record<FieldKind, …>`** over the SDK's re-exported `FIELD_KINDS`, so a kind the standard adds fails the build here instead of reading as "no images"; the kernel `@pipelex/mthds-form` owns the same lookup but is reachable only through `@pipelex/mthds-ui`, which is build-side, and `validate.ts` ships in the workshop bundle, so the ten-line walk lives here rather than pulling a view package into `dependencies` for every `npx @pipelex/mcp` user. `signatureLine` appends ` (produces images)`, the one channel that reaches a ChatGPT install whose cached tool list predates the member.

#### `capabilities/inputs.ts`

The inputs-template logic. Zod input/output schemas (`files?` beside `method_id?`, `pipe_ref?`, `explicit?` default true, `format?` default json), the API call (`buildInputs`, adapting the MCP `uri` provenance label to the build envelope's `source`), and projection of the report into `structuredContent` plus a composed Markdown summary that includes the template in a fenced code block (the build routes return a plain `message`, not `rendered_markdown`). The three source forms are mutually exclusive (rule `one_selector`). A `method_ref` request is a **server pass-through** — the address rides the build envelope itself (`BuildInputsRequest.method_ref`) and the runner resolves it. A `method_id` request **fetches-and-forwards** via the shared `fetchMethodFiles` (in `capabilities/shared.ts`): the SDK's `getMethodClosure` → files, each labeled with the method id as provenance, adapted to the build envelope's `source` here — the SDK's own canonical expansion, since the build routes have no server-side `method_id`; a source-less stored method (the SDK's `EmptyMethodSourceError`) is an `input_domain` no-verdict at `method_id` raised without calling the build route, and fetch-leg failures classify against `/v1/methods/{id}`. No view, no `_meta`.

#### `capabilities/show.ts`

`pipelex_show_method` (**console-only**): exactly one of `method_id` / `method_ref` (`validateMethodReferenceRequest`), an optional `pipe_ref` checked against the declared pipes, one `POST /v1/validate` with `VALIDATE_VIEW_TOKENS` (the SDK always adds the Markdown render, which the tool discards), projected through `validate.ts`'s `projectValidationReport` with views on for the pipe named, plus the template from `inputs-template.ts`'s `inputsTemplateFor`, projected client-side from the pipe's `input_form` descriptor by `mthds/protocol`'s `projectInputsTemplate` (a descriptor it cannot walk yields no template; `mthds_inputs_template` still reads `/v1/build/inputs`). It composes its own summary (the signature, the template, and the "who goes first" rule the instructions complete per host); the graph and the form's artifacts ride `_meta` for `run-graph`. The graph is the API's dry run of the entry pipe: for a `method_ref` package whose manifest names a `main_pipe`, that pipe, whatever the bundle declares, and otherwise the bundle's own `main_pipe`. A deployment older than pipelex-api 0.27.5 dry-runs the bundle's `main_pipe` alone, so it returns no graph for a package whose manifest alone names its entry pipe, while that package's form and template still come.

### The capability core: code generation and the workspace writers

#### `capabilities/codegen.ts`

The code-generation logic (`mthds_codegen`). Zod input/output schemas (`files?` / `method_ref?` / `method_id?` under `one_selector`, a required `target` with no default, an optional `output_dir` for the workshop's write arm), the API call (`CodegenClient.codegen()` — always `kind: "types"`, never a `pipe_ref`, which the route rejects on `types`), and the projection of the report into `structuredContent` plus a composed Markdown summary (the route returns a plain `message`). **Every selector is a server pass-through** — no `fetchMethodFiles` leg; the runner resolves `method_ref`, the hosted platform resolves `method_id`. The `target` enum is closed in both directions against the SDK's `CodegenTarget`: `CODEGEN_TARGETS` is `as const satisfies readonly CodegenTarget[]` (a dropped target fails), and `CODEGEN_TARGET_PROFILES` is a `Record<CodegenTarget, …>` (a gained target fails until its profile — the audience clause of the decision rule, what the target emits, and its file names — is written; the tool description derives from the audience alone, and the `target` field description adds the rest, which is parameter detail the length budget keeps out of the description). **Every valid response is preflighted through the SDK's own `runCodegenCheck` in memory, on BOTH arms**, before it is written or relayed: one call establishes lock structure, canonical and unique paths on both sides, and stamp/hash agreement, so the hand-written checks keep only what the SDK cannot know — presence and typing, `isStampableArtifactPath` per artifact, that the report's `target`/`kind` **echo the request** (a report for another language is internally current, so the offline check cannot see it), and that `lock_filename` is exactly **`codegen.lock`** (pinning the exact name keeps the lock where `pipelex codegen check` looks for it, makes it unable to alias an artifact path, the one hole the preflight cannot see because `runCodegenCheck` never learns the lock's filename, and keeps a `../../…` name from reaching a model on the inline arm, which has no containment of its own; the writer still contains the lock itself). **The write arm is `CodegenContext.saveRoot`** — the same name and meaning as `ArtifactsContext.saveRoot`; `generateMthdsCode` owns it (hoisted report check → preflight → `writeCodegenTree` → projection), so `codegenResult` stays pure, synchronous and filesystem-free. On the written arm content is withheld from every stream (`written_to` per file, `output_dir`, `is_current`, `orphans`, `orphans_truncated`, `drifts`, `truncated: false`, no fenced blocks); `output_dir`'s presence is the arm discriminator. A refused or failed write is a `status: "error"` no-verdict — never a fallback to riding the content. **Bounding is by whole file, with the lock's bytes reserved off the top**: `boundArtifacts` gives the lock its bytes first and lets the artifacts fill the remainder under `CODEGEN_CONTENT_CAP` (64 KiB UTF-8 across the set), stopping at the first that does not fit — the rest carry `path` and `bytes` with `content` absent, `truncated: true`. A half file neither compiles nor passes the check, and dropping the lock to fit the code it anchors is the wrong casualty. Classify options are picked by request shape (files → 422 at `target`; by-ref → `method_ref`; by-id → `method_id`), and the 403 arm composes the deployment's auth wording with the hosted feature-flag gate through `classifyError`'s `forbidden` option. No view, no `_meta`, no `available_view_specs` (decided out on 2026-08-29).

#### `capabilities/codegen-writer.ts`

The generated-tree writer behind `output_dir`, and the **write-side policy** the download tool must never share. `writeCodegenTree` returns a value and never throws. In order: contain the directory through `resolveSaveDir` (the one call that creates the target directory; a destination's missing parents are created later, at write time, through `createContainedSubdirectory`); contain every destination *and the lock* with `containedPath` alone, creating nothing, so a refusal leaves the tree byte-identical but for the target directory `resolveSaveDir` may have created; inspect every existing destination with **`lstat`** — a regular file carrying a codegen stamp (or, for the lock, the `# codegen.lock` prefix) is overwritten *hand-edited or not*, and a symlink, a directory or an unstamped file refuses the WHOLE write as `input_domain`@`output_dir`; write verbatim with the default overwriting flag, the deliberate inverse of the SDK download's exclusive `wx` create; then walk the directory (symlinks skipped, vendor/VCS directories pruned, under a file-count cap and a decoded-bytes budget that apply to orphan candidates only) and run `runCodegenCheck` with the lock **re-read from disk under a strict UTF-8 decoder**. `hasCodegenStamp` is a one-function mirror of the SDK's internal `hasStamp` (source of truth `pipelex/pipelex/codegen/stamp.py`), kept to one function so the swap is one line once the SDK exports it.

#### `capabilities/graph-page.ts`

The method graph page `mthds_validate` writes beside the `{ path }` files it validated (`writeGraphPage`, triggered by `ValidationContext.saveRoot`, which only the workshop's `mthds_validate` context sets, so the save's validation leg writes none). The page embeds the `.mthds` files in the `mthds-sources` element and loads `@pipelex/mthds-ui`'s standalone viewer and elkjs from jsDelivr, pinned by exact version and SRI (`GRAPH_PAGE_ASSETS`, checked live by `graph-page.e2e.ts`); the viewer builds the static graph in the browser, so the page needs no API call and is written whatever the verdict. The embed is written by `@pipelex/mthds-ui/static-graph`'s own `serializeMthdsSourcesEmbed`, which is why the core and the workshop declare mthds-ui as a devDependency at the console's range (tsup inlines the serializer, a few kilobytes, so `npx @pipelex/mcp` installs gain nothing), and why `GRAPH_VIEWER_VERSION` must equal the installed version: the viewer the page loads is the reader that serializer is kept in step with. `graph-page.test.ts` holds the version and both viewer hashes to the installed package without the network, so an mthds-ui bump fails there until the pin and the hashes move with it. The write policy is codegen's, not the download tool's: `lstat` the destination, create a missing page with `wx`, replace only a file carrying `GRAPH_PAGE_MARK` (a `generator` meta element), and leave a foreign file, a symlink or a directory untouched. A failure is a returned `GraphPageOutcome`, never a throw and never a change to the verdict; `toolResult` renders its `## Method graph` section after the error details.

#### `capabilities/workspace-boundary.ts`

The containment routine every filesystem-touching capability shares: `isInsideRoot` (containment without creation), `containedPath` (a relative destination joined under a directory, or nothing when it escapes), `resolveSaveDir` (containment plus the one `mkdir` of the target directory, real-path-checked on the deepest *existing* ancestor before it and again after, with the `ToolError` location a parameter, `dir` / `output_dir`) and `createContainedSubdirectory` (the same rule for a destination's parent inside that directory, with the caller's wording for an escape). `workshop/src/files.ts`, `artifacts.ts`, `codegen-writer.ts`, `graph-page.ts`, `catalog-write.ts` and `catalog-link.ts` import it. It also owns `checkDeepestExistingAncestor`, the probe every directory-creating site runs **before** `mkdir` — a real-path check that runs only afterwards reports an escape through a symlinked component instead of preventing it. **Containment only — never policy.**

#### `capabilities/artifacts.ts`

The run-saving capability (`mthds_download_artifacts`, **workshop-only**), **thin over the SDK's artifact stack** for the files: it reads the run through the results route itself (so a running or failed run never creates a directory), resolves the target — `dir`, or `runs/<run id>` from the run id the API answered (`defaultRunDir`) — and contains it through `workspace-boundary.ts`'s `resolveSaveDir`, writes the full `main_stuff` verbatim to `main_stuff.json` **first** (`writeOutputFile`: `wx`, a numeric suffix on a taken name, the partial file removed on failure; a failed write stops the save as `input_domain`@`dir` before anything is fetched), checks for references with the SDK's `collectArtifacts`, then hands the results in hand to the SDK's `downloadArtifacts` (`results` form, `scope: "main_stuff"` named explicitly), which resolves the whole set through the bulk route (`resolveArtifacts` → `POST /v1/resolve-storage-url/bulk`) and owns the filename rule, the never-overwrite create, the bounds and the per-item verdict. What stays here is the workshop's own: the tool envelope (run-state verdicts, `scope` and `output` on the completed verdict, `saved_paths` with the output first, paths made relative to the working directory, each item's `found_at` as the SDK answered it, bounded at `MAX_FOUND_AT_PATHS` with the rest counted in `found_at_omitted`, since the SDK answers one path per occurrence and the verdict is model-facing), the output file, the deployment gate, the **plain-http rule** (`allowsPlainHttp` — the SDK's `allowHttp` opt-in follows `PIPELEX_BASE_URL`'s scheme, `http:` being the local compose stack; `PIPELEX_MCP_ARTIFACTS_ALLOW_HTTP` overrides it both ways, and an unrecognized value refuses), the classification into `ToolError`s (`itemToolError` maps the SDK's per-item codes; `BULK_RESOLVE_ERROR_OPTIONS` textures the route's whole-request refusals; the SDK's thrown artifact errors are arms of `classifyError` in `shared.ts`, ahead of the generic `PipelineRequestError` arm), and the prose summary. The per-deployment seam is `ArtifactsContext.saveRoot`: the workshop sets it to its working directory; absent, the tool refuses fail-closed. Verdict discipline is the run family's (`state`-discriminated; `running`/`failed` are produced) plus `all_saved` for the walk; partial success is produced. No view, no `_meta`. It carries no walker, filename rule or downloader of its own — a change to any of those is an SDK change; the output file is the one thing it writes itself, because writing one JSON value is not the network work the SDK's stack exists for.

### The capability core: inputs and uploads

#### `capabilities/prepare.ts`

The input-preparation logic (`mthds_prepare_inputs`, **workshop-only**). Zod input/output schemas (`files?` / `method_ref?` / `method_id?` under `one_selector`, `pipe_ref?`, required filled `inputs`), and the whole request handed to `@pipelex/sdk`'s `prepareInputs`, which uploads local paths / `data:` URLs / bytes to Pipelex storage and rewrites them to `pipelex-storage://`; the result projects into `structuredContent` (`inputs`, `uploads: string[]`) plus a composed Markdown summary with the prepared inputs in a fenced block. **Every selector is a server pass-through** — since `@pipelex/sdk` 0.17.0 `prepareInputs` takes all three and reads the signature from one `POST /v1/validate` with `views: ["input_form"]`. Classify options are picked by request shape (files → 400/422 at `files`, the same texture `mthds_validate` gets for the same body; by-ref → `method_ref`; by-id → `method_id`) — **never at `pipe_ref`, which stopped riding the wire when pipe selection became client-side**. The SDK raises every client-side refusal of its own as a plain `InputPreparationError`, so all of them land at `pipe_ref` through `ClassifyErrorOptions.preparation`: right for *which pipe*, wrong for a broken closure, a missing descriptor or a bad file value, which only the console's walk tells apart (below) until the SDK raises them as distinct errors. **No produced-invalid arm** — an unresolvable closure is a no-verdict `status:"error"`. No view, no `_meta`.

#### `capabilities/console-inputs.ts`

`pipelex_run`'s input walk (`prepareConsoleInputs`), **pass-through only**, which replaced the console arm `prepare.ts` had behind an `allowUpload` seam. It calls `validate` itself for the pipe's `input_form` descriptor, picks the pipe in the SDK's order, walks the same kinds, and rewrites `http(s)` / `pipelex-storage://` values to `{ url }` while refusing any upload-needing value up front (`UploadNotAllowedError` → `input_domain`@`inputs`, the hint naming `pipelex_upload_attachments`), so it never hands raw inputs to `prepareInputs` and never triggers a server-side `readLocalPath` (the LFI/DoS/existence-oracle hazard). **That mirror is forced, not lazy**: the filesystem read happens *inside* the SDK's walk, before the upload a client seam could refuse, and no value-shape pre-screen finds it without the descriptor — a bare string is a local path at a file position and ordinary text everywhere else. Keep the mirror in step with the SDK's `prepare-inputs.ts`: the invariant is that the console never prepares a different pipe from the one the SDK, and the run route, would. `default_pipe_ref` is read on **presence**: a stated `null` (or a stated ref the descriptor does not describe) is a refusal at `pipe_ref`, and only an **absent** field leaves the blueprint and single-pipe fallbacks standing. Its three client-side refusals take three locators, because they are three questions: `preparation` at `pipe_ref` for *which pipe*; `UnresolvableClosureError` through `closure` at the selector for *which method*; `MissingInputFormError` through `missingDescriptor`, `config` at `PIPELEX_BASE_URL`, for *which deployment*. A report with no `input_form` is refused, never degraded to a walk where no refusal can fire — and the test is for a usable **record**, not for `undefined`, since the report is extension-open transport nothing validates at runtime and a `null` in that slot used to die on `Object.keys` two frames down. The descriptor guards are this repo's and not the SDK's, and they run at every depth: the top-level field list, an `object`'s `fields` elements and a `list`'s `item` (a stated `item: null` passes an `!== undefined` test and then has `.kind` read off it). A malformed node falls to the pass-through arm, which is safe because it declares no file position, so nothing upload-bearing escapes unrefused; a malformed top-level field list is refused outright, because there would be nothing left to walk. `pipelex_run` skips the walk, and its `/v1/validate`, when `inputs` is absent or empty; its `files` selector arm serves the live leg alone.

#### `capabilities/attachments.ts`

The chat-attachment ingest capability (`pipelex_upload_attachments`, **console-only**) plus the mandated four-field host-attachment Zod schema (`download_url`/`file_id` required, `mime_type`/`file_name` optional — declared here rather than imported from `skybridge/server`'s `FileRef`, because the capability core stays Skybridge-free; a local mirror emits a byte-identical JSON Schema). Per attachment, sequentially: fetch within the boundary → `uploadFile` → `pipelex-storage://`. The host's `file_name` is user-supplied, so it is reduced to a bare printable basename before it names a stored asset. Per-item errors ride `attachments[i].error` and **partial success is a produced verdict** (`status:"ok"`, `is_valid:false`) — successful uploads are never discarded because a sibling failed. Never touches the filesystem. No view, no `_meta`.

#### `capabilities/attachment-fetch.ts`

The **attachment fetch boundary**: the console's analogue of the workshop's path trust boundary, deny-by-default, reporting failures as values rather than throwing. Its rules are in `.claude/rules/attachment-fetch.md`, which loads whenever this file is read, and its contract is SPEC.md's "Attachment fetch boundary (console)"; read both before changing anything here.

#### `capabilities/upload-grant.ts`

The run form's upload grant (`pipelex_request_upload`, **console-only and app-only**: `_meta.ui.visibility: ["app"]`). The view sends the file's name, type and size, never its bytes; the capability asks `POST /v1/upload/grant` for a presigned, create-only `PUT` with the caller's token and relays it. **The grant is a bearer capability, so it rides `_meta.upload_grant` and nowhere else** — `structuredContent` carries only the reference, the expiry and the cap, and nothing logs it. Its refusals are picked by status in `uploadGrantErrorOptions`: the route's `400` is the platform's `require_active_org` (`config` at the credential, since no file changes it), its `422` is the body (`input_domain`), and its `413` is the declared size over the cap, classified through `classifyError`'s `tooLarge` option (`input_domain` at `size`). The grant's shape check lives in `capabilities/upload-grant-shape.ts`, which imports one type and nothing else, because the view bundles it for the browser. The bucket sources the views may reach are `hosted/app-buckets.ts`: **every source there is one bucket's own host, a plain origin.** The platform signs on the GLOBAL virtual-hosted host (`<bucket>.s3.amazonaws.com`), both its upload grants and the fresh links its bulk resolve route mints, and the lists carry the REGIONAL virtual-hosted form beside it, which is where the runtime signs a run's baked `public_url` from `pipelex` 0.66.0 (measured against api-dev on 2026-09-26) and what a pinned platform endpoint would produce. **The shared regional endpoint is deliberately not allowed**: the runtime signed PATH-style there before 0.66.0 (`s3.us-west-2.amazonaws.com/<bucket>/…`), where a bucket can be scoped only by path, and the Dev console's acceptance on 2026-09-25 showed a host did not keep the path; the endpoint's origin alone would admit every bucket in the region. A path-style source must never come back. The views still paint from the fresh links on `_meta.resolved_urls` (see `capabilities/run.ts`), because the baked link expires an hour after the run. `upload-grant.e2e.ts` checks a live grant's host against the upload list, write-free, since a grant stores nothing until the file is sent.

#### `capabilities/upload-ceiling.ts`

`MAX_UPLOAD_BYTES` (**derived** from AWS API Gateway's 10 MiB request quota and base64's 4/3 inflation, not hardcoded) plus `SizeGuardedPipelexApiClient`, which refuses an oversize upload locally with the same `RejectedAssetError` the SDK maps a real `413` onto, `code: "too_large"` included, and a message that names the true limit. **It does not reach a caller the way a real `413` does**: the SDK's `uploadFile` maps a real `413` before its catch-all, but wraps anything else `upload()` throws in an `UploadTransportError`, so the local refusal arrives as that wrapper's `cause`. `classifyError` unwraps it ahead of the transport arm. Without that, an oversize file classified as a retryable `runtime` fault telling the agent to retry, and the ceiling's tests could not see it, because they called `upload()` directly rather than going through `uploadFile` as every real caller does. It overrides `upload` (the wire call), which is the one seam both upload paths share: the SDK's own `prepareInputs` walk calls it through `this`. It does **not** skip reading/base64-encoding a local asset first — the SDK owns that inside `uploadFile`, so a real pre-flight needs a change in `@pipelex/sdk`. **The app-level 50 MiB `MAX_UPLOAD_MIB` is unreachable through the public gateway; never quote it as the limit of a path that crosses it.** The run form's upload grant is the one path that does not cross it (the browser sends the file straight to the bucket), and there the 50 MiB is the limit.

### The capability core: runs and their results

#### `capabilities/run.ts`

The durable-run family (`mthds_run` / `mthds_run_status` / `mthds_run_results`) over the SDK's run lifecycle (`start` / `getRunStatus` / `getRunResult`). A completed result walks the **full** `main_stuff` twice in memory, on both shells and for free: `collectArtifacts` for the stored-file count and `imageCandidatesOf` for `structuredContent.image_candidates` (absent, not empty, when the output references no stored file) — bare references, deduplicated, capped at `MAX_IMAGE_CANDIDATE_ENTRIES` with the remainder in `image_candidates_omitted`, because the walk deliberately reads the FULL output and an unbounded projection of it is model-facing content outside the `MAIN_STUFF_CAP` discipline `main_stuff` obeys beside it. A completed result also carries the graph's three I/O artifacts on `_meta`, on the same terms as the graph itself (`viewsAvailable`, never `structuredContent`): `pipe_io_contracts` and `output_form` as a **pair**, because that is the renderer's own rule — `GraphViewer` shows a data node's VALUE only when it holds both, and the concept's structure table otherwise, so half the pair renders exactly like neither and is withheld instead of costing the wire — plus `input_form`, which answers only for the method's own inputs and is optional *given* the pair rather than independent of it — the renderer consults it only inside the gate the pair opens, so it rides only when the pair does. Each must be a non-empty map to ride (`hasArtifactEntries`, shared with `validate.ts` from `shared.ts`): the hosted results relay the keys as `null` for a run whose runner predates them, and an empty map drives nothing. One merged summary sentence then names the shell's image tool where there are candidates and, on a shell whose `RunContext.artifactDownloadAvailable` is set (the workshop), `mthds_download_artifacts` as the way to keep the run — the output as `main_stuff.json`, and the files with the `public_url` expiry — on **every** completed result, files or not, because a model that does not know the tool retypes the output into a file; the same flag makes the truncation sentence name the tool as the way to read the rest. Prose only, the structured contract is untouched. **The results tool never inlines an image and takes no flag that would let it**; that is the campaign's settled decision, not an omission. `pipelex_run` (the console's, by `PipelexRunContext` / `PipelexRunClient`) takes `method_id?` or `method_ref?` only, maps `pipe_ref` onto `pipe_code` when the caller named one, and runs `console-inputs.ts`'s walk first; its hints name `pipelex_show_method`, and an unknown run id reads as not visible to the caller's organization. `mthds_run` starts from `files?`, `method_ref?`, or `method_id?` (rule `run_source`: files + `method_id` is the one legal pair — the files run, the id is run-history linkage; `method_ref` is a complete run source of its own and pairs with nothing). The platform resolves `method_id` natively on `/v1/start` (id-only runs the stored method's current content; beside files it rides the SDK's named `method_id` option — `PipelexStartOptions`, never `extra`, which the SDK refuses at runtime for reserved keys). `method_ref` rides the SDK's named Pipelex-API run-source extension, is resolved by the runner (git fetch at the tag), and the resolved commit comes back as `method_provenance` on the start ack — narrowed defensively (`narrowMethodProvenance`), projected into `structuredContent`, and echoed in the summary so the run stays explainable when a tag moves. Also owns `main_stuff` bounding (the prune ladder under `MAIN_STUFF_CAP`), the run-usage projection over the SDK's `summarizeUsage` — the arithmetic is the SDK's and is never re-derived here: `projectRunUsage` reshapes the summary into the model-facing `structuredContent.usage` (its `state`, `cost_usd` for the SDK's `total_cost_usd`, one `tokens` figure adding the SDK's `input` and `output` totals, `calls`, `assembly_error`), present on every completed result; per-pipe stays off the model-facing surface — `projectUsageByPipe` puts the SDK's `by_pipe` rows, in its order, on view-only `_meta.usage_by_pipe` alongside the full per-call `tokens_usages` for a future detailed-cost surface, and usage is never rendered into the prose; **the views' fresh links** (`freshStorageLinks`: on a shell with views, a completed result resolves every stored reference of its output, then of its executed graph, deduplicated, `BULK_RESOLVE_MAX_URIS` per request, one request after another through `RunClient.resolveStorageUrls` under one `VIEW_LINKS_TIMEOUT_MS` deadline, and rides the minted `https:` links on `_meta.resolved_urls` — best effort and never part of the verdict, so a failed or slow request stops the walk, keeps what the earlier ones minted and, when `classifyError` calls the failure retryable, sets `_meta.resolved_urls_partial`, which the views read the results again for; every reference is asked for because the payload's baked `public_url` expires an hour after the run, so a reference left without a fresh link paints nothing in a conversation reopened later); and the per-route classify options, including the by-id variants picked by request shape. A failed start goes through `classifyStartError`, which refuses a retry whenever the run may exist anyway (a timeout, a connection lost after sending, a 500, 502, 504 or 408; the 500 is the runner's failed start, which the platform relays as such and which can follow a start Temporal already recorded); its hint and its "Run may have started" headline live in `capabilities/start-outcome.ts`, which imports nothing so the views can bundle it, and the hint is the marker `startMayHaveRunError` reads, in the tool's headline and in both run views, since a start spends inference credit and the SDK cannot yet send the `Idempotency-Key` the hosted `/v1/start` honours.

#### `capabilities/run-failure.ts`

Why a failed run failed, on both shells: `runFailureOf` narrows the runner's stored error report into the `failure` object every failed arm of the run family carries (the status tool on a terminal status other than COMPLETED, and the `failed` state of the results, image and download tools), and the module words it twice, `failureSummaryLines` for the model's summary and `failureDisplayOf` for the console's views. **The two wordings differ on purpose**: the platform serves the runner's VERBOSE report, so `message` can quote a provider's raw text, which the model reads and the person never does; the views say why from `title`, what to do from `user_action`, and show a support line (run id, error type, time the run ended) that `views/components/failure-details.tsx` renders with a Copy button. Retry advice comes from the report's `retryable` alone, never inferred, and a `false` is worded as the report's expectation, since the runner sets it for a failure it could not classify too. A `wait_and_retry` user action never keeps the runner's detail, in `structuredContent` as in the summary: it takes this module's own sentence, or an empty detail when the report's `retryable` is `false`, since the runner words its detail for a pipe still inside its retries ("the system will retry automatically"), which is false of the stored report of a run that has ended. Every text field is bounded by code point (`FAILURE_MESSAGE_MAX_CODE_POINTS` for the message, `FAILURE_FIELD_MAX_CODE_POINTS` for the rest, `failureMessageOf` for the failed arm's `failure_message`), since the runner embeds its exception's text unbounded and the message reaches the model twice. The report reaches the results-side tools from the results route's failed arm when the platform relays it there, and otherwise from one status read of the same run (`readFailedRun` and `failureOfFailedArm` in `run.ts`), which is also where the time the run ended comes from, so the image and download seams (`ImagesClient`, `ArtifactClient`) carry `getRunStatus` too. That read is bounded by `FAILED_RUN_READ_TIMEOUT_MS`, which aborts it and stops waiting for it both, and a read that fails makes the summary say the reason is unknown rather than missing (`failedArmSummaryLines`). The views bundle this module, so it imports types only; the zod `runFailureSchema` lives in `run.ts`. Its tests run over real failed runs recorded from the dev plane (`capabilities/failed-run-fixtures.ts` over `__fixtures__/failed-runs/`).

#### `capabilities/images.ts`

The image-display capability, on **both** shells (`pipelex_show_images`, `mthds_show_images`). It reads the run through the results route (so a `running`, `failed` or candidate-free run is a produced verdict that fetches nothing), prefilters the stored references by storage key with `shared.ts`'s `imageCandidatesOf`, intersects the caller's `images` / `indices` selection with what the run produced (an unknown reference or an out-of-range index is an `input_domain` no-verdict, refused before any call), then fetches each survivor through the SDK's bounded `client.fetchArtifact` under four named caps in `shared.ts` — `MAX_INLINE_IMAGE_BYTES`, `INLINE_IMAGES_BUDGET`, `MAX_INLINE_IMAGES` (which bounds *attempts*), `MAX_IMAGE_CANDIDATE_ENTRIES` (which bounds how many are *enumerated*, the rest counted in `omitted`) — plus its own `INLINE_IMAGE_TIMEOUT_MS` and `INLINE_IMAGES_DEADLINE_MS`. **The deadline is the one that is easy to leave out, and then to under-apply**: the per-image timeout is per image and the walk is sequential, so without a shared wall-clock budget six stalled objects accumulate into a three-minute call and a host with a shorter deadline loses the whole result, successful pictures included. Each fetch gets `min(INLINE_IMAGE_TIMEOUT_MS, remaining)` **and** `AbortSignal.timeout(remaining)`, and the signal is not belt-and-braces: `fetchArtifact` resolves the reference before arming `timeoutMs`, under a fixed 30s budget only `options.signal` reaches, so the timeout alone left a 60s walk able to run to 90s (120s of call with the run lookup). Since the SDK re-throws a caller's abort untouched, the deadline arrives as a raw `DOMException` and both catch sites test `deadline.aborted` first — otherwise this tool's own budget reads as a whole-request failure, and as a no-verdict when nothing had yet inlined. A candidate reached with none left is `withheld: "deadline"` unattempted. The content-type gate reads the **response's** header, not the resolve route's `content_type`, which the SDK documents as a guess from the reference's extension. A picture that does not fit is a `withheld` reason (`size` / `budget` / `count` / `type` / `deadline` / `empty`), never an error and never resized; `empty` is the zero-byte object, which clears every other gate and would be emitted as `data: ""` — permanent, unrenderable context; a per-reference failure rides `error` through `shared.ts`'s `itemToolError`. A repeated selection is deduplicated in `selectCandidates`, preserving the caller's order — the entries are in the order *considered*, which is the caller's for a narrowed call and discovery order only otherwise. Verdict discipline is the run family's, plus `all_inlined` — which answers for the **run**, so the walk is handed `candidates.length` beside the selection and a narrowed call reports `false` while the run holds a picture it did not ask for; `omitted` counts against it too, but `omitted` is this listing's truncation (what the call *considered* lost to the cap) and is reached with `indices`, never `images`. Partial success is produced — **but a whole-request refusal that stopped the walk before any picture arrived is a `status: "error"` no-verdict** carrying the classified cause, since nothing was produced and the generic summary would otherwise bury a paywall or a rejected credential. **Every emitted block is `{ type: "image", data, mimeType, _meta: { uri } }` and carries no `annotations`** — see [Image blocks carry no annotations](#image-blocks-carry-no-annotations); the `_meta` half is measured on Codex by the probe's `meta` variant, not assumed from the standard. No view, no result `_meta`, no filesystem.

### The console's views

#### `views/run-graph.tsx`

The **run-graph** Skybridge view, registered on `pipelex_show_method`. It is the generic renderer for a method's run graph, deliberately **not** named after its trigger: today it shows the **dry-run graph** the show feeds it; a run tool can register the same component for a **live-run graph** later. It reads the verdict from `useToolInfo` (`output`) and the graph from `responseMetadata.graph_spec` (the view-only `_meta` channel), then renders it with `@pipelex/mthds-ui`'s `GraphViewer` (inline preview + a `useDisplayMode` fullscreen toggle, sized from `useLayout`). On a runnable verdict it also renders the **input form** below the graph: `@pipelex/mthds-ui/form/react`'s `RunPanel` over the wire input-form descriptor (`responseMetadata.input_form` — since kernel 0.5.0 the descriptor IS the field derivation and `RunPanel` requires it) with the IO contract co-walked beside it (`responseMetadata.pipe_io_contracts`), each looked up for the pipe in play with `@pipelex/mthds-form`'s twin selectors `getPipeInputForm` / `getPipeIOContract` (the pipe node the user last clicked via `GraphViewer`'s `onNodeSelect`, else the pipe the show named or the effective entry pipe, from `responseMetadata.form_pipe_ref` then `main_pipe_ref`, else **nothing** — `views/run-graph-selection.ts`'s `selectedPipeFor` is that rule, kept pure so it is tested in Node, and it deliberately has no "first pipe in the contract map" arm: a verdict with no entry pipe opens no form of its own, and since the capability still ships the pair there, a pipe the user clicks is the only thing that produces one). The graph is not always of that pipe: the graph arm stamps the pipe it dry-ran on `graph_spec.pipeline_ref`, which is the entry pipe on a current deployment but the bundle blueprint's `main_pipe` on one older than pipelex-api 0.27.5, where a `method_ref` package can open the form on a pipe the graph does not show. The view keeps the graph and captions it when the refs differ — `graphPipeRefOf` reads the graph's pipe, `graphCaptionFor` words the caption, both in `run-graph-selection.ts` and only saying the form runs the entry pipe while it does — and renders nothing extra when they agree or the graph names no pipe. Run calls `pipelex_run` through `useCallTool` with the show's own `method_id` / `method_ref` and the form's pipe as `pipe_ref`, follows the run with the shared `useRunPolling` hook, fetches `pipelex_run_results` itself with the shared `useRunResults` hook once the run is terminal (a view's own call mounts no other view, so `run-follow` never appears for it), and shows the results in place: the results panel takes the form's place, the dry-run graph gives way to the executed graph fed the results' own artifact pair, and the form folds behind "Edit inputs and run again", which brings the dry-run graph back with it, since only that graph's nodes switch the form's pipe — `views/run-graph-stage.ts`'s `formViewStage` is that transition table, `formRunInFlight` holds Run disabled until the run's results are read or their fetch has given up (a second run in that window would drop the only handle on the first one's output; `useRunResults` gives up after `RESULTS_FETCH_MAX_ATTEMPTS` reads, from `views/run-results.ts`, so no failure can hold it for good), and `runStatusLineFor` is the line under the form, all pure and tested in Node. The run it started, and its pipe, ride host-persisted view state (`run_id`, `run_pipe_ref`), which a remount follows again once, restoring that pipe as the form's too, since no conversation message carries the id; each press of Run clears the state before starting, so a failed start leaves nothing an older run could be restored from. **It sends no completion message** (design R2 of L-260925-53eb57 in the workspace ledger): the user reads the output here, and the prompt was a draft in claude.ai's composer and nothing at all on ChatGPT; `run-follow`, where the model started the run, keeps its handoff. Two things to know: `running` is set synchronously inside `onRun` because that is the panel's only duplicate-run guard across the round trip, and a file-bearing input stores a picked file through the `uploadFile` callback `views/run-graph-upload.ts` builds: it calls `pipelex_request_upload` for a grant, sends the file with `@pipelex/sdk/upload`'s `uploadWithGrant` under the SDK's own time limit (the view passes no timer of its own, since the SDK bounds the `PUT` itself from `@pipelex/sdk` 0.24.0), and returns the reference only once storage has answered. A failed send is worded by `storageFailureMessage` from the error's `code` (`UploadTransportError`, `RejectedAssetError`) and never relays the SDK's message, which is advice for a caller holding the grant — a retry with the same grant before it expires, a longer `timeoutMs`, a look at the page's CSP — that the person at the form cannot follow; its tests drive the SDK's real `uploadWithGrant` over a stubbed `fetch`, so a change in how the SDK classifies storage's answer fails them. **The panel swallows a rejected upload silently** (its rejection handler is empty), so the view writes the failure into a line under the form itself, one per field, keyed by the field id the panel passes and dropped when that field's value changes (a pasted link, a clear, a later upload) or its list gains or loses a row, since a failed row holds nothing and a removed one reads the same by value — `clearChangedFields` in `views/run-graph-upload.ts`, since the panel commits nothing when an upload fails; without that, a failed upload looks exactly like the bug this path fixed, a dialog that opens and a field that stays empty. That module imports only `@pipelex/sdk/upload` and `capabilities/upload-grant-shape.ts`, never the SDK's main entry, which reaches `node:fs` and cannot be bundled for a browser. It renders the form alone when a result carries the form pair but no graph, and a compact empty state for invalid results and for results carrying neither. ## The files union and the resolution seam

Every files-taking tool — the workshop's alone, since no console tool takes `files` — (`mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`, `mthds_run`, `mthds_save_method`) shares one per-item input union: inline contents (`{ content, uri? }`) or a file path (`{ path }`). The arms are non-strict with first-match semantics — a pathological item carrying both keys parses as the content arm and `path` is ignored (strict arms were rejected in Phase 0: an unknown-key failure would surface as a noisy zod union error from the SDK layer instead of our instructive `ToolError`).

On every method-taking tool (`mthds_validate`, `mthds_run`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`), `files` is **optional** beside separate top-level selectors — `method_ref?` (a published method address, `github.com/<owner>/<repo>[/<selector>][@<tag>]`) and `method_id?` (a registered method's catalog id). Neither is a third union arm: an address or an id is not a file, and a mixed array would falsely suggest merging. `validateMethodSelectorRequest` enforces the two selector rules (SPEC.md → "Method Selectors"): the tooling tools take **exactly one** source form; `mthds_run` lets files + `method_id` pair (files run, id is linkage) while `method_ref` pairs with nothing. Resolution: `mthds_validate`, `mthds_codegen` and `mthds_prepare_inputs` forward either selector to the server (prepare's ride `POST /v1/validate`, the route its signature comes from); `mthds_inputs_template` forwards `method_ref` on the build envelope and expands `method_id` via **fetch-and-forward** (`fetchMethodFiles`), the one remaining user of that leg; on `mthds_run` both selectors resolve natively server-side on `POST /v1/start` — see SPEC.md's Run Scope.

What a `{ path }` item *does* is decided by the **resolution seam**, not the schema: each capability's context carries an optional `resolver?: FileResolver`, and `resolveSubmittedFiles(files, resolver)` runs **ahead of** the request-shape checks (`validateMethodSelectorRequest` sees only resolved `{ content, uri? }` items). With a resolver (the workshop), `{ path }` items are read from disk and the resolved item carries `uri` = the submitted path — that's the provenance win: diagnostics locate to files the agent can open. Without one, each `{ path }` item is rejected with an instructive `input_domain` error at `files[i].path`; no shell builds such a context now, but the refusal stays as the fail-closed default. Resolvers report failures as `FileResolution` values, never throw; every resolution failure is `input_domain` at `files[i].path`, `retryable: false` — the resolver supplies only message and hint.

## The output streams

SPEC.md's "The result streams" is the contract; this section is how the code keeps it. It mirrors the workspace's "format follows consumer" rule, which loads from the workspace's `.claude/rules/surface-output.md`. A tool result carries up to three independent streams (`pipelex_show_method` uses all three; the workshop has no views, so its `_meta` carries no view data, only a valid verdict's `main_pipe_ref` and a completed run's full output and usage records, described below):

- **`structuredContent`** — the machine contract the model reads. A machine consumer branches on these fields, never on transport.
- **`content` text** — the human/LLM-readable Markdown summary. For `mthds_validate` it is the API's `rendered_markdown` and is deliberately **not duplicated** into `structuredContent`; `pipelex_show_method` composes its own, carrying the signature and the template. For `mthds_inputs_template` the capability composes it (the build routes return a plain `message`) and deliberately **does** repeat the template in a fenced code block — the template is the small payload the model must read, not a large view artifact.
- **`_meta`** — large data that **never reaches the model's context**: the views' data, and a completed run's full output and usage records. The graph (`_meta.graph_spec`) rides here so the agent acts on the verdict + Markdown summary, never the raw spec; the `run-graph` view reads it back via `responseMetadata.graph_spec`. `_meta` still travels on the raw MCP result, so a non-LLM programmatic consumer can read it off the wire — it is withheld from the model, not from the transport. The form's per-pipe artifact pair rides the same channel (`_meta.pipe_io_contracts` and `_meta.input_form` — the wire input-form descriptor the capability requests via the `views` token list — plus `_meta.output_form`, its twin requested by the same list and read by nothing yet) on a runnable verdict whose two artifacts each carry at least one entry, for the input form, while `_meta.main_pipe_ref` rides every valid verdict with an entry pipe, on both shells; the entry-pipe gate applies to the *advert*, not to the pair. Because the model never sees `_meta`, `structuredContent.available_view_specs` is its structured signal a view exists to surface: it lists the renderable view kinds — `"dry_run_graph"` (the method graph from the validation dry run, riding `_meta.graph_spec`) and `"input_form"` (the entry pipe's fill-in form, derived from `_meta.input_form` with `_meta.pipe_io_contracts` beside it; only on a runnable verdict with a settled entry pipe and both artifacts carrying that pipe, since a form whose Run can only fail — or whose fields cannot be derived, or that has no pipe to be for — is not worth advertising, even though the artifacts themselves still ride so a clicked pipe can get one). (The view-kind identifier and the `_meta` key are intentionally distinct: the key mirrors the API's `graph_spec` field and the view's `responseMetadata.graph_spec` reader, while the identifier names what kind of view it drives.)

A completed run's full output (`_meta.main_stuff`) and its usage records (`_meta.tokens_usages`, `_meta.usage_by_pipe`) ride `_meta` too, on both shells and ungated by views, so a programmatic consumer keeps what the model's bounded copy dropped; see `capabilities/run.ts` above.

`pipelex_run_results` uses the same channel for the same reason, and carries the same artifact names: `_meta.pipe_io_contracts` and `_meta.output_form` as a pair with `_meta.input_form` beside them, which is what makes the executed graph in either view show a completed run's actual values instead of its concepts' structure tables, and what the results panel derives the output's field from. **This was a shipped regression between `@pipelex/mthds-ui` 0.20.0 and the SDK carrying the fields**: 0.20.0 deleted `StuffViewer`, which had been rendering the value, and replaced it with a gate on the pair — so every hosted run graph silently dropped to the structure table until the producer chain (the Temporal build, the platform relay, `RunResults`) was finished and this read it. `run-graph`'s dry-run graph is deliberately NOT fed the show's pair: the renderer suppresses the data view on a dry run before it consults the props, so wiring them there would change nothing. Its executed graph, after a run from the form, is fed the results' pair like `run-follow`'s.

## Verdicts, errors and `classifyError`

A successful `mthds_list_methods` call is `status:"ok"` with counts and a `methods` page; it is a read result, not a method verdict, so it has no `is_valid` field. The failure arm still uses the shared `status:"error"` + `errors[]` shape.

A *produced* verdict is always `status: "ok"`, regardless of whether the bundle passed — discriminate on `is_valid` (and, for validation, `is_runnable`). This discipline is shared by both tools: an unresolvable closure on `mthds_inputs_template` is a produced `is_valid: false` verdict with `validation_errors[]`, exactly like an invalid bundle on `mthds_validate`. `status: "error"` is reserved for **"no verdict could be produced"**: bad request shape, unreachable/misconfigured API, or a runtime fault. Those carry an `errors[]` array, each tagged with an `ErrorClass`:

- `input_domain` — the submitted request is wrong (empty `files`, blank `uri`, blank `pipe_ref`, API 400/422 — which on `/v1/build/inputs` includes an unknown `pipe_ref` and an unresolvable `main_pipe` default).
- `config` — environment/auth is wrong (`PIPELEX_BASE_URL`/`PIPELEX_API_KEY`, API unreachable, 401/403/404).
- `runtime` — unexpected server-side fault (API 5xx, unknown errors, a reachable-but-malformed report).

`classifyError` (in `capabilities/shared.ts`) maps `@pipelex/sdk` error types (`ApiUnreachableError`, `ClientAuthenticationError`, `ApiResponseError`, `PipelineRequestError`) and HTTP statuses onto these classes; each capability passes `ClassifyErrorOptions` for its route-specific 400/422 locator/hint and 404 route name, plus the deployment's auth-failure texture (`options.auth`, threaded from the context's `authError` field — the hosted console's "reconnect the connector and sign in again" wording at `authorization` vs the default `PIPELEX_API_KEY` env-var wording). A route a deployment gates beyond authentication passes `options.forbidden` too: it replaces the hint on a **403 only** (never a 401), keeping the auth locator — `mthds_codegen` uses it because the hosted `/v1/codegen` sits behind a feature flag as well as a plan, so a valid credential can still be refused and "check your key" would mislead. Every `ToolError` also carries `retryable` — set here, where the concrete SDK error/HTTP status is still known, because the class+locator pair alone can't tell an unreachable API (transient) from a missing run lifecycle (permanent, same `config`@`PIPELEX_BASE_URL`) or a 5xx from a malformed report (both `runtime`); the `run-follow` view's poll loops branch on it via `isTransientPollError`. When you add a new failure mode, classify it here — including its `retryable` verdict — rather than letting it fall through to a generic `runtime` message. **The execution-locus gate's two 403s are the standing example, and both are branched on the runner's declared `error_type` ahead of the generic 401/403 arm** (`MethodStructuresRefusedError`, a fetched package declaring in-process Python structure classes; `CustomCodeRequiresSandbox`, any method shipping `.py` on a deployment that is not sandbox-hosted): they are `input_domain` at whatever named the method — `CustomCodeRequiresSandbox` at `ClassifyErrorOptions.methodLocation`, set per request shape because `/v1/start` gates a submitted bundle and a stored method's injected source too, and `MethodStructuresRefusedError`, which only a fetched package can trigger, always at `method_ref` — and the whole point is that the generic arm sends a caller whose credential is fine to go and mint a key.

A `ToolError` also carries an optional `kind`, which **refines a class that the headline cannot use**. Its only member is `paywall`, set in the 402 arm: a plan limit is deliberately `config`, so every class-derived headline announced "the Pipelex API is unreachable or misconfigured" for a billing refusal — and on a host that shows the agent only the top content line, that was the entire message. Each capability now declares its headlines as an `ErrorSummaries` record (three classes **plus** `paywall`) and looks one up through `summaryForToolError`, which consults `kind` before `class`. The mandatory `paywall` entry is the point of the type: a new capability that forgot one would silently inherit the connectivity headline, and this makes that a type error instead of a review catch. The `class` contract is untouched — a machine consumer still branches on `class`; `kind` is what lets it tell a billing refusal from an unreachable API without sniffing the message, exactly as `retryable` separates a transient `config` from a permanent one. A future cause of the same shape gets a new `kind` member and a headline in every table; it does not get re-classified.

## Projection rules

### `validationResult`

- `projectValidationReport` is shared by `mthds_validate` (views off, so no graph, form artifact or advert ever appears on the workshop) and `pipelex_show_method` (views on, for the pipe the caller named); the rules below are the views-on reading.
- Valid + runnable → `is_valid=true`, `is_runnable=true`; the graph is returned on `ValidationResult.graphSpec` (projected onto the tool result's `_meta.graph_spec` by `toolResult`), never in `structuredContent`.
- Valid + pending signatures → `is_valid=true`, `is_runnable=false`, `pending_signatures` populated.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated.
- `available_view_specs` is populated from what was produced: `"dry_run_graph"` exactly when `graphSpec != null` (a valid verdict with a graph, on a shell that renders views), `"input_form"` exactly when a settled entry pipe (`mainPipeRef`) has an entry in `pipe_io_contracts` AND in the `input_form` descriptor, on a valid + runnable verdict whose two artifacts both rode. **The advert is narrower than the artifacts' own gate**: the pair rides whenever the verdict is runnable and both maps carry something (a runner that ignored the `views` token returns no descriptor, and then nothing rides and nothing is advertised, rather than an empty form), because `_meta` never reaches the model and the maps are what the view looks a pipe up in — gating them on the entry pipe made a click on a graph node dead for every pipe. A verdict with no entry pipe (a stated `default_pipe_ref: null`, or a blueprint ref that keys neither map) therefore advertises nothing and opens nothing, while a pipe the user clicks still gets its form. Note the advert can outlive `main_pipe`: the form derives from the descriptor, so a plain-object contract that fails to narrow advertises a working form and no signature. `[]` otherwise (invalid, pending signatures without a graph, error). When the list is non-empty a `## Views` note worded for the present kinds (`viewsNote`) is appended to the Markdown summary. Add a new view kind to the `viewSpecSchema` enum and set it here when its spec is produced.
- `main_pipe.output.images` is present exactly when the output-form descriptor arrived AND its entry for the effective entry pipe narrowed to a node AND the image walk either completed or found at least one image; absent otherwise, which is "unknown" and not "none". Independent of `viewsAvailable`, like the rest of the signature.
- `main_pipe` is present on **every valid verdict** with an effective entry pipe (`defaultPipeRefOf`) whose contract entry narrows cleanly — pending signatures included, independent of `viewsAvailable` (the ref derivation is hoisted out of the views branch to feed it, so `_meta.main_pipe_ref` also rides a valid non-runnable verdict; the view ignores it). `item_count` is present exactly on the fixed arm, `required` is `presence !== "optional"`, and per-slot JSON Schemas stay out. When it was produced, `signatureLine` appends a `## Main pipe` section to the Markdown summary **before** the `## Views` note.
- The capability always calls the API with `allowSignatures: true`, `render: ["markdown"]`, and `views: ["input_form", "output_form"]` (the descriptor opt-in — lenient on the server, so a runner that predates a token simply returns no descriptor for it, and the members reading it stay absent). A report missing `rendered_markdown` is a hard error.

### `inputsResult`

- Valid → `is_valid=true`, resolved `pipe_ref`, echoed `format`/`explicit`, and the template on exactly one of `inputs` (json) / `inputs_toml` (toml) — the unused field is absent.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated; no `pipe_ref`, no template fields.
- The request always sends its defaults explicitly: `format: "json"`, `explicit: true` unless overridden. A valid report missing its format-selected template field is a hard error (surfaced as a `runtime` no-verdict).
- The summary is composed by the capability (title, API `message`, resolved pipe, fenced template block matching `format`, then the next step: `mthds_prepare_inputs`, or straight to `mthds_run` when every file value is already a URL or a storage reference).

### `codegenResult`

- Valid → `is_valid=true`, `target` / `kind` echoed, `crate_fingerprint` and `engine_version`, `artifacts[]` and `lock` from `boundArtifacts`, and `truncated` always present (`false` when everything rode whole).
- Invalid produced verdict → `status="ok"`, `is_valid=false`, `validation_errors` populated; no artifact fields.
- A valid arm without a well-formed artifact list, a lock string, or a lock filename throws, which `generateMthdsCode` surfaces as a `runtime` no-verdict — what arrives is written into a user's tree, so it is checked rather than trusted.
- The summary is composed by the capability: title, API `message`, the axes line, the verbatim-write instruction, one `## \`path\` (N bytes)` section per file with a fenced block (`fenced` grows the fence past any backtick run in the content), the lock last, and a `## Withheld for size` section listing the withheld files when `truncated`.

## Standing conventions

### Image blocks carry no annotations

**No image content block this server emits may carry `annotations`, ever.** The MCP standard's `annotations` hint (audience, priority) is optional and looks harmless; the host probe behind the image tools found that **Codex refuses an annotated image block outright** with `tool call error … Unexpected response type`, against a control proving the identical block without them is accepted and the picture reaches the model. Shipping with annotations would have broken the feature entirely on one of three named workshop hosts, diagnosable only from production. The `ContentImage` type in `shared.ts` does not declare the field, and `images.test.ts` asserts on the emitted block's exact key set — keep both. The study, recorded under L-260920-fc66db in the workspace ledger, also records what the probe settled about cost: a host bills an image block at the model's **native vision price** (pixels), and its **base64 size is free** — so the byte caps are a transport guard, not a cost control, and the reason the feature is a deliberate tool is that a picture in context is **permanent**, not that it is expensive.

### Every API client comes from `createPipelexApiClient`

**Every Pipelex API client is built by `createPipelexApiClient` (`capabilities/shared.ts`), never with `new`.** The factory passes the context's `appInfo`, which is how every request names itself `pipelex-mcp/<version> (<workshop|console>; host=<host>)` in its `User-Agent`, the version being the shell's own package version, since the two servers are versioned apart and is attributed to the `mcp` surface. Each shell sets that identity on every context of its own table through the patch helper beside its context set — `patchHostedApiContexts` in `hosted/tools.ts`, `patchLocalApiContexts` in `workshop/src/tools.ts` — the console per request from the connector's `User-Agent`, the workshop lazily from the `initialize` handshake's `clientInfo`, which is only known after the contexts exist. The `pipelex/sdk-client-factory` and `pipelex/no-raw-fetch` lint rules (`eslint-rules/pipelex-api-boundary.mjs`, pinned by `tests/api-boundary-lint.test.ts`) refuse a direct construction or a bare `fetch` elsewhere; pass a subclass to the factory as its second argument, and keep third-party fetches (which must not carry the header) in the exempted `attachment-fetch.ts`. See `docs/client-identification.md`.

### What each package declares

**Each package's `dependencies` carries exactly what its own entrypoint reaches at runtime, and nothing else.** The workspace gives the two surfaces the separate manifests their opposite needs call for. The workshop's tarball ships `dist/main.js` alone, so every `npx @pipelex/mcp` user downloads the whole of `packages/workshop`'s `dependencies` closure before a single tool call; it therefore declares only what that bundle leaves external — `@modelcontextprotocol/sdk`, `@pipelex/sdk`, `mthds` and `zod` — and nothing of the console's. **The core is a devDependency of both servers and is inlined by both builds**: tsup externalizes only a package's `dependencies` and `peerDependencies`, so it bundles the core's source into `dist/main.js`, and the core's own imports then resolve from the workshop's manifest — which is why the workshop re-declares every runtime dependency of the core at the same range, and `tests/workspace-manifests.test.ts` fails when it does not. The console's `package.json` declares what its server and its views reach, `skybridge`, React and the view packages included; `packages/console/vite.config.ts` bundles the views into `dist/assets`, and the build toolchain (`vite`, `@vitejs/plugin-react`, `@tailwindcss/vite`, `alpic`, `@skybridge/devtools`) stays in its devDependencies. None of that can reach a workshop install any more, whatever block it sits in: the console is never published. **`skybridge` belongs to the console alone**, and the manifest test holds that too: as a dependency of the published package it had put its **non-optional** peers (`react`, `react-dom`, `vite`, `nodemon`, `@skybridge/devtools`) into every `npx @pipelex/mcp` install. **The console never resolves a workspace package at runtime**: it starts from `dist/server.bundle.js`, the esbuild bundle of the whole server that `skybridge build` emits for Vercel and `npm run build` copies into `dist/` (`packages/console/scripts/emit-server-bundle.mjs`), named as the start command in the root `alpic.json` and in the `Dockerfile`. That bundle is not optional: Alpic's runtime image carries the root `node_modules` from its install stage and the build output directory, and the core's entry there is a workspace symlink to a directory the image does not hold, so anything that imported `@pipelex/mcp-core` at runtime would crash. The bundle's path is Skybridge's Vercel output and not a promised interface, so `check:bundle` boots it from an empty directory on every `make check` (see [Build](development.md#build)) — **start the console any other way, from `dist/__entry.js` say, and it crashes on Alpic**. **`check:bundle` pins the console's side of this boundary and nothing else**: it proves the console's bundle needs nothing from `node_modules`. On the workshop's side, a runtime import of a package its manifest does not declare still builds green, because tsup inlines whatever is not external; the manifest test catches the core's dependencies, and anything else is by hand — when you add a package, the question is which entrypoint reaches it and whose manifest it therefore belongs in. The dependency switches follow the same rule: `make use-local-ui` / `make use-npm-ui` install `@pipelex/mthds-ui` and the SDK switches install `@pipelex/sdk` into each of the three members, never into the root, and npm keeps an entry in the block it already sits in — mthds-ui is a runtime dependency of the console's views but a devDependency of the core and the workshop, which import only the graph page's embed serializer and inline it.

The SDK dependency is the **published `@pipelex/sdk` npm package** (public on npm), not a `file:../pipelex-sdk-js` link. CI just runs `npm ci` — there is no sibling repo to check out. To develop against local `../pipelex-sdk-js` (or `../mthds-ui`) changes, use the Makefile switches — `make use-local-sdk` / `make use-local-ui` (or `make use-local` for both) point the dep at the sibling repo via a `file:` link in every manifest that declares it (both in all three packages), and `make use-npm-sdk` / `make use-npm-ui` (or `make use-npm`) switch back to npm; `make check` refuses to run while `@pipelex/sdk` or `@pipelex/mthds-ui` in any manifest is a `file:`, `link:` or `portal:` link (the `check-no-local-deps` guard), so don't commit the link. Bump the `^x.y.z` range once the change is published. `mthds` **is** a direct dependency again, and deliberately: `catalog-write.ts` imports `serializeMethodFiles` / `parseMethodFiles` from `mthds/protocol`, and that module exists precisely so the platform, `@pipelex/sdk` and this server agree on the stored-source shape instead of each re-porting it. It is imported by the core, so the core and the workshop that inlines it both declare it; relying on it arriving transitively through `@pipelex/sdk` would leave the version it resolves to outside the published package's control.

### The console's stylesheet and the form kernel

**The input form's kernel, `@pipelex/mthds-form`, is NEVER declared here — it is reached through `@pipelex/mthds-ui/form`, which re-exports it whole.** This inverted at mthds-ui 0.20.0, and the old reasoning is worth knowing because it reads so plausibly: the kernel used to be an *optional peer* of mthds-ui, never installed transitively, so the view could not build without our own entry and a direct (dev) dependency was the only way to get one. Since 0.20.0 it is an ordinary **dependency** of mthds-ui, so declaring it here buys nothing and costs a **second copy** in the tree — and the kernel ships React contexts (`FieldStringsProvider`, `FieldPresentationProvider`), so two copies mean a provider mounted above the panel silently resolves to defaults inside it. That is not theoretical: this repo pinned `^0.5.0` while mthds-ui pinned `^0.8.0`, and a sub-1.0 caret cannot bridge a minor, so the bump to 0.24.0 really did install both until the direct entry was dropped. If you ever need the kernel's own helpers, import them from `@pipelex/mthds-ui/form` (`getPipeInputForm`, `getPipeIOContract`, `InputForm`, `PipeIOContracts` all come through). **Styling: since mthds-ui 0.25.0 the console's own Tailwind compiles the kernel's controls, and nothing loads a stylesheet for them.** The controls are Tailwind classes living in the kernel's shipped JavaScript, so `packages/console/src/index.css` imports `@pipelex/mthds-ui/tailwind.css`, which is nothing but two `@source` lines into the kernel's `dist`, written relative to mthds-ui's own place in `node_modules` — no path here names the kernel. It also maps, in an `@theme inline` block, the shadcn colours the kernel uses that `@alpic-ai/ui/theme` does not name (`input` to `--color-border`, `secondary` to `--color-muted`): Tailwind generates a colour utility only for a colour its theme names, so without the mapping `bg-input` is simply absent and every control in `RunPanel` renders with no surface. `inline` is load-bearing — it compiles the utility to the alpic variable itself, so alpic's `.dark` block re-themes it, where a plain `@theme` would resolve the reference once on `:root` and inherit the light value everywhere. **Never import `@pipelex/mthds-ui/form-kernel.css` here**: that prebuilt sheet is for a host without Tailwind, and it would add a second preflight. It is roughly what 0.20.0 to 0.24.0 injected into every host inside `@layer mthds-form`, and this stylesheet then had to declare the whole layer order by hand (the kernel above `base`, or preflight stripped every control's surface; below `utilities`, or its `.hidden` beat our `.sm:inline`), bridge each bare shadcn name the sheet read (`var(--primary)`) to alpic's `--color-*`, and pin `--font-sans` and `--font-mono` against the sheet's `theme` sublayer. None of that exists any more, and none of it should come back: one Tailwind build, one preflight, one copy of every utility. The one `@source` the stylesheet writes itself is for `@alpic-ai/ui`'s components, and that path is relative to the stylesheet rather than a package name: the workspace hoists the package into the root `node_modules`, three levels above the stylesheet, so it reads `../../../node_modules/@alpic-ai/ui/src`. **Every failure here is silent**: an `@source` that names nothing, a scan that finds nothing, a colour the theme lacks — each just leaves classes out of the build, which stays green, and the result reads as a contrast bug rather than a stylesheet one. So when the form looks wrong, run **`npm run check:cascade`** rather than eyeballing the panel. `packages/console/scripts/check-cascade.mjs` refuses an `@source` that is missing or that does not sit inside the package Node resolves; requires every class in the `utilities` layer of the kernel's own prebuilt `dist/styles.css` — the kernel's complete list of what its controls use, resolved from mthds-ui's directory — to appear in the built stylesheet, which is what catches a scan path that found nothing (mthds-ui's `tailwind.css` documents one nested-install layout both its paths miss) or a colour to map; and resolves the winning declaration for the properties that matter — `!important`, then layer rank, then specificity, then document order, with longhand and logical-property expansion so `*{padding:0}` is weighed against `.px-5{padding-inline:…}`. **Never verify cascade order by reading the layer order back out of the build**: lightningcss deletes an `@layer a, b, c;` statement and honours it by hoisting the blocks, so the names the source writes never reach the output, and a position check passed in the state where every control was invisible.
