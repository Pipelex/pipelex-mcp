# Architecture

This page is the account of how `pipelex-mcp` is built and why each piece is shaped the way it is: the workshop, the capability core it is built on, and the rules the code keeps between them. [`SPEC.md`](../SPEC.md) is the contract the code implements and [`tools.md`](tools.md) the tool-by-tool reference; this page is the layer beneath both. **Read a module's entry before changing the module**, and when a change makes an entry wrong, fix the entry in the same change.

Rules that must hold while particular files are open also live in `.claude/rules/`, where Claude Code loads each one only when a file it names is read: the workspace writers, the manifest and the live suite.

## One server over one core

The repo ships one thin server over a capability core, as one package at its root: the plain MCP-SDK stdio workshop (the Pipelex plugin's server) for coding agents, whose shell sits at the top of `src/`, built on the core in `src/capabilities/`. **The workshop owns its tool table**, `src/tools.ts`, built from the capability functions in `src/capabilities/`, and the contract it emits is pinned byte for byte (see [Testing conventions](testing.md#testing-conventions)). The table module builds its own capability contexts too, and states the workshop's settings there rather than receiving them as options: `buildLocalToolContexts` sets the cwd-bound `{ path }` resolvers and the working directory as every writer's `saveRoot`. The capabilities carry no per-server flag: the workshop renders no views, so no result carries a graph or a form on `_meta` and every `available_view_specs` is empty, while the schemas still declare the view kinds because the contract pins them. **Every tool name a text in the core produces comes from `capabilities/tool-names.ts`**, `WORKSHOP_TOOL_NAMES`; the connector's `pipelex_*` tools are never named there. Workshop-only code, the workshop's own table among it, may write `mthds_*` names literally. Result summaries and the problems they render are checked capability by capability in the core's tests.

The whole of it is a thin MCP front-end over the existing Pipelex validation stack — it does no validation itself. It forwards file contents to a **Pipelex API** (`POST /v1/validate`, `POST /v1/pipe-io`, `POST /v1/codegen`) through the `PipelexApiClient` from the `@pipelex/sdk` npm package (published from the `js/` directory of `Pipelex/pipelex-sdk`), then projects the API's reports into MCP output. `@pipelex/sdk` is the Pipelex hosted-platform SDK — the same one `pipelex-app` uses, and the only one carrying the durable run lifecycle the later run-backed tools need; it re-exports the open `mthds/protocol` surface. It is the one API client, but the core also imports `mthds/protocol` directly (`catalog-write.ts`, `inputs-template.ts`), so the manifest declares `mthds` as well.

## Modules

The code is a handful of small files under `src/`, and the list names each by its path there: `capabilities/…` are the core's, the workshop's shell sits at the top of `src/` beside `tool-definition.ts` and `shell-test-support.ts`, and the `login` command's modules are under `login/`. Older commits and items cite two earlier layouts: before the workspace split (pipelex-mcp#89) the shell's files sat under `src/local/`, and from the split to the flatten the core lived in `packages/core/src/` and the shell in `packages/workshop/src/`.

A module this page does not list carries its account in its own header comment: `catalog-write.ts`, `catalog-publish.ts` and `catalog-link.ts` (the save and the pull, the publish, and the `.pipelex/method.json` link file, whose contract is SPEC.md's Catalog Write Scope), `inputs-template.ts`, `client-identification.ts` (see [`client-identification.md`](client-identification.md)), `tool-names.ts` and `tool-definition.ts`, the shape the workshop's table is written in.

### The workshop shell

#### `server.ts`, `tools.ts`, `main.ts`

Constructs the plain MCP SDK server and registers the workshop's table. `tools.ts` is that table: the workshop's capability contexts (`LocalToolContexts`, `buildLocalToolContexts`, which binds the cwd-bound file resolvers and the working directory) and `localToolDefinitions`, in the order a host lists them. **The key and the base URL are decided per tool call, not per server**: `registerLocalTool` asks the server's credentials resolver (`credentials.ts`) at the start of every call and runs that call over contexts patched with the answer through `patchLocalApiContexts`, the same seam that carries the handshake's `appInfo`, so every capability keeps reading plain `baseUrl`, `apiKey` and `apiNotes` fields and none of them knows where the key came from. The resolver is a `LocalServerOptions` seam, `credentials`, which defaults to the server's environment and the home `.env` when the server builds its own contexts; contexts a test supplies keep the values they carry unless a resolver is supplied with them. `main.ts` is the bin's entry point and dispatches on its arguments: **a first argument of `login` always runs the login command** (`login/command.ts`), whose own arguments are `--paste` and `--help` and anything else a usage error with a non-zero exit, so a mistyped `login --paset` says what is wrong instead of starting the server, which would wait silently on standard input; **every other argument list starts the stdio server exactly as before**, stray arguments included, since no host starts the workshop with `login` first and a host registration that passes some must not break. For the server, `main.ts` owns the stdio transport and graceful shutdown; `log.ts` keeps diagnostics on stderr so stdout remains protocol-only.

#### `credentials.ts`

The home `.env`, the file `pipelex login` writes and the workshop reads whenever its host passes no key, and the per-call resolution that reads it. `resolvePipelexHome` locates the home directory: `PIPELEX_HOME` from the injected environment when it is not empty, `~` or a leading `~/` expanded, else `.pipelex` under `os.homedir()`, which is injectable and never read through `process.env.HOME` directly; a `PIPELEX_HOME` that is neither absolute nor `~`-prefixed, `~user/…` included, is refused as `relative`. `readHomeEnv` checks the file on `stat` before opening it (a regular file, at most `MAX_HOME_ENV_BYTES`, a symlinked `.env` followed to its target), parses it with Node's own `util.parseEnv`, which reads `export` lines, quoted values and trailing comments, and reports every failure as a status, never a throw. `resolveWorkshopCredentials` holds the rules, which the module's header states: the host's non-empty key wins and the file is then not read; otherwise the file's key, paired with the environment's `PIPELEX_BASE_URL`, else the file's (`fileBranchBaseUrl`), else the hosted API; with no key in either place the call goes out keyless to the environment's base URL or the hosted API; an empty value counts as unset everywhere. Its answer carries the key's source (`host`, `file` or `none`) and the two sentences a failure's Markdown adds (`notes`, the `ApiNotes` of `capabilities/shared.ts`): `notes.apiKey` says which key failed, names the API by its origin alone (`apiOrigin`), shows the file under the user's home as `~/…`, and names the command that saves a key, `LOGIN_COMMAND`; `notes.baseUrl` names the API in use by its origin and where its base URL was set: by the host's `PIPELEX_BASE_URL`, by no one, so the hosted API, or, when the key is the file's, the environment sets no `PIPELEX_BASE_URL` and the file sets one, by the file, saying that the host's `PIPELEX_BASE_URL` overrides it. `problemSummary` appends the first to a credential problem and the second to every problem the base URL can cause, so an unreachable API or a route the deployment does not serve sends the user to the setting that chose it rather than to an environment variable the host never set. A `source` of `file` alone does not mean the base URL is the file's, since the environment's `PIPELEX_BASE_URL` is paired with the file's key when it is set. The file is never cached, so a key saved mid-session is used from the next call; reading a small file once per call costs nothing measurable. Nothing here logs, and no text it writes quotes the key or the file's contents. **It deliberately departs from the pipelex runtime, in these respects**: the runtime loads the home `.env` with `override=True`, so the file beats the environment, while here the host's key wins, because a key typed into a host's configuration has to mean what it says; and the runtime resolves a relative `PIPELEX_HOME` against the working directory, which here is the project the host spawned the workshop in, so a relative home would read a `.env` a cloned repository can ship, whose base URL would then decide where the user's bundles are sent. The working directory's own `.env` is never read for the same reason.

**The module also writes the file, for the login**, so that one module reads and writes it under one set of rules. `saveApiKeyToHomeEnv` follows pipelex's `set_env_file_entry`, so either login serves the workshop and the pipelex CLI alike: every assignment of `PIPELEX_API_KEY`, an `export` one included, is replaced where it stands (keeping its `export`, so a file a shell sources still exports it), every other line is kept byte for byte, comments, quoting, a byte-order mark and CRLF endings included, the value is written unquoted, and the directory is created at `0700` when missing. **The key keeps the base URL it was checked against**: the login passes it as `checkedBaseUrl`, and when it differs from the one the file alone yields (its own, else the hosted API, compared as the client reads a base URL, trailing slashes dropped and an http(s) URL normalized), it is written beside the key under the same rules, in the same write, one temporary file and one rename, since a host that does not pass the shell's environment, Claude Desktop or Mistral Vibe for instance, reads the file alone and would otherwise send the key to another API than the one that accepted it. The decision is made on the very content being rewritten and compared with the checked base URL, never the environment's, so a `PIPELEX_BASE_URL` another program wrote in the file while the key was checked is put back to the one that accepted it; with no `PIPELEX_BASE_URL` in the environment and no such change, the file alone yields the checked base URL and nothing about it is written. Without `checkedBaseUrl` the writer plans with the one a check made now would use, `fileBranchBaseUrl` over that same content. The result names the base URL it wrote (`baseUrl`). A checked base URL that is not host-only (`hostOnlyHttpUrl`, a copy of the rule the SDK's client holds a base URL to and refuses to be built on otherwise: trailing slashes dropped, then an http or https URL whose path is `/`, with no credentials, query or fragment) is refused as `invalid_base_url`, whether it would be written or not, since every tool call and every hosted `pipelex` command would fail on it, and a value a `.env` file cannot hold unquoted, one carrying a `#`, a line break, enclosing quotes or a space at either end, is refused as `unwritable_value`, naming the variable and never quoting it; both say whether the value came from the environment or the file (`from`), so the login names the one to fix. The line rules mirror `util.parseEnv`, so a value quoted over several lines is one assignment and a line inside another variable's value is never taken for one, and the new content is parsed before anything is written: the write is refused unless it gives each value it writes exactly and every other variable the value it had, so a line the writer would misread is never rewritten. A symlinked `.env` is resolved with `realpath` first, so a dotfiles link stays a link and its target is rewritten, and one pointing at nothing is refused rather than replaced by a file. The content goes to a temporary file opened exclusively at `0600`, its mode set again past the umask and synced, which is renamed over the target, so the key never sits in a file another user can read and a workshop reading the file mid-write never sees half of it. A file that exists but cannot be read under the reader's rules, is over `MAX_HOME_ENV_BYTES` or is not UTF-8 is refused (`unreadable`), since its other lines could not be kept. `checkHomeEnvWritable` runs every one of those checks on a placeholder key, planned with the base URL a check made now would use, the one the save would write beside it included, writing nothing, and checks that the nearest existing directory is writable; the login runs it before a key is minted, so a file it cannot write is reported before an unused key exists, and the save checks everything again. `isWellFormedApiKey` is the shape both the login and the writer hold a key to: `plx_sk_`, then `[A-Za-z0-9._~-]` only, since the value is written unquoted. Every failure is a status, never a throw, and no status quotes the key.

### The login

`npx -y @pipelex/mcp@latest login` (`LOGIN_COMMAND`, the one spelling every text gives it: with `@latest`, since a copy already in the npx cache from before the command existed ignores its arguments and starts the server, a hang that looks like the login) is a port of `pipelex login` in pure Node, since the workshop's users have no Python. Its modules sit under `src/login/`, and every seam a test needs, the environment, the home directory, standard input, the browser opener, the listener, the API client and the wait, is injected through `LoginDependencies`.

#### `login/command.ts`

The command, from its arguments (`parseLoginArgs`, which never echoes an argument that could be a pasted key) to its exit code: `0` saved, `1` nothing saved, `2` a usage error, `130` an interrupted prompt. It first runs `checkHomeEnvWritable`, so a relative `PIPELEX_HOME` (refused with the same sentence a tool call gives, `RELATIVE_HOME_SENTENCE`), a home `.env` it could not write, or a base URL the key would be checked against that the API client refuses is refused before any key exists, the last naming whether this shell or the file set it. The app's origin is `PIPELEX_APP_URL` from the environment, else from the home `.env`, where a developer sets it once beside a development base URL, else `https://app.pipelex.com`, and must be `scheme://host[:port]`, which `asOrigin` checks with the writer's `hostOnlyHttpUrl` and refusals of its own, an empty `?` or `#` among them (a refused value is never quoted, since it may carry credentials). The browser flow opens the loopback listener and starts the wait before anything else, so a callback refused while the browser is still being opened is reported rather than lost, prints the link to `/auth/cli?callback_port=<port>&state=<state>`, naming `--paste` for SSH and containers, so a machine where nothing opens still has a way through, opens the browser, says so when none could be opened, an opener that throws included, and waits up to `LOGIN_TIMEOUT_MS`, five minutes, long enough to create an account on the way; each refused callback is reported as it happens, and the timeout's message says that a key the page may have minted, whose redirect never reached the listener, went unused and should be revoked, and names `--paste`. Either flow then holds the key to `isWellFormedApiKey` and checks it with `GET /v1/me` through `createPipelexApiClient`, the client naming the workshop in its `User-Agent`, **against the base URL a tool call pairs with a key read from the file** (`fileBranchBaseUrl`: the environment's `PIPELEX_BASE_URL`, else the file's, else the hosted API), never the one this shell's own `PIPELEX_API_KEY` would resolve, since the key is bound for the file; the line announcing the check names the file when the base URL is the file's, and the save is handed the base URL checked, so the file cannot be changed under it. A refusal of the key, read from the SDK error's problem code (`auth.missing_credential`, `auth.invalid_credential` or `auth.credential_expired`, which the SDK also reads a bare 401 or 403 as), refuses it and saves nothing, and for a browser login says the key went unused and should be revoked, since the page already minted it; any other failure saves it with a warning that it could not be checked, naming the API by its origin alone; an accepted key names the account. When the save wrote `PIPELEX_BASE_URL` beside the key (see `credentials.ts`), the success message says so, naming the API by its origin alone, and that the pipelex CLI, which loads that file with `override=True`, now uses that API in every shell; a value the writer refuses is refused by the pre-flight, before any key exists. A save that fails after the key arrived says the key went unused, and for a browser login that it should be revoked, since the page already minted it. When the login's own environment carries a `PIPELEX_API_KEY`, it warns that a workshop started from that shell uses that value instead, printing neither. The success message says the workshop uses the saved key whenever its host passes none, from its next tool call, since the command cannot see a key stored in a host's own configuration. The browser opener is the platform's own, `open`, `xdg-open` or `explorer.exe` (which takes the URL whole, where `cmd`'s `start` would split it at `&`), launched detached and unreferenced with its exit code ignored; it listens for `spawn`'s `'error'`, since a missing opener emits one and nothing listening for it would end the login mid-wait. `xdg-open` is launched only when the injected environment sets `DISPLAY` or `WAYLAND_DISPLAY`, as Python's `webbrowser` registers it, since over SSH it starts and then fails, which an ignored exit code cannot see, and the `--paste` guidance would never be printed. Output goes through `process.stdout.write` and `process.stderr.write`, progress and success on the first, refusals and warnings on the second, and nothing quotes the key.

#### `login/loopback.ts`

The one-shot listener the browser hands the key back to, the page's contract being `pipelex-app/src/lib/cli-login.ts`. It binds `127.0.0.1`, never `localhost` (RFC 8252 §7.3), on a port the system picks, and accepts only `GET /callback` with exactly one `state`, compared with this login's in constant time (`timingSafeEqual`), and exactly one non-empty `api_key`; any other request is answered and the wait goes on, since any page open in the browser can send a request to a local port, and a refused callback's key is discarded. **Nothing a request carries may end the login**: a request target that is no URL at all, such as `//` or `//[`, on which `new URL` would throw inside the request handler and kill the process, is read with `URL.parse` and answered 400, and the handler's body is wrapped, so a request whose handling throws anyway, a refusal callback that fails for instance, is answered 500 and the wait goes on, with nothing logged, since the URL may carry the key. The page a callback's key is accepted with says "Key received", never that the user is logged in, since the terminal checks the key only after the page is served. `generateState` draws 32 random bytes in base64url, inside the page's `[A-Za-z0-9._~-]{1,256}`. The pages carry `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and `Connection: close`, and the listener logs nothing, since the callback's URL carries the key. The key is handed over once its page is flushed, so closing the listener right after cannot cut the browser's answer short, and a key that arrives before the wait starts is kept. A connection silent past the read timeout is dropped, so it cannot hold the listener, and `close` destroys every connection it tracked, a browser's idle keep-alive or speculative socket included, which the server's own `close` leaves open until its timeout; that is what lets the command exit as soon as it is done.

#### `login/paste.ts`

The hidden prompt of `--paste`, for a machine whose browser cannot reach the listener (over SSH, in a container). It refuses a standard input that is not a terminal before reading anything, which includes Claude Code's `!`, then reads in raw mode and handles the keys itself: Enter ends the line, Backspace and Ctrl-U edit it, Ctrl-C interrupts, Ctrl-D on an empty line or the end of the input ends it, and an escape sequence, an arrow key or a bracketed paste's markers, is skipped rather than typed. Nothing typed is written back, and the terminal's mode is restored on every way out, an interrupt, the end of the input and an error included. Its input is a `HiddenInput`, the slice of a TTY stream it uses, so a test types into a fake terminal.

#### `files.ts`

The local workshop's filesystem-backed `FileResolver`s. `localFileResolver` reads one text file of one extension, `inputs_path`'s `.json` on `mthds_run` and `mthds_prepare_inputs`: it resolves the path relative to the server's working directory, rejects any other extension *before touching the filesystem* (this keeps a prompt-injected `.env`/`.git/config`/key path from ever being opened), enforces the realpath containment boundary, and maps escapes, missing files, non-regular files and read failures to `FileResolution` failures (never throws), each a `Refusal` holding the sentence, what to do next, a stable `reason`, and whether the file was unreadable or changed while read, which `refusalProblem` turns into a problem (see Verdicts, errors and problems). Its options set the fallback clause of what to do next and an optional size cap checked on the stat before the read; the `inputs_path` resolver uses both, falling back to inline `inputs` and capped at `MAX_INPUTS_FILE_BYTES`. `localMethodFileResolver` is the resolver of a method's files, the method-taking tools' and, with `save: true`, which words its refusals for a tool that takes a folder alone (`SAVE_FALLBACK`), the save's. Its `statMethodFile` makes every check of one `{ path }` item of `files` that reads no byte of it: the extension gate on `METHOD_FILE_EXTENSIONS` (`.mthds` and the template suffixes, `capabilities/shared.ts`) before the filesystem, real-path containment and a regular file, answering the path as the caller wrote it, resolved against the working directory without following a link and relative to it, from which the core makes the tree path, and the size the stat gave, so the core holds the whole list to the deployment's limits before reading any. Its `readMethodFile` makes the same gates again (`methodFileTarget`) and reads the item as bytes within `maxBytes`, the limit on one file of a method, on the stat, then a read of at most one byte past that size, a file whose length moved being refused as changed while it was read. The working-directory, file and size checks are one private helper (`containedTarget`) both resolvers share, so neither can drift from the other's containment. Consumed by the local stdio shell.

`localMethodFileResolver` also carries the folder's two arms, which every tool that takes `method_dir` uses. `locateMethodDir` finds the folder and reads nothing under it: its real path inside the working directory, a directory, so the save can read its link before its files. `readMethodTree` (`readMethodFolderTree`) lists the folder under the limits it is handed with `listFolderTree` (`capabilities/method-tree.ts`, below) and refuses before reading a byte: a folder that is itself a virtual environment, no `.mthds` file at the folder's top (naming the deeper ones), and any refusal of the standard's lister (a symbolic link, a limit crossed, two names that collide). It then reads every file of the tree once through the listing's checked reader, into a `MethodTreeRead` holding the listing, its digest, the graph page it left out and the bytes by tree path, so what the secret guard checks and the SDK sends are those bytes, never read again. A refusal ends what to do next with the caller's own fallback: `files` for the method-taking tools (`FOLDER_FALLBACK`), saving the folder again for the save.

#### `capabilities/method-tree.ts`

A method folder's tree as the workshop lists it: the MTHDS standard's membership rule, applied by `mthds`' own `listMethodTree`, which is held to the standard's conformance corpus, rooted at the folder handed over (`discover: false`). `listFolderTree(folder, limits)` answers a `FolderTree`, the files by tree path in byte order with their sizes and SHA-256, the digest, and a `readFile` that opens a file without following a link, reads at most one byte past its listed size and checks the hash, since `mthds`' own reader reads the whole file before checking; a name the disk holds in another normalization than its NFC tree path is found by `onDiskPath`, segment by segment, and read with the same bound. A run's inputs file (`inputs.json` or `inputs.toml` at any depth, a symbolic link of either name included) is the standard's own `run_inputs` default from `mthds` 0.33, so it is neither listed nor counted. The module owns the one file the workshop leaves out on top of the standard's rule: the method graph page `mthds_validate` writes, a `method-graph.html` at the folder's top carrying `GRAPH_PAGE_MARK`, is left out and reported in `graphPage`, the digest recomputed over what is left, so a validation never moves what a folder sends or saves. It never counts against the limits: `mthds` cannot leave a file out of its walk, so the walk takes each limit widened by `SCAN_ALLOWANCE_FILES` or `SCAN_ALLOWANCE_BYTES`, a bound passed there being reported against the limit under it, with that limit's owner and number and the words that the walk stopped past it plus the allowance (`walkLimitError`), and `keptLimitBreach` holds the limits exactly on the files kept. A limit passed comes back as a `FolderLimitError`, `mthds`' `TreeLimitExceededError` with the `owner` of the limit, read from the limits' `workshopSet`. `describeTreeRefusal` turns the lister's `MethodTreeError` codes into a message, what to do next, closing with the caller's own fallback clause, and the code itself as the refusal's `reason`, and a limit's message blaming the deployment only for a limit it announced; `empty_tree`, which the module also answers when nothing is left once the page is left out, is the caller's to word, since a folder with nothing in it is refused for having no `.mthds` file at its top. A difference between this module and the standard's corpus is a workshop bug.

#### `capabilities/tree-limits.ts`

The limits a deployment holds a method's tree to, learnt rather than hardcoded: `methodTreeLimitsOf(context, buildClient)` asks the SDK's `methodTreeLimits()` (`GET /v1/version`'s `limits.method_tree`) and never throws. Every tool that sends a method's tree holds it to them, a folder while it is listed and a list of files as it is read, `mthds_save_method` and every method-taking tool alike, so one `TreeLimitsMemories` (`createTreeLimitsMemories` in `tools.ts`) is shared by all their contexts. One answer is kept per base URL for `TREE_LIMITS_TTL_MS`, ten minutes, since the base URL is decided per call and one platform's limits never stand for another's; a concurrent ask joins the one in flight, a handshake slower than `TREE_LIMITS_HANDSHAKE_MS`, three seconds, is abandoned, and one that failed or was abandoned is remembered for `TREE_LIMITS_FAILURE_TTL_MS`, a minute, so the calls that follow list at once under the workshop's own limits instead of each waiting again, while an answer arriving late is still kept. Whatever the outcome, every limit is bounded: one the deployment does not announce takes its value from `FALLBACK_TREE_LIMITS`, a file count of 10,000 and the runner's default byte limits, 32 MiB for one file and 64 MiB in all, so a tool pointed at a home directory costs a refusal rather than a long scan and never reads an unbounded tree into memory. The answer is a `FolderLimits`, whose `workshopSet` names the limits the workshop set itself, so a refusal can say whose limit it was.

#### `capabilities/secret-guard.ts`

The tripwire for a secret in a method's tree, run on the bytes a tool read before anything of the method is sent, by every tool that sends one: the method-taking tools on a folder or a list of files (`resolveMethodSource` in `shared.ts`) and the save. `secretFindings(files)`, over each file's path and bytes, reports a file whose last path segment is a known secret file's name, matched ignoring case, whatever it holds unless its rule's `unless` says the bytes are something else (a `.key` file that is a zip archive is a Keynote deck; `.pem` is no name rule at all, since a certificate is public and a private key in one is found as a PEM block), and any other file whose bytes hold a well-known key format, read as Latin-1 so every encoding's ASCII runs are searched, and once more without NUL bytes for UTF-16, each format being a provider's documented prefix followed by enough of the key's body that prose naming the prefix does not match. A finding carries the path and what it matched, never the matched text, since the refusal is shown to a model and may be logged; `secretRefusalText` words it, naming each file as the caller finds it, telling how to keep the file out by how it was sent (`SecretRefusalArm`: a `.gitignore` line or a dotted name for a folder, leaving it off the list for a list of files), and closes with what the caller does next, the refusal's reason being `secret_suspected`. It is a list of well-known shapes, not a secret scanner, and SPEC.md says so where the user reads it.

### The capability core: reading and listing

#### `capabilities/catalog.ts`

The list capability (`mthds_list_methods`) and its narrow `CatalogClient.listMethods()` test seam. It calls only the SDK's `listMethods`, validates the rows of the one page it gets back, and bounds names/descriptions by Unicode code point. **Search, ordering and paging belong to the server** (`q` / `limit` / `cursor`): filtering a returned page locally would be searching fifty rows of ten thousand and calling it a search, and re-sorting would reorder a page against the cursor that produced it. A blank query omits `q` rather than sending `""`, which the API rejects as bad input. **Non-negotiable projection invariant:** `mthds`, `python`, `input_data`, `pipe_output`, `org_id`, and `created_by_user_id` must never reach `structuredContent`, `content`, `_meta`, or logs — the index projection stopped returning them, but keep validating what *arrives* rather than trusting the declared type, so a looser server cannot leak through. There is deliberately no total count (counting means reading the whole catalog) and no `has_source`: recomputing it would cost a `getMethod` per row, so a source-less method now surfaces at the point of use, as the platform's refusal of the by-id call. **The summary carries a render directive on purpose**: a listing is read near-verbatim by the user, so `catalogSummary` tells the model to report each method with name **and** description, and puts the description before the demoted `method_id`. Keep that directive in the summary, not (only) in the tool description — ChatGPT caches a connector's tool list at add-time, so the summary is the sole channel where a presentation fix reaches existing installs. No view, no `_meta`.

#### `capabilities/org-files.ts`

The files list (`mthds_list_files`), modelled on `catalog.ts`: one page of `GET /v1/files` per call, read through a narrow `FilesClient.listFiles(query)` seam in the SDK's page shape (`{ items, nextCursor }`). **Every filter and the paging belong to the server**, for the method list's reasons, and `queryOf` leaves a blank search and an absent filter out rather than sending them empty. The input is checked before anything is sent: the trimmed query is held to the route's 200 code points (`FILES_QUERY_MAX_CHARS`), format keys are folded to the platform's own (`normalizeFormats`: trimmed, one leading dot dropped, lowercased, each once), and a `method_id` with an `@` suffix is refused with the bare id to pass rather than stripped (`normalizeMethodId`, through the shared `bareMethodIdOf` and `bareMethodIdRefusal` that `prepare.ts` uses for a test upload's method), since the route takes only a bare id. `projectFiles` checks every row as it arrives and fails the whole page on a broken one; an absent `nextCursor` is such a break, never the end of the list. **`created_by` never reaches a stream**, as the method list's creator ids do not, and the projection keeps only what lets a model choose a file and use it. **The summary teaches the one step a model would get wrong**: a listed file's `uri` goes where a run's input takes a file, with nothing to upload, so the inputs skip `mthds_prepare_inputs`. Only a null cursor ends a listing, because the server filters the rows a page reads and never refills it, so an empty page that carries a cursor says so in words, and every continuation repeats the listing's filters, to which the route binds its cursor. A refusal of the request is the platform's problem, relayed with the wire field it names (`q`, `format.<index>`); the module used to translate that field into the tool's argument, which only reworded what the platform said, and the argument checks it makes before sending are its own `client.argument_invalid` problems (`too_long`, `not_a_format`, `version_suffix`). A member-chosen name is collapsed to one line and escaped (`escapeMarkdownInline`) before it goes in bold on its summary row, so it cannot close the bold and plant a fake uri, and sizes promote from KiB to MiB through `upload-ceiling.ts`'s `formatMib`. Its client is the SDK's, from `createPipelexApiClient`, built inside the `try` so that a base URL the client refuses is reported as a problem rather than thrown. No view, no `_meta`.

#### `capabilities/models.ts`

The model deck capability (`mthds_models`, **workshop-only**, since a chatbot never writes a pipe's `model` field) and its narrow `ModelsClient` seam over two SDK calls: `models()` (`GET /v1/models`) for a listing and `checkModelReference()` (`GET /v1/models/check`) for a check. **A listing projects the deck.** On the Pipelex runner the protocol's `models` list holds the presets, each stamped with its category, and the category-keyed `aliases` and `waterfalls` extensions name handles only as targets and steps. A listing passes the category to the route. `projectDeck` checks what arrives rather than trusting it (a missing `models` list, a nameless entry, a category that is not a name or a misshapen extension throws into a `client.response_unreadable` no-verdict) and skips an entry with no category, but **keeps a category it does not know under the runner's name**, after the protocol's, as the protocol's reader rule requires of a client that does not leave it out. **A check asks the runner and relays its verdict.** The runner answers from pipelex's own reference parser, resolver and suggestion rule, the ones a validation runs, and it knows every model it can call, so its `resolved` and `not_found` are definitive for every kind and agree with a validation; the module parses no reference, ranks no name and reads no deck for a check, and it used to do all three with a TypeScript port of that logic, whose answers could part from the runner's for a handle or a check without a category. The reference goes as the caller wrote it, since the runner trims it and refuses one it cannot read, and its rule is the only one. `wireVerdictSchema` checks the verdict, one arm per `kind` as the wire is discriminated, each match holding exactly the fields its kind carries: a verdict that fails it is a `client.response_unreadable` no-verdict, and a field it does not name is stripped, which is the projection onto the output schema. `resolution` and every category are read open: a resolution the tool does not know reads as `not_found`, under the spec's reader rule. A refusal of the reference or the category is the runner's problem, relayed as is with the field it names; the module used to tell the runner's refusals apart by `error_type`, a member the problem document no longer carries. The deck and the verdict are keyed by `DeckCategoryName`, the open `ModelInfo["type"]` of `mthds`, so every table indexed by a category has to say what an unknown one does: `categoryLabel` names a known category's pipe type, from `CHECK_PIPE_TYPE_OF`, which covers the protocol's categories and `doc_gen`, the family of `PipeDocGen` that the check covers and the listing does not, and says the tool does not know any other. **The filter stays closed**: its enum is `CHECK_CATEGORIES`, the keys of `CHECK_PIPE_TYPE_OF`, a total `Record` over the SDK's `ModelCheckCategory`, which is `mthds`'s `MODEL_CATEGORIES` then `doc_gen`; `PIPE_TYPE_OF` is total over the protocol's alone, so the build fails when the protocol or the SDK gains or drops a category, as it does for codegen's targets, and the descriptions take their category list from it (`CATEGORY_PIPE_TYPES`). A listing refuses `doc_gen` at `category` (`client.argument_invalid`, reason `not_listed`), since the deck has no such category, and a check takes it. The check summary leads a miss with the same name under another sigil, the likeliest fault, and flags a match that reaches no model as a warning, since a validation accepts it and a run fails. Every summary, like the description, says the deck is what the runner can serve rather than what the account may use. No view, no `_meta`.

#### `capabilities/method-versions.ts`

What a `method_id` names now that saved methods have versions: a bare `mt_…` the latest published version, `mt_…@<n>` version n, `mt_…@draft` the draft. The workshop is released before every platform resolves the suffix, so this module asks `GET /v1/version` whether `method_versions` is among the extensions (`methodVersionsSupport`, three seconds at most, never throwing), keeps the answer in the `MethodVersionsMemories` that `buildLocalToolContexts` hands every by-id capability, **one `MethodVersionsMemory` per base URL**, each with its own cached answer, in-flight handshake and generation, since the workshop resolves its base URL on every tool call and one platform's `supported` must never label another's bare id; a capability reads the memory of the base URL its own client is built with, through `methodVersionsOf` (`supported` for ten minutes; `unsupported` and a failed handshake never, since a stale `unsupported` would report a bare id as the draft once it names the published version), and plans each by-id call (`planMethodSelector`, through `planById`, which the method-taking capabilities share with `selectorFailure` and `withMethodContent`): every selector is sent exactly as given, on every platform, and the answer is asked only for a bare id whose result says what it read, beside the request rather than before it: the plan is made at once with the answer as a promise (`SelectorPlan.reads`), and `withMethodContent` awaits it once the request has answered. It also writes what each result says about the content it read (`methodContentSentence`) or ran (`runContentReport`, from the start acknowledgement's `method_version`, which also proves the capability, and whose absence on a run by bare id drops a cached `supported`), reads a refused suffix by what a platform that does not resolve it sends, as the SDK reads it — a miss (`pipelex.catalog.not_found` of anything but a version, or `request.not_found`) or a `422` the SDK could not read (`client.response_unreadable`) — and adds to the relayed problem's `message` a note worded by the platform's answer, leaving its code, domain and retry as they came (`noteSelectorRefusal`); a refusal only a resolving platform sends (`pipelex.catalog.not_published`, `pipelex.catalog.not_found` of a version) proves the capability, and the never-published one gets a note naming the method's own `@draft`. It refuses a suffix on the run's linkage form (`linkageSuffixError`, a `client.argument_invalid` whose reason is `suffix_on_linkage`). A context without a memory asks on every call and a fake client without `version()` reads as `unknown`, so no hermetic test inherits another's answer or sends a handshake. The webapp's `src/lib/method-versions-support.ts` is the same check with its server-instance concerns.

#### `capabilities/validate.ts`

The validation logic. Zod input/output schemas, the API call (`validateRequest`, the SDK's `validate` with a folder's or a list's tree as its `tree` source, or a selector, and the same render and view options on every arm), and projection of the API report into MCP `structuredContent` plus `_meta.main_pipe_ref` (`toolResult`). `validateMethodTree` validates a tree already read and checked, as the save does with the folder it saves, with no second read, scan or limits handshake, and a no-verdict result carries `refusedForPython` when the execution-locus gate refused the method (`isExecutionLocusRefusal`, `shared.ts`), which the save reads to store the draft unvalidated. Also accepts `method_ref` (a published method address) and `method_id` as **server pass-throughs**: the selector rides the `/v1/validate` body (`ValidateMethodSelector`) and the hosted API resolves it — no fetch-and-forward, no method source in the conversation. The three source forms are mutually exclusive (`validateMethodSelectorRequest`, rule `one_selector`). It also projects the **main pipe's signature** (`mainPipeSignatureOf` → `structuredContent.main_pipe`, plus one rendered line in the summary): the ref, the ordered inputs with their concept refs and multiplicities, and the produced concept — read from `pipe_io_contracts[main_pipe_ref]` (a required field on every valid report, not gated by the `views` token), with the input-form descriptor consulted for input **order** alone. The ref itself is `defaultPipeRefOf`: the report's `default_pipe_ref` — the API's own statement of what a selector-less run would execute, and the only signal that knows a `method_ref` package's manifest — with `blueprintMainPipeRefOf(bundle_blueprint)` behind it **only when the field is absent** (an older runner), never behind a stated `null`, which means the server determined no entry pipe at all. Every member is narrowed against what arrived, with any malformed one omitting the whole signature rather than emitting a partial one. The signature's `output` also carries **`images`**, the produces-images signal: the capability requests the standard's output-form descriptor beside the input form (`views: ["input_form", "output_form"]`) and `imageFieldPaths` walks the entry pipe's single output node for `kind: "image"`, recursing into an `object`'s `fields` and a `list`'s `item`, yielding paths in `$` notation (`["$"]` for a top-level `Image`, `["$[]"]` for an `Image[]`, `["$.picture"]` for a field of a structure). Three things are load-bearing: **`[]` and an absent member are different answers** (described-and-none versus nobody-said), a `document` node is deliberately not a picture, and `kind: "unknown"` is opaque rather than empty. **The third only holds because the walk reports its own completeness**: `imageFieldPaths` returns `{ paths, complete }`, and `complete` is false for an opaque node, an unknown kind, a non-record, a nameless field and the depth ceiling — all of which used to yield a bare `[]`, i.e. a confident "produces no pictures" off a node nobody had read. The member is published only when the walk was complete **or** it found at least one image; an incomplete walk that found nothing withholds it, and a `document` stays `complete` because "not a picture" is an answer, not a failure to look. The walk is a **total `Record<FieldKind, …>`** over the SDK's re-exported `FIELD_KINDS`, so a kind the standard adds fails the build here instead of reading as "no images"; the kernel `@pipelex/mthds-form` owns the same lookup but is reachable only through `@pipelex/mthds-ui`, which is build-side, and `validate.ts` ships in the workshop bundle, so the ten-line walk lives here rather than pulling a view package into `dependencies` for every `npx @pipelex/mcp` user. `signatureLine` appends ` (produces images)`, the one channel that reaches a ChatGPT install whose cached tool list predates the member.

#### `capabilities/inputs.ts`

The inputs-template logic (`mthds_inputs_template`, **workshop-only**). Zod input/output schemas (`method_dir?` / `files?` / `method_ref?` / `method_id?` under `one_selector`, `pipe_ref?`, `explicit?` default true, `format?` default json), one `POST /v1/pipe-io` through the SDK's `pipeIo` for the one pipe, a folder or files sent through its `tree` form, and the projection of its answer. Every selector is a **server pass-through**: the runner resolves an address, the hosted platform resolves an id, and nothing is fetched or expanded client-side. The route selects the pipe — the caller's `pipe_ref`, else the method's entry pipe — and its valid arm is keyed by exactly the `pipe_ref` it resolved, so `inputsResult` projects the template from `input_form[pipe_ref]` through `inputs-template.ts`'s `inputsTemplateFor`, applying `explicit` and `format` client-side; an answer with no resolved pipe or no descriptor the projection can walk throws, and the caller reports it as a `client.response_unreadable` no-verdict. The invalid arm passes the report's faults through as `errors`, problem items, in a produced verdict. A refusal of the route is its problem, relayed as is whatever selector named the method: the route's refusal of a pipe selection (`request.pipe_not_found`, `request.pipe_ambiguous`) names the pipe itself, and a runner too old to serve the route answers a bare 404, which the SDK reads as `request.not_found`, never as a missing package or method. It composes its own summary (the resolved pipe, the template fenced in the standard's own rendering, the next step); no view, no `_meta`.

### The capability core: code generation and the workspace writers

#### `capabilities/codegen.ts`

The code-generation logic (`mthds_codegen`). Zod input/output schemas (`method_dir?` / `files?` / `method_ref?` / `method_id?` under `one_selector`, a required `target` with no default, an optional `output_dir` for the workshop's write arm), the API call (`CodegenClient.codegen()` — always `kind: "types"`, never a `pipe_ref`, which the route rejects on `types`), and the projection of the report into `structuredContent` plus a composed Markdown summary (the route returns a plain `message`). **Every selector is a server pass-through** — the runner resolves `method_ref`, the hosted platform resolves `method_id`. The `target` enum is closed in both directions against the SDK's `CodegenTarget`: `CODEGEN_TARGETS` is `as const satisfies readonly CodegenTarget[]` (a dropped target fails), and `CODEGEN_TARGET_PROFILES` is a `Record<CodegenTarget, …>` (a gained target fails until its profile — the audience clause of the decision rule, what the target emits, and its file names — is written; the tool description derives from the audience alone, and the `target` field description adds the rest, which is parameter detail the length budget keeps out of the description). **Every valid response is preflighted through the SDK's own `runCodegenCheck` in memory, on BOTH arms**, before it is written or relayed: one call establishes lock structure, canonical and unique paths on both sides, and stamp/hash agreement, so the hand-written checks keep only what the SDK cannot know — presence and typing, `isStampableArtifactPath` per artifact, that the report's `target`/`kind` **echo the request** (a report for another language is internally current, so the offline check cannot see it), and that `lock_filename` is exactly **`codegen.lock`** (pinning the exact name keeps the lock where `pipelex codegen check` looks for it, makes it unable to alias an artifact path, the one hole the preflight cannot see because `runCodegenCheck` never learns the lock's filename, and keeps a `../../…` name from reaching a model on the inline arm, which has no containment of its own; the writer still contains the lock itself). **The write arm is `CodegenContext.saveRoot`** — the same name and meaning as `ArtifactsContext.saveRoot`; `generateMthdsCode` owns it (hoisted report check → preflight → `writeCodegenTree` → projection), so `codegenResult` stays pure, synchronous and filesystem-free. On the written arm content is withheld from every stream (`written_to` per file, `output_dir`, `is_current`, `orphans`, `orphans_truncated`, `drifts`, `truncated: false`, no fenced blocks); `output_dir`'s presence is the arm discriminator. A refused or failed write is a `status: "error"` no-verdict — never a fallback to riding the content. **Bounding is by whole file, with the lock's bytes reserved off the top**: `boundArtifacts` gives the lock its bytes first and lets the artifacts fill the remainder under `CODEGEN_CONTENT_CAP` (64 KiB UTF-8 across the set), stopping at the first that does not fit — the rest carry `path` and `bytes` with `content` absent, `truncated: true`. A half file neither compiles nor passes the check, and dropping the lock to fit the code it anchors is the wrong casualty. A refusal is the route's problem, relayed as is whatever selector named the method; the hosted authorizer requires the `FF_PLAYGROUND` feature flag for `/v1/codegen` beside the plan checks, and the workshop adds no sentence of its own about that gate: the caller reads the problem the SDK reads from the refusal. No view, no `_meta`, no `available_view_specs` (decided out on 2026-08-29).

#### `capabilities/codegen-writer.ts`

The generated-tree writer behind `output_dir`, and the **write-side policy** the download tool must never share. `writeCodegenTree` returns a value and never throws. In order: contain the directory through `resolveSaveDir` (the one call that creates the target directory; a destination's missing parents are created later, at write time, through `createContainedSubdirectory`); contain every destination *and the lock* with `containedPath` alone, creating nothing, so a refusal leaves the tree byte-identical but for the target directory `resolveSaveDir` may have created; inspect every existing destination with **`lstat`** — a regular file carrying a codegen stamp (or, for the lock, the `# codegen.lock` prefix) is overwritten *hand-edited or not*, and a symlink, a directory or an unstamped file refuses the WHOLE write as `client.target_exists` at `output_dir`; write verbatim with the default overwriting flag, the deliberate inverse of the SDK download's exclusive `wx` create; then walk the directory (symlinks skipped, vendor/VCS directories pruned, under a file-count cap and a decoded-bytes budget that apply to orphan candidates only) and run `runCodegenCheck` with the lock **re-read from disk under a strict UTF-8 decoder**. `hasCodegenStamp` is a one-function mirror of the SDK's internal `hasStamp` (source of truth `pipelex/pipelex/codegen/stamp.py`), kept to one function so the swap is one line once the SDK exports it.

#### `capabilities/graph-page.ts`

The method graph page `mthds_validate` writes beside the `.mthds` files of a tree read wholly from disk, a folder's or a list of `{ path }` items' (`writeGraphPage`, triggered by `ValidationContext.saveRoot`, which only the workshop's `mthds_validate` context sets, so the save's validation leg writes none). The page embeds the `.mthds` files in the `mthds-sources` element and loads `@pipelex/mthds-ui`'s standalone viewer and elkjs from jsDelivr, pinned by exact version and SRI (`GRAPH_PAGE_ASSETS`, checked live by `graph-page.e2e.ts`); the viewer builds the static graph in the browser, so the page needs no API call and is written whatever the verdict. The embed is written by `@pipelex/mthds-ui/static-graph`'s own `serializeMthdsSourcesEmbed`, which is why the core and the workshop declare mthds-ui as a devDependency (tsup inlines the serializer, a few kilobytes, so `npx @pipelex/mcp` installs gain nothing), and why `GRAPH_VIEWER_VERSION` must equal the installed version: the viewer the page loads is the reader that serializer is kept in step with. `graph-page.test.ts` holds the version and both viewer hashes to the installed package without the network, so an mthds-ui bump fails there until the pin and the hashes move with it. The write policy is codegen's, not the download tool's: `lstat` the destination, create a missing page with `wx`, replace only a file carrying `GRAPH_PAGE_MARK` (a `generator` meta element), and leave a foreign file, a symlink or a directory untouched. `carriesGraphPageMark` is that ownership test, reading only the file's head without following a link, and `method-tree.ts` asks the same one before leaving a page out of a method's tree. A failure is a returned `GraphPageOutcome`, never a throw and never a change to the verdict; `toolResult` renders its `## Method graph` section after the error details.

#### `capabilities/workspace-boundary.ts`

The containment routine every filesystem-touching capability shares: `isInsideRoot` (containment without creation), `containedPath` (a relative destination joined under a directory, or nothing when it escapes), `resolveSaveDir` (containment plus the one `mkdir` of the target directory, real-path-checked on the deepest *existing* ancestor before it and again after, with the refusal's location a parameter, `dir` / `output_dir` (`client.argument_invalid` for a directory outside the working directory or that is no directory, `client.write_failed` for one that cannot be created or used, `client.not_configured` for an unusable working directory), answering in `created` the topmost directory it had to create, so a writer can tell a directory it made from one it found), `createContainedSubdirectory` (the same rule for a destination's parent inside that directory, with the caller's wording for an escape) and `escapedDirectoryError` (the same real-path rule asked before a directory is READ, creating nothing, which `catalog-write.ts` asks of a save's `link_dir` and files' directory before it reads a link there). It also owns `deepestCommonDirectory`, the deepest directory holding a set of paths, which places the method graph page. `src/files.ts`, `artifacts.ts`, `codegen-writer.ts`, `graph-page.ts`, `catalog-write.ts` and `catalog-link.ts` import it. It also owns `checkDeepestExistingAncestor`, the probe every directory-creating site runs **before** `mkdir` — a real-path check that runs only afterwards reports an escape through a symlinked component instead of preventing it. **Containment only — never policy.**

#### `capabilities/artifacts.ts`

The run-saving capability (`mthds_download_artifacts`, **workshop-only**), **thin over the SDK's artifact stack** for the files: it reads the run through the results route itself (so a running or failed run never creates a directory), asking for `DOWNLOAD_RESULT_ARTIFACTS` alone — `main_stuff`, which it writes, and the artifact `DOWNLOAD_SCOPE` walks, both `main_stuff` today — resolves the target — `dir`, or `runs/<run id>` from the run id the API answered (`defaultRunDir`) — and contains it through `workspace-boundary.ts`'s `resolveSaveDir`, marks a directory that call created with a `.gitignore` of `*`, the topmost one for the default location and the target itself for a `dir` the caller names (`markGenerated`, `wx`, so a directory it found and an existing `.gitignore` are never touched; the mark keeps a run saved into a method's folder out of what `method_dir` sends, and out of git; when it cannot be written, `removeCreatedDirectories` takes the empty directories the call created back off the disk so a retry marks them, and `withMarkNote` adds one summary line when it was), writes the full `main_stuff` verbatim to `main_stuff.json` **first** (`writeOutputFile`: `wx`, a numeric suffix on a taken name, the partial file removed on failure; a failed write stops the save as `client.write_failed` at `dir` before anything is fetched), checks for references with the SDK's `collectArtifacts`, then hands the results in hand to the SDK's `downloadArtifacts` (`results` form, `scope: "main_stuff"` named explicitly), which resolves the whole set through the bulk route (`resolveArtifacts` → `POST /v1/resolve-storage-url/bulk`) and owns the filename rule, the never-overwrite create, the bounds and the per-item verdict. What stays here is the workshop's own: the tool envelope (run-state verdicts, `scope` and `output` on the completed verdict, `saved_paths` with the output first, paths made relative to the working directory, each item's `found_at` as the SDK answered it, bounded at `MAX_FOUND_AT_PATHS` with the rest counted in `found_at_omitted`, since the SDK answers one path per occurrence and the verdict is model-facing), the output file, the deployment gate, the **plain-http rule** (`allowsPlainHttp` — the SDK's `allowHttp` opt-in follows `PIPELEX_BASE_URL`'s scheme, `http:` being the local compose stack; `PIPELEX_MCP_ARTIFACTS_ALLOW_HTTP` overrides it both ways, and an unrecognized value refuses), the reading of each per-item verdict into a problem (`itemProblem`: the download's own codes, which the SDK reads as `runtime.unexpected`, become the core codes they are — `client.download_limit_exceeded`, `client.write_failed` at `dir`, `client.aborted`, `runtime.unavailable` for a chunk whose resolve failed — and the fetch boundary's codes are the SDK's reading, through `shared.ts`'s `fetchItemProblem`; a whole-request refusal is the SDK's thrown problem, relayed), and the prose summary. The per-deployment seam is `ArtifactsContext.saveRoot`: the workshop sets it to its working directory; absent, the tool refuses fail-closed. Verdict discipline is the run family's (`state`-discriminated; `running`/`failed` are produced) plus `all_saved` for the walk; partial success is produced. No view, no `_meta`. It carries no walker, filename rule or downloader of its own — a change to any of those is an SDK change; the output file and the directory mark are the only things it writes itself, because writing one JSON value is not the network work the SDK's stack exists for.

### The capability core: inputs and uploads

#### `capabilities/prepare.ts`

The input-preparation logic (`mthds_prepare_inputs`, **workshop-only**). Zod input/output schemas (`method_dir?` / `files?` / `method_ref?` / `method_id?` under `one_selector`, `pipe_ref?`, required filled `inputs`), and the whole request handed to `@pipelex/sdk`'s `prepareInputs`, which uploads local paths / `data:` URLs / bytes to Pipelex storage and rewrites them to `pipelex-storage://`; the result projects into `structuredContent` (`inputs`, `uploads: string[]`) plus a composed Markdown summary with the prepared inputs in a fenced block. **Every selector is a server pass-through** — since `@pipelex/sdk` 0.17.0 `prepareInputs` takes all three, and since 0.27.0 it reads the signature from one `POST /v1/pipe-io` for the one pipe, the named `pipe_ref` riding the body and the route selecting the pipe, with no dry run and no execution-locus gate. A failure is the SDK's problem, relayed whatever the selector: the route's refusal of a pipe selection is its own problem (`request.pipe_not_found`, `request.pipe_ambiguous`), and every `InputPreparationError` the SDK raises carries the problem of its cause — `input.file_unreadable` for a local path it cannot read, the server's problem for a refusal the API answered, `client.argument_invalid` for an argument it refused — so a broken closure, a missing descriptor and a bad file value are told apart by their codes. The two spellings of `pipe_ref` the SDK would refuse (`alias->domain.pipe_code`, a bare `pipe_code`) are refused here first (`pipeRefRefusal`), so the refusal is known to have sent nothing. **No produced-invalid arm** — an unresolvable closure is a no-verdict `status:"error"`. **What the uploads are recorded as** (`kind`) is settled by `uploadMarkingOf` before anything is sent, and handed to the SDK as the prepare request's `upload` member, which it sends on every upload of the walk: nothing for `uploaded`, the platform's default, and for `test` the bare id of the method, either the selector's `method_id`, which must be bare (`bareMethodIdOf`; a suffixed one is refused at `method_id` with the bare id to pass), or the saved method a `method_dir`'s link file names, checked for being a bare id and against the configured API's host. A folder holding the legacy `pipelex-method.json` (`holdsLegacyLink`) is refused at once with the move instruction, as the save and the pull refuse it. Every other way of naming no method (a list of files, a published address, no link, an unreadable or damaged link, another API's link) matters only if something is uploaded, so `uploadMarkingOf` returns it as `unmarkable` rather than refusing: the request goes out with the SDK's `allowUploads: false`, which inputs that are all addresses never trip, and the SDK's `UploadNotAllowedError`, raised before anything is read or sent, is answered with that refusal, `client.argument_invalid` at `kind` naming the input that needed an upload. `test_method_id` is echoed only when the walk uploaded something. The folder's real path reaches it as `MethodTreeToSend.folder`, which `shared.ts` sets for a tree read from `method_dir`. The platform's refusal of a test upload arrives as the SDK's `TestFileRefusedError`, whose problem is the server's own when the refusal carried one, and otherwise `auth.forbidden` for a role that may not change methods or `client.argument_invalid` at `method_id` for a method the platform does not hold or is erasing. No view, no `_meta`.

#### `capabilities/upload-ceiling.ts`

`MAX_UPLOAD_BYTES` (**derived** from AWS API Gateway's 10 MiB request quota and base64's 4/3 inflation, not hardcoded) plus `SizeGuardedPipelexApiClient`, which refuses an oversize upload locally with the same `RejectedAssetError` the SDK maps a real `413` onto, `reason: "too_large"` included, carrying the problem of a refusal made before anything left: `client.argument_invalid` at `inputs` for the reason `upload_too_large`, with a `message` naming the file, its size and the true limit. **It does not reach a caller the way a real `413` does**: the SDK's `uploadFile` maps a real `413` before its catch-all, but wraps anything else `upload()` throws in an `UploadTransportError`, so the local refusal arrives as that wrapper's `cause`. The wrapper carries its cause's problem (`wrappedProblem` in the SDK), so the refusal reaches the caller as it was built. Without that problem the SDK would read the bare `413` status as an answer it could not read, and the ceiling's tests could not see it if they called `upload()` directly rather than going through `uploadFile` as every real caller does. It overrides `upload` (the wire call), which the SDK's own `prepareInputs` walk calls through `this`. It does **not** skip reading/base64-encoding a local asset first — the SDK owns that inside `uploadFile`, so a real pre-flight needs a change in `@pipelex/sdk`. **The app-level 50 MiB `MAX_UPLOAD_MIB` is unreachable through the public gateway; never quote it as the limit of a path that crosses it.**

### The capability core: runs and their results

#### `capabilities/run.ts`

The durable-run family (`mthds_run` / `mthds_run_status` / `mthds_run_results`) over the SDK's run lifecycle (`start` / `getRunStatus` / `getRunProgress` / `getRunResult`). The status tool reads the status, then the run's progress snapshot once, whatever the status, through `readRunProgress`, best effort under `PROGRESS_READ_TIMEOUT_MS` as `readFailedRun` is under its own deadline (both through `readWithinDeadline`, which aborts the request and stops waiting for it), and `statusResult` hands the snapshot to `run-progress.ts`; a degraded read gets its reassurance that the run is unaffected only when the platform could not read the run and the snapshot does not report it stuck (`reassuresDegradedRead`), so the progress paragraph and the degradation never contradict each other. The results read asks for exactly what `completedResult` projects (`RUN_RESULTS_ARTIFACTS`): `main_stuff` and `tokens_usages`; the graph, its data artifacts and `working_memory` are never asked for. A projection that starts reading another artifact must add it there, because an unselected artifact is absent from the SDK's answer. A completed result walks the **full** `main_stuff` twice in memory, for free: `collectArtifacts` for the stored-file count and `imageCandidatesOf` for `structuredContent.image_candidates` (absent, not empty, when the output references no stored file) — bare references, deduplicated, capped at `MAX_IMAGE_CANDIDATE_ENTRIES` with the remainder in `image_candidates_omitted`, because the walk deliberately reads the FULL output and an unbounded projection of it is model-facing content outside the `MAIN_STUFF_CAP` discipline `main_stuff` obeys beside it. One merged summary sentence then names `mthds_show_images` where there are candidates and `mthds_download_artifacts` as the way to keep the run — the output as `main_stuff.json`, and the files with the `public_url` expiry — on **every** completed result, files or not, because a model that does not know the tool retypes the output into a file; the truncation sentence names the same tool as the way to read the rest. Prose only, the structured contract is untouched. **The results tool never inlines an image and takes no flag that would let it**; that is the campaign's settled decision, not an omission. `mthds_run` starts from `files?`, `method_ref?`, or `method_id?` (rule `run_source`: files + `method_id` is the one legal pair — the files run, the id is run-history linkage; `method_ref` is a complete run source of its own and pairs with nothing). The platform resolves `method_id` natively on `/v1/start` (id-only runs the content its selector names, planned and reported through `method-versions.ts`; beside files, where it must be bare, it rides the SDK's named `method_id` option — `PipelexStartOptions`, never `extra`, which the SDK refuses at runtime for reserved keys). `method_ref` rides the SDK's named Pipelex-API run-source extension, is resolved by the runner (git fetch at the tag), and the resolved commit comes back as `method_provenance` on the start ack — narrowed defensively (`narrowMethodProvenance`), projected into `structuredContent`, and echoed in the summary so the run stays explainable when a tag moves. Also owns `main_stuff` bounding (the prune ladder under `MAIN_STUFF_CAP`), the run-usage projection over the SDK's `summarizeUsage` — the arithmetic is the SDK's and is never re-derived here: `projectRunUsage` reshapes the summary into the model-facing `structuredContent.usage` (its `state`, `cost_usd` for the SDK's `total_cost_usd`, one `tokens` figure adding the SDK's `input` and `output` totals, `calls`, `assembly_error`), present on every completed result; per-pipe stays off the model-facing surface — `projectUsageByPipe` puts the SDK's `by_pipe` rows, in its order, on `_meta.usage_by_pipe` alongside the full per-call `tokens_usages` for a future detailed-cost surface, and usage is never rendered into the prose; and every failure relayed as the SDK's problem. A failed start is the SDK's reading of it: a start whose request may have reached the API, a transport failure that does not prove nothing was sent or an answer the SDK could not read, is `client.outcome_unknown`, whose `retry` is `outcome_unknown` and whose step is to read the run history. `startErrorResult` opens the summary of such a failure with `START_OUTCOME_UNKNOWN_LINE`, "Run may have started", chosen by the problem's `retry` alone and never by its wording, because a start spends inference credit and the SDK cannot yet send the `Idempotency-Key` the hosted `/v1/start` honours.

#### `capabilities/run-failure.ts`

Why a failed run failed: `runErrorOf` projects the run's own problem, the problem document the platform stores for a run that did not succeed, into the `run_error` every failed arm of the run family carries (the status tool's `error` on a terminal status other than COMPLETED, and the `run_error` of the `failed` state of the results, image and download tools), and `runErrorSummary` gives the model's summary its account: that the run ended and how, the problem as the SDK's `renderProblemMarkdown` renders it (title, detail, next step, code with its domain and retry verdict, each fault), and a support line (`supportLineOf`: the run id, the problem's code and the time the run ended). The projection is the caller's view of the problem, `diagnostics` dropped, so a runtime serving the operator's view never hands the model the provider's raw answer, and it keeps every other member as served, so the result is still an open problem document. Nothing here words, infers or overrides anything: the code, the domain, the retry verdict and the next step are the problem's own. A value that is no problem document is no run problem, and the summary says the run stored none. Every text is bounded by code point, since the runner bounds no text it writes and the problem reaches the model twice: the `detail`, the `message` and the next step's `detail` to `FAILURE_MESSAGE_MAX_CODE_POINTS`, the `title` to `FAILURE_FIELD_MAX_CODE_POINTS`, and the `errors` to `RUN_ERROR_MAX_ITEMS` faults of `RUN_ERROR_ITEM_MAX_CODE_POINTS` each, the rest counted in `errors_omitted`. `boundedValue` bounds the structured members the same way, the problem's `params` and `location` and each fault's `params` and `location`, with what an object's bounding left out, members and the entries of the lists it holds, counted in one text member named `…` rather than in a list, so a typed list such as `missing_blobs` still reads as the protocol declares it and the result passes `isProblem`; `omissionKey` lengthens that name to `……` and beyond while the object, as served or as bounded, has a member by it, so the count never takes a member's place, and `boundedLocation` carries a location's `path` whole, since a pipe path cut anywhere names another pipe; a fault's `suggestions` keep their cap with `suggestions_omitted`, and its `suggested_fix`, a patch applied as written, is carried whole or left out with `suggested_fix_omitted`, never cut. The problem reaches the results-side tools from the results route's failed arm, the `run_error` the `409`'s `run.failed` nests, when the platform relays it there, and otherwise from one status read of the same run (`readFailedRun` and `runErrorOfFailedArm` in `run.ts`), which is also where the time the run ended comes from, so the image and download seams (`ImagesClient`, `ArtifactClient`) carry `getRunStatus` too. That read is bounded by `FAILED_RUN_READ_TIMEOUT_MS`, which aborts it and stops waiting for it both, and a read that fails makes the summary say the reason is unknown rather than missing (`failedArmSummary`). The zod `runErrorSchema` lives here. Its tests run over real failed runs recorded from the dev plane (`capabilities/failed-run-fixtures.ts` over `__fixtures__/failed-runs/`), each holding the problem its run stored, and over problems written by hand in the same module (`OPERATOR_VIEW_LLM_COMPLETION_PROBLEM`, `TIMED_OUT_RUN_PROBLEM`, and `relayingArmOf` for the failed arm that relays one).

#### `capabilities/run-progress.ts`

How far a hosted run has got: `runProgressOf` narrows the SDK's `RunProgress`, the snapshot the hosted progress contract defines, into the status tool's `structuredContent.progress`, and `progressParagraph` gives its Markdown the paragraph `Progress: <summary>`, the platform's own line with a line break collapsed to a space. **The summary is relayed and never worded here**, because the contract words it from the snapshot alone so that every client, the hosted console's run status included, says the same progress the same way. The projection keeps the contract's known members only (`root_path`, `chain` and a later platform's members dropped) and each optional member only when it has its type, since the MCP server checks `structuredContent` against the output schema and turns a mismatch into a failed call, and the SDK checks only the members a reader leans on; a snapshot whose required members do not have theirs is no snapshot. It is model-facing, so it is bounded: `selectInvocations` keeps at most `MAX_PROGRESS_INVOCATIONS`, those running, failed or carrying a health annotation first with their ancestors, then the others in snapshot order, and returns them in snapshot order, which lists every invocation after its ancestors, so the list still nests; the count left out rides beside it as `progress_invocations_omitted`. An invocation's `last_failure` is `{ problem, at }`, read from the wire as the hosted contract states it (`lastFailureOf`), its problem carried as a run's own is, through `runErrorOf`, since the SDK's `ProgressFailure` type still says `{ message, at }`; a failure holding no problem document is left out. The other free texts (`degradation.message`, `skip_reason`) are bounded with `run-failure.ts`'s bounds; the summary is not. `progressReportsStuck` is what keeps `run.ts` from reassuring a degraded run the snapshot says is stuck. The zod `runProgressSchema` lives here, beside the projection it describes. Its tests run over the contract's own worked example and hand-written snapshots in `capabilities/run-progress-fixtures.ts`.

#### `capabilities/images.ts`

The image-display capability (`mthds_show_images`). It reads the run through the results route, asking for `main_stuff` alone (`SHOW_IMAGES_RESULT_ARTIFACTS`), so a `running`, `failed` or candidate-free run is a produced verdict that fetches nothing. It then prefilters the stored references by storage key with `shared.ts`'s `imageCandidatesOf`, intersects the caller's `images` / `indices` selection with what the run produced (an unknown reference or an out-of-range index is a `client.argument_invalid` no-verdict at `images` or `indices`, refused before any call), then fetches each survivor through the SDK's bounded `client.fetchArtifact` under four named caps in `shared.ts` — `MAX_INLINE_IMAGE_BYTES`, `INLINE_IMAGES_BUDGET`, `MAX_INLINE_IMAGES` (which bounds *attempts*), `MAX_IMAGE_CANDIDATE_ENTRIES` (which bounds how many are *enumerated*, the rest counted in `omitted`) — plus its own `INLINE_IMAGE_TIMEOUT_MS` and `INLINE_IMAGES_DEADLINE_MS`. **The deadline is the one that is easy to leave out, and then to under-apply**: the per-image timeout is per image and the walk is sequential, so without a shared wall-clock budget six stalled objects accumulate into a three-minute call and a host with a shorter deadline loses the whole result, successful pictures included. Each fetch gets `min(INLINE_IMAGE_TIMEOUT_MS, remaining)` **and** `AbortSignal.timeout(remaining)`, and the signal is not belt-and-braces: `fetchArtifact` resolves the reference before arming `timeoutMs`, under a fixed 30s budget only `options.signal` reaches, so the timeout alone left a 60s walk able to run to 90s (120s of call with the run lookup). Since the SDK re-throws a caller's abort untouched, the deadline arrives as a raw `DOMException` and both catch sites test `deadline.aborted` first — otherwise this tool's own budget reads as a whole-request failure, and as a no-verdict when nothing had yet inlined. A candidate reached with none left is `withheld: "deadline"` unattempted. The content-type gate reads the **response's** header, not the resolve route's `content_type`, which the SDK documents as a guess from the reference's extension. A picture that does not fit is a `withheld` reason (`size` / `budget` / `count` / `type` / `deadline` / `empty`), never an error and never resized; `empty` is the zero-byte object, which clears every other gate and would be emitted as `data: ""` — permanent, unrenderable context; a per-reference failure rides `error` as the full problem the SDK's fetch raised, read through `problemOf`. A repeated selection is deduplicated in `selectCandidates`, preserving the caller's order — the entries are in the order *considered*, which is the caller's for a narrowed call and discovery order only otherwise. Verdict discipline is the run family's, plus `all_inlined` — which answers for the **run**, so the walk is handed `candidates.length` beside the selection and a narrowed call reports `false` while the run holds a picture it did not ask for; `omitted` counts against it too, but `omitted` is this listing's truncation (what the call *considered* lost to the cap) and is reached with `indices`, never `images`. Partial success is produced — **but a whole-request refusal that stopped the walk before any picture arrived is a `status: "error"` no-verdict** carrying that refusal's problem, since nothing was produced and the generic summary would otherwise bury a paywall or a rejected credential. **Every emitted block is `{ type: "image", data, mimeType, _meta: { uri } }` and carries no `annotations`** — see [Image blocks carry no annotations](#image-blocks-carry-no-annotations); the `_meta` half is measured on Codex by the probe's `meta` variant, not assumed from the standard. No view, no result `_meta`, no filesystem.

## The files union and the resolution seam

Every files-taking tool (`mthds_validate`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`, `mthds_run`) shares one per-item input union: inline contents (`{ content, uri? }`) or a file path (`{ path }`). The arms are non-strict with first-match semantics — a pathological item carrying both keys parses as the content arm and `path` is ignored (strict arms were rejected in Phase 0: an unknown-key failure would surface as a noisy zod union error from the SDK layer instead of the workshop's own `client.argument_invalid` problem at the item's field).

On every method-taking tool (`mthds_validate`, `mthds_run`, `mthds_inputs_template`, `mthds_codegen`, `mthds_prepare_inputs`), `files` is **optional** beside separate top-level selectors — `method_ref?` (a published method address, `github.com/<owner>/<repo>[/<selector>][@<tag>]`) and `method_id?` (a registered method's catalog id). `method_dir?`, the method's folder, sits beside them on the same terms. None is a third union arm: a folder, an address or an id is not a file, and a mixed array would falsely suggest merging. `resolveMethodSource` refuses a folder's pairings before reading it (beside `files` at `method_dir`, beside `method_ref` at `method_ref`, and beside `method_id` at `method_id` on the tooling tools), and `validateMethodSelectorRequest` then enforces the two selector rules (SPEC.md → "Method Selectors") on whether a tree was read: the tooling tools take **exactly one** source form; `mthds_run` lets a tree + `method_id` pair (the tree runs, the id is linkage) while `method_ref` pairs with nothing. Resolution: `mthds_validate`, `mthds_codegen`, `mthds_inputs_template` and `mthds_prepare_inputs` forward either selector to the server (the last two ride `POST /v1/pipe-io`, the route the template and the signature come from), and no tool expands one client-side; on `mthds_run` both selectors resolve natively server-side on `POST /v1/start` — see SPEC.md's Run Scope.

What a `{ path }` item or a folder *does* is decided by the **resolution seam**, not the schema: each capability's context carries an optional `resolver?: FileResolver`, and `resolveMethodSource(source, resolver, rule, limits)` runs **ahead of** the request-shape checks, turning `method_dir` or `files` into one `MethodTreeToSend`: the tree in the SDK's `MethodTreeSource` form, built over the bytes already read, and every file of it as a `SentFile` (its tree path, where the caller finds it, whether it came from disk, its bytes). A folder is located and read whole through the resolver's `locateMethodDir` and `readMethodTree`, then put in the sent form by `folderTreeToSend`, which the save uses too. A list of files is made in stages by `resolveFilesTree`, which reads no byte before the whole list has passed every check needing none: first that it names a method at all, one inline item or one `{ path }` item with the `.mthds` extension (`namesBundle`), a list of other files being refused at `files` before any item is stated, read or hashed, since the SDK would otherwise upload its files before the runner refused a tree with no bundle; each `{ path }` item stated through `statMethodFile`; the tree paths, rooted at the deepest directory holding every `{ path }` item (`deepestCommonDirectory`, shared with `workspace-boundary.ts`), or at the working directory when the list holds an inline item, a path given twice kept once and two spellings of one name once NFC-normalized refused; each inline item placed at the tree's top under its `uri`'s `.mthds` file name or `bundle.mthds`, `bundle-2.mthds` and on (`inlineTreePath`), and tree paths the standard refuses, names it never admits and colliding paths refused at their item (`treePathViolation`, `isExcludedName` and `pathCollisions` from `mthds`); then the deployment's limits, asked for every list, on the sizes known before any read (`treeTotalRefusal`, whose words name the limit's owner through `limitWords`); then the reads through `readMethodFile`, one at a time, each within the limit on one file and the running total within the limit on all. A folder asks `limits` only once it is to be read from disk. Both refuse a `.mthds` file holding nothing but whitespace once it is read (`isEmptyBundle`), at its item for a list and at `method_dir` for a folder, as an inline item with no content is refused, and both pass the secret guard before the tree is handed on, so a refusal of either sends nothing. Without a resolver, each `{ path }` item is refused at `files[i].path` and a folder at `method_dir`; no shell builds such a context now, but the refusal stays as the fail-closed default. Resolvers report failures as values, never throw; every resolution failure is a `client.argument_invalid` problem at the argument's own field, one item of its `errors` per fault — the resolver supplies only the reason, the message and the remedy, which is folded into the message.

Each capability passes `tree: request.tree.source` to its SDK call, `validate`, `pipeIo`, `codegen`, `prepareInputs` or `start`, and the SDK, since 0.48.0, sends it as the protocol's `files` map, deciding whether it travels inline (text, or base64 for a file that is not UTF-8) or by hash after uploading the blobs the organization lacks; `tree-wire.test.ts` holds the crate routes to that body. A template file is a file of the tree like any other: the runner finds it where the step's `template_file` leads, so nothing in the workshop keys a template, parses a `.mthds` file or knows a `PipeDocGen` step. A refusal of the tree sent is the platform's problem, relayed as the SDK reads it, `request.blobs_missing` with its `missing_blobs` among them, so nothing here tells which part of a request a refusal is about, but for one case the answer cannot say: a `413`. `shared.ts`'s `withTooLargeNote` adds to a `413`'s `message` what it can tell, from the call's route, tree and client, and a start's inputs. `tooLargeStepOf` tells the step first, from the route `answeredRoute` reads in the SDK's error message, since the SDK's `apiUrl` is the base URL alone: the tool's own route is the request, and `POST /v1/blobs/missing` or a file's upload refused with a `413` (`MethodFileTransferError`) is the tree's preparation, which names the method's files and never the inputs. On the request, `inlineTreeWeight` weighs the tree's inline map once as the SDK weighs it, and `treeTravelOf` asks `GET /v1/version` how it went, as the SDK decides it: inline to a deployment keeping no blob store, else inline within the lower of `INLINE_TREE_MAX_BYTES` and the handshake's `limits.method_tree.max_inline_bytes`, since the SDK's own readers of it are not exported, and by hash past it. The tree is named alone when it went inline and nothing else rode the request, a start's inputs alone when none of the method's files rode it, both with their weights when they rode together or the handshake did not answer, and nothing when neither rode it. The code, domain, retry and next step stay the problem's own. Each wraps its result in `withFilesSent`. A tree never reaches a by-ref or by-id request, because the selector checks refuse a tree beside `method_ref`, and on `mthds_run` a tree beside `method_id` runs the tree.

`inputs_path` takes the same seam for a run's inputs. The run and prepare contexts carry a second optional resolver, `inputsResolver`, and `resolveInputsSource` (`capabilities/shared.ts`) settles `inputs` / `inputs_path` into the one inputs object beside the files resolution, ahead of the request-shape checks: both supplied, a blank path, a resolver failure, invalid JSON and a value that is not a JSON object are each `client.argument_invalid` at `inputs_path`, and a context without the resolver refuses the path as it refuses a `{ path }` item. It is a separate argument rather than a `{ path }` shape inside `inputs`, because an inputs map may declare an input named `path`. After it, nothing downstream can tell a loaded file from an inline object.

## The output streams

SPEC.md's "The result streams" is the contract; this section is how the code keeps it. It mirrors the workspace's "format follows consumer" rule, which loads from the workspace's `.claude/rules/surface-output.md`. A tool result carries up to three independent streams. The workshop has no views, so its `_meta` carries no view data, only a valid verdict's `main_pipe_ref` and a completed run's full output and usage records, described below:

- **`structuredContent`** — the machine contract the model reads. A machine consumer branches on these fields, never on transport.
- **`content` text** — the human/LLM-readable Markdown summary. For `mthds_validate` it is the API's `rendered_markdown` and is deliberately **not duplicated** into `structuredContent`. For `mthds_inputs_template` the capability composes it (`/v1/pipe-io` returns no `rendered_markdown`, and its valid arm no `message`) and deliberately **does** repeat the template in a fenced code block — the template is the small payload the model must read, not a large view artifact.
- **`_meta`** — large data that **never reaches the model's context**: a valid verdict's `main_pipe_ref`, and a completed run's full output and usage records. `_meta` still travels on the raw MCP result, so a non-LLM programmatic consumer can read it off the wire — it is withheld from the model, not from the transport. The workshop renders no views, so no graph or form artifact rides here, and `structuredContent.available_view_specs`, the model's structured signal that a view exists, is always empty; the schemas still declare the view kinds because the contract pins them.

A completed run's full output (`_meta.main_stuff`) and its usage records (`_meta.tokens_usages`, `_meta.usage_by_pipe`) ride `_meta` too, so a programmatic consumer keeps what the model's bounded copy dropped; see `capabilities/run.ts` above.

## Verdicts, errors and problems

A successful `mthds_list_methods` call is `status:"ok"` with counts and a `methods` page; it is a read result, not a method verdict, so it has no `is_valid` field. Its failure arm is the shared `status:"error"` + `problem` shape.

A *produced* verdict is always `status: "ok"`, regardless of whether the bundle passed — discriminate on `is_valid` (and, for validation, `is_runnable`). This discipline is shared by every tool that judges a method: an unresolvable closure on `mthds_inputs_template` is a produced `is_valid: false` verdict with its `errors`, exactly like an invalid bundle on `mthds_validate`. `status: "error"` is reserved for **"no verdict could be produced"**: bad request shape, unreachable or misconfigured API, or a runtime fault. Such a result carries one `problem`, the MTHDS problem document in the caller's view, under the open `problemSchema` of `capabilities/shared.ts`: the protocol's members are typed, `location` is the protocol's structured object, and any member a newer platform adds passes through. The member is a single problem, never an array, and is called `problem` so that it never collides with a verdict's `errors`, which are problem items.

**The workshop classifies nothing.** Since the `@pipelex/sdk` release that reads the hosted problem, every error the SDK throws is a `ProblemError` carrying the problem the platform sent, or the SDK's own reading of the status or the transport failure when it sent none, and the SDK is the one place that holds that knowledge, so a fix reaches every client. `problemOf` turns any caught failure into the problem a result carries: an SDK error's problem through `mthds`' `reportedProblem`, with the operator-only `diagnostics` dropped (`callerView`), and anything else as `runtime.unexpected` with the error's own sentence as `message`. Nothing overrides the SDK's code, domain, retry or next step, with one interim exception: a method create that may have reached the catalog, which `catalog-write.ts`'s `createFailureProblem` reports as `client.outcome_unknown`, the SDK's reading kept in `message`, until the SDK can send the create's idempotency key, since a retry would create a second method. `createMayHaveLanded` takes only proof that the create did not happen: an argument the SDK refused, a step before the create that failed (a file's upload, or an answer from another route than `POST /v1/methods`, which `answeredRoute` reads from the error), or a refusal the create's route answered; anything else, an error the SDK did not raise included, may have landed. The classifier this replaced (`classifyError`, its per-route `ClassifyErrorOptions`, its `class`, `retryable`, free-string `location`, `hint` and `kind`, and each capability's `ErrorSummaries` headline table) existed because the SDK's errors carried only an error domain and a retry flag; it reworded and relocated what the server said, and drifted from the console's twin. A code is read only where a tool's own behaviour depends on it: `isExecutionLocusRefusal` reads the runner's two execution-locus codes so that the save stores a draft unvalidated, and the run family reads `retry: "outcome_unknown"` to say a start may have created a run.

**A refusal the workshop makes itself is a problem it builds**, before anything is sent, with `mthds`' `buildProblem` and a code of the protocol's core registry, through three helpers in `capabilities/shared.ts`. `argumentProblem` builds `client.argument_invalid`, its `params` the `argument` and a stable snake_case `reason`, its `location.field` the argument's path, and its `message` the workshop's sentence followed by what to do; that sentence travels in `message` because the registry's `detail` and `next_step` are generic to the code. `refusalProblem` reads a file resolver's `Refusal` (`files.ts`), which says whether the file was unreadable (`client.file_unreadable`, with its path and the system's reason), changed while read (`client.workspace_busy`) or refused (`client.argument_invalid` with the resolver's reason). `faultsProblem` folds several faults found in one request into one `client.argument_invalid` whose reason is `several_faults`, whose location is the first fault's, and whose `errors` hold one problem item per fault, so a result never carries an array of problems; a fault whose `retry` is not `no` is returned on its own instead, its `message` naming each other fault by its code and where it is (`faultLabel`), because a problem item carries no retry verdict and the wrapper's `no` would hide it, and what was read while files were changing cannot be trusted anyway. `workspace-boundary.ts` builds its own the same way: `client.not_configured` for a working directory it cannot resolve, `client.argument_invalid` for a destination outside the workspace or not a directory, and `client.write_failed` for one it cannot use. The Pipelex extension codes the workshop could name, such as a link-file conflict or a generated file it will not overwrite, are not built: `buildProblem` holds the core registry alone, so the workshop uses the nearest core code until the SDK carries the Pipelex registry.

**A failure inside a produced result is a full problem at its item**, never a problem item, since each needs its own `retry`: an image `mthds_show_images` could not fetch, an artifact `mthds_download_artifacts` could not save, the graph page `mthds_validate` could not write and the rename `mthds_save_method` could not make. `fetchItemProblem` reads the bulk resolution's per-item `{ code, detail }`, which carries no problem, through the SDK's `ArtifactFetchError`, so an item reads as a thrown fetch failure of the same code does.

**Where the key and the base URL came from is the rendering's, not the problem's.** The environment is no argument of the call, so `PIPELEX_API_KEY` and `PIPELEX_BASE_URL` have no place in a problem's `location`. `credentials.ts` decides, on every call, the two sentences that say where they came from (`ApiNotes`: which key was sent, none, the host's, the saved one or an unreadable file, and which API is in use and where its base URL was set), and `patchLocalApiContexts` (`tools.ts`) threads them into every context as `apiNotes`. `problemSummary` renders a problem with `mthds`' `renderProblemMarkdown` (the title as a heading, the detail, the client's message when it differs, the next step and its kind, the code, the request id, the run id and the location, and a multi-fault problem's items) and appends the key's sentence to a credential code (`auth.missing_credential`, `auth.invalid_credential`, `auth.credential_expired`) and the base URL's to any code the base URL can cause (those, `client.unreachable`, `client.not_configured`, `client.response_unreadable`, `request.not_found` and `runtime.unsupported`). A refusal by role, `auth.forbidden`, gets neither, since no key and no base URL changes a role. `toolResultContent` wraps that summary, with the files sent when the request went out, as the one text block of a no-verdict result.

## Projection rules

### `validationResult`

- No graph, form artifact or view advert ever appears: the workshop renders no views, so `available_view_specs` is always `[]` and `_meta` carries `main_pipe_ref` alone.
- Valid + runnable → `is_valid=true`, `is_runnable=true`.
- Valid + pending signatures → `is_valid=true`, `is_runnable=false`, `pending_signatures` populated.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, the report's faults in `errors`, problem items with their code, detail, params and location as the runner wrote them.
- A valid verdict's non-empty `warnings` are relayed as sent, problem items like the faults, the template check's `template_check_warning` items among them; an empty list is omitted. The Markdown already lists them under `## Warnings`.
- `main_pipe.output.images` is present exactly when the output-form descriptor arrived AND its entry for the effective entry pipe narrowed to a node AND the image walk either completed or found at least one image; absent otherwise, which is "unknown" and not "none".
- `main_pipe` is present on **every valid verdict** with an effective entry pipe (`defaultPipeRefOf`) whose contract entry narrows cleanly — pending signatures included, so `_meta.main_pipe_ref` also rides a valid non-runnable verdict. `item_count` is present exactly on the fixed arm, `required` is `presence !== "optional"`, and per-slot JSON Schemas stay out. When it was produced, `signatureLine` appends a `## Main pipe` section to the Markdown summary.
- The capability always calls the API with `allowSignatures: true`, `render: ["markdown"]`, and `views: ["input_form", "output_form"]` (the descriptor opt-in — lenient on the server, so a runner that predates a token simply returns no descriptor for it, and the members reading it stay absent). A report missing `rendered_markdown` is a hard error.

### `inputsResult`

- Valid → `is_valid=true`, resolved `pipe_ref`, echoed `format`/`explicit`, and the template on exactly one of `inputs` (json) / `inputs_toml` (toml) — the unused field is absent.
- Invalid produced verdict → `status="ok"`, `is_valid=false`, the report's faults in `errors` as problem items; no `pipe_ref`, no template fields.
- The request always sends its defaults explicitly: `format: "json"`, `explicit: true` unless overridden. A valid report missing its format-selected template field is a hard error (surfaced as a `client.response_unreadable` no-verdict).
- The summary is composed by the capability (title, API `message`, resolved pipe, fenced template block matching `format`, then the next step: `mthds_prepare_inputs`, or straight to `mthds_run` when every file value is already a URL or a storage reference).

### `codegenResult`

- Valid → `is_valid=true`, `target` / `kind` echoed, `crate_fingerprint` and `engine_version`, `artifacts[]` and `lock` from `boundArtifacts`, and `truncated` always present (`false` when everything rode whole).
- Invalid produced verdict → `status="ok"`, `is_valid=false`, the report's faults in `errors` as problem items; no artifact fields.
- A valid arm without a well-formed artifact list, a lock string, or a lock filename throws, which `generateMthdsCode` surfaces as a `client.response_unreadable` no-verdict — what arrives is written into a user's tree, so it is checked rather than trusted.
- The summary is composed by the capability: title, API `message`, the axes line, the verbatim-write instruction, one `## \`path\` (N bytes)` section per file with a fenced block (`fenced` grows the fence past any backtick run in the content), the lock last, and a `## Withheld for size` section listing the withheld files when `truncated`.

## Standing conventions

### Image blocks carry no annotations

**No image content block this server emits may carry `annotations`, ever.** The MCP standard's `annotations` hint (audience, priority) is optional and looks harmless; the host probe behind the image tools found that **Codex refuses an annotated image block outright** with `tool call error … Unexpected response type`, against a control proving the identical block without them is accepted and the picture reaches the model. Shipping with annotations would have broken the feature entirely on one of three named workshop hosts, diagnosable only from production. The `ContentImage` type in `shared.ts` does not declare the field, and `images.test.ts` asserts on the emitted block's exact key set — keep both. The study, recorded under L-260920-fc66db in the workspace ledger, also records what the probe settled about cost: a host bills an image block at the model's **native vision price** (pixels), and its **base64 size is free** — so the byte caps are a transport guard, not a cost control, and the reason the feature is a deliberate tool is that a picture in context is **permanent**, not that it is expensive.

### Every API client comes from `createPipelexApiClient`

**Every Pipelex API client is built by `createPipelexApiClient` (`capabilities/shared.ts`), never with `new`.** The factory passes the context's `appInfo`, which is how every request names itself `pipelex-mcp/<version> (workshop; host=<host>)` in its `User-Agent`, the version being the workshop's own package version, and how it is attributed to the `mcp` surface. The workshop sets that identity on every context of its table through `patchLocalApiContexts`, the patch helper beside its context set in `tools.ts`, lazily from the `initialize` handshake's `clientInfo`, which is only known after the contexts exist. The factory also makes the config's key the whole decision: handed no key, the SDK's client falls back to the process's own `PIPELEX_API_KEY`, so the factory passes an empty one, the SDK's "no key", and a call the workshop resolved as keyless sends no `Authorization` header. The `pipelex/sdk-client-factory` and `pipelex/no-raw-fetch` lint rules (`eslint-rules/pipelex-api-boundary.mjs`, pinned by `tests/api-boundary-lint.test.ts`) refuse a direct construction or a bare `fetch` elsewhere; pass a subclass to the factory as its second argument. See `docs/client-identification.md`.

### What the manifest declares

**`package.json` is the package npm publishes, and its `dependencies` carry exactly what the bundle reaches at runtime, and nothing else.** The tarball ships `dist/main.js` alone, so every `npx @pipelex/mcp` user downloads the whole `dependencies` closure before a single tool call; the manifest therefore declares only what that bundle leaves external — `@modelcontextprotocol/sdk`, `@pipelex/sdk`, `mthds` and `zod`. `mthds` lists a method folder's tree (`capabilities/method-tree.ts`), reading the folder's `.gitignore` files with its own matcher, and holds the rules of a tree path a list of files is checked against (`capabilities/shared.ts`). tsup externalizes only `dependencies` and `peerDependencies` and bundles everything else it reaches into `dist/main.js`, so a runtime import of a package the manifest does not declare still builds green, inlined without a word; when you add a package, the question is whether the bundle should carry it or every install should download it. `@pipelex/mthds-ui` is a devDependency for that reason: the bundle inlines only the graph page's embed serializer. The dependency switches keep each entry where it sits: `make use-local-ui` / `make use-npm-ui` install `@pipelex/mthds-ui` and the SDK switches install `@pipelex/sdk`, and npm keeps an entry in the block it already sits in. `tests/manifest.test.ts` holds what of this can be tested: the package's name and files, `@pipelex/mthds-ui` kept out of `dependencies`, `@pipelex/mthds-form` never declared, and the build before every pack.

**The manifest is also where a sprint pin is written, so a publish guard keeps one off npm.** While a sprint builds against an unreleased `@pipelex/sdk`, `wt pin` writes its sprint prerelease (`X.Y.Z-sprint.g<sha>`) into `package.json`, the site `.worktree.toml` declares, and the release train collapses it with `make use-npm-sdk` before the sprint branch merges. The manifest's `prepublishOnly` script runs `scripts/check-publishable.ts`, which refuses a sprint prerelease, a git source, a URL or a local source in any dependency block, naming each package. It reads each spec with `npm-package-arg`, the parser npm itself uses, and lets through only a registry version, range or tag, so a spelling nobody foresaw is refused rather than published. Every route to the registry passes through it: `release.yml` and a bare `npm publish` run it as `prepublishOnly`, and `make publish` runs it as a prerequisite as well and passes `--ignore-scripts=false`, so an npm configured to skip lifecycle scripts cannot skip it there. It is deliberately not part of `make check`, which has to stay green with a pin in place on a sprint branch. `scripts/publish-guard.ts` carries the classification and its reasons, and `tests/manifest.test.ts` drives the guard through a real `npm publish --dry-run --offline`.

The SDK dependency is the **published `@pipelex/sdk` npm package** (public on npm), not a `file:../pipelex-sdk/js` link. CI just runs `npm ci` — there is no sibling repo to check out. To develop against local `../pipelex-sdk/js` (or `../mthds-ui`) changes, use the Makefile switches — `make use-local-sdk` / `make use-local-ui` (or `make use-local` for both) point the dep at the sibling checkout via a `file:` link in `package.json`, and `make use-npm-sdk` / `make use-npm-ui` (or `make use-npm`) switch back to npm; `make check` refuses to run while `@pipelex/sdk` or `@pipelex/mthds-ui` is a `file:`, `link:` or `portal:` link (the `check-no-local-deps` guard), so don't commit the link. Bump the `^x.y.z` range once the change is published. `mthds` **is** a direct dependency, and deliberately: the core imports the method tree's lister, digest and tree-path rules from it, and the inputs template's projection and the model deck's vocabulary from `mthds/protocol`, which exist precisely so the platform, `@pipelex/sdk` and this server agree on the standard instead of each re-porting it. It is imported by the core, so the manifest declares it; relying on it arriving transitively through `@pipelex/sdk` would leave the version it resolves to outside the published package's control.
