pipelex-mcp · v0.12.0 · live on npm + Alpic

MTHDS methods, inside any MCP host.

One capability core, shipped as two servers: a local workshop that desktop hosts spawn in your working directory, and a hosted console you connect as a URL from ChatGPT or claude.ai on the web.

TL;DR

Discover, validate, prepare and durably run .mthds methods from inside the chat or the coding agent you already use — same eight tools, same names, same contracts on both servers. Pick one server per host: workshop where there's a filesystem, console everywhere else.

Local workshop → coding agents

claude mcp add pipelex \
  --env PIPELEX_API_KEY=plx_sk_... \
  -- npx -y @pipelex/mcp

Reads .mthds straight off disk, uploads local assets. Node 24+.

Hosted console → chat hosts

https://pipelex-mcp-a3c6a115.alpic.live/mcp

Add as a custom connector, then sign in with your Pipelex account. Ships interactive views + ChatGPT file attachments.

The one rule: never connect a single host to both servers. Same tool names on both means ambiguous routing — and a claude.ai connector syncs into Claude Code automatically, so that happens by accident. See Gotchas.

The surface

Eight tools

Every tool returns a structured verdict the agent can act on, plus a Markdown summary a human can read. Big payloads (method graphs, full outputs, per-pipe cost) ride a view-only channel, so the model never pays their tokens.

ToolWhat it gives youWhere
mthds_list_methods Your org's saved methods by name + description → the canonical mt_… id. Source-free: no method code ever crosses the conversation. both
mthds_validate Stable verdict — is_valid, is_runnable, structured errors, pending signatures — from files or a method id. On the console, a valid verdict also renders the dry-run graph. both + view
mthds_inputs_template A fill-in template of a pipe's declared inputs (JSON or TOML), with the concept and content shape of each. both
mthds_prepare_inputs Turns filled, file-bearing inputs run-ready → pipelex-storage://. Workshop uploads local paths and bytes; console is pass-through only. both
mthds_upload_attachments A file the user drops in the chat → pipelex-storage://, fetched and uploaded server-side. The bytes never enter the model's context. console · ChatGPT
mthds_run Starts a durable run and returns a run_id immediately — never blocks a tool call. both + view
mthds_run_status Cheap lifecycle read by run_id. The console's view polls it itself — zero model turns. both
mthds_run_results Terminal outcome + run-level usage: cost in USD, tokens, inference calls. both

Run state lives behind the durable run_id on the platform — start a run today, ask about it next week in a fresh conversation.

How it fits together

Two shells, one core

Both servers are thin shells over the same capability core, so tool names, schemas and contracts can't drift apart. Only the console adds views and host-specific plumbing; only the workshop can touch your filesystem.

local workshop

Install it in your coding agent

Nothing to install globally — hosts spawn it on demand with npx. You need Node 24+ and a plx_sk_ platform key. The server name is yours; pipelex yields mcp__pipelex__mthds_validate-style tool names.

claude mcp add pipelex --env PIPELEX_API_KEY=plx_sk_... -- npx -y @pipelex/mcp

Or install the pipelex plugin from the pipelex-plugins marketplace — its manifest spawns the same workshop.

~/.codex/config.toml

[mcp_servers.pipelex]
command = "npx"
args = ["-y", "@pipelex/mcp"]
env = { PIPELEX_API_KEY = "plx_sk_..." }

~/.cursor/mcp.json

{
  "mcpServers": {
    "pipelex": {
      "command": "npx",
      "args": ["-y", "@pipelex/mcp"],
      "env": { "PIPELEX_API_KEY": "plx_sk_..." }
    }
  }
}

Cowork runs in the desktop app, so it has a filesystem — use the workshop there, not the console.

claude_desktop_config.json

{
  "mcpServers": {
    "pipelex": {
      "command": "npx",
      "args": ["-y", "@pipelex/mcp"],
      "env": { "PIPELEX_API_KEY": "plx_sk_..." }
    }
  }
}

PIPELEX_BASE_URL defaults to https://api.pipelex.com. Point it at http://localhost:8081 to work against a local OSS pipelex-api runner — but durable runs need the hosted API; a bare runner has no run lifecycle.

hosted console

Connect it to your chat

The console holds no server-side API key, and there is nothing to paste. Add the connector by its bare URL; your host walks you through signing in with your Pipelex account.

Every connector UI — ChatGPT, claude.ai, Claude Desktop, Cursor

https://pipelex-mcp-a3c6a115.alpic.live/mcp

Add it as a custom connector, then sign in. The handshake is OAuth through WorkOS AuthKit and the host drives all of it — including picking which organization you want to work in.

Your verified session is what authorizes every call the console makes on your behalf, so the catalog you see and the runs you spend are your own. The token rides the transport, never a tool argument, so it never enters the model's context.

There is no keyless mode: every tool call needs a signed-in session. When one expires or is revoked, calls come back as a config no-verdict at authorization that tells you to reconnect and sign in again — nothing fails silently.

Upgrading from a ?api_key= connector

Bring-your-own-key was removed in 0.12.0. A connector still registered with ?api_key=plx_sk_... — or an Authorization: Bearer plx_sk_... header — no longer connects at all, rather than merely losing its tools. Remove it and re-add it by the plain URL above.

Five minutes

Go play with it

Once it's connected, you drive it in plain language — the agent picks the tools. A tour that exercises the whole surface:

  1. "What Pipelex methods do I have?" — the catalog, by name and description.
  2. "Validate ./methods/invoice.mthds" — on the workshop, hand it the path; it reads the file itself. On the console, paste the contents.
  3. "Show me the graph" — on ChatGPT or claude.ai the verdict brings the interactive method graph with it.
  4. "What inputs does the main pipe need?" — the fill-in template, concept by concept.
  5. "Run it on this PDF" — attach the file in ChatGPT, or point at a local path in Claude Code.
  6. "Is that run done yet?" — then "What did it cost?" for tokens, calls, and USD.

An invalid method is not an error — it's a verdict, with structured, located diagnostics the agent can repair against. Errors are reserved for "no verdict could be produced": bad request, bad key, unreachable API.

Known sharp edges

Gotchas

One host, one server

A claude.ai Pipelex connector syncs into Claude Code automatically — so if you also registered the workshop locally, both are live under the same tool names and nothing guarantees which one the model picks. In Claude Code, /mcp → expand "Show unused connectors" and disable Pipelex there (or deniedMcpServers per project).

ChatGPT caches the tool list at add-time

It never re-issues tools/list. A newly shipped tool — or a changed tool description — stays invisible to an existing connector until you remove and re-add it. 0.12.0's move to OAuth needs exactly that — an existing bring-your-own-key connector cannot be upgraded in place.

Attachments cap at 7 MiB, ChatGPT only

A transport ceiling, not a product choice: the upload route takes a base64 body behind an AWS gateway with a hard 10 MiB request quota. ChatGPT hands over far larger files happily, so you will meet this — the refusal fires before any bytes are fetched and names the limit. No other host injects a file reference into a connector call.

The console can't touch your filesystem

By design. It rejects { path } items and refuses any input that would need an upload, pointing you at the workshop. That's what keeps a public endpoint from being turned into a file-read oracle by a prompt-injected path.

For the curious

The critical changes

Six abridged diffs — the decisions everything else follows from

1 · One files union, two behaviours

src/capabilities/shared.ts

export const filesInputSchema = z.array(
  z.union([
    z.object({ content: z.string(), uri: z.string().nullable().optional() }),
+   z.object({ path: z.string() }),   // local workshop only
  ]),
);

Both shells register the identical schema, so the contract never forks. What a { path } item does is decided by a seam, not the schema — which is why misrouting between the two servers self-diagnoses on the first call instead of failing as an opaque schema error.

2 · The seams each shell fills

src/local/server.ts

return buildToolContexts({
  env,
+ resolver: localFileResolver(rootDir),  // reads { path } from disk
+ allowUpload: true,                     // uploads local assets
+ viewsAvailable: false,                 // tools-first: no views
});

The hosted console leaves all three at their defaults: no resolver, no upload, views on. Every per-deployment difference in the product is one of these three flags.

3 · Paths are a trust boundary, not a convenience

src/local/files.ts

+ if (!path.endsWith(".mthds")) return refuse(...);   // BEFORE any fs access
+ const real = await fs.realpath(resolved);           // symlinks followed
+ if (!isInside(rootDir, real)) return refuse(...);   // cwd containment

The extension check comes first on purpose: a prompt-injected .env or key-file path is never opened, not even to be rejected. Resolvers report failures as values, never throw.

4 · The signed-in caller's token overrides the server's key, unconditionally

src/hosted/contexts.ts

- const key = bearer(req.headers.authorization) ?? req.query.api_key;   // BYOK, deleted
+ const token = authInfo?.token;                    // verified by Skybridge against AuthKit's JWKS
+ return overrideContexts(base, token ?? "", ...);  // "" — NOT undefined

The override is unconditional on both branches: a server-held PIPELEX_API_KEY must never fund a signed-in caller's work, because the credential picks the active organization and therefore the whole visible catalog. The empty string is the load-bearing detail — PipelexApiClient reads options.apiKey ?? process.env.PIPELEX_API_KEY, so undefined would silently borrow the deployment's key, the exact opposite of failing closed. BYOK was written to be disposable and was duly deleted rather than migrated.

5 · One _meta key is the entire attachment mechanism

src/hosted/server.ts

_meta: {
+ "openai/fileParams": ["attachments"],
},

Naming the field here is what makes ChatGPT's runtime rewrite the model's reference to a user's file into a signed-URL object before the call arrives. Without it the field is simply never populated. The tool's description is part of the same mechanism — the host gates substitution on it too, so that text gets reviewed like a schema.

6 · Derive the limit, don't hardcode it

src/capabilities/upload-ceiling.ts

- const MAX_UPLOAD = 50 * 1024 * 1024;  // app-level, unreachable in practice
+ const GATEWAY_REQUEST_LIMIT_BYTES = 10 * 1024 * 1024;   // hard AWS quota
+ export const MAX_UPLOAD_BYTES = Math.floor(
+   ((GATEWAY_REQUEST_LIMIT_BYTES - ENVELOPE_ALLOWANCE) * 3) / 4,  // base64 4/3
+ );

≈7.4 MiB, matching the wall measured live. Refusing locally throws the same error type the SDK maps a real 413 onto, so every downstream classifier keeps working — only the message improves, because it can name the true limit where the server's cannot.
